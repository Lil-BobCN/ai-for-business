# Ontology：AI Coding 在本体中的建模和实战

> 阅读版原型：以真实参考资料为底稿，重排成一篇可以连续阅读、边读边思考的文章。
>
> 本文不替代原始口播资料。视频中的案例、数字和判断仍然属于作者观点，正式使用前需要独立核验。

## 先说结论

AI Coding 真正要解决的，不只是“让模型把代码写出来”，而是让一个模糊的业务意图，经过需求、设计、任务、实现、测试和发布，最后变成可以被团队共同理解、持续追溯、反复校验的工程结果。

如果只有一个强大的 Agent，却没有一套能表达对象、关系、规则和流程的共同语言，代码产出量可能会上升，产品迭代周期、质量和交付确定性却未必同步改善。

这也是视频引入 Ontology（本体）的原因：把原本散落在需求文档、项目管理工具、代码仓库、测试系统和发布系统中的对象与关系，组织成一张可以被人理解、被 Agent 检索、被规则校验的图。

> **思考一下｜“会写代码”与“能交付结果”之间**
>
> 这里真正变化的单位，可能不是代码行数，而是一个意图能否一路保持原义，直到生产环境。
>
> **可以追问**：如果代码产出量翻倍，但需求澄清、回归测试和发布追溯没有变快，效率到底提升在哪里？
>
> **可延展方向**：把团队的效率指标从“写了多少代码”扩展到“意图经过多少次返工才变成可交付结果”。

## 阅读路线

1. **问题从哪里来**：AI Coding 提高了执行速度，但需求、交接、文档和质量追溯仍然可能断裂。
2. **为什么难**：意图模糊、系统复杂、认知有限和现实反馈共同拉大了语义跨度。
3. **Agent 缺什么**：Agent 擅长执行，却需要外部结构帮助它判断边界、阶段和关系。
4. **本体是什么**：用类、关系、实例和规则，把散落在工具里的工程对象组织起来。
5. **如何落地**：让需求、设计、任务、代码、测试和发布形成可追溯链条。
6. **如何持续变好**：用门禁、影响分析和报告把错误反馈写回本体。

## 一、AI Coding 的问题，往往从需求还没有成为需求开始

很多业务人员会说：“帮我在这个页面上加一个按钮。”这句话听起来很具体，但它通常已经跳过了需求定义，直接给出了一个解决方案。

按钮到底要解决什么问题？谁会使用它？使用之后改变哪个业务状态？它和现有流程、权限、数据、接口有什么关系？如果这些问题没有被说清楚，产品和技术团队接到的就不是一个完整需求，而是一段未经澄清的实现建议。

类似的问题还会发生在交接中。业务会变化，团队会变化，负责产品的人会变化，但过去为什么这样设计、曾经踩过哪些坑、哪些约束不能碰，往往没有形成可追溯的结构。文档可能落后于代码，知识可能随着人员变动消失，测试用例也未必能说明系统真正覆盖了什么。

> **思考一下｜不要把解决方案误当成问题**
>
> “加一个按钮”只是一个可见动作。真正需要保存的，是触发这个动作的业务意图、对象边界、成功标准和约束。
>
> **可以追问**：当别人直接告诉你“怎么做”时，你会先追问哪三个问题，才能判断他真正想解决什么？
>
> **可延展方向**：为每个需求同时记录“想改变什么”“影响谁”“什么算完成”，再决定是否真的需要按钮、接口或页面。

## 二、四种不确定性，让自然语言很难直接变成工程结果

视频把软件工程中的困难抽象成四类问题。

第一类是**意图模糊**。我们可能知道自己想要什么，却说不清楚；即使说清楚了，听的人也未必按照同一个含义理解。自然语言有歧义，同一个词在业务、产品和技术语境里可能指向不同对象。

第二类是**系统复杂性**。扫雷小游戏和每天承载几千万订单的支付系统，面对的复杂度不是一个量级。系统规模、依赖数量、性能要求和故障代价，都会改变“一个小改动”实际需要穿过的关系网络。

第三类是**认知局限**。初级开发者、高级架构师和领域专家面对同一件事，能够识别的风险、约束和替代方案并不一样。Agent 也一样，它的结果依赖训练、上下文、工具和当前任务的表达方式。

第四类是**现实不确定性**。有些需求只有上线之后，经过真实用户反馈才会变得清楚。产品与用户共同创造出来的新信息，不可能全部在开发之前被预知。

> **思考一下｜哪些问题值得形式化，哪些问题必须留给现实反馈**
>
> 本体和规则可以减少语义歧义、流程遗漏和关系断裂，却不能提前替用户创造所有反馈。
>
> **可以追问**：你的工作里，哪些不确定性可以通过更好的定义和校验减少，哪些必须通过上线、观察和迭代才能知道？
>
> **可延展方向**：把问题分成“可以提前约束”和“只能通过反馈学习”两类，避免用流程去假装解决现实本身。

## 三、为什么数学看起来更适合 AI，而软件工程更难

视频用数学做了一个对照。数学命题可以用形式化语言描述，定义和证明过程可以被严谨地检查，参与协作的人也不需要面对一个复杂的生产系统。很多数学对象可以进入形式化验证工具，编译通过就意味着证明满足了某些明确条件。

软件工程则不同。需求往往从自然语言开始，系统存在大量上下文，团队成员有不同立场，很多质量标准只有在真实运行之后才会显现。即使模型能够很好地执行一个局部任务，也不代表它理解了整个产品的语义跨度。

因此，问题不是简单地把更多代码交给模型，而是要缩短从意图到可验证结果之间的语义跨度，同时增加可以被机器检查的中间结构。

> **思考一下｜中间结构才是协作的抓手**
>
> 如果只有“需求文本”和“代码结果”两个端点，Agent 只能在巨大的空白里猜测。需求、设计、任务、测试和发布记录，都是缩短语义跨度的中间结构。
>
> **可以追问**：在你的项目中，哪个中间产物最容易被跳过，却最能帮助下一个人理解为什么要这样实现？
>
> **可延展方向**：不要先问“模型能不能直接做完”，先问“我们能不能给它一个更小、更明确、可检查的中间问题”。

## 四、Agent 强在执行，弱在判断；本体提供的是共同约束

视频对 Agent 的判断是：执行能力已经非常强。它可以调用工具、运行脚本、生成代码，也能在语义跨度较小、验证方式明确的任务上稳定地产出结果。

但 Agent 的判断能力仍然依赖上下文。它不知道你的品位，也不知道你为什么偏好某种取舍；当目标本身没有定义清楚时，它可能用一个看起来合理的方案填补空白。它可以完成动作，却不一定知道哪些动作不应该做、什么时候还不能进入下一阶段、哪些关系必须保持一致。

本体的作用不是替 Agent 思考所有问题，而是把一部分共同约束显式化：有哪些对象？对象之间有什么关系？哪些字段必填？什么流程可以进入下一步？什么操作需要审计？哪些状态组合本身不合法？

> **思考一下｜把“应该记住”变成“可以检查”**
>
> 规则写在人的经验里，Agent 每次都要重新猜；规则写进对象、关系和校验里，Agent 才能在执行时获得稳定边界。
>
> **可以追问**：团队里有哪些“大家都知道，但没有任何系统能检查”的约定？
>
> **可延展方向**：优先形式化那些一旦违反就会造成返工、数据漂移或线上风险的约定，而不是一开始就试图把所有经验都编码进去。

## 五、本体不是一张漂亮的图，而是一套可执行的语义结构

视频把本体的基本要素拆成类、关系、实例和规则。

**类**描述一类对象及其属性和行为，例如需求、设计、任务、测试用例、应用、接口和发布。**实例**是某个具体对象，例如某个应用的一项关联关系完整性检查需求。**关系**把对象连接起来，例如一个需求关联一个设计，一个设计拆解出多个任务，一个发布包含若干提交。**规则**则决定哪些关系和状态是允许的，哪些字段必须存在，哪些操作需要被拒绝或触发通知。

当这些对象和关系被组织起来，需求就不再只是一个孤立的 Markdown 文件，代码也不再只是一个孤立的仓库。它们可以共同出现在一张图里：需求连接设计，设计连接任务，任务连接代码、测试和发布；每个对象都可以追溯到自己的来源和后续影响。

> **思考一下｜图谱的价值不在于“看起来复杂”**
>
> 一张图只有在能够回答问题时才有价值：这个改动影响哪些应用？这个需求有没有对应设计？这个发布包含哪些提交？这个任务为什么还不能进入下一步？
>
> **可以追问**：如果只能先建三类对象，你会选择需求、任务和发布，还是选择别的组合？每一条关系要回答什么问题？

## 六、从需求到发布：把软件流程拆成可追溯的链条

一个典型的 AI Coding 流程，可以从需求开始，经过需求澄清、设计、任务拆解、编码实现、测试、审计与归档，最后进入发布。

在本体里，这些阶段不是几句流程说明，而是对象和关系的集合。需求可以有范围、状态、澄清记录、功能性需求和非功能性需求；设计可以关联技术决策、接口协议和数据模型；任务可以有状态、负责人、检查清单和执行记录；测试可以关联测试用例、测试套件、回归策略和结果；发布可以记录版本、提交 ID、环境和部署结果。

这样做的意义，是让流程中的每一次转换都留下可检查的依据。需求没有澄清完成，就不应该假装已经进入设计；设计没有形成必要的约束，就不应该直接拆任务；任务没有达到完成条件，就不应该把它标记成已交付。

> **思考一下｜流程不是线，而是带条件的图**
>
> 真正的流程不是“做完 A 就做 B”，而是“满足哪些条件，A 才能进入 B；如果出现 blocker，应该回到哪一个上游对象”。
>
> **可以追问**：你们当前流程中，哪一个阶段最容易被口头跳过？跳过之后，谁会在什么时候承担代价？
>
> **可延展方向**：把阶段入口和出口条件分别写成规则，让 Agent 在进入下一阶段前主动检查，而不是事后依赖人工提醒。

## 七、规则让 Agent 不只是“建议”，而是受到边界约束

本体中的规则可以从轻到重逐步建立。

最基础的是 Schema 级别的完整性检查，例如字段是否必填、值是否符合类型、对象是否存在。再往上是关系和拓扑检查，例如是否存在孤岛节点、循环依赖、黑洞节点，或者一个对象是否缺少应该连接的上游和下游。

更进一步的是流程门禁：需求没有完成澄清，不能进入设计；设计缺少必要的技术决策，不能进入任务拆解；接口协议不符合约定，保存操作就应该失败。失败不是一句“请注意”，而是一个明确的错误信息，告诉 Agent 违反了哪条规则、应该如何修复。

视频展示的一个重要方向，就是让 Agent 真正操作本体时受到约束。如果它提交了不符合格式的接口协议，系统拒绝保存，并返回具体错误。Agent 根据错误修改后再次提交，规则因此成为执行循环的一部分。

> **思考一下｜好的错误信息也是知识**
>
> 一个能说明违反了什么、为什么违反、如何修复的错误，比一条泛泛的提示更能帮助 Agent 保持在正确路径上。
>
> **可以追问**：当前系统里哪些错误只能告诉人“失败了”，却没有告诉 Agent 下一步应该修复什么？
>
> **可延展方向**：把高频失败整理成结构化错误类型，让错误本身成为工作流的输入，而不是流程的终点。

## 八、图谱让影响分析和反向追溯成为可能

当代码、需求、应用、接口、基础设施和发布记录都拥有关系之后，变更就可以被反向追踪。

例如，一个接口协议升级，影响范围不必完全依赖个人记忆。系统可以沿着图谱找到依赖这个接口的应用、代码、测试、负责人和发布计划，并提示哪些对象需要重新评估。业务指标出现波动时，也可以沿着指标、业务链路、应用、配置和基础设施逐层向下排查。

这同样适用于发布：一次发布对应哪个 Spec？包含哪些 Feature？对应哪些提交 ID？部署到了哪些环境？如果这些关系都保存下来，发布就不再只是某个人在聊天窗口里说“已经发了”。

> **思考一下｜追溯不是为了记录过去，而是为了缩短下一次判断**
>
> 如果每次变更都要重新问“谁会受影响”，说明系统还没有把影响关系保存下来。
>
> **可以追问**：你最希望对哪一种改动自动生成影响分析？接口变更、数据模型变更、权限变更，还是业务规则变更？
>
> **可延展方向**：从一个高代价、关系相对稳定的变更类型开始，把影响分析做成可重复执行的流程。

## 九、报告不是终点，而是本体持续变好的反馈

图谱建立之后，还需要不断检查它是否保持一致。分析报告可以发现跨制品的技术漂移、任务颗粒度不一致、规范缺失、孤岛对象和不合理关系。这些发现反过来可以用于优化本体定义、补充规则、调整流程和改善 Agent 的工作方式。

因此，本体不是一次建完的知识库，而是一个会被实际工作持续检验的系统。它记录的不只是“现在有什么”，还应该帮助团队发现“哪里不一致”“哪条关系正在失效”“哪一种错误反复出现”。

> **思考一下｜把复盘结果写回系统**
>
> 如果每次复盘都只停留在会议纪要里，下一轮工作仍然要重新犯同样的错误。只有把发现写回对象、关系和规则，经验才会变成组织能力。
>
> **可以追问**：最近一次复盘中，哪一个发现最适合被改造成字段、关系、门禁或自动报告？
>
> **可延展方向**：为每一类重复问题指定一个回写位置，避免“分析报告很多，系统行为不变”。

## 十、把本体用于 AI Coding，真正改变的是什么

当常规任务被本体、流程和门禁约束之后，模型之间的差距可能会缩小：需求澄清、编码、测试和文件检查等标准化任务，不一定都需要最强的模型才能稳定执行。模型真正需要发挥最大价值的地方，可能会转向复杂判断、开放性探索和难以形式化的问题。

这并不意味着模型变得不重要，而是模型不再被迫独自承担所有上下文管理和流程记忆。系统负责提供稳定结构，规则负责拒绝不合法状态，图谱负责提供相关对象，Agent 负责在这些边界里完成工作。

从这个角度看，Ontology 不是给 AI Coding 再加一层概念，而是给软件工程建立一套共同语义：让人、Agent、代码、文档、流程和发布记录可以围绕同一组对象协作。

> **最后想一层｜本体真正管理的可能不是知识，而是承诺**
>
> 一个需求承诺要改变什么，一个设计承诺如何改变，一个任务承诺交付什么，一个测试承诺如何证明，一个发布承诺把什么带到哪个环境。
>
> **可以继续讨论**：如果把“承诺”作为软件工程的核心对象，你的团队目前最缺失的是哪一种承诺？
>
> **可迁移方向**：从一个真实项目开始，画出“意图 → 设计 → 任务 → 实现 → 证据 → 发布”的最小闭环，再决定哪些对象值得进入本体。

## 这篇文章留下的讨论入口

- AI Coding 的效率，应该用代码产出量衡量，还是用意图到交付的稳定性衡量？
- 哪些团队约定值得被写成规则，哪些判断必须保留给人和现实反馈？
- 本体的最小可用范围是什么：需求、任务、代码、测试、发布，还是另一个更小的闭环？
- 如何避免图谱变成新的文档负担，让它真正减少沟通和追溯成本？
- 当 Agent 被规则拒绝时，错误信息怎样才能成为下一步行动的清晰指引？
