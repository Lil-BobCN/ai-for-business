# 学习与实践方案：从企业问题构建 Ontology

## 设计目标

学习和实践使用同一个真实问题：从一个真实企业流程出发，检查 Agent 为什么无法可靠回答业务问题；沿数据、术语、关系、规则和权限逐层找根因；自己构建 Ontology 并接入查询；再看新的业务要求如何逼出模型扩展和治理。

Wiki 是概念、来源和争议的学习资料，不是实践数据。实践数据采用公开发布的真实数据集；不模拟一家不存在的公司，也不把不同数据集拼成同一家公司。

## 新资料带来的调整

我重新通过 LLM Wiki MCP 阅读了当前全部 663 个 Wiki Markdown 页面，其中 394 个页面是上一轮盘点时没有的。新内容增加了三组重要材料：

- 架构师阿Q的互联网、企业应用和数据架构演进案例，反复用“出现瓶颈 → 采用一种解法 → 引入新的技术/组织复杂度”讲架构。它适合作为课程的推理方法，不代表经过独立核验的行业演进史。
- 标准数字化资料从标准文件、元数据和草案，延伸到语义表达单元、标准本体、标准生命周期、接口与平台架构。它提供了真实标准对象域，可用来对照“文档语义化”和“企业运营 Ontology”分别解决什么问题。草案正文与已发布标准元数据必须分开使用。
- 新增 Ontology 与 Agent 的边界、OWL/RDF、权限、数据治理和架构问题页，使课程能把静态语义模型、真实数据映射、检索、动作和治理串成更完整的实践链。

因此，课程会先学会从瓶颈推导方案，再拿真实采购流程构建企业 Ontology；标准数字化作为并行对照案例，不强行拼接进采购公司的数据。

## 实践题选择

### 主练习：BPI Challenge 2019 采购流程

这是目前最适合做第一套 Ontology 实践的真实企业流程数据。数据来自荷兰一家大型涂料企业及其约 60 家子公司，挑战主题是采购订单处理与合规；4TU 提供的原始 XES 事件日志约 729 MB，另有约 68 MB 的对象中心事件日志（OCEL），均标为 CC BY 4.0。挑战说明提出了可直接使用的问题：按采购项目分类和描述流程；关联收货、发票、付款并分析耗时；识别流程偏离和金额异常。

来源： [BPI Challenge 2019 题目](https://www.tf-pm.org/competitions-awards/bpi-challenge/2019)、[4TU 原始事件日志](https://data.4tu.nl/articles/dataset/BPI_Challenge_2019/12715853)、[4TU 对象中心事件日志](https://data.4tu.nl/datasets/46a7e15b-10c7-4ab2-988d-ee67d8ea515a)。

OCEL 已知对象类型有 `PO`、`POItem`、`Resource`、`Vendor`，事件中还有公司、单据类型、收货和发票校验等属性。原始挑战说明称数据包含 76,349 张采购单、251,734 个采购项目和 42 种活动；标识已匿名化，金额经过线性变换。

**首题：**“某采购项目先出现发票、后出现收货。什么条件满足后，Agent 才能判断这张发票可以清账？”

挑战题页面把流程分为四类：三方匹配、发票在收货之后；三方匹配、发票先于收货；不要求收货的两方匹配；寄售。对“发票先于收货”的三方匹配，挑战说明发票可以先录入但应保持阻塞，收到货且发票金额与收货/采购项目金额匹配后才能清账。因此，Agent 不能只按事件先后下结论；它需要先识别采购项目所属匹配流程，再关联收货、发票、金额和清账事件。练习的匹配逻辑来自挑战发布方材料；它不是所有采购组织的通用政策，仍须检查数据字段是否足以验证。

这不是凭空假设“先票后货就是违规”，而是一个精确练习：**同样的事件顺序，在不同匹配类型下含义不同。**如果数据中缺少匹配标记、收货记录或金额，Agent 应指出缺口，不自行推断合规。

**数据质量门槛：**OCEL 抽样事件时间出现 `1948-01-26`，与数据集约 2018 年的时间范围不符。开始做日期和时长题之前，先与原始 XES 对照确认转换是否有问题；核实前只用事件相对顺序，不依赖绝对日期。

### 备选与辅助数据

| 数据源 | 适合练什么 | 边界 |
|---|---|---|
| [Olist 巴西电商数据](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) | 约 10 万笔真实匿名订单，多表覆盖客户、订单、订单行、卖家、商品、付款、评价和交付时间；适合订单/履约业务 Ontology。数据标 CC BY-NC-SA 4.0，下载端点可匿名访问。 | 历史快照；没有仓库过程、完整物流事件、客服工单、审批和退款动作。非商业使用与相同方式共享条件需要保留。它应是独立电商案例，不能和 BPI 拼成一家公司。 |
| [NIST OSCAL](https://pages.nist.gov/OSCAL/) 与 [oscal-content 样例](https://github.com/usnistgov/oscal-content/tree/main/examples) | 仓库采用 [CC0 1.0](https://github.com/usnistgov/oscal-content/blob/main/LICENSE.md)；含机器可读控制目录、系统控制实现、评估计划/结果和整改工件，适合练标准要求怎样关联系统、组件与评估证据。 | 样例工件不是已确认的真实企业运行记录；它是标准与控制数据模型，不替代主业务数据。 |
| [IETF Datatracker API](https://datatracker.ietf.org/api/) | 真实工作组、人员、文档、版本提交、状态、审查/表决和最终 RFC 的组织流程模型；可作标准制定流程对照。 | 它不是公司经营数据，也不是可一概视为 CC0/CC BY 的完整数据集；保留引用和标识较稳妥，批量再发布正文/评论需检查 [IETF Trust 条款](https://trustee.ietf.org/documents/trust-legal-provisions/)。 |
| [全国标准信息公共服务平台](https://std.samr.gov.cn/) 的公开项目接口 | 可读到真实国家标准项目/草案的编号、名称、制修订类型、日期和状态等项目元数据；很贴近国内标准化流程，可作为只读来源补充标准生命周期。 | 目前观察到的是平台前端使用的未正式文档化 JSON 接口，稳定性和再利用许可未确认；公开记录不等于可自由批量再发布，也不含完整的意见正文和处理过程。 |
| [Olist 之外的客服对话数据](https://www.kaggle.com/datasets/thoughtvector/customer-support-on-twitter) | 多轮消息、回复关系和响应时效。 | 社交媒体对话不是企业工单；无明确 SLA、问题分类、解决结果。许可为 CC BY-NC-SA 4.0，商业使用受限。 |

本地标准数字化资料目前有 9 项标准档案、其中 6 项有公开征求意见稿，其余 3 项只有元数据卡片；它们没有完整的标准制定组织运营日志、审查/投票/意见处理数据。因此这批资料适合作为语义层和标准内容案例，不足以单独提供完整的企业运营数据题。

## 问题驱动课程

### 1. 同一业务问题需要哪些证据？

从 BPI 挑战的采购异常题开始，拆出要判断的采购项目、收货、发票、金额、流程状态和适用规则。先区分“日志观测到的事件”与“业务规则得出的结论”。

**产出：**一张问题卡，列出要回答的主张、需要的证据及缺失项。接着问：这些证据在数据中究竟长什么样？

### 2. 企业架构为何会不断增加系统和数据层？

读架构师阿Q的三条线：互联网流量增长、企业业务与部门复杂度增长、数据量与用途增长。用这些叙述训练“瓶颈 → 解法 → 新复杂度”的推理法，再回到采购日志观察采购订单、项目、供应商和流程事件分散在何种记录中。

**产出：**一张“业务瓶颈—系统/数据来源—当前缺口”图。架构师视频是 ASR 作者观点，不当作已证实的普遍历史规律。接着问：多张表/事件日志之间要共享什么业务含义？

### 3. 先理解业务对象，再谈 Ontology

从 BPI 数据识别采购单、采购项目、供应商、处理人员、发票/收货相关事件。比较原始 XES 与 OCEL：扁平案例视图和对象中心视图分别保留了什么、丢失了什么？对象类型、事件和状态是否要分开建模？

**产出：**自己画出的领域图和术语表，不照抄 OCEL 类型。接着问：从数据字段映射到这些概念的依据是什么？

### 4. 从真实记录构建并校验领域模型

围绕字段来源、标识符、事件顺序、对象关联、金额口径和可空值设计映射。将每条映射标为“数据直接给出”“建模解释”或“缺证据”。再检查重复、孤立、时间异常和违反已知结构约束的记录。

**产出：**领域模型第一版、源字段映射表和数据质量清单。接着问：标准数字化中如何把不同类型文档表达成可比较的语义单元？

### 5. 用标准数字化作对照：内容语义化与企业业务本体有何不同？

把采购流程的业务 Ontology 与 Wiki 中的标准内容语义化单元、标准本体、标准生命周期和标准平台架构对照。一个描述企业运营对象与动作；另一个规范标准文件如何拆分、描述、关联与交付。比较它们的对象域、表达单元、关系、规则和生命周期，保留标准正文草案与官方元数据的证据边界。

**产出：**一张“标准文档模型 vs 采购业务模型”对照表，并说明哪些建模方法可能迁移、哪些不能直接迁移。接着问：有了模型，如何回答问题而不超出来源证据？

### 6. 让模型支持查询、解释和 Agent

用同一采购题比较结构化查询、流程挖掘和关系查询。Agent 回答时引用事件与对象证据；字段缺失或挑战规则未覆盖的情况，要明确说“发现异常，但无法判定违规”。之后再评估是否需要接入组织自己的采购政策和流程规章。

**产出：**一组可复现查询和答案证据模板。接着问：当建议变成实际付款、放行或审批动作，需要新增什么？

### 7. 执行动作前的权限、审批与验收

先设计只读 Agent：识别异常、说明依据、请求补充信息。再讨论人工审核、角色/功能权限、动作副作用、审计记录和失败恢复。真实数据不含授权接口时，不编造业务操作记录；付款、放行等后续动作只作为明确标注的设计讨论。

**产出：**评测题集、人工检查点、权限矩阵和待补业务规则来源。接着问：新部门、新单据和新政策加入时，Ontology 怎么演化？

### 8. 新需求怎样产生 Ontology 的下一轮变化？

逐步扩展一个采购项目：增加多次收货、发票差异、退货/贷项、供应商绩效或标准条款关联。每次只在新问题需要时扩展概念或关系，并验证旧查询是否仍正确。

**产出：**一份带来源、版本、迁移影响和回归测试的模型变更记录。把新发现的证据缺口形成 Wiki query；只有有可追溯材料时才新增知识页面。

## 学习节奏

每轮由 Agent 带你围绕一个具体问题走完：**观察异常 → 拆根因 → 检查真实字段与来源 → 提出模型/查询方案 → 用数据反驳或修正 → 说明方案适用条件和边界 → 你提出下一问。**Agent 的作用是质疑并帮助构建逻辑链，不代替你给业务概念和规则背书。

贯穿课程的两个案例保持分开：采购事件日志负责真实企业流程建模；标准数字化资料负责理解文档语义表达和标准 Ontology。它们可以在第五阶段比较，不把标准草案当成采购公司的业务政策。

## 请一起讨论的选择

1. 是否用 BPI Challenge 2019 采购流程作为主实践题？挑战材料提供了四类匹配流程的规则，可支撑第一题；若要推广成某个组织的正式采购政策，还需该组织自己的规则来源，日志不能代替政策。
2. 是否把 Olist 电商作为第二个、单独的对照项目，还是先只做好采购这一条链？
3. 标准数字化这条线先作为概念对照，还是后续单独做“标准制定流程 Ontology”（可再评估 IETF Datatracker 或 SAMR 公开流程数据）？
4. 你最终更想把 Ontology 应用到采购、标准数字化，还是一个你熟悉的行业？这会影响第一道练习题，但不改变问题驱动的学习方法。
