# 工具调用

工具调用是让 Agent 根据任务意图选择外部函数或服务，并提交调用参数，由应用执行后返回结果的接入方式。本页采用的是通用方法定义；视频中的具体工具接口没有独立核验。

## 来源观点

作者将 function calling 和 tool calling 视为同一类能力，并称现在统一改名为 tool calling。作者建议把高频查询、业务更新、本体数据校验和部分规则封装成外部工具，让 Agent 根据意图调用。

订单演示被描述为通过 tool calling 定位订单、查询关联事实和状态，再执行规则校验并生成回复。

第 4 集作者补充了客服查单场景的设计考虑：Agent 需要读取业务数据上下文，并通过合适的工具查询订单、仓储和物流信息。作者还提出，删除信息、退款等高风险动作需要控制，不能由 AI 不受限制地自行驱动；异常情况可以暂停并交由人工确认。

这一集没有给出工具接口、权限模型、风险分级或异常处理实现。以上内容是作者提出的设计观点，不代表该场景已经部署相应机制。

## 规则和数据更新

把业务规则、数据校验或本体数据更新做成可调用函数，会带来可执行和可复用的好处，也会引入新的治理责任：

- 函数输入输出需要稳定；
- 更新操作需要权限和副作用说明；
- 规则需要版本、责任人和回归测试；
- 失败和冲突需要返回明确状态；
- 执行过程需要日志和来源记录。

来源没有展示实际函数定义、参数结构、更新事务或回滚机制。

## 与 MCP 的关系

视频把 MCP 作为另一种可承载多个查询、更新和校验工具的形态，并提到上下文消耗和服务延时。来源没有提供同一条件下的测量，也没有展开鉴权、版本兼容、审计和可观测性。

因此，不能把“使用 MCP”直接写成必然更慢或更耗上下文，也不能把 tool calling、MCP、skills 和 sub agents 当作严格互斥的分类。

## 边界

工具调用只能说明 Agent 与外部能力之间存在调用接口，不能证明模型选择正确、返回事实可信、业务规则正确或系统具备生产级安全性。工具结果还需要经过权限、来源、版本和业务状态检查。
