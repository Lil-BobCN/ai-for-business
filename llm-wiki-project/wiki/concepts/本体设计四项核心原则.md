# 本体设计四项核心原则

## 定义

本体设计四项核心原则是视频作者在该段口播中转述的 Palantir 本体设计方法论骨架，按优先级排序为：领域驱动设计、不要重复构建相似的实体、对外扩展开放、组合优于继承。作者称这四项原则出自 Palantir 官方总结，但视频中未给出文档链接或原文，属 `unknown / 待外部核验`。

## 来源观点

以下均为视频作者在该段口播中提出的陈述。

### 原则一：领域驱动设计（最高优先级）

- 本体论建模的是真实世界，而不是基于元数据直接建模。
- 正确顺序三步：理解业务领域 → 设计本体模型（对象类型、属性、属性关系、接口）→ 映射元数据与逻辑（结构化、半结构化、非结构化，经数据管道从数仓、数据表、文档构建）。
- 反例：拿到一张 CSV 就把每一列映射为一个 property，把订单号、客户名、客户邮箱、产品 SKU 都塞进一个"订单"实体。正确做法是拆成订单、客户、产品三个对象类型，再用语义关系连接。
- 判断标准：构建完本体后，一个用户或 AI Agent 能不需要查阅具体文档，凭直觉理解它描述的业务含义。

### 原则二：不要重复构建相似的实体（DRY）

- 英文叫 Don't Repeat Yourself，每个概念只存在一个规范化的表示。
- 触发条件为三次法则：同一事物出现一次是巧合、两次是模式、三次必须重构。
- 反例：部门孤岛——销售建 SalesCustomer、支持建 SupportCustomer、财务建 BillingCustomer，三套类型都有 Customer Name、Email、Phone 加各自特殊字段，导致同一客户三条记录、信息不一致、三套 Action 各自维护。
- 两种修法：一是统一为单一规范化类型 Customer，共享属性；二是若各部门定义确有本质差异，定义 CustomerBase 接口放公共属性，各部门类型各自 implement 并扩展特殊字段。

### 原则三：对外扩展开放

- 对已上生产线的本体，修改要关闭；核心模型上线验证后应锁定，新需求通过扩展添加，而不是往核心 Object 塞字段。
- 反例：上帝对象——Equipment 最初只有序列号、模型、Location 三个核心属性，研发认证加 4 个字段、财务加折旧字段、维护加 5 个维保字段，层层叠加到 150+ 属性；对任何具体设备而言大量字段为空，且任何团队改核心类型都可能破坏其他团队使用。
- 正确做法：核心 Equipment 保持三字段不动，认证信息建 EquipmentCertificate 链接类型，能力转建接口；每个新需求都是独立扩展模块。

### 原则四：组合优于深层次的继承

- 反例：Asset → Physical Asset → Building 的深继承链，一个实体需逐层下探才能获得能力。
- 作者称 Palantir Foundry 的接口支持多重实现，一个实体可以同时是 Building，也可以是 Resource。
- 对比：接口组合下，实体实现 Building、Resource 等接口即可直接应用能力，无需一层层往下探。

## 项目分析

- 四项原则的优先级排序本身是可迁移的方法论骨架：先确定领域边界与实体边界，再谈字段与实现。
- 原则三与原则四可视为同一症状（改动无处安放）的两个出口：上帝对象是往核心类型塞字段，深继承链是能力只能沿层级下传；接口与扩展是在给"改动"开一个不触碰核心的出口。
- 原则一与原则二共同指向"概念边界"问题：前者要求先有领域共识，后者要求同一概念只有一份表示。

## 反例或边界

- 当业务定义本身在争议中（组织调整、产品线合并），"从领域出发"的第一步缺少稳定输入，先建草稿本体暴露分歧可能更现实。
- "核心模型上线后锁定"与"小步快跑、允许不完美"之间的张力，作者未直接调和。
- 原则二未回答"谁有权拍板哪个是规范化表示"。
