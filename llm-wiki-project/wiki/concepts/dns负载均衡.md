# DNS 负载均衡

DNS 负载均衡指通过 DNS 解析把同一域名解析到多个 IP，从而把用户流量分散到不同服务器实例上，不使用常规负载均衡器也能完成简单的流量调度。本页记录 [[架构师阿Q]] 第 5 集口播中对这一方式的描述与批评。

## 定义

视频作者在该段口播中提出：用户访问域名（例如 `www.aq.com`），通过 DNS 解析到多个 IP，然后访问每个 IP 对应的服务器实例，就完成了流量调度。它没有使用常规的负载均衡器，但也的确完成了简单负载均衡的功能。

## 来源观点（`unknown / 待外部核验`）

作者给出的优点与缺点：

- 优点：实现简单、成本低。
- 缺点一：**服务器故障切换延迟大**。DNS 与用户之间是层层缓存，即便故障发生时及时修改 DNS 或摘除故障服务器，由于中间经过运营商的 DNS 缓存，且缓存很有可能不遵循 TTL 规则，导致 DNS 生效时间缓慢，用户仍会访问到故障服务器。
- 缺点二：**流量调度策略简单、支持的算法较少**，作者称 DNS 一般只支持轮询方式。
- 结论：生产环境中很少用这种方式实现负载均衡。
- 补充：一些大公司一般也会利用 DNS 实现**地理级别**的负载均衡，实现就近访问、提高访问速度；这种方式一般是入口流量的基础负载均衡，下层会有更专业的负载均衡设备实现负载架构。

## 已核验事实

本页暂无工具直接验证的事实。「DNS 一般只支持轮询」属作者概括，未经独立核验。

## 项目分析

- 作者对 DNS 方案的两条批评都不是「功能不够」，而是「控制权不在你手里」：DNS 记录的生效时间由运营商缓存决定，调度策略由 DNS 协议能力决定。这一观察被整理者提炼为 [[控制权边界]] 这一选型维度。
- 由此得到的通用教训：把控制权交给他人缓存的机制，不适合放在需要快速切换的关键路径上。

## 反例与边界

- 作者同时承认 DNS 在地理级负载均衡与就近访问场景中仍被大公司使用，因此「生产环境很少用」应限定在「作为唯一或主要负载均衡手段」的语境下理解。
- 本集未讨论 DNS 调度与 CDN 的关系，也未讨论故障切换的兜底应放在哪一层。
