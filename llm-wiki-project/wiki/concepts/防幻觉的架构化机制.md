# 防幻觉的架构化机制

## 定义

防幻觉的架构化机制是视频作者零点未来在「AI+企业」第 5 集中提出的一种防幻觉思路：不靠提示词写「不要编造数据」，而是通过缺 Context、缺 Object Type、缺权限、缺函数几层叠加，让 Agent「根本接触不到」相关信息，从而在架构层面消除编造的可能。

## 来源观点

以下均为视频作者在该段口播中提出的观点，属 `unknown / 待外部核验`。

作者以「公司今年总营收是多少？」为例，说明 Palantir 的做法有几层：

1. 没有配置财务的 Context，Agent 看不到；
2. 没有 Financial Report 的 Object Type，检索不到；
3. 没有授权财务的权限，算不了；
4. 没有授权财务的函数，同样算不了。

几层叠加后，Agent 对营收彻底不知情——不是被告知不能说，而是根本接触不到。最终回答是「我没有权限访问公司的财务数据」。

作者强调，这是从架构层面解决的问题，而不是写一条 prompt 说「你不要编造数据」就 OK。

## 项目分析

- 该机制与提示词工程形成明确对照：把防幻觉从「行为约束」升级为「能力约束」。
- 与 [[concepts/本体作为约束层]] 同向：约束在架构层生效，而非在生成层生效。
- 与 [[concepts/确定性走context探索走query]] 互补：Context 侧过宽会引入噪声，但 Context 侧缺失正是防幻觉的第一道闸。

## 反例或边界

- 失效模式转移：作者称防幻觉「从架构层面解决」，但隐含前提是权限配置本身正确。失效模式从「模型乱说」变为「权限配错」，且后者更不易被用户察觉，作者未讨论此风险。
- 函数可信性假设：作者主张「业务规则和模型交给 function」，但未说明函数写错时如何发现，Agent 会「错得很自信」。
- 审计日志的消费方缺失：作者把「全链路可追溯」列为工程问题，但未说明谁来看这些记录。
- 列举项与层数不一致：文中列举 Context、Object Type、权限、函数四项，而叙述中另有「三层叠加」的说法，需核对原音。
