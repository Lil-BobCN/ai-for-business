# Agent 中断条件与检查点

## 定义

Agent 中断条件与检查点，指在 Agent 执行链路中预先约定“在什么情况下必须停下来等待人工输入”的判定条件，以及承载这一暂停与恢复动作的运行状态保存点（checkpoint）。它把“人机协同”从一句口号变成可测试的链路节点。

## 来源观点（视频作者主张，`unknown / 待外部核验`）

视频作者在该集口播中提出，业务流程不可能全盘交给 Agent，像操作数据、库存操作、金额这类高危操作必须由人工确认，因此 Agent 必须知道自己在什么情况下可以停下来等审核。他明确列举了三类应设中断的场景：

1. **指代不明**：查询到多个订单，无法确定是哪一个；
2. **信息不足**：关键信息不够，需要再与用户沟通、让其补充；
3. **证据冲突**：检索到的事实与用户陈述不符，需要人工决策。

作者给出的落地方式是：把业务规则写进本体的 schema，AI 命中规则即暂停；用 LangGraph 的 checkpoint 保存快照与运行进度，配合 `thread_id` 实现“停下—等人输入—恢复”。

## 项目分析

- 三类场景对应三种不确定性：前两类是“还缺东西”，第三类是“东西互相打架”。第三类才是真正需要人来承担判断后果的地方。
- 作者把“人机交互”放在整条链路的最后一段来讲，但它其实是前置设计问题：不是等 AI 做错了再补人工，而是先约定清楚哪些动作不能由 AI 单独完成。高危操作清单一旦确定，系统的中断点也就跟着确定了。
- 可迁移的推导方式：先列不可全自动的动作（按“可逆性”和“影响面”两个维度排队），再倒推 Agent 该在哪里停。
- 可迁移的落地形式：把每个业务场景的中断条件写成一行可测试的判定（触发条件、需要的输入、恢复条件），就能把“人机协同”变成可以回归测试的用例。

## 反例与边界

- 中断条件完全建立在业务规则被正确建模、并被持续维护之上：规则写进本体之后由谁更新、规则之间冲突怎么办、规则过期了系统会不会继续停在一个早已不该停的地方，本集均未给出答案。
- 哪一类条件适合用规则硬编码、哪一类更适合交给模型判断后再由规则校验，作者未展开。
- 如果一个业务动作很难事先判断危险程度（例如金额不大但涉及承诺时效），中断条件应由系统规则决定还是由模型自己判断，仍是开放问题。
