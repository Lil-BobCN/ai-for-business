# 拓扑子图作为检索单元

拓扑子图作为检索单元是视频作者 catface996 在《Ontology：AI Coding 在本体中的建模和实战》中描述的一种本体设计选择：预先定义可检索的图路径，作为检索入口。

## 定义

除了搜索 instance，作者的系统还预先定义了各种拓扑子图作为检索单元。例如"发布图谱"：project → release plan → release → 里程碑 → feature → Spec → 多个部署（前端/后端）。也可以只取 Spec 与 Plan 两个 class 形成一个小拓扑子图来检索。

## 来源观点（均归属 catface996，`unknown / 待外部核验`）

- 作者称其系统有 23 个拓扑子图。
- 是否把向量化数据铺进某个子图、定义多少个子图，作者称这是"业务上的决策，不是工具或流程上的决策"。
- 检索时先取 instance 的摘要信息（name、description），判断后再通过工具（如 `Cali Instance Detail`，待确认）拿详情；也可按 instance 的拓扑结构（outgoing、深度 1 或 2）搜索。

## 已核验事实

- 无。子图数量与检索机制均来自作者口播，未做独立核验。

## 项目分析

该设计揭示一个容易被忽略的张力：在图谱里能问出什么问题，取决于事先把哪些路径定义成了可检索路径。系统因此倾向于回答"设计过的那些问题"。与既有 [[concepts/本体检索策略选型]]、[[concepts/向量检索与图扩展]] 相关。

## 反例或边界

- 当业务提出一个从未定义过的问法时，是让人补子图定义，还是让模型自由遍历？两者在成本与稳定性上意味不同，作者未展开。
- 拓扑检索会遇到大量链接的"黑洞"节点（见 [[concepts/图谱健康度检测-黑洞孤岛循环依赖]]）。
