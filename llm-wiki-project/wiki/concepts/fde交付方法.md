# FDE 交付方法

FDE 交付方法，是从真实业务痛点出发，依次完成业务理解、方案设计、数据治理、AI 协作开发、评测上线和持续迭代的企业 AI 应用交付路径。本页整理视频作者提出的方法框架与当前分析，不代表课程效果、岗位结果或项目收益已经验证。

## 学习路径与关键能力

视频作者将零基础学习 FDE 概括为五个阶段：

1. 业务理解与方案设计；
2. 驾驭 AI 协作开发；
3. Agent、RAG 和检索策略选型；
4. 企业知识治理、数据清洗和 Ontology 建模；
5. 业务建模、项目实战和交付落地。

作者强调，编码门槛下降不等于数据治理和业务判断门槛下降，并称企业知识治理是重要且困难的环节。

在第 1 集中，作者认为 AI 可以参与资料分析、本体构建、代码开发和测试验证；FDE 的关键能力在于理解各阶段要解决的问题、拆解任务、组织 AI 完成工作，并判断结果是否符合业务要求。作者据此认为，AI 协作可以降低上手门槛，让学习者从具体项目开始边做边学。

第 1 集课程导览和第 2 集课程导学均未提供各环节的效果数据、人工投入、验收标准或学习结果，不能据此建立通用岗位标准。这些内容属于作者关于岗位能力和学习路径的观点，相关论证和实践仍需其他材料核验，来源页见 [[68-3小时零基础入门fdeontology业务本体原理精讲与项目实战教学理清知识图谱rag与agent协同从零搭建企业ai客服中台附全部源码--2-文章--19-第-1-集9月30日-fde-木羽b站--14wet35]] 和 [[第 2 集｜01-课程导学：FDE学习路径与订单客服实战目标]]。

## 本体导向的学习路径

第 5 集将学习步骤进一步表述为：

1. 掌握 AI 编程基础；
2. 学习需求梳理和问题拆解；
3. 理解 Agent、RAG、GraphRAG、Ontology、skills、workflow、单智能体和多智能体等架构选项；
4. 完成评估、上线和 Vibe Coding 项目开发。

这是一条视频作者提出的学习建议，不是经过学习者评测验证的培训效果。LightRAG、GraphRAG、Microsoft GraphRAG、LangChain 等在本集中只是选型举例，没有形成实测比较。

第 5 集作者把业务本体建设描述为 FDE 现场交付的核心技术之一，认为 FDE 需要把企业领域中的客户、订单、商品、包裹、物流和业务资料组织成共同业务模型，再将其作为 Agent 的统一上下文查询和推理入口。

按该集电商客服示例，现场工作可初步拆成：

```text
观察跨系统查询痛点
  -> 盘点订单、仓储、客服、物流和业务规范资料
  -> 抽取业务对象与字段
  -> 对齐身份和关系
  -> 关联状态、来源和时间
  -> 提供给 Agent 查询或推理
  -> 依据业务指标评测并迭代
```

这是根据作者案例整理出的分析框架。来源没有给出正式 Schema、抽取工具、数据质量指标、权限设计、冲突处理或上线结果。

## 岗位认识与课程安排

第 2 集作者提出从三个切面认识 FDE 岗位：

- 行业趋势；
- 日常工作范围；
- Palantir、OpenAI 等公司的岗位定义或实践。

该框架是入门课程的组织方式，不是经过外部资料验证的岗位标准。岗位热度、职位数量、国内机会、薪资和公司实践仍需分别核验，见 [[FDE 相关数字原音与统计口径待核验]] 和 [[FDE 岗位定义与 Palantir、OpenAI 实践待核验]]。

该集还预告了两天的实战节奏：第一天认识岗位、介绍 Ontology，并用订单客服资料构建业务模型；第二天计划将模型接入 Agent 与 RAG，面向订单处理服务。这是课程作者提出的教学路径，不构成后续实施或效果证据。

## 项目交付链路

第 11 集后半段把项目过程概括为：

```text
业务调研
  -> 需求与方案拆解
  -> 数据治理
  -> 应用开发
  -> 评测与上线
  -> 监控、反馈和持续迭代
```

第 4 集作者以客服查单场景补充了一条更贴近现场的交付路径：

```text
观察真实操作链路
  -> 与业务方约定验收标准
  -> 关联业务数据并选择技术方案
  -> 开发与生产上线
  -> 业务人员试用、反馈和迭代
  -> 共同评估交付并沉淀经验
```

这两个流程来自不同集数的作者表述，颗粒度不同，不应合并成一个已经验证的标准流程。

第 4 集作者还将工作环节归于 OpenAI，称其包含需求探索、技术范围界定、系统设计、开发构建和生产上线；该转述尚未核对原始材料。

作者还提出，应按需求与目标决定技术复杂度，可从单一模型接入，逐步扩展到自动化能力、Workflow 或 Agent Teams，再到复杂系统托管。文稿中的 `Agent's Views`、`Scales` 等表达存在 ASR 不确定性，不据此定义具体技术层级或产品。

## 客服案例与方案边界

第 4 集用咖啡机主机与分开发货的赠品奶泡壶说明跨订单、仓储和物流信息查询的场景。作者提出，把买家、商品、订单和物流状态建立关联，可以让客服从一个入口追踪完整信息链路。作者称案例真实，但没有提供案例主体、系统记录或上线结果。该描述没有给出数据结构、规则或实现细节，不能仅凭描述认定它就是 Ontology。

第 5 集也用咖啡机主机与分开发货的赠品奶泡壶说明跨订单、仓储和物流信息查询的场景。该案例没有给出数据结构、规则、来源优先级或实现细节，不能仅凭描述认定它就是 Ontology，也不能证明“上下文充分即可使用小模型”适用于复杂意图、歧义实体、异常状态和长链路任务。

第 5 集的订单案例还暴露出需要提前约定的验收问题：

- 同一订单包含多个包裹时，订单完成如何定义；
- 主商品签收但赠品未签收时，客服应如何表述；
- 订单、物流和知识库状态冲突时，哪个来源优先；
- 关系展开的跳数和上下文大小如何控制；
- 高风险操作是否需要人工确认。

## 可迁移的交付资产

结合视频内容和当前分析，可以整理出需要在项目间复用的资产：

- 业务对象、属性、关系和状态定义；
- 不同系统之间的身份与字段对齐记录；
- 数据来源、时间和版本信息；
- 工具输入输出和错误契约；
- workflow、skills 和 Agent 的任务模板；
- 规则、责任人、版本和回归题库；
- 工具执行日志、来源溯源规范和人工介入记录；
- 业务场景评测集、验收标准和人工介入标准。

这些是当前分析提出的交付要求，视频没有证明课程或演示已经完整交付这些资产。

## 交付验收与风险控制

第 4 集作者把“以结果为目标”作为 FDE 的岗位定位，并称交付责任不应止于部署组件。该说法是作者转述的观点，未给出量化指标、基线、结果归因或责任分配规则，不能当作 Palantir 的正式定义。

需求探索阶段可以把业务人员当前的操作步骤、涉及系统和预期结果写清楚，并在开发前约定验收口径。实际评估可结合业务方共同确认的指标和基线；具体指标应依据场景选择，来源没有给出任何可复用的效果数据。

作者还提出，删除信息、退款等高风险操作应设置人工确认，遇到业务异常时可以暂停并交由人工处理。来源没有说明权限等级、触发条件和审批流程，因此这应视为控制设计建议，而非已验证的系统实现。

## 边界与证据状态

作者关于岗位薪资、证书含金量、项目数量、课程时长和接单收入的说法，不能作为 FDE 方法有效性的证据。课程提供项目案例也不等于学习者能够独立完成同类交付。

FDE 方法的实际效果需要由真实需求、数据质量、评测结果、上线运行和客户反馈共同验证。第 4 集没有提供项目效果的测量数据，也没有说明业务结果未达成时各方如何分担责任。第 5 集没有提供项目效果测量数据，也没有说明业务结果未达成时各方如何分担责任。
