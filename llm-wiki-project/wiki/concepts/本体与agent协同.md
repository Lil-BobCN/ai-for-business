# 本体与 Agent 协同

本体与 Agent 协同，是把业务对象、属性、关系、状态、来源和规则组织成可查询的业务上下文，再通过检索、工具调用或其他接入形式交给 Agent，用于回答问题、校验事实或执行任务的方法。本页同时整理来源观点与当前分析，不能把课程演示自动视为生产系统能力：现有内容以视频作者口播为准，其中订单客服链路标注为本地 ASR（`partial`），第 12 集给出的定位亦未经独立核验。

## 业务上下文视角（第 5 集）

第 5 集作者把 Agent 的核心需求描述为“知道自己正在处理什么业务”。在订单客服场景中，Agent 需要依次掌握：

```text
用户身份
  -> 客户
  -> 订单
  -> 商品或套装
  -> 包裹
  -> 快递、运单和物流状态
  -> 业务完成口径与异常规则
```

这条链路来自视频作者对电商案例的口播描述，证据为本地 ASR，状态为 `partial`；链路本身没有对应的 Schema、API 或运行日志。

### 本体最小组成

作者用 `objects`、`properties` 和 `links` 描述本体的最小组成：

- `objects` 对应客户、订单、商品和包裹等业务对象；
- `properties` 对应对象的字段、特征和状态；
- `links` 对应客户下单、订单包含商品、商品对应包裹等关系。

ASR 中出现的 `optics` 无法确认原词，不能作为已确定的第四个构成要素。

### 共同业务模型与跨系统对齐

第 5 集把 Ontology 描述为将订单系统、仓储系统、物流记录、客服资料、PDF 和 CSV 组织成共同业务模型的方式。其重点不是某一种文件格式，而是把分散资料中的身份、对象、状态和关系对齐，使 Agent 可以从某个业务对象继续查询关联信息。

这与 [[结构化查询]] 和 [[图遍历与 BFS 扩展]] 存在概念联系，但该集没有证明实际使用了 BFS，也没有提供字段映射、实体消歧、主数据规则或关系展开算法。

作者把“主机已经到了、奶泡壶呢”描述为一条从身份核实到物流状态查询的完整链路。该演示说明了逐级定位和关联查询的业务价值，但不能直接证明本体已经解决了权限、数据新鲜度、状态冲突或异常责任问题。

## 与知识图谱及其他模型的边界

作者认为本体关系网“看起来像知识图谱”，但在第 5 集没有说明两者的形式化边界。当前仍需区分：

- 数据字典主要描述字段和口径；
- ER 图主要描述表、实体和结构关系；
- 主数据管理关注跨系统身份和权威记录；
- 知识图谱通常强调实体、关系和事实的图结构；
- Ontology 在具体项目中是否额外承担约束、规则、权限、来源和时间语义，需要结合实际实现判断。

因此，第 5 集可以补充概念案例，但不能单独支持“Ontology 等同于知识图谱”或“Ontology 必然覆盖上述全部能力”的结论。

## 模型能力与上下文供给

视频作者提出，只要上下文完整，即使千问 3B 或 1.5B 等小模型也可能回答订单问题。这是作者关于模型与上下文关系的主张，没有指定模型版本、评测集、准确率、失败样例或与更大模型的对照。

工程上仍需验证：

- 上下文是否完整、正确且在权限范围内；
- 关系跳数增加后，模型是否能保持实体和状态对应；
- 状态冲突、歧义订单和过期数据如何暴露给 Agent；
- 哪些问题可以交给小模型，哪些问题需要更强模型、规则或人工处理。

## 接入形态：Agent 作为编排者（第 12 集）

第 12 集视频作者木羽 Cheney 在口播中对该协同的定位作出补充，提出：

- Agent 是组织执行的编排者，它不产生事实。
- Agent 通过 tool calling、skills、MCP 等不同形式接入本体检索接口与 RAG 检索接口。
- Agent 把本体和 RAG 检索出来的信息组织成一个上下文来进行回答。
- 由此，“要不要做 RAG、要不要做本体”不是二选一的技术题，而是“这个业务需要哪种证据”的需求题。

> **已核验事实**：无。上述定位为视频作者口播口径，未经独立核验。

### 执行链路复盘

```text
用户提问
  -> Agent 通过 tool calling 接入本体业务模型
  -> 找到核心对象
  -> 用“向量模型加图扩展”检索算法取回关联对象、属性与事实依据
  -> 组织上下文生成回答
```

### 项目分析

- 该定位划出了“何时单独用、何时融合用”的判断前提：Agent 只负责编排，证据由本体与 RAG 两类供给提供。
- 与 [[工具调用-mcp-sub-agents-skills-任务组织比较]] 呼应：本集列举的接入形式与该比较页讨论的任务组织方式一致。
- 与 [[本体问答-agent-skills]]、[[本体构建-agent-skills]] 相关。

## 课程中的架构主张（第 11 集、第 2 集）

第 11 集作者称，LangGraph 负责流程编排，Semantica 提供检索算法并读取 OWL 文件，Agent 通过 tool calling 调用本体能力。第 2 集则预告将业务模型接入 Agent 与 RAG。

这些内容仍缺少工具 Schema、OWL 读取路径、推理器配置、模型名称、数据更新机制和可复现运行结果。相关边界见 [[本体与 Agent 接入边界待核验]] 和 [[Semantica 能力、API 与推理边界待核验]]。

## 接入契约

从现有各集材料可以整理出一份最小接入契约：

- 输入：用户意图、业务对象、标识或查询条件；
- 输出：事实、关系、状态、来源和必要业务上下文；
- 错误语义：空结果、歧义、权限不足、查询失败和规则失败；
- 可追溯信息：工具名、参数、执行时间、数据版本和规则版本；
- 执行边界：只读查询、数据更新、规则校验和人工审批必须区分。

这是对来源缺口的工程化整理，不是第 5 集提供的正式接口定义。

## 反例与边界

- 订单系统显示“已签收”、物流系统或知识库显示“运输中”时，本体不能自动决定哪个来源权威；
- 关系稠密时把某个对象的全部相邻分支带入上下文，可能造成上下文膨胀；
- PDF、CSV 和业务系统之间可能存在身份冲突、字段缺失和时间口径差异；
- 本体关系网不能自动证明具备 OWL 推理、事务更新、权限控制或生产可用性；
- 一次订单客服演示不能覆盖退货、缺货、拆单、跨渠道身份和异常升级；
- 若 Agent 同时接入本体接口与 RAG 接口，由谁决定这一次该调哪一个、或两个都调，第 12 集未回答；
- 该决策写在哪里（提示词、编排层、路由规则），第 12 集未涉及。

## 开放问题

- 本体接口与 RAG 接口的调用决策应由哪一层负责？
- 是否应把“证据类型”当作架构分层依据（确定型事实走本体、文档型依据走 RAG、混合型走编排）？
