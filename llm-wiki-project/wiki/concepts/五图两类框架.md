# 五图两类框架

五图两类框架是视频作者在"零点未来：AI+企业"第 9 集中提出的一个概念分类框架，把五个带 graph 的词拆成两类：本体、知识图谱、上下文图谱、代码图谱回答"系统知道什么"；图谱工程（Graph Engineering）回答"系统怎么干活"。这是作者自创框架，非行业公认划分。

## 框架内容（作者口径）

作者在该段口播中提出：这五个词其实是两类东西。

- 前四个——本体、知识图谱、上下文图谱和代码图谱——回答的是同一个问题，叫做"系统知道什么"；它们是地图，是原料，越攒越值钱，就跟数据一样。
- 最后一个图谱工程回答的是另外一个问题，就是"系统怎么干活"，它跟业务是要天天打交道的。

作者让大家记住一句话：**"知道什么"决定答得对不对**，这是前四个词干的事情；**"怎么干活、稳不稳"**，才是 graph engineering 做的事情。

## 一句话记忆（作者原述）

**规则书 ontology、世界网 knowledge graph、业务上下文地图 context graph、代码的管网图 code graph，以及最后一张 Agent 的轨道 graph engineering。**

## 类比（作者原述）

- ontology 有点像游戏的规则、城市的规划图
- knowledge graph 有点像游戏里面的角色还有建筑
- context graph 就是当前游戏的一个关卡、任务目标还有资源的状态
- code graph 有点像游戏引擎里面的代码结构
- graph engineering 就是游戏引擎和运行的整个系统

## 场景对照表（作者原表）

| 场景 | 用哪张图 |
|---|---|
| 机器推理、推出新结论、统一语义术语 | ontology |
| 通用常识问答、推荐、多跳问答 | knowledge graph |
| Agent 进公司干活、影响分析、审计追踪 | context graph |
| 代码导航、改代码影响评估 | code graph |
| 有套路的业务流程编排、稳定可控的 Agent 流水线 | graph engineering |

## 四层全景架构（作者原述）

| 层 | 内容 |
|---|---|
| 定义层 | ontology，定义概念与语义关系，是基础 |
| 表示层（表征层） | 知识图谱、上下文图谱、代码数据 |
| 工程层 | graph engineering，给 Agent 的工程运作 |
| 应用层 | 给 Agent 提供的运行环境与运行工具 |

## 采购寻源 Agent 示例（作者演示，非客户案例）

作者用采购寻源 Agent 串场演示五图协作：

1. 用本体定义采购业务域——什么是供应商、品类、零件这些实体，搭好基座。
2. 知识图谱存数据，查询企业已有的供应商、供应关系、历史采购记录。
3. 上下文图谱根据当前任务理解任务背景，分析本次采购的品类、需求、数量、目标成本，辅助决策（ASR 作 `反正决策`，待确认），分析历史推荐决策的原因。
4. code graph 是自身实现这套系统的代码结构。
5. 用 Agent 去做这个事情时，要建立 Agent 执行的轨道。

作者收束：五张图各司其职，其实缺一不可；它们不是互相替代，而是分工协作。

## 项目分析

- 与 [[企业-ai的data-logic-action三层模型]] 可对照：两者都是分层框架，但五图两类框架把"知道什么"与"怎么干活"切开。
- 与 [[本体与知识图谱职责边界待核验]] 直接相关，可补充"规则书 vs 实例网"的比喻与分工线。

## 反例与边界

- 四层架构是分工还是施工顺序存在张力：定义层被放在最底下、被称作"基础"，但另外三层并不会等它做完才存在——企业里通常已经有数据、有代码、也有在跑的流程。这四层更像是各管一段，而不是一道严格的先后工序。
- 作者把"知道什么"与"怎么干活"分开讲，但在真实系统里，Agent 每次执行都会产生新的状态和决策记录，这些记录本身又会回流成上下文图谱的输入，两者的边界是流动的。
