# 宽表拆分规则

"宽表拆分规则"是本来源视频作者认为整条链路中最值钱的一环：由于一个 Object Type 只能对应一张表，几百列的企业宽表必须先拆成聚焦小表才能映射成本体，而"哪一列属于哪个实体"的判断是 FDE 最贵的时间。本页内容属作者口播观点，`unknown / 待外部核验`。

## 定义

Palantir 有一条硬性规则：一个 Object Type（实体类型）只能对应一张表。因此宽表不能直接映射，必须在 Pipeline 里拆成几张聚焦小表（如订单表、商品表、物流表），各自映射到对应 Object Type，再用 link 连接。

## 来源观点

- 现实中企业数据常是一张几百列的大宽表，订单、客户、商品、物流混在一起。
- Pipeline Builder 内置 AI 可辅助写拆分代码，但"怎么拆、哪一列属于哪个实体"仍需人为判断。
- 这是纯粹的业务场景建模，也是 FDE 工程师最贵的那部分时间。
- 作者判断：真正值钱的不是定义实体本身（供应链的 Shipment、SKU，医疗的 Patient 等行业共识度高），而是把"宽表到实体的 Mapping 规则"产品化；垂直行业玩家比 Palantir 更有动力做。

## 已核验事实

本页暂无经工具直接验证的事实。"一个 Object Type 只能对应一张表"是否为硬性规则待核验。

## 项目分析

作者把这条链上最难被替代的一环指认为"宽表到实体的映射规则"，而非实体清单本身。商业含义是：护城河来自行业里反复出现的表结构，而不是来自某个行业的对象命名约定。可迁移做法：把"字段到实体的映射规则"当作可复用资产管理，可能比沉淀整套行业本体更接近能交付的形态。

## 反例与边界

- 如果每个客户的 SAP 宽表都千企千面，沉淀下来的到底是模板，还是一套拆表的决策流程，作者未回答。
- 作者对 Palantir"没动力做"的判断是商业动机推断，非可核验事实。
