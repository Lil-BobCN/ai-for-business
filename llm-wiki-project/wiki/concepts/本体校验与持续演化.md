# 本体校验与持续演化

本体校验与持续演化，是在本体建模完成后，持续检查对象、属性、关系和业务约束是否正确，并使业务数据变化、定义变化和 Agent 使用的上下文保持可追溯一致的工作。视频作者提出了这一方向，但没有提供正式校验流程、指标或版本实现。

## 来源观点

视频作者明确表示，构建 Ontology 只是第一步。后续还要验证：

- 本体中的对象是否定义正确；
- 业务含义是否符合实际；
- 对象之间的关系是否正常；
- 通过测试确认本体是否能解决目标业务问题；
- 库存、订单等数据变化后，本体是否能够同步更新。

作者用电商客服作为例子，把库存和订单变化与知识图谱增量更新问题并置。该说法说明作者关注时效性，但没有区分实例数据更新、关系事实变化和本体定义变化。

## 校验对象

### 结构校验

检查对象、属性、关系和约束是否满足预先定义的结构要求，例如：

- 关系两端是否使用了正确的对象类型；
- 必填标识是否存在；
- 关系方向和基数是否符合定义；
- 属性取值和状态是否在允许范围内。

本集没有提供具体 Schema、约束语言或校验器，因此以上内容是当前分析整理的工程化检查维度。

### 语义校验

确认关系是否符合业务方对业务含义的理解。例如，顾客与订单、订单与商品、订单与包裹之间的关联，不能只因为字段能够连接就被视为业务上正确。

视频作者强调业务含义的重要性，但没有说明由谁确认、如何留痕或出现争议时由谁裁定。

### 业务场景测试

使用真实或脱敏的业务问题检查本体是否能够支持目标回答或流程。电商客服场景可以测试：

- 同一订单包含多个商品时能否分别定位；
- 一个订单拆分为多个包裹时能否正确展开；
- 主商品已签收、赠品仍运输中时能否保持状态对应；
- 状态冲突或缺失时能否暴露不确定性；
- 关系错误时能否阻止 Agent 继续执行。

“通过大量测试确认有效”是视频作者的主张，来源没有给出题库、基线、准确率、通过阈值或失败样例。

### 上下文进入前的校验

当前分析认为，若 Ontology 用作 Agent 上下文，关系校验最好在上下文组装或工具执行前完成。错误关系可能同时影响回答和执行，但本集没有给出硬门槛、置信度、人工复核或回滚机制。

该分析不构成已验证的系统设计，具体接入边界见 [[本体与agent接入边界待核验]]。

## 持续演化的三个对象

为避免把不同变化都称为“本体更新”，可以区分：

1. **实例数据更新**：订单状态、库存数量、包裹位置等业务事实发生变化。
2. **关系事实更新**：订单与包裹、商品与物流记录之间的关联发生新增、删除或修正。
3. **本体定义更新**：对象类型、属性含义、关系约束或业务规则发生变化。

这一区分属于当前分析，并非视频作者给出的正式分类。三类变化应当保留各自的时间、来源、版本和责任信息。

## 仍待确定的治理问题

- 实例数据变化是否自动触发关系重新计算；
- 本体定义变化是否必须经过业务人员确认；
- 旧版本本体产生的回答和执行结果如何追溯；
- 状态冲突由规则、Agent 还是人工处理；
- 关系校验失败时是阻断上下文、降级回答还是转人工；
- 数据清洗规则与本体定义如何共同演化；
- 订单、库存和物流系统的来源优先级如何确定。

这些问题与 [[本体与数据约束及版本演化待核验]] 直接相关。

## 边界与证据状态

本页关于校验层次、版本区分和上下文前置校验的内容，属于当前分析提出的工程化整理。视频来源只直接支持“需要校验、测试和持续更新”这一方向性主张。

本集没有提供：

- 校验代码或规则配置；
- 业务验收标准；
- 回归测试集；
- 数据版本或本体版本格式；
- 更新失败处理；
- 权限、审计和人工审批机制；
- 线上运行结果。

因此，不能据此断言某个 Ontology 平台已经具备持续演化或生产级校验能力。
