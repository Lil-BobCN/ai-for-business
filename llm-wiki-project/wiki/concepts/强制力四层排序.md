# 强制力四层排序

强制力四层排序是视频作者 catface996 在《Ontology：AI Coding 在本体中的建模和实战》中提出的约束强度排序，回答"为何写了规范 agent 仍照犯"这一问题。本页是对既有 [[concepts/本体约束的分层与生效时机]] 的具体化与排序化，建议交叉引用而非重复。

## 定义

作者强调逻辑是强制力的来源，因为这些逻辑基本由机器或代码执行，而非让大模型推理。排序如下（由强到弱）：

```
Schema 必填（最强）
  └─ 关系基数校验（如 Spec:Plan = 1:1；Plan 下可多个 ADR/接口协议/数据模型）
      └─ 拓扑图校验（聚合、堆栈、状态聚合）
          └─ 函数与动作（Function 运算、Action 权限/审计/通知）
              └─ 提示词（最弱）
```

## 来源观点（均归属 catface996，`unknown / 待外部核验`）

- **Schema 必填**：字段值必填、格式正则（如电话号码 11 位）；User Story 的成功标准用 Given/When/Then 语法结构，至少保证语法结构不被打破。
- **关系基数校验**：Spec 与 Plan 为 1:1，Plan 下可有多个 ADR、接口协议、数据模型。
- **拓扑图校验**：数据聚合、堆栈、状态聚合（如多个任务已归档、一个仍在开发中，聚合出"当前"任务状态）。
- **函数与动作**：Function 做运算（如检查 User Story 是否大于两个、Spec 是否已生成 Flow）；Action 做权限检查、审计、高风险操作通知。
- **提示词**：最弱，靠提示词限制 agent 或模型。

## 已核验事实

- 无。排序属作者口径，未做独立核验。

## 项目分析

该排序比任何具体实现都更有迁移价值，因为它回答了一个实际问题：为什么很多团队写了满满一页规范，agent 还是照犯不误——因为规范停留在最弱的那一层。越靠近"机器可判定"的规则，越不依赖模型自觉。

## 反例或边界

- 哪些规则值得从提示词升级成 Schema 或函数，判断依据应是"违反后的代价"还是"被违反的频率"，作者未给出。
