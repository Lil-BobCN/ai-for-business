# 本体约束的分层与生效时机

语义表达、数据校验和业务规则分别回答“含义是什么”“数据是否合规”和“满足条件后如何处理”。视频作者将三者放在本体建模的讨论中；它们的执行时机和实现组件不能因此视为相同。

## 来源观点

视频作者用以下例子说明三类约束：

| 类别 | 作者举例 | 作者描述的作用 |
|---|---|---|
| 语义表达 | 研究生属于学生 | 表达概念之间的含义或关联 |
| 数据校验 | 设备编号不能为空、功率必须为数值 | 检查数据是否满足入库条件 |
| 业务规则 | 库存低于阈值时生成补货建议并交人工确认 | 运行时依据业务条件提出后续处理 |

这些例子来自本地 ASR，状态为 `partial`。作者没有指出使用的约束语言、校验器、规则引擎、Workflow 或 Agent 接口，也未展示运行日志。

## 当前分析

三类内容可以共享业务模型背景，但所处阶段不同：

- 语义表达通常用于描述概念及其关系；
- 数据校验关注数据写入或处理时是否满足约定；
- 业务规则关注运行时条件及其触发后的动作、建议或审批。

把它们都称为“本体规则”容易掩盖执行责任。描述了一个规则，不代表系统已实现该规则；Agent 获得了上下文，也不代表它能安全执行动作。库存阈值是否适合放入本体，还取决于阈值变化频率、业务所有权及执行组件，本集没有提供这些依据。

## 设计时需要确认

- 哪些约束只用于说明业务语义，哪些必须由程序强制执行；
- 数据校验在导入、更新或查询链路的哪个阶段运行；
- 业务规则由规则引擎、Workflow、Agent 还是其他服务执行；
- 触发动作是否只生成建议，是否需要人工确认；
- 规则来源、版本、生效时间和执行结果如何记录；
- 校验失败或规则冲突时如何阻断、降级或转人工。

这些是从来源示例整理出的待确认问题，不是视频中已经给出的实现方案。
