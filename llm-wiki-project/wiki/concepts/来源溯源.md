# 来源溯源

## 定义

来源溯源指让系统能够回答"这条结论凭什么这么说"的工程能力：把结论与其原文出处绑定，使可追溯性成为产品能力而非排查手段。从机制上看，来源溯源是把答案、事实或推导结果连接回其依据、关系、工具执行和源文件的机制。

本页对这一定义的提炼属于当前分析。现有来源只展示了部分来源信息和执行过程，没有展示完整的正式数据模型、接口契约或日志结构。

## 来源观点

### 本体问答中的依据、关系与来源文件（第 10 集）

来源文件 `第 10 集｜09-本体问答开发：Semantica检索服务与应用架构.md` 在展示"整单是否签收"的问答时，提到结果中包含订单商品、包裹物流状态、引用依据，以及出库记录、仓储记录和装箱明细等来源文件。该来源还把本体关系、查询结果和外部接入数据之间的回溯能力列为框架应用层的一部分，并强调问答结果应显示依据、关系和来源文件。

该来源没有展示正式的数据模型或接口契约。

### 订单客服 Agent 的可见执行链路（第 11 集）

来源文件 `第 11 集｜10-Agent业务集成：工具调用与订单客服问答.md` 进一步强调，订单客服 Agent 的每一步都可以看到，包括定位对象、调用工具、传入参数、查询关联事实、查询商品状态和执行规则校验。

订单演示中的可见链路是：

```text
对象定位
  -> 工具调用
  -> 事实返回
  -> 状态查询
  -> 规则校验
  -> 回复生成
```

该来源没有展示正式日志结构、溯源字段、来源权限、版本号或冲突处理机制。

### 一一映射与最小证据包（第 12 集）

视频作者木羽Cheney 在第 12 集口播中给出两种具体做法：

**一一映射。** 构建 RAG 链路时遵循前面构建本体的共同约束，针对本体中定义的 Schema 对象做原文抽取，并建立一一映射——对象来源于哪一个原始文本、类型来源于哪一个文本、某些属性来源于哪一些文本——这样查询到相关信息时就能把出处一起带出来。

**最小证据包（可延展方向）。** 作者在思考题中提出给每条自动结论设计一个"最小证据包"：结论、引用的规范原文、文件位置、生效版本。

> [!note] 已核验事实：无。一一映射与最小证据包均为视频作者口播口径与思考题建议，未经独立核验。

## 项目分析

可审计的问答或 Agent 返回值至少应区分以下内容：

| 类别 | 应区分的内容 |
| --- | --- |
| 结论 | 最终结论；直接支持结论的事实或依据 |
| 检索结果 | 本体关系或查询结果；来源文件 |
| 工具执行 | 工具名称和调用参数 |
| 来源数据 | 数据版本和更新时间；检索时间 |
| 规则 | 使用的规则；规则版本和推导时间 |
| 人工环节 | 人工介入、修改或发送动作 |

这样，下游系统可以检查来源字段，业务人员可以复核答案，而不必只相信一段自然语言；还可以把"模型答错了"进一步拆解为对象定位、工具参数、数据事实、规则校验或回复生成环节的问题。

围绕出处路径本身：

- 一一映射是把可追溯性做进数据层、而不是做进提示词的最小工程手段。
- 该做法决定了系统能否回答"你凭什么这么说"，也决定了后续人工审核与验收时有没有东西可审。
- 与 [[本体给事实-rag给依据]] 直接衔接：RAG 补的正是这条出处路径。

## 边界

- "能指出来源"不等于"来源可信"。来源文件可能过期、相互矛盾、权限不足，或本身存在录入错误。
- 来源链还需要说明关系来自原始事实、向量召回、图扩展还是规则推导。
- 工具执行过程可见，也不等于原始事实、规则和模型输出已经通过验证。
- 一一映射依赖抽取质量、切分粒度、增量更新机制三者同时成立。
- 原文改动、切分边界移动、对象合并之后旧映射由谁维护，第 12 集未涉及。
- 来源映射是否应作为一等数据资产管理（记录来源文件、版本、片段、抽取时间），第 12 集未展开。

## 待确认问题

- Semantica 是否返回结构化的来源字段；
- LangGraph 或工具层是否记录对象、工具、参数和返回值；
- 多个来源冲突时，是并列展示、选择优先级还是阻断回答；
- 来源文件权限、版本和更新时间是否进入返回结果；
- 规则推导结论如何与原始事实区分；
- 人工修改或发送的客服回复是否进入审计日志；
- 当一份原文更新、切分粒度改变之后，已建立的映射如何维护？谁判断旧映射是否仍有效？
- 最小证据包是否应作为可解释性验收的固定检查项？
