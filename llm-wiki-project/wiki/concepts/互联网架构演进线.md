# 互联网架构演进线

互联网架构演进线是一种把互联网后端架构的高频技术名词按"瓶颈出现顺序"串联起来的叙事框架：每个新组件都由一个具体瓶颈逼出，形成"瓶颈 → 命名解法 → 新瓶颈"的迭代闭环。本页记录的是视频作者在《第 1 集｜互联网架构就这？1个故事讲清楚》口播中提出的版本，属作者观点，未经独立核验。

## 定义

该框架的核心主张是：架构演进不是由技术偏好驱动，而是由具体故障或瓶颈驱动；因此演进顺序即瓶颈出现顺序。作者用一条单线故事把每个解法记成一个名词。

## 来源观点

视频作者在该段口播中提出的演进顺序为：

单机架构 → 应用与数据库分离 → 应用集群 + 负载均衡 → 缓存 → 读写分离 → 分库分表 → CDN + 反向代理 → 搜索引擎 + NoSQL → 分布式 → 微服务 → 容器化 → Kubernetes → 云原生。

作者给出的"哪一层解决哪一类问题"对应表（作者口播归纳）：

| 架构层 | 解决的问题 |
| --- | --- |
| 单机架构 | 从零搭建 |
| 应用与数据库分离 | 资源争抢 |
| 应用集群 + 负载均衡 | 高并发 |
| 缓存 | 查询性能与数据库压力 |
| 数据库读写分离 | 数据库读写阻塞 |
| 分库分表 + 分布式数据库 | 海量存储 |
| CDN + 反向代理 | 访问速度与系统安全 |
| 搜索引擎 + NoSQL | 复杂查询 |
| 业务拆分 + 分布式 | 业务膨胀与代码维护 |
| 微服务架构 | 团队协作 |
| 极致弹性、容器化 + 云平台 | 运维、成本与自动化 |

作者在缓存一段给出全篇少见的边界说明：数据库缓存区只存原始表数据，而三层缓存"什么快、什么常用就缓存什么"，还存页面、接口结果、静态资源、计算结果。

## 已核验事实

本页暂无独立核验事实。演进线中的技术名词本身是公开存在的通用技术概念，但"演进顺序由瓶颈出现顺序决定"这一主张未经独立核验。

## 项目分析

该框架的可迁移价值在于其讲述结构："问题 → 命名解法"适合用来整理任何技术领域的演进史，也适合检验自己是否理解某个组件为什么存在。作者结尾的对应表可直接当作架构评审时的定位工具。

## 反例或边界

- **单向演进 vs 可逆性缺失**：作者结尾主张"没有最好的架构，只有最适合业务的架构"，但全篇故事线是单向的，未展示"微服务改回单体"这类反向案例。
- **只讲收益侧**：作者在微服务一段用"运维同学直接哭了"点到一次代价，其余环节基本只讲收益。真实系统中缓存带来一致性成本、读写分离带来主从延迟、分库分表带来跨库事务与迁移成本，这些代价与收益同时发生。
- **驱动力在中途换过一次**：前半段触发条件是"系统扛不住"，到 CDN 与搜索引擎一段换成用户体验、风险与查询类型不匹配。被"性能"逼出的组件与被"业务形态"逼出的组件，验收标准不同。
- **隐含前提**：该框架成立依赖"瓶颈能被清楚识别"与"每个组件只带来收益直到下一个问题出现"两个前提，现实中多个瓶颈往往同时出现。
