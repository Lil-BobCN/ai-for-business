# 结构化查询

结构化查询是把明确的业务条件映射到字段、关系和约束清晰的数据查询中的方法。本页的定义属于当前分析；来源提供了应用示例和方法定位。

## 来源观点

第 10 集将结构化查询列为本体检索的三类主要策略之一，并以订单状态、商品明细和物流签收等条件明确的问题说明其适用场景。

第 11 集进一步把结构化查询放到 Agent 的下游执行链路中，并转述了一种公开做法：提取 GraphDB schema、识别对象标识，再执行 SPARQL 查询。作者把自然语言转为 SPARQL 与自然语言转为 SQL 作类比。

这些内容没有给出具体查询语言、查询语句、数据模式、执行计划或可核验的查询实现。第 11 集也没有提供订单演示的实际字段值、API 签名或返回数据，因此不能据此认定演示实际使用了 SPARQL。

## 订单场景

订单问题中的订单标识、商品、明细编号、销售渠道、签收状态和物流状态具有明确关系。将这些条件映射到结构化查询，有助于分别取得一个订单内多个商品的状态，并让客服回复有可检查的事实依据。

## Agent 接入

如果由 Agent 调用结构化查询，接口至少需要定义：

- 查询对象和允许的条件；
- 返回字段和对象关系；
- 空结果、歧义和权限错误的处理方式；
- 查询时间、数据版本和来源；
- 查询结果是否可以触发更新或规则校验。

模型生成查询时还需要限制查询范围、资源消耗和权限边界。

## 边界

当问题包含订单号、状态、时间范围或明确关系时，结构化查询通常更容易生成可检查的条件，也便于审计结果字段。它可以与 [[图遍历与 BFS 扩展]] 或 [[向量检索与图扩展]] 组合，但具体组合方式需要由系统设计决定。

自然语言中的同义表达、缺失字段、跨实体多跳关系和模糊条件会使结构化映射不稳定。查询结果正确也不代表底层数据已经更新或不存在冲突。

## 待确认问题

- Semantica 是否提供独立的结构化查询接口；
- 第 11 集的演示是否实际使用 SPARQL；
- 查询条件由用户、模型还是路由器生成；
- 查询失败、空结果和多个来源冲突时的返回契约是什么；
- 结构化查询与向量检索、图遍历之间如何自动选择。
