# 用业务约束换技术简化

用业务约束换技术简化是一种架构解法思路：当某个技术难题在存储层或数据层难以解决时，转而引入一条业务层面的约束条件，把难题转化为一个更容易处理的问题。本页依据视频作者在该段口播中给出的异地双活解法整理。

## 来源观点（视频作者口播主张，`unknown / 待外部核验`）

作者在该段口播中提出，面对同一份数据被两个机房同时修改的写冲突问题，路径是：先在数据层尝试（时间戳定序 → 否决，因为两台机器时钟很难完全一致），再退回同步机制（数据同步中间件自动重试 → 只能保证最终一致），最后跳到应用层加路由规则，让"同一个用户的相关请求只分发到一个机房"。具体实现包括按域名或 URL 路径区分业务、按用户 ID 计算哈希值分流、按地理位置就近路由（如华北用户到北京机房、华南用户到广州机房）。作者给出的原则是优先保证核心业务双活，而非全部业务双活。

## 已核验事实

本页暂无独立核验事实。

## 项目分析

这是把一致性问题从存储层上移到流量分发层，用一条业务约束（同一用户归属固定）换掉一类技术难题。可延展方向是研究这一类解法：把约束条件显式写出来（同一用户、同一地域、同一时段），再评估约束在业务变化后是否还站得住。

## 反例或边界

这种解法把复杂性推给了"业务关联关系的梳理"——需要将有业务交互的应用都配置在一个机房，完成业务逻辑闭环，避免跨机房调用。如果一个业务的用户天然会跨机房操作（例如全国性的即时交易），这条路由规则是否还成立，来源未讨论。
