## 一句话摘要

视频作者在这一集里回答"本体已经能给出事实依据，为什么还要接 RAG"：他先复盘上半场讲过的本体检索方式与 Semantica 这个开源框架的可用程度，再用电商客服的最小 MVP 串起"用户提问 → Agent 通过 tool calling 接入本体业务模型 → 向量模型加图扩展检索 → 组织上下文生成回答"的执行链路，然后从演示界面里一条带出处的「核对结果明细」切入，说明本体给出的是事实、RAG 补上的是原文依据，并把本体定义成底层的业务约束——传统 RAG 与 GraphRAG 都只是遵循这套约定的完整实现方案——最后落到三种实现路径的差别，以及把原文片段与 Schema 对象建立一一映射的做法。

## 主要论点（均归属视频作者木羽Cheney，`unknown / 待外部核验`）

1. **对 Semantica 的评价**：视频作者在该段口播中提出，Semantica 各阶段功能链路都已实现，但实现比较粗糙，直接调接口落地肯定不行，需要做精细化优化，交付方必须有自己的技术理解和判断。
2. **执行链路复盘**：用户提问 → Agent 通过 tool calling 接入本体业务模型 → 找到核心对象 → 用"向量模型加图扩展"检索算法取回关联对象、属性与事实依据 → 组织上下文生成回答。省去客服跨系统查询、匹配订单、组织话术的慢且易错流程。
3. **本体给事实、RAG 给依据**：本体对象来自散落文档，但每个对象可能来自某文件、某链路，还带非结构化信息；要追到"原本片段、原本出处"就需 RAG 与本体共同构成上下文。
4. **本体是约束层**：本体核心不是知识图谱，知识图谱只是展示形式；传统 RAG 与 GraphRAG 都是遵循本体约定的完整实现方案。
5. **三种实现路径**：传统 RAG → 按本体约束抽取 → 向量与图融合检索，复杂度递增；融合适用于数据乱、形式多、场景广。
6. **一一映射做法**：构建 RAG 链路时遵循本体共同约束，对 Schema 对象做原文抽取并建立一一映射，查询时带出出处。

## 关键结构：三种实现路径（作者口播口径）

| 路径 | 抽取/索引环节 | 检索环节 | 作者给出的适用条件 |
|------|----------------|----------|--------------------|
| 传统 RAG | 解析（PDF 用 PDF 解析器、CSV 用 CSV 解析）→ 切分 → 转 embedding 向量入库 | 向量库中找最相关语义、算相似度 → 填充上下文 | 默认起点 |
| 按本体约束抽取 | 让大模型按本体约定抽取实体与关系、定位原文片段；embedding 路线不变，索引/关联数据时遵循本体事实约束 | 同传统 RAG | 已有本体、需要抽取对齐 |
| 向量检索与图辅助检索协同 | 向量走向量路径、图走图路径 | 最后融合或去重，形成增强上下文 | 数据乱、形式多、检索场景定义广泛 |

## 演示与项目内容

- 演示界面「核对结果明细」中出现的规范原文（"只有确认包裹订单、所有包裹均有可靠签收，才能够配送，才能够判定为整单的……"）与指向具体文件的页码，被作者用作"RAG 补的是出处"的证据。
- 项目做法：构建 RAG 链路时遵循本体共同约束，对 Schema 对象做原文抽取并建立一一映射——对象、类型、属性分别来自哪一份文本——查询时把出处一起带出来。
- 上述界面、规范原文、文件页码均为项目演示内容，实际行为应以项目源码与运行结果为准。

## 待核验项

- 作者对 Semantica 的负面评价属个人判断，需与 `entities/semantica` 既有内容并列保留。
- "本体是约束层、知识图谱只是展示形式"是作者口播口径（用"简单理解成"表述），与学术/工程常见定义是否一致待核验。
- "通用领域规范可直接网上获取"未给来源，覆盖度、许可、可复用程度差异大。
- 本体与 RAG 都称"提供事实依据"，但两类依据强度不同，冲突时以谁为准未回答。
- 融合检索决策仅给定性适用场景，无阈值、评测方法或错误归因。
- "一一映射"依赖抽取质量、切分粒度、增量更新机制三者同时成立；原文改动、切分边界移动、对象合并后旧映射维护未涉及。
