## 内容摘要

视频作者提出，企业 AI 落地的主要障碍是业务上下文不足，而非模型本身不够强。作者把 Palantir 的 Ontology 描述为一套连接业务数据、语义、逻辑和操作能力的模型，并认为 Agent 需要在其中读取业务对象、遵循权限规则，再执行工作流动作。

作者以供应链为例，说明如何从定义业务对象与属性开始，补充业务逻辑，再配置谁能执行哪些动作。接着，作者将其称为从 RAG 到 OAG 的转变：前者以文本段落为检索单位，后者以业务对象和关系为检索单位。这个术语区分没有在视频中给出完整定义或比较证据，不能据此推断所有 RAG 系统都只能处理文本，或不能调用工具。

视频还强调人工审批、安全策略和审计，并以供应链中断处置说明 Agent 如何协助分析影响、生成方案并准备采购等动作。作者同时指出项目可能成本高、迁移困难，并存在隐私与伦理争议。结尾提出一个尚未展开的方向：用少量企业数据和 One-Shot 或 Few-Shot 方法生成 Ontology 草稿。

## 作者描述的对象映射与分层

下表保留视频作者的概念映射，不代表已核验的 Palantir 技术规范：

| 原文术语 | 作者所述映射或职责 |
|---|---|
| `DataSet` | `Object Type` |
| `Data Table` 的行 | `Object` |
| `Data Table` 的列 | `Property` |
| 不同 `Object Type` | 通过 `Link` 连接 |
| `Data` 层 | 来自不同系统的数据源 |
| `Logic` 层 | Ontology 的语义模型 |
| `Action` 层 | 执行部分，例如 `Workshop`、AI Agent 自动化 |

## 供应链示例

视频作者把供应链建模过程概括为三步：

1. 定义业务对象及其属性，例如供应商的编号、名称、区域、交付周期和风险评分。
2. 写入业务逻辑，例如计算库存可支撑天数、判断补货对象。
3. 配置执行动作及权限，规定谁能做什么、什么条件下可以做，以及动作完成后需要记录什么。

在应急案例中，作者描述了从库存阈值告警、影响分析与风险模拟，到生成备选方案、人工审核，再到创建采购单、通知客户和反馈闭环的流程。作者声称传统流程可能需要 3–5 天并涉及 20 个系统，而该方案约需 15 分钟；视频没有提供计时口径、对照组或可核验的运行材料，因此这些数字仅作为待核验主张记录。

## 主要观点与证据状态

### 来源转写内容：partial

- 作者把 Ontology 描述为整合业务对象、关系、逻辑与动作的业务模型，并称其连接不同系统的数据。
- 作者提出 Data、Logic、Action 三层描述，并以供应商和补货流程说明建模与执行。
- 作者描述 AIP 的接入路径包括连接 Ontology、设置安全策略，再由 Agent 按任务执行工作流。
- 作者主张人应处于审批环节，并将这种方式概括为“辅助驾驶”。

## 分析与边界

本视频的核心论证链是：企业 AI 缺少业务上下文，因此需要将数据、业务语义、逻辑和动作组织起来；Agent 在权限约束与人工审核下调用这些业务能力；建模和复用可能带来效率收益，也可能伴随较高成本和迁移困难。这是视频作者的框架性判断，来源没有提供独立实验或跨产品比较。

作者所称的 OAG 与 RAG 区分缺少术语全称、边界定义和公平比较，暂不作为通用技术分类。人工审批流程也未说明审核者能否查看建议依据、发现错误或应对高负荷审核。快速试点、长期复用、前期建模成本与供应商锁定之间的适用条件同样没有量化。
