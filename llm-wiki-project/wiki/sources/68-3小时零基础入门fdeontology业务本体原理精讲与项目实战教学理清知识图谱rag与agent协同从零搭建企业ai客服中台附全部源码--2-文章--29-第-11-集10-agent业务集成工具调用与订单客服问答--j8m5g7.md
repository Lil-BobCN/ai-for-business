## 主要论点与发现

### 接入契约是本集的核心问题

视频作者在该段口播中提出：能从本体找到对象和关系，还不足以完成业务任务，需要明确 Agent 如何取得并使用这些信息。

这一论点具有可复用价值。文档中的“思考一下”和“综合解读”进一步提出输入、输出、错误语义与溯源字段等接口要求，但这些属于文档中的解读，不能全部归为作者口播，更不能视为演示已经实现的功能。

### 产品做法与演示实现需要分别归属

| 主张对象 | 来源中的主张 | 支持证据与强度 |
|---|---|---|
| GraphDB | 提取本体 schema，通过对象标识及内置 SPARQL 工具查询 | 作者转述“公开做法”；没有官方链接、版本或查询示例，证据弱 |
| Palantir | `logic function` 将领域本体能力封装为 Agent 可调用函数 | 作者对博客／文档的回忆性描述；出处及正式术语待核验 |
| LangGraph | 承担演示中的 Agent 编排和工具调用链路 | 架构口播；没有源码、依赖版本或运行日志 |
| Semantica | 提供检索算法并直接读取 OWL 文件 | 架构口播；没有正式 API 或独立运行结果 |
| OpenRouter | 演示已集成该服务，填写自己的 Key 即可试用 | 作者说明；没有配置文件、具体模型或试用验证 |

GraphDB 的 SPARQL 做法不能转移为“Semantica 演示使用了 SPARQL”；Palantir 的函数能力不能转移为“本演示具备同样的更新与治理机制”。来源也没有说明 OpenRouter 后实际使用哪个模型。

### 四种接入形态与三类任务建议

视频作者给出的组织建议如下：

| 任务条件 | 作者建议 | 来源明确性与限制 |
|---|---|---|
| 固定流程与分支 | workflow 或 skills 编排 | 属于架构建议；没有展示流程定义或状态控制 |
| 需要 Agent 按意图自主选择操作 | tool calling 或 MCP | 订单演示被描述为使用 tool calling |
| 复杂任务，尤其涉及人工介入 | sub agents 或 workflow 加 Agent | 强调显式定义介入条件；本集未展示完整人工介入流程 |

作者还建议将查询、更新和校验等多项能力封装到 MCP，并指出上下文消耗与服务延时。但没有相同条件下的测量结果，不能写成“MCP 必然比其他方式更慢或更费上下文”。

四种形态也不是严格互斥的选项：来源自己指出 sub agents 可以调用工具、执行 workflow。因此，这张分类更适合作为任务组织的起点，而不是完整的技术分类标准。

### 订单演示说明了分项状态查询，但没有证明延迟原因

来源中的问题原文为：

> “我的这个订单咖啡机收到了，奶泡壶为什么还没有到”

据口播叙述，链路为“定位订单 → 查询关联事实 → 查询状态 → 规则校验 → 生成回复”。来源明确给出的案例状态为：

| 案例对象 | 来源中的状态表述 |
|---|---|
| 咖啡机主机 | “已经签收了” |
| 奶泡壶 | “运输中的这样一个状态” |

回复原文为：

> “你好，感谢你的咨询，根据我们的这个查询呢，你的这个订单主机已签收了，然后奶泡壶正在运输中，尚未签收。”

这支持一种业务建模思路：同一订单内不同商品的状态应分别查询。但“运输中”说明当前位置或状态，尚未解释延迟原因，也未给出预计到达时间。因此，演示更接近**订单状态答复**，不能直接标为已完成延迟归因。

口播还描述了客服点击启动处理、再发送回复的过程，说明人仍参与操作；这不足以证明已经实现持久化审批、异常升级或完整的人工介入工作流。

来源未提供工具名、参数结构、SPARQL 查询、API 签名、配置文件或 SQL DDL；明细编号、销售渠道等只有字段类别，没有实际值，不应补造结构化数据。

### FDE 学习路径有方法价值，课程效果没有验证依据

作者提出的五阶段路径可概括为：业务理解与方案设计、AI 协作开发、Agent 与 RAG 选型、知识治理与 Ontology、业务建模与项目实战。这是学习建议，没有学习者评测、交付质量或就业跟踪数据支持其效果。

商业介绍中的主要数字应保留原文口径：

| 项目 | 来源原文口径 | 分析 |

| 总课时 | “60 小时”“60+ 小时” | 近似口径，不构成明显冲突 |
| 课程结构 | “六个阶段”“六大阶段” | 不同段落的模块边界不完全一致 |

| 周期 | “60 多小时最多一个月”“直播课大概两个月左右” | 可能分别指学习投入与授课周期，来源没有明确区分 |

## 矛盾、张力与限制

1. **查询、校验、推理和更新的边界不清。** 作者将业务规则封装、校验和本体数据操作相邻讨论，但没有展示事务、授权、规则语言或推理器。读取 OWL 文件不能证明所有这些能力已经实现。

2. **可见流程与可审计证据之间仍有缺口。** 来源强调每一步透明，却未给出日志结构、规则编号、版本、来源时间或数据快照。“思考一下”中的审计建议应保留为解读与设计建议。

3. **一次演示与通用适用性之间存在证据跨度。** 来源没有提供多订单歧义、拆单、缺货、部分退货、跨渠道身份、物流数据过期等测试结果。这些属于未覆盖场景，不能反过来断言系统一定无法处理。

4. **文件资产稳定性与系统可替换性未被证明。** 文档解读认为 OWL 最稳定、编排与检索层可替换，但接口契约、对象标识和检索实现可能影响迁移。来源没有提供替换实验。

5. **技术教学与商业承诺需要分开评价。** 五阶段学习路径、六阶段课程、八个项目和六项结果不是相同分类；目前有口径与映射缺口，尚不足以判定自相矛盾。就业、证书和收入承诺则需要独立证据。

1. **创建本集 `source` 页面。** 标题复用“第 11 集｜10-Agent业务集成：工具调用与订单客服问答”，文件名可用 `agent-business-integration-11.md`。记录作者、URL、bvid、cid、派生文件路径和提取方式；逐段区分口播、文档解读及当前分析。ASR 保持 `partial`，主张保持 `unknown`；如统一页面使用 `mixed`，必须明确各段归属。
