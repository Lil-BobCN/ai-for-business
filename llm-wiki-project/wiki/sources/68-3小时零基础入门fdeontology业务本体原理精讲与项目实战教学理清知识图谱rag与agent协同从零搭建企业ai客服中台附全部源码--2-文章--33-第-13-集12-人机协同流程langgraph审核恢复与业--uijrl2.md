## 一句话摘要

视频作者在这一集里给整套实战补上最后一块——人机协同：先说明为什么高危操作必须留给人工、Agent 要知道自己什么时候该停下来，再用客服台的现场演示走一遍“系统显示已签收、用户说没收到”这类事实冲突如何触发人工审核、人工提交补充意见后 Agent 又如何恢复执行，接着交代 LangGraph 的 checkpoint 与线程 ID 机制、这条链路底层的三段实现（Semantica 图检索、RAG 文档检索、审核界面）与源码部署方式，最后落到业务验收的指标口径，并为整期公开课与课程收口。

## 主要论点（视频作者观点，`unknown / 待外部核验`）

1. **人机交互是 Agent 落地的核心**。业务流程不可能全盘交给 Agent，操作数据、库存操作、金额等高危操作必须人工确认，因此 Agent 必须知道何时停下来等审核。
2. **三类应设中断的场景**（作者明确列举）：
   - 查询到多个订单，无法确定是哪一个（指代不明）
   - 关键信息不足，需再与用户沟通补充（信息不足）
   - 检索到的事实与用户陈述不符，需人工决策（证据冲突）
3. **实现方式**：把业务规则写进本体 schema，AI 命中规则即暂停；用 LangGraph 的 checkpoint 保存快照与运行进度，配合 `thread_id` 实现“停下—等人输入—恢复”。
4. **底层链路构成**（作者明确交代）：
   - Agent 编排：LangGraph
   - 本体查询：Semantica 做图检索，查询业务本体的 OWL 文件
   - 文档检索：集成 RAG 流程，与本体**共用同一套业务模型定义**
   - 审核界面：由业务规则决定何时请人工
5. **业务验收**：以“情形—应该看到什么—关键检查点”三列组织，情形包括正常查单、无可用条件依据、快照后状态、人工修改；只有甲方或公司领导认可有效，项目才算交付完成。

## 演示案例（客服台）

用户问“咖啡机到了、奶泡壶怎么还没到”→ Agent 走“定位订单 → 选择下一步 → 查询关联事实 → 生成回复”；用户改口“主机没收到”而系统显示已签收 → Agent 转入人工审核 → 人工提交补充意见“可以和物业前台确认一下” → Agent 恢复执行、生成草稿，回复同时保留“系统查询确实已签收”与“建议和前台确认是否代为保管”，并交代奶泡壶仍在查询中。

## 课程与市场数字（课程方主张，`unknown`）

60+ 小时、8 个真实项目、六阶段、八大项目构成（三个热门项目、两个 1:1 工业级复刻、两个百万级企业项目）、FDE“应届生起薪年包超过 30 万、年薪中位数超过 50 万”、“没有任何一个行业比 FDE 更火”、“岗位多、人才少的红利期”、工信部高级认证及报名渠道。这些内容出现在本集后半段的销售语境中，应与前半段技术判断分开看待。

## 待核验项

- 演示过程与演示结论均来自视频作者单方展示：Agent 是否真能在“事实冲突”时自动进入人工审核、草稿文本的实际生成方式、审核界面与业务规则的对应关系，均需看源码与运行环境。
- 技术主张待核验：LangGraph 的 checkpoint 机制能否在生产负载下稳定支撑“暂停—恢复”；Semantica 与 RAG 是否真的共用同一份业务模型定义；把业务规则写进本体即可触发中断的可行性与代价。
- 作者引用的 Palantir 与 OpenAI 对 FDE 的“官方定义”两处均未给出处，需回到原文核对。
