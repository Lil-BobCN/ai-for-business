## 一句话摘要

视频作者提出：AI Coding 想要的效果与实际拿到的效果之所以不一致，根子在"语义跨度"和"可形式化验证"两件事上，而解法是用本体（Ontology）把需求、设计、任务、代码、规范与流程建成一张类、关系、实例与规则齐备的图谱，让制品可以按拓扑稳定加载、让校验可以用机器强制、让流程可以被门禁拦住，从而把每一步的成功率抬到足够高。

## 主要论点链（均归属 catface996，`unknown / 待外部核验`）

1. **问题诊断**：软件生命周期管理存在决策不落库、知识随人走、文档落后于代码、测试覆盖度说不清等问题；抽象后剩四个变量——意图模糊、系统复杂性、认知局限、现实不确定性。
2. **数学领域反证**：这四个变量在数学中几乎消解，但 AI 在数学上并未猛进，故真正拦路虎是**语义跨度**与**可形式化验证**。
3. **agent 能力边界**：执行强、判断弱；判断弱源于"不知道自己不知道"及协作中的信息不对称。
4. **语料均匀性**：模型与人都在"均匀、有一定跨度"的语料上学习；跨度过大则失败。
5. **面向制品优于面向角色**：制品可标准化，角色不稳定。
6. **成功率连乘**：单步 90% 时五步约 59%、百步趋近零；单步 99.5% 时五步约 98%、百步约 60%。故须把单步成功率抬到 99.9% 量级。
7. **提升单步成功率的手段**：多 agent 并行（失败经验不共享）vs loop（失败原因作为下一步输入，作者选 loop）。
8. **限制单步成功率的三要素**：判断标准不明确、信息缺失、错误无法定位。
9. **符号主义补三件事**：可查（图谱关系检索比向量检索稳定）、可校验（格式校验先于语义校验）、可强制（流程门禁）。
10. **本体四要素 + 强制力分层**：逻辑是强制力来源，由机器执行而非大模型推理。
11. **实战**：从意图 → 需求 → 设计 → 任务拆解 → 代码，制品沿拓扑稳定加载。

## 边界与反例

- 检索目前仍以关键字为主，作者承认还没用上语义检索。
- 拓扑检索会遇到大量链接的"黑洞"节点，需要额外的检测能力，说明图一旦长大，遍历本身也会成为问题。
- 渲染和生成过程"时间有点慢"，作者多次等待，说明这套流程的交互成本并不为零。
- 本体带来的稳定性，是用额外的建模与维护成本换来的，对小团队、小系统是否划算，口播里没有给出判断依据。

## 可迁移素材

- "四个抽象问题"作为需求评审检查清单（意图清不清楚、复杂度在哪、谁的经验在起作用、哪些只能在线上才知道）。
- "数据—信息—知识—判断"四层，用来判断一件事能不能交给机器。
- "面向制品而非角色"的拆解原则。
- "报错要能引导修复"——把失败信息设计成下一步的输入，是 loop 能不能自愈的前提。
- 把纪律（发布必须从开发环境开始、生产必须人工审批）显式化成可执行的约束，而不是停留在口头约定。
