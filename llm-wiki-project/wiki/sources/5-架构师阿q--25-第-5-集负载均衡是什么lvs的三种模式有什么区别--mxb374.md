## 一句话摘要

视频作者用「业务变大、单机不够、多机组集群」这条最短路径引入负载均衡，先按实现方式把负载均衡器分成 DNS、硬件、软件三类并比较各自代价，再聚焦到软件方案里性能最高的四层负载均衡 LVS，逐个讲清 NAT、DR、TUN 三种工作模式的报文流转过程与适用边界。

## 主要论点（视频作者口播，`unknown / 待外部核验`）

### 1. 负载均衡的必要性

视频作者在该段口播中提出：业务初期单台服务器即可满足需求；用户流量增长后单台难以应对压力，于是将多台服务器组成集群；为了统一管理流量入口，需要通过负载均衡器将海量请求按预设算法分发到集群中的不同服务器。作者明确本集讲的是**广义的负载均衡器**。

### 2. 负载均衡器三分类及各自代价

| 类别 | 代表 | 作者给出的优点 | 作者给出的代价 |
| --- | --- | --- | --- |
| DNS 实现负载均衡 | 域名解析到多个 IP | 实现简单、成本低 | 故障切换延迟大（层层缓存、缓存可能不遵循 TTL）；调度算法少，一般只支持轮询；生产环境很少用 |
| 硬件负载均衡 | F5、A10 | 性能好、功能强大 | 价格非常昂贵 |
| 软件负载均衡 | Nginx、HAProxy、LVS | 简单、便宜、灵活、易扩展 | 作者未展开代价；仅指出 LVS 因纯四层、内核态而性能最高 |

作者补充：大公司一般也会利用 DNS 实现**地理级别**的负载均衡，用于就近访问；这种方式一般是入口流量的基础负载均衡，下层会有更专业的负载均衡设备。

### 3. 软件负载均衡内部的四层与七层分工

- Nginx：七层负载均衡，支持 HTTP 协议。
- HAProxy：七层负载均衡软件，性能也很不错。
- LVS：纯四层负载均衡，运行在内核态，作者称其性能是软件负载均衡中最高的，因为工作在四层所以也更通用。

### 4. LVS 三种模式的报文流转（作者口播）

**NAT 模式（Network Address Translation）**

- 客户端 → Director：源 IP = CIP，目标 IP = VIP
- Director 经 IPVS 改目标 IP 为 RIP，源 IP 仍为 CIP
- Real Server 响应 → Director：源 IP = RIP，目标 IP = CIP
- Director 改源 IP 为 VIP 后响应客户端：源 IP = VIP，目标 IP = CIP
- 特点：后端服务器无需暴露真实 IP；负载均衡器需处理双向流量，容易成为性能瓶颈。

**DR 模式（Direct Routing）**

- Director 与 Real Server 均配置 VIP：Director 配到对外网卡，Real Server 配到 lo 网卡
- 通过 ARP 参数（`arp_ignore`／`arp_announce` 一类）使只有 Director 响应 ARP 请求
- Director 改目的 MAC 为 Real Server 的 MAC（RIP 的 MAC），源 MAC 为 Director 的 MAC（DIP 的 MAC）
- Real Server 经 ETH0 收包，因 lo 上配置了 VIP 而接收处理，直接回客户端
- 特点：需改写二层包头，Director 与 Real Server 必须同一广播域；Real Server 需配置 VIP 并禁用 ARP 响应。

**TUN 模式（IP Tunneling）**

- 客户端 → 负载均衡器：源 CIP，目标 VIP
- 负载均衡器在报文头部再封装一层 IP：源 DIP，目标 RIP，发往 Real Server
- Real Server 拆第一层封装，发现内层目标为 lo 上的 VIP，处理并经 lo → ETH0 直接回客户端
- 特点：支持跨机房部署；隧道封装／解封装有额外开销；Real Server 需支持隧道协议并配置 VIP。

## 整理者提出的可迁移记法

把三种模式的差别压缩成三个问题：

1. 请求报文改了哪一层（NAT 改三层目标 IP、DR 改二层 MAC、TUN 加一层 IP 封装）；
2. 响应报文走不走过调度器（NAT 走，调度器承压；DR 与 TUN 不走，性能高）；
3. 由此带来什么拓扑约束（NAT 要求后端网关指向调度器，DR 要求同一广播域并禁用 ARP 响应，TUN 要求后端支持隧道协议）。

## 整理者标注的疑误（`〔待确认〕`）

- ASR「只支持 R2 的轮巡方式」→ 按上下文应为「轮询」
- ASR「Keep Alive」→ 按上下文应为 Keepalived
- ASR「老网卡」→ 按上下文应为 lo 网卡
- ASR「ARP 的 ignal 参数」→ 按上下文应为 `arp_ignore`／`arp_announce` 一类参数
- 同音误听还原：附载均衡／附在均衡器 → 负载均衡；内合态 → 内核态；D2 模式／TAN 模式 → DR 模式／TUN 模式；IPTAN 领济 IP 税 → IP Tunneling、IP 隧道；缘 IP → 源 IP；手部 → 头部；Load 接口／功网 → lo 接口／公网；ETH-01 卡 → ETH0 网卡；跨机防 → 跨机房；运为 → 运维；致能分发 → 智能分发；实力 → 实例；录邮寄 → 路由器；王贵 → 昂贵；要 Engines Hyproxy → Nginx、HAProxy；不属 → 部署；Directed Server → Director Server

## 内部矛盾与口误

- **口误（已由整理者标注）**：DR 模式一段中，作者将 DR 模式的特点误记为「NAT 模式的特点是仅请求流量经过负载均衡器，响应流量直达客户端，性能极高」，与 NAT 一节「双向流量」的结论直接冲突。按上下文应为 DR 模式的特点。属口误，非来源间冲突。
