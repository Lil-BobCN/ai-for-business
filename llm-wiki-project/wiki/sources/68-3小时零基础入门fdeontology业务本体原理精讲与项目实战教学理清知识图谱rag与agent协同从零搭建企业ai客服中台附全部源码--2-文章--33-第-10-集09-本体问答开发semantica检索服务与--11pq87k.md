## 主要论点与证据

1. **演示原型与企业持续运行的服务有不同要求。** 作者指出，企业数据会变化、访问持续发生，服务还需要稳定运行并追溯依据。这是有价值的部署检查视角，但本集没有提供并发、稳定性或生产运行数据，证据仅为作者的论述。

2. **作者将 Semantica 描述为覆盖四层能力的框架：**
   - 数据接入与处理；
   - 本体构建、实体与关系抽取、建图及校验；
   - 向量检索、图检索及向量检索加图扩展；
   - 应用接入和来源追溯。

   该清单来自视频口播，没有项目文档、代码或独立测试佐证，证据强度较弱。作者提到“14k Star”，而系列第 1 集资料记录其说法为“13000 多”；两者都只是不同时间的口播数字，不能据此确认项目当前 Star 数。

3. **作者描述的检索链路是“配置组合 → embedding 选种子实体 → 清洗与校验 → BFS 图扩展 → 返回结果”。** 这一描述可转化为待验证的系统实现假设；本集没有给出具体算法参数、代码或评测结果，也无法确认 API 名称和扩展边界。

4. **回答路径分为检索上下文直答和规则推导。** “小李是经理”加“经理也是员工”推出“小李是员工”，展示了规则推导的例子，但不能据此证明 Semantica 的具体实现、推理语义或异常处理。规则错误、例外与事实冲突都可能造成系统性错误。

5. **问答演示将结论与引用依据、来源文件一起展示。** 作者以“整单是否签收”为例，提到咖啡主机、奶泡壶及出库、仓储、装箱资料。它说明演示意图包含来源信息，但没有展示真实返回结构、字段定义或冲突来源时的处理方式。

本集没有 SQL DDL、配置文件、API 签名或结构化数据表可逐字保留。文中出现的 `ask`、`retriever query with reasoning`、`context.context_retriever`、`Person SDK`、`MTP` 等名称带有 ASR 不确定性，不宜当作已确认 API 或接口清单。
