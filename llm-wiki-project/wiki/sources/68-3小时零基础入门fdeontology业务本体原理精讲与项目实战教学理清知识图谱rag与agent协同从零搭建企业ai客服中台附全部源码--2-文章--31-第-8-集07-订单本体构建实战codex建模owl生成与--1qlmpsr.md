## 一句话摘要

视频作者在本集里把 Ontology 从概念推进到动手：把 79 份散落的电商业务资料（CSV、PDF、JSON、`TXT`、markdown）在一个 Codex 项目里跑完"业务对象梳理 → 模型逐轮确认 → 知识抽取 → 生成 `.owl` 本体文件 → 导入系统"的完整链路，并在过程中交付三个团队内部使用的本体构建 Agent Skills（Ontology Design、Ontology Extract、Ontology Build）。

## 主要论点（均为作者口播观点，`unknown / 待外部核验`）

1. **Ontology 的价值要落到可跑链路上**——作者用电商订单场景演示从散落文件到 `.owl` 的完整链路。证据为 Codex 应用链路中的实际运行过程，但作者承认未带观众动手，且"直接交给 Codex"是体验课简化，非行业标准。
2. **建模真正难点是业务含义从哪来**——编号体系对应、状态描述理解属于业务定义而非技术选型。证据为作者经验性归纳，无对照数据。
3. **两条建模路径**——有既有模型则基于它构建、反复调试、接入 Agent 测试、出问题即时调整约束；无则梳理需求痛点交 AI 出方案、人工逐轮判断。作者强调"不要自己定义，交给 AI"，但判断权仍在人手里。
4. **三个 Skill 的职责划分**——Design 定边界与约束、Extract 从原始材料提知识、Build 生成标准 `.owl`。作者称其为团队内部使用、公开课免费发放。
5. **文件格式只影响读取方式，不决定业务模型**——把数据清洗问题与建模问题划开。
6. **本体是给 Agent 的上下文核心信息**——收尾定位，下一集三条链路（自然语言查单、异常处理审查与状态更新、人工介入）建立在本集 `.owl` 之上。

## 实战链路：从散落文件到标准 `.owl`

作者在该段口播中提出的链路顺序如下（属教学演示，非生产做法）：

1. **原始数据形态**：电商领域下仓储、订单、客服、签收、商品中心、物流接口、业务规范等来源的散落资料，共 79 份，格式包括 CSV、PDF、JSON、`TXT`、markdown。
2. **统一交给 Codex 读取分析**：作者明确说明这不是行业标准规范，真实系统要按业务场景单独构建解析链路；本集为体验课简化。
3. **三轮自然语言提示词驱动建模**（详见 [[三段式本体建模节奏]]）：
   - 第一轮：梳理业务对象、各自记录什么、哪些信息能关联；"读不出来、互相矛盾的就直接指出来，不要乱猜"。
   - 第二轮：分析业务适合怎么构建本体，要求把候选类型、属性、保留理由逐条列出，并分清哪些是资料依据、哪些是建模建议。
   - 第三轮：把业务模型固定下来，逐条确认对象类型、属性和关系，由人裁决（例如把"装箱分配"独立成对象）。
4. **Extract 与 Build**：依次加载 Ontology Extract 与 Ontology Build 技能，从原始材料提取知识，再生成标准 `.owl` 文件。
5. **导入系统**：导入后可见对象之间的关联关系与实体记录，形成可供 Agent 上下文问答的链路。

## 矛盾与张力

1. **"交给 AI 定义"与"判断权在人"的张力**——作者说"不要自己梳理、不要自己定义，交给 AI"，但每轮判断仍由人做，AI 方案质量实际取决于人的建模经验。若团队无人能承担业务定义责任，三轮对话易退化为"看起来合理"的通用模板。
2. **演示链路 vs 生产做法**——作者自承把全部资料直接交给 Codex 不符合行业标准，真实系统要按业务场景单独构建解析链路。演示链路在数据敏感、来源异构或体量更大场景下未必成立。
3. **"打包成 Skill 就能完成建模"隐含前提**——假设模型能可靠遵守流程、且业务方有人能判断输出对错，两者均未验证。
4. **与 Wiki 现有内容的潜在冲突**——本集"文件格式不决定业务模型"与数据工程中格式影响抽取质量的常见认知存在张力，值得记录为待核验判断（见 [[文件格式与业务模型分离]]）。
5. **ASR 不确定项密集**——源文件列出大量 `待确认` 术语，引用时须以原视频为准，不可猜测性修正。
