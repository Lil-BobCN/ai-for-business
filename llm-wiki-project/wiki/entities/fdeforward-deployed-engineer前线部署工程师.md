# FDE（Forward Deployed Engineer，前线部署工程师）

FDE（Forward Deployed Engineer，前线部署工程师）是一类被派驻到客户现场、直接理解客户业务并交付可运行软件的工程角色。它既不是传统软件工程师，也不是售前方案架构师，也不是咨询顾问，而是同时兼具三者特质的混合角色。该岗位名称与角色定位在 Palantir 的实践中被广泛使用；本页主要依据零点未来《AI+企业》第 3 集的口播内容整理，其中所有定义、数字与人物归属均为视频作者主张，属 `unknown / 待外部核验`。

## 定义与三要素

视频作者在该段口播中提出，FDE 的定义包含三个关键要素：

1. **坐在客户现场** —— 不是远程，不是邮件往来，是在物理状态下要在现场。
2. **填补鸿沟** —— 不是卖标准产品，而是解决"我的产品"和"你的场景"之间那一段没有人能做的事情。
3. **交付可运行的软件** —— 不是报告，不是翻页的 PPT，而是真正能够跑起来的生产级交付。

作者称该定义出自 `Bob MacGuru`〔人名待确认，按其身份描述疑为 Bob McGrew〕，并称其为"目前公认最准确的定义"；英文原文与出处尚未核对，见 [[bob-mcgrew身份与fde定义原文待核验]]。

## 来源观点：工作分布与三阶段

作者引用一份据称对 1500 名 FDE 的调研：一周约工作 45 小时，47% 的时间在客户现场，31% 写代码，22% 做内部协调与研究总结。调研主体、时间与方法均未给出，属待核验主张。

作者把 FDE 工作分为三个阶段：

- **Audit（审计调研）** —— 进驻客户现场，花几周深入不同部门了解工作流程（营销、运营、采购、财务等），核心动作是判断哪些环节适合用 AI Agent、哪些用简单代码即可、哪些留给人工判断。
- **评估** —— 把人类解决的步骤拆解出来，每一步打分，建立标准答案样本（SOP），再拿 AI 的输入去对标。作者强调评估框架是获取高管信任的基石。
- **Deployment（部署交付）** —— 从最小的自主单元开始：先让 Agent 读数据，证明能做对，再让它写工单、写代码、推 PR，每一步都有授权、每一步都经过验证；不做大的迁移，而是在现有基础上逐步建立 API 与 Agent。

## 来源观点：Echo 与 Delta 双团队模型

作者称 Palantir 发展出 Echo 与 Delta 的双团队模型：Echo 是嵌入分析师，负责理解客户需求、管理客户关系、带有 sales 属性、定义方案，人才来源多为行业专家；Delta 是部署工程师，负责快速写代码、做原型，接近创业公司联合创始人的气质。两者相加构成一个完整的创业团队。详见 [[echo与delta双团队模型]]。

## 来源观点：此刻爆发的四条原因

1. **智能商品化** —— ChatGPT、Claude、Gemini 的能力差距在缩小，"谁的模型更强"越来越不重要，"把模型用在什么地方、怎么用"成为护城河。
2. **Agent 品类未定型** —— 传统 SaaS 的产品发现路径清晰，而 AI Agent 到底应该是聊天窗口、自主 workflow、进程、插件还是全新形态的操作系统，没有人知道；作者引 `Bob MacGuru` 的说法：唯一能发现答案的方法就是坐在客户现场和他们一起工作。
3. **能力与采用之间的鸿沟** —— 作者引 `Bob MacGuru` 的 Waymo 类比：坐在无人驾驶车里的人不会感叹"没有人开车"，只会说"堵车了"；AI 越强，普通人越觉得它稀松平常，最后一段路需要有人去填。
4. **Token 经济** —— 传统 SaaS 边际成本接近于零，而 AI Agent 每次运行消耗 Token、每次调用有推理成本，选型判断必须贴着客户真实环境做。详见 [[token经济与ai-agent成本结构]]。

## 来源观点：适用三条件与咨询公司风险

作者强调不是所有公司都需要 FDE，并引 `Bob MacGuru` 的 "Don't do this at home"。需要 FDE 的三个条件：①所在市场没有成型或现成的产品，产品形态不确定；②不同客户需求高度异质，差异非常关键；③单个客户合同金额足够大，能撑住驻场团队成本（驻场、差旅、高薪资）。三个条件缺一个，传统 SaaS 模式更健康。详见 [[fde适用三条件]]。

作者给出的最大风险是 FDE 做着做着变成一家咨询公司。分界线在于：真正的 FDE 每次现场部署都会把经验抽象回产品，产品变得更强；咨询公司每次从零开始，没有产品杠杆。详见 [[fde与咨询公司分界线的衡量方法待核验]]。

## 来源观点：转型路径

作者认为三类背景最容易转型：咨询顾问与产品经理（已有把数据翻译成业务的能力，短板是工程能力）、软件工程师（技术强，短板是沟通能力）、创业者或创业公司核心成员（天然接近 FDE 素质模型）。作者还给出 30 天入门路线图：AI Agent 基础、结构化输出、Production、Evaluation，以及客户沟通与 Presentation 等软性要求。作者引 `Bob MacGuru` 强调，Delta 团队要的不是追求抽象、完美代码、能维护十年的工匠型工程师，而是能快速交付、不怕第一版代码被扔掉的人。

## 项目分析

FDE 在本 Wiki 中承担"岗位本体"的角色，与 [[fde交付方法]]（方法层）互补：前者回答"这个角色是什么、在什么市场结构下成立"，后者回答"交付怎么做"。本集对现有 Wiki 的贡献有三点：一是把 FDE 从"先进做法"降级为"特定市场结构下的解法"（三条件筛子）；二是新增 Token 经济、土路/高速路、双团队模型三个概念；三是把"评估"重新定位为高管信任接口，与 [[业务验收指标口径]] 呼应。

## 反例与边界

- 效果数字缺少对照组与统计口径："高 30%–50%"未说明样本量，"7 倍增长"描述的是招聘信息数量而非岗位存续时间。
- "现场"的必要性可能是阶段性的——它更像当前工具与客户成熟度共同决定的结果，而非永久规律。
- 作者自己给出的三条件构成反向闸门，与全篇推荐语气存在张力。
