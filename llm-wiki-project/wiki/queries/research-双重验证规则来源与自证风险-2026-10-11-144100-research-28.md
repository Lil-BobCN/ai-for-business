# Research: 双重验证规则来源与自证风险

# 双重验证规则来源与自证风险

> **术语澄清**：本页的"双重验证"不指双因素认证（2FA），而指两重含义的叠加——(1) 同一份数据/事实同时接受两类校验：本体公理层面的推理一致性与约束层（SHACL 形状）层面的结构与数据质量校验 [1][2][7]；(2) 验证规则本身存在多个来源（领域文档、专家、LLM 抽取、标准规范），当"规则来源"与"验证执行者"同源时产生**自证风险**：用生成规则的主体去判定规则是否被满足，验证结论无法独立于生成过程。

本页是 [[本体验证规则来源与自证风险待核验]] 的证据整理，并与 [[本体约束的分层与生效时机]]、[[本体校验与持续演化]]、[[可形式化验证]] 直接衔接。

## 一、验证规则的两条技术来源

### 1.1 本体公理：把自然语言数据规则形式化

[1] 的核心主张是：数据规则可以用本体公理（ontology axioms）形式化，这有助于消除以自然语言表述的规则所带有的歧义。此时规则的来源是"本体自身的公理体系"，验证方式是逻辑推理。其代价是——规则必须经过一次"自然语言 → 逻辑形式"的翻译，而翻译环节本身引入新的解释空间。

### 1.2 SHACL 形状：面向图结构与数据质量的可执行约束

[7]（W3C 规范）将 SHACL 定义为"依据一组条件验证 RDF 图"的语言；[9] 将其概括为一个广泛支持的 W3C 标准，用于描述数据集必须满足的条件。分工上，[2] 给出清晰划分：**OWL 推理支持逻辑一致性（logical consistency），SHACL 则验证图结构、必需属性与数据质量条件**。两类规则来源并不互相替代，而是覆盖不同的失效模式。

### 1.3 从 OWL 到 SHACL：转换与边界

[10] 讨论了两者转换中的关键差异：

- `sh:node` 是一种**验证委派**——它断言焦点节点必须同时通过另一个形状的验证，即形状之间可以传递验证义务；
- `owl:Restriction` 与 `sh:PropertyShape` 的对照体现从**开放世界推理**到**封闭世界验证**的范式切换（"验证该类在本图中的每个实例，若三元组缺失或错误，即产生 `sh:Violation`"）；
- **SHACL Rules 是 SHACL 从纯验证跨入蕴含（entailment）领域的临界点**——一旦形状开始产生新三元组，验证层就同时变成了规则来源层，这是本主题最需要留意的结构性问题。

### 1.4 本体参与时 SHACL 的语义差异

[8] 关注的任务是"给定一组约束 + 从图中选定的目标节点或概念"的验证，并明确其与 OWL 的不同，研究路径涉及语义定义与**重写（rewriting）**。工程含义是：同一条规则在"是否考虑本体推理"两种设定下，验证结果可能不同——**规则来源相同，语义基准不同，结论却不同**。

## 二、"双重验证"的四种组合形态

1. **公理 + 推理机**：规则来源是本体公理 [1]，验证者对蕴含闭包求一致性。
2. **形状 + 校验器**：规则来源是 SHACL 形状 [7][9]，验证者在具体图上求违规。
3. **LLM 抽规则 + LLM 评估**：规则由模型从文档中抽取，验证也由模型完成。[5] 利用 LLaMA3 的涌现式自验证能力判断给定参考材料能否充分回答某问题；[6] 则把 LLM 用作知识图谱补全模型的自动评估器——两条路线的共同点是验证者与大模型同源。
4. **文档/专家规则 + 形式化翻译**：来源是领域文档与专家，中间经一次形式化翻译 [1]，而翻译正确性缺少独立裁判。

其中形态 3 才是"自证风险"的核心；形态 1/2/4 的风险主要来自语义基准与翻译层，而非主体同源。

## 三、自证风险的五种具体形态

### 3.1 生成者—验证者同源

当同一模型既建本体/抽规则、又评估结果时，验证回路里没有独立信息源。需注意立场平衡：[5][6] 都把这种同源验证描述为"能力"与"自动化机会"（emergent self-verification、automatic evaluation），**并未讨论同源自评的偏差上界**。现有证据不足以支持"自证可靠"或"自证不可靠"的任一强结论。

### 3.2 未物化的蕴含：验证的"假通过"

[10] 明确警告：**SHACL 不会验证未物化的蕴含三元组**；若验证依赖推断出的类别成员或属性值，这些推理必须先写入图中。工程后果是——若同一管线同时负责物化与验证，"验证通过"可能只反映物化步骤的选择，而非数据本身的正确性。这是一种结构性自证，与 [[本体schema与实例事实]] 的划分直接相关。

### 3.3 版本漂移与规则腐化

[10] 给出两类典型失配：本体属性被弃用而形状仍然引用它；形状施加的约束与后续本体修订相矛盾。此时验证仍会运行、仍会给出结论，但**规则来源（现行本体）与验证依据（历史形状）已经分叉**。这与 [[本体校验与持续演化]] 描述的演化问题一致，也是 [[本体与数据约束及版本演化待核验]] 关注的核心边界。

### 3.4 开放世界本体上的封闭形状

[10] 的另一条 caveat：把形状闭合到一个参与开放世界本体（外部参与方会扩展它）的类上，就会为"尚未枚举的合法属性"产生违规。这不是自证，而是**规则来源的世界假设与实际运行时世界不一致**造成的系统性误报。

### 3.5 闭环自演化的双刃

[3] 描述了 AI for science 中知识图谱的实时闭环反馈，使科研生态具备"自演化"能力。闭环提高了迭代速度，但该来源从正面叙述此闭环，**未交代验证判据（validation criteria）的来源与更新机制**——这正是自证风险在系统层面的形态：若闭环只有内部判据，错误可能被写入图谱并被后续推理继承。

## 四、缓解路径（限于来源可支持的层面）

- **来源分离**：把规则来源锚定在公开、可追溯的规范或领域权威，而非生成过程的副产物；W3C SHACL 规范 [7] 与实现层说明 [9] 可充当外部锚点。
- **执行分离**：让验证器独立于生成器。[4] 的 Symbolic-in-the-Loop（SITL）验证框架是神经符号路线的代表，其要点是把符号层放入回环，使验证始终针对最新的符号状态（该来源摘录不完整，具体机制需回原文核对）。
- **先物化、再验证**：显式区分"物化/推理"与"验证"两个阶段，避免 [10] 指出的未物化蕴含导致的假通过。
- **语义基准显式化**：在验证报告中声明"是否启用本体推理/重写"这一设定 [8]。
- **版本联动**：形状与本体同步演进，弃用属性时同步清理形状引用 [10]。
- **约束分层与架构化防幻觉**：把不同强制力的规则分层放置（见 [[本体约束的分层与生效时机]]、[[强制力四层排序]]），让"自证风险高"的规则层不承担最终裁决；把验证作为架构职责而非提示词职责（见 [[防幻觉的架构化机制]]、[[本体作为约束层]]）。

## 六、矛盾与空白

1. **同一现象、两种定位**：LLM 自验证在 [5][6] 中被当作能力与效率手段，在验证理论视角下却是自证风险来源；两组来源之间没有对话。
2. **规则来源的"权威"未定**：OWL 公理 [1]、SHACL 形状 [7]、LLM 抽取 [5][6] 都声称可提供规则，但相互之间没有优先级判据。
3. **语义基准未统一**：[8] 说明本体参与会改变验证语义，[10] 说明物化状态会改变验证结果；实务上缺少"验证报告必须声明语义基准与物化状态"的共识。
4. **量化缺失**：没有任何来源给出"同源验证 vs 独立验证"的误差对比数据。
5. **企业场景空白**：缺少企业本体（如 [[订单客服本体]]）中约束来源治理的一手案例。
6. **证据强度差异**：[7][9] 属标准/厂商文档，[1][3][6][8] 属学术来源，[2][10] 属专栏/博客；[4][8] 的可用摘录均不完整，引用具体论断前应回原文核对。
