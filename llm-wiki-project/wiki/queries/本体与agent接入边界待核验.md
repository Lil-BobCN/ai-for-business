# 本体与 Agent 接入边界待核验

## 问题

本体如何被 Agent 调用？它提供的是结构化查询、图遍历、规则推理、文档检索，还是这些能力的组合？工具的输入输出、订单定位依据、状态冲突处理、权限边界和人工介入机制是什么？第 2 集预告的 Agent、RAG 接入是否实际完成，二者如何分工？现有课程演示能否证明系统具备超出一次性样例的通用能力？

## 课程中的描述

### 第 11 集：工具调用与订单客服问答

作者将客服问答链路描述为：

```text
用户问题
  -> 定位订单
  -> 查询关联事实
  -> 查询商品状态
  -> 规则校验
  -> 生成客服回复
```

作者同时称底层使用 LangGraph 编排、Semantica 提供检索算法、直接读取 OWL 本体文件，并通过 tool calling 接入本体。

### 第 2 集：课程目标与 Agent、RAG 预告

作者预告将使用订单客服资料构建业务模型，再计划接入 Agent 与 RAG。该集将 Ontology 描述为 Agent 的业务上下文来源，但没有提供 Agent 或 RAG 的工具接口、查询方式和职责划分。

### 第 5 集：业务模型与 Agent 上下文

作者将业务模型描述为由 `objects`、`properties` 和 `links` 组成，并以“主机已经到了、奶泡壶呢”的案例展示从用户身份、订单、商品、包裹到物流状态的逐级关联。该集没有给出实际工具调用、Schema、模型版本、查询语句、规则实现或运行日志。

该集还提出了以下待核验内容：

- Ontology 与数据字典、ER 图、主数据管理之间的差异；
- 对象、属性和关系之外，是否存在约束、规则、权限、来源和时间语义；
- PDF、CSV 与业务系统的字段、身份和时间口径如何对齐；
- 作者所说的本体关系网是否使用正式本体语言，还是仅指项目数据模型；
- 第 5 集提到的自研本体平台正式名称、版本和能力边界；
- 作者关于“开源侧没有太好的本体平台”的说法适用的时间范围和比较标准；
- Codex、Claude Code、`cursor`、DeepSeek Harness 等工具在课程中的具体职责；
- ASR 中的 `optics`、`gbt`、`sable`、`派 agent` 等字符串对应的原始口播。

## 证据状态与边界

以上内容来自本地 ASR 和视频口播，证据状态为 `partial` 或 `unknown`。目前没有源码、配置、API 签名、依赖版本、运行日志或实际模型名称，不能据此确认演示系统的实际架构或通用能力。

第 5 集提出“上下文充分即可使用千问 3B 或 1.5B”等小模型的说法，但其适用条件尚未验证。需要核实上下文完整性、实体歧义、关系跳数与模型规模之间如何评测；哪些问题适合由小模型回答，哪些需要更强模型、规则或人工介入；关系展开是否设置跳数、分支数、token 预算或相关性筛选。

## 关键缺口

- 工具名称、参数和返回字段；
- 订单对象和商品对象的标识方式；
- 空结果、多个订单、拆单和状态冲突的处理；
- 规则校验是条件判断、规则引擎还是 OWL 推理；
- OWL 文件的读取方式，以及是否存在推理器；
- LangGraph 状态图和人工介入节点；
- Semantica 的正式 API 和检索配置；
- Agent 与 RAG 的查询分工和上下文拼装方式；
- 数据更新、权限控制和审计机制；
- 订单、赠品、包裹和物流之间的模型变更如何影响上层 Agent 或检索接口；
- 在线模型降低本地推理资源需求后，资料抽取、索引构建、图存储和可视化仍需多少本地资源；
- 订单系统显示“已签收”、物流系统显示“运输中”时，哪个来源优先；
- 是否保存数据时间、来源系统、版本和置信度；
- 状态冲突由规则引擎处理、交给 Agent 判断，还是转人工复核；
- 业务对象的身份冲突、拆单、退货和跨渠道订单如何表示。

## 下一步研究动作

1. 获取演示项目的确切源码版本和配置文件。
2. 记录工具 Schema、订单定位逻辑、返回事实和规则校验结果。
3. 核对 OWL 读取路径是否包含推理器、规则引擎或仅进行文件解析。
4. 使用拆单、缺货、部分退货、跨渠道订单和物流状态过期样本进行复测。
5. 对关系展开设置跳数、分支数和上下文预算，并比较不同模型规模的回答质量。
6. 将工具执行日志、来源字段和人工操作记录与本体数据版本关联起来。
7. 逐项核对第 5 集 ASR 中的待确认术语，避免把转写错误写入产品或技术结论。
