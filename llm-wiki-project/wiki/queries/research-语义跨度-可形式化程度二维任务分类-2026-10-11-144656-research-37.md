# Research: 语义跨度 × 可形式化程度二维任务分类

# 语义跨度 × 可形式化程度二维任务分类

## 命题与动机

本页综合形式化方法与 AI Agent 治理两组材料，提出一个用于任务分诊的二维框架：一项任务能否交由 AI/Agent 承接、以何种方式验证，取决于两条相对独立的轴——

- **语义跨度**：从自然语言表达的意图，到"机器可判定的验收标准"之间需要补足的语义解释层数。该概念的严格定义以既有页面 [[语义跨度]] 为准，本页仅将其作为坐标使用。
- **可形式化程度**：任务的验收标准能否写成形式化规约，并由机器做出确定性判定。对应既有页面 [[可形式化验证]]。

之所以需要两轴而非一轴：形式化方法基于严格数学手段规约、设计、构建、验证、演进计算系统，是保障计算系统可信性的重要手段，已成功应用于各类软硬件系统 [4]；它能严格定义可接受行为、合成满足规范的程序、验证既有程序的正确性 [1]，并通过形式化规约语言精确描述需求、逐步精化与验证 [3]。但形式化方法进入 AI 系统后存在独特挑战 [2]。换言之，"任务验收需要多严格"与"任务验收能被形式化到什么程度"是两个问题：前者是需求，后者是可行性。

多维分类在 Agent 领域已有先例：[7] 指出 Agent 分类可从经典能力架构以及贴近工程实践的自主程度与交互方式两个视角展开。本页沿同一思路，把"任务"而非"Agent"作为分类对象。证据结构上，[1][2][3][4] 主要支撑"可形式化程度"一轴，[5][6] 支撑低可形式化端的治理与证据替代路线，[7] 提供多维分类方法学先例；"语义跨度"一侧的直接来源见 [[语义跨度]]。

## 维度一：语义跨度

判定问题：把任务意图翻译成"机器可判定的验收标准"，中途需要插入多少层领域解释。

- **低跨度**：意图与验收标准几乎同构，如编译通过、类型检查通过、接口字段符合契约。
- **中跨度**：需要一层领域概念映射（业务概念 → 数据字段 → 状态机），如订单状态流转是否合法。
- **高跨度**：验收标准依赖语境与隐含知识。[6] 给出的验证问题"用户的核心诉求是否得到解决"，其证据是"最终环境状态、工具结果"，属于需要解释而非直接判定的典型。

跨度越大，正确性越难在事前写死，验证越依赖事后证据。既有 [[数据-信息-知识-判断四层框架]] 可作为该轴的直观刻度：越靠近顶层"判断"，语义跨度越大。

## 维度二：可形式化程度

本页将材料整理为三档（属本页归纳，非来源原文分档）：

- **高**：存在形式化规约语言，可精确描述可接受行为并支持合成与验证 [1][3]。
- **中**：可写成测试、断言或检查清单，机器可执行但覆盖不完备。
- **低**：只能事后审计、人工评审或统计评估。

AI 系统使这条轴整体向下移动：[2] 指出形式化方法在 AI 系统中有五个独特挑战（具体条目本批材料未展开，见"待核验"）。但下移不等于归零：机器人策略学习与验证领域展示了用形式化方法定义可接受行为、对学习所得策略进行验证的路线 [1]。

当形式化不可行时，工程上存在两条替代路线：一是**治理替代**——Microsoft Agent Control Specification 将 Agent 行为的核准与权限落实成文档，并转化为实际的系统边界，其稽核不仅保证事后可追查，还承担预防功能 [5]；二是**证据替代**——从运行轨迹中提取学习信号，以最终环境状态与工具结果作为事实证据 [6]。

## 四象限任务分类

| 象限 | 语义跨度 | 可形式化程度 | 典型任务 | 首选验证/治理策略 |
|---|---|---|---|---|
| Q1 可证明区 | 低 | 高 | 编译、类型检查、单元测试、接口契约、策略规范验证 [1][4] | 机器形式验证与自动测试；失败可自愈 [[自愈成功率与报错引导修复]] |
| Q2 单点主观区 | 低 | 低 | 单步操作但成败标准含主观或统计成分的输出 | 抽样人工评审 + 统计口径，需明确样本量与判定标准 |
| Q3 规约工程区 | 高 | 高 | 端到端业务流程约束、跨系统数据规则 | 规约精化 [3] + 约束层 [[本体作为约束层]] + 人机协同确认 [[action分级与确认机制]]、[[agent中断条件与检查点]] |
| Q4 治理审计区 | 高 | 低 | 开放式业务目标（体验提升、探索性任务） | 边界文档化与事后审计 [5] + 轨迹证据 [6] + 可审计机制 [[agent可解释性不可信与可审计三元组]] |

补充说明：

- Q3 是框架中最关键、也最可疑的象限。它的成立依赖一个工程假设：形式化规约与逐步精化可以把高语义跨度任务重新拉回可形式化一侧 [3]。若该假设不成立，两轴可能高度相关，二维框架退化为单轴排序（见"待核验"）。
- Q4 的治理路线与形式化验证的哲学不同：前者以文档、权限、审计实现"可追责" [5]，后者以规约与证明实现"可判定" [4]。
- 按 [[面向制品与面向角色]] 的思路，坐标迁移的常见手段是把意图固化成制品（[[制品即说明书]]），从而压低语义跨度。

## 任务分诊流程（本页归纳）

1. 判纵轴：验收标准能否写成机器可判定的规约？能则高；只能列出证据则低（可参照 [6] 的"验证问题—证据"表结构）。
2. 判横轴：从意图到验收标准需要补几层领域解释（在数据 → 信息 → 知识 → 判断中处于哪一层）。
3. 按象限选择验证策略；对 Q3/Q4，优先评估工程投入能否把任务迁移到 Q1/Q2 一侧，而非直接上更复杂的 Agent [3]。
4. 记录坐标与迁移历史，作为 [[code-first升级阶梯与l0-l4成熟度模型]] 的输入。

- [[成功率连乘与单步确定性]]：把长链路拆成低跨度、可形式化的单步，是压低连乘损耗的主要手段；二维坐标可用于识别链路中最脆弱的环节。
- [[强制力四层排序]] 与 [[最小闭环与组织治理基础]]：可形式化程度下降时，强制力来源从机器判定退向流程、清单与组织约束。
- [[神经符号]]：神经符号工程正对应"高跨度 + 中等可形式化"地带——用形式系统约束生成过程。
- [[function-workflow-agent三分法与组合]] 与 [[workflow与agent的分界]]：Q1 适合 Function，Q3 适合 Workflow，Q4 才需要 Agent；本框架可与 [[选型两轴与一条红线]] 对照阅读。
- [[自主权判据]]：本页推论——自主权应与可形式化程度反向匹配，越不可形式化，越需要确认、留痕与中断机制。
- [[agent验收指标清单]] 与 [[业务验收指标口径]]：验收指标的机械化程度，是"可形式化程度"在工程上的直接体现。

- [[确定性走context探索走query]]：在检索层面复现同样的二分——确定性需求走 Context，探索性需求走 Query。
- [[把-agent-当软件管理]]：对 Q3/Q4 任务，管理范式先于能力选型。
- 在既有图谱中，[[语义跨度]] 与 [[可形式化验证]] 主要出现在 AI Coding 与本体建模语境（见 [[ai-coding-本体系统]]）；本页将两者交叉为二维框架，并补入形式化方法方向的外部材料。

## 争议、缺口与待核验

- **两轴是否正交**：语义跨度与可形式化程度可能是相关的（高跨度任务往往也低可形式化）。若如此，Q3 象限可能近乎空集，框架退化为单轴排序；目前材料不足以裁决，需要实例证据。
- **"可形式化"是固有属性还是工程变量**：[2] 强调 AI 系统带来的形式化障碍（偏固有），[3] 强调规约工程与逐步精化（偏可改变）。本页暂取"工程条件下的坐标"立场，待案例验证。
- **形式化方法五挑战未列项**：[2] 的摘要只给出结论，五个挑战的具体条目需回溯原文。
- **Microsoft Agent Control Specification 规范文本未核验**：[5] 为媒体性质报道，规范的适用范围、强制力与落地案例需查官方文档。
- **两种验证哲学的关系**：事前规约（形式化）与事后证据（轨迹、最终环境状态 [6]）是互补还是竞争，材料未给出裁决。
- **术语缺口**：本批材料未直接使用"语义跨度""可形式化程度"二词，二维分类属本页综合构造，尚缺原始出处。
- **成本侧证据不足**：形式化与本体建模的投入产出边界仍属待核验项（参见 [[本体建模成本收益边界待核验]]）。
