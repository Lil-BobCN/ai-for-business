# 本体与数据约束及版本演化待核验

## 问题

当 Ontology 被用来定义业务含义、而具体数据被用来描述业务事实时，二者发生冲突应如何裁定？订单、库存和物流状态的变化，哪些属于实例数据更新，哪些属于关系事实修正，哪些已经构成本体定义或版本变化？关系校验应由业务人员、规则系统、Agent 还是人工审批共同完成？

## 当前已知

视频作者在本地 ASR 口播中提出：

- Ontology 描述领域中的概念、属性、关系和约束；
- 订单、顾客、商品等可以作为电商业务对象；
- API、数据库、CSV、PDF 等来源需要先统一和清洗，再映射到业务模型；
- FDE 可能需要在缺少现成约束规范的客户现场推动业务含义定义；
- 错误关系进入 Agent 上下文后，可能导致错误回答或错误执行；
- Ontology 建成后需要校验、业务测试和持续更新。

以上内容的证据状态为本地 ASR `partial`，作者主张为 `unknown / 待外部核验`。来源没有提供 Schema、数据样本、规则配置、版本格式、测试集或运行日志。

## 未解决的边界

### 本体与数据谁约束谁

来源一方面把本体描述为业务含义的定义，另一方面又称具体数据可以说明业务模型应当遵循的约束。尚不清楚：

- 数据异常时应清洗数据、修改本体，还是保留冲突并转人工；
- 业务方确认与数据统计之间谁具有更高裁定权；
- 清洗规则是否必须由本体约束；
- 本体定义是否允许从数据中反向发现新对象或新关系。

### 清洗与建模的先后

来源把数据处理作为一条主线，但清洗时已经需要识别实体、对象和关联关系。尚不清楚：

- 清洗规则是否独立于本体；
- 本体未定义的对象如何进入候选模型；
- 数据驱动发现的关系如何获得业务确认；
- 业务定义和数据映射是否需要共同版本化。

### 实例更新与本体演化

订单状态、库存数量和物流位置的变化通常表现为实例或事实更新，但业务规则、关系基数、对象类型和属性含义变化可能属于本体演化。尚不清楚：

- 哪些变更需要提升本体版本；
- 旧版本上下文产生的回答和执行结果如何追溯；
- 关系事实修正如何影响历史记录；
- Agent 使用的上下文如何标记其本体和数据版本。

### 校验闭环

作者强调关系校验和大量测试，但未说明：

- 客户确认、自动规则、回归测试和人工复核如何分工；
- 什么条件下允许关系进入 Agent 上下文；
- 校验失败时是否阻断回答或执行；
- 业务方如何确认 FDE 在现场定义的约束确实符合真实流程。

## 下一步研究动作

1. 查找正式 Ontology 工程或知识图谱版本化资料，区分模式变更、实例更新和关系事实修正。
2. 为电商订单、拆单、库存和物流状态设计最小冲突样例，记录不同来源的时间、权威级别和处理结果。
3. 核对现有项目是否保存对象、关系、来源、时间、置信度、本体版本和数据版本。
4. 设计一组进入 Agent 上下文前的关系校验规则，并明确失败时的人工介入条件。
5. 获取课程演示源码、Schema、配置或运行日志，核对作者所说的“本体更新”具体指什么。
6. 回听原始音视频，确认 `共同语异模型`、`Agentology`、`订单伪号` 等 ASR 存疑术语，避免术语误读影响后续研究。
