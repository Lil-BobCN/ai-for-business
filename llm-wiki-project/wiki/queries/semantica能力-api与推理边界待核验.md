# Semantica 能力、API 与推理边界待核验

## 待核验问题

Semantica 的正式项目身份、当前能力和接口是什么？第 1、10、11 集提到的数据处理、业务本体构建、检索、规则推导、来源追溯、工作台、OWL 读取、Agent 工具调用和订单客服链路，分别对应哪些可核验实现？本体、知识图谱查询与推理的边界应如何准确表述？

## 来源中的描述

本地 ASR 将 Semantica 描述为一个开源框架，覆盖数据处理、本体构建、多类检索和应用接入。第 1 集称其“完全开源并持续维护”，并称当时有“13000 多颗 Star”；第 10 集口播出现“14k”。这些项目状态和数字均未经独立核验，现有材料无法判断两个 Star 数口径的差异是时间变化还是近似表达。

第 1 集列出的能力包括文件、网页和数据库接入，解析、清洗、去重、标准化，实体关系抽取，知识图谱与业务本体构建，语义检索、图遍历、规则推理、数据校验和来源追溯。该集还称 Semantica 具有“最佳实现方向”，但没有提供比较依据。上述能力及评价都需要对照官方仓库、文档或源码逐项核实。

第 10 集描述了检索、规则推导、来源追溯和工作台相关内容，但现有材料不足以确定这些描述分别对应的实现、接口或验证结果。

第 11 集称 Semantica 可直接读取 OWL 文件，并向 LangGraph Agent 提供检索算法。作者还以“经理也是员工”为例说明规则推导，并把订单演示中的状态查询和规则校验放入 Agent 工具调用链路。这些口播描述不能独立证明 Semantica 已实现 OWL 推理、规则引擎、事务更新或完整的 Agent API。

## 证据缺口

- 来源没有给出 Semantica 官方仓库、具体版本、许可证、源码片段、API 文档或可复核的返回数据。
- 来源没有给出 OWL 读取路径、推理器配置、工具 schema、订单对象标识或规则版本。
- 来源没有说明规则与事实冲突、多来源冲突、权限过滤和人工介入如何处理。
- 第 1 集的能力清单没有实现细节、演示证据或评测结果。
- 来源没有说明订单演示实际使用的模型、OpenRouter 配置和依赖版本。

## 下一步研究动作

1. 查找 Semantica 的官方仓库和版本文档，确认项目身份、许可证、Star 数和部署方式。
2. 在源码或 API 文档中核对数据处理、OWL 读取、检索器、SDK、规则引擎和来源返回字段。
3. 获取订单演示源码，记录工具参数、返回契约、规则校验和模型配置。
4. 查找 OWL 推理、规则推导和知识图谱查询的权威资料，重新表述概念边界。
5. 使用冲突订单和多商品物流样本复测流程，而不是只复现单个干净案例。
