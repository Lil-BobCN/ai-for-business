## 一句话摘要

视频作者提出：AI Coding 想要的效果与实际拿到的效果之所以不一致，根子在"语义跨度"和"形式化验证"两件事上，而解法是用本体（Ontology）把需求、设计、任务、代码、规范与流程建成一张类、关系、实例与规则齐备的图谱，让制品可以按拓扑稳定加载、让校验可以用机器强制、让流程可以被门禁拦住，从而把每一步的成功率抬到足够高。

## 口播文章

### 开场：现状、期望，以及本期要聊的四件事

视频作者在开场先摆出一张对照图：左边是"我们现有的软件生命周期管理遇到的问题"，右边是"我们希望达到的管理效果"。

左边的问题被作者归成三类。第一类是决策记录没有被记录到项目管理工具里——不论是 GRA（待确认）这样的工具，还是其他的一些文档管理工具，很多决策过程并没有被沉淀下来。第二类是知识可能会随着人的变动而消散在整个团队里面。第三类是文档其实远远落后于代码仓库。

右边则是作者希望达到的效果：需求里面带着设计方案，带着成功标准，也带着一些度量标准。

不过作者紧接着提醒：右边这种状态并不是"今天你用了一个项目管理工具"就会变成这样的，工具只解决了其中一部分问题。所以这次要把话题展开，聊一聊怎么用 Ontology 来做这件事情。

整场分享要聊四类问题。第一，AI Coding 到底能解决什么、解决不了什么，以及我们用 AI Coding 时本质上要解决的问题是什么，这一部分会跟大家做一个讨论。第二，AI agent 今天强在哪里、弱在哪里，怎么让它做得更强，或者说不那么弱。第三，本体是什么，它凭什么能让 AI 有更好的指令遵循，从而减少动作上的幻觉。第四，是一段完整实战：作者会介绍一个需求怎么在本体里面，从这个需求变成设计，再变成任务的拆解，然后再到代码的实现，整个过程是什么样的。

### 三个常见场景：为什么个人效率没有变成交付提速

这一部分，作者主要解释的是：为什么我们想要的 AI Coding 效果，跟我们实际拿到的效果不一致。

作者的观察是：个人用起来可能觉得 AI Coding 的效率已经非常高了，代码产出量也足够高，但是产品迭代的周期有没有缩短？迭代的次数有没有增加？质量有没有提升？这些其实都关系到 AI Coding 出来的产物，能不能按照我们想要的要求发布到生产环境。

作者先讲了三个常见的场景。

第一个常见场景是，业务方提的所谓"需求"，其实是在给方案。业务同学更多的时候是说"你帮我去加个按钮"——比如"我这个公交车这个页面你帮我加个按钮，怎么怎么做"。作者认为，这其实不是在提需求，而是已经直接告诉你怎么去做了，等于已经把解决方案给了出来。原因在于业务方不太了解整体的产品设计与技术设计，他会觉得"加个按钮"就是一件小事情，但实际上它对产品的改动、对设计的改动、对技术的改动，可能都是很大的。

第二个场景是变化。业务会变化，承接这些业务的团队也会变化，中间会有产品相关的一些交接。这个时候我们没有办法很好地做到：把一个产品从零到一、再从一到一百过程中踩过的坑、形成的积累和经验，变成可追溯的文档。到了交接的时候，我们确实能拿出一些交接材料，但"为什么会走到今天""怎么走到今天的"这些经验全都丢了。

第三个场景是系统本身。等系统复杂了之后，虽然我们有很多回归测试用例、各种测试用例的集合，每个阶段我们也去做相关的测试，但实际上它的覆盖度到底到什么程度，作者说有的时候心里也没底，于是就变成会有一些缺陷逃逸到线上环境去。

作者把这三个场景称作共性问题，并说从这些共性问题往上抽一下会发现：有一些问题其实是在整个软件生命周期里面都会出现的，比如复杂度的问题，或者更本质的那些问题。

> **思考一下｜"加个按钮"到底是不是需求**
>
> 这一段把讨论从"AI 工具好不好用"拉回到"需求是怎么进到系统里的"。作者指出业务方常常直接给方案而不是给问题，这其实是一个很常见的组织现象：越是熟悉现场的人，越容易跳过问题陈述，直接给出自己想象中的解。这为后面"意图模糊"埋下了伏笔——如果入口处的意图本身就带着预设方案，那么后面所有的语义跨度都会被放大。
>
> **可以追问**：如果业务方给出的永远是方案而不是问题，那么"从方案反推意图"这件事应该由谁来做、在哪个环节做，才不至于在设计和编码阶段付出成倍的返工成本？
>
> **可延展方向**：可以把"用户提出的方案 → 背后的真实目标 → 可验证的成功标准"看成一条翻译链，研究这条链上每一跳的信息损失率，以及用本体化的需求制品能否把损失记录下来。

### 四个抽象问题：意图模糊、系统复杂性、认知局限与现实不确定性

作者接着往下抽象。他说，比如今天做一个扫雷的小游戏，在本机运行，它面临的复杂度，跟今天去做一个一天要支持几千万单的支付系统，复杂度肯定是不一样的，这是本质上的一些问题。同样，一个十人左右的创业公司小团队的管理模式，跟一个几百人甚至上千、上万人的团队协作，它的管理模式、复杂度、沟通成本其实也是不一样的。

另一块是方法论和工具。作者提到，我们使用的软件工程方法论，有的是瀑布、有的是"运机"（待确认）；软件工程的管理工具也各不相同，有人用"机软"、"沉到"（待确认）这样的工具去做相关管理，也有人是自己企业里开发了一套小的管理系统，因为要跟自己的业务系统打通。这些差异会决定我们对项目管理能力的程度，比如追溯得全面与否、质量管理做得怎么样，或者说时效性上都会有差异。

作者划定了这次讨论的范围：今天讨论的问题主要集中在下面这一层，就是"规划与追溯"。也就是说，怎么用工具也好、方法论也好，来管理好我们整个软件生命周期，而不去考虑团队的问题，也不去解决它复杂的本质问题。

这三类问题再抽象一下，作者是这样说的：一类是本质问题，比如信息不存在——有些需求只有到了线上环境之后，我们才能拿到用户的反馈，这样的信息是本质的问题，我们解决不了。第二类是团队协作的问题，因为团队里面一定会有各自的角色，角色会导致立场不同，触发点也会不一样。第三类是工具、方法论或者流程这一类，它们其实相对标准、相对可控，所以这次只集中在这个领域来向大家介绍。

在流程类、工具类或者成熟度这一类纯工程问题上，作者又把它抽成了四个点：意图模糊、系统的复杂性、认知的局限性，以及现实的不确定性。

他逐个解释。意图模糊是指，我们很难准确描述清楚我们想要的产品是什么；或者我们知道自己想要什么，但有可能讲不清楚；也有可能即便我讲清楚了，对方也未必理解清楚。因为自然语言本身就是有二义性的，而且每个人的理解不太一样。系统的复杂性则是前面那个例子：做一个扫雷小游戏，跟去开发一个支付系统，复杂度一定是不一样的。认知的有限是指，如果今天让一个初级的程序员，跟一个高级架构师或者专家级的架构师去做同一件事情，因为他们的经验不一样，拿到的结果也是不一样的。最后是现实的不确定性，尤其是有些需求其实只有当我们把产品投入到线上环境之后、有了用户的反馈，才共同去创造了一些新的需求出来，这样的不确定性我们没有办法提前预知。

作者于是提出一个反问：是不是这四个问题，导致了我们今天在软件工程里面没有办法很好地拿到想要的预期？为了回答这个问题，他换到数学领域去看。

### 用数学领域做对照：四个问题都消解了，AI 为什么仍没有猛进

在数学领域，作者认为这四个问题几乎都不存在。

第一，意图其实就是一个命题，非常明确，一定不会有二义性。不管是谁，只要他对数学是理解的，就一定能明白这个意图是什么，因为数学问题可以用形式化的语言来表述，而形式化的语言是没有二义性的。

第二，系统的复杂度不存在。因为我们去解决数学问题的时候，不需要复杂的工程，甚至不需要几百人的团队协作。

第三，认知的局限基本上也没有。因为解决那些顶尖数学问题的人，一般也是顶尖的数学家，他们已经代表了人类的智力顶峰，所以相对而言也就不存在所谓的认知局限。

第四，现实的不确定性同样不存在。作者说，像现在很多数学问题，比如一些公理或者定理，其实都是可以做形式化的，用 `metallab`（待确认）、`lenfo`（待确认）这样的工具；当我们把一个数学的证明过程用 `lenfo` 做形式化之后，它编译通过，其实就代表这个命题要么被证明、要么被证伪。所以作者说，会发现在数学问题上，这四个问题都已经被很好地解决了。

但事实上，作者观察到：数学领域虽然有了 AI，但并没有特别猛进。为什么呢？他给了两个原因。第一个是语义的跨度——当我们去证明一个复杂的数学问题时，我们其实不知道该怎么证明它，整个的语义跨度是非常大的。第二个是可形式化验证的问题——数学领域还好，它的可形式化验证已经相对丰富；但在软件工程里面，说"我通过执行一段脚本就可以把这个需求很好地验证掉、或者说把产品很好地验证掉"，这件事好像也不太可行。

围绕这两个核心问题应该怎么解决？作者说，这个时候我们会引入比如解决语义跨度的一些方向，以及可以做形式化验证的一些工具和方法论。

> **思考一下｜"四个问题都消解了"的领域，为什么反而没有被 AI 攻下**
>
> 这一段是整场分享里最有意思的一次反证：数学领域的意图明确、系统简单、认知顶尖、现实确定，按理说最该被 AI 拿下，但作者观察到并没有。他给出的解释把"难度"从一个整体拆成了两个可操作的变量——语义跨度，以及能否形式化验证。这个拆法本身就值得单独拿出来讨论。
>
> **可以追问**：如果语义跨度大但可形式化验证程度高（比如数学），和语义跨度小但几乎无法形式化验证（比如大量业务系统），哪一种更可能先被 AI 稳定接管？现实中的工程任务大多落在两者之间的哪个位置？
>
> **可延展方向**：可以按"语义跨度 × 可形式化程度"做一个二维分类，把不同类型的研发任务放进去，看看哪些格子适合交给 agent 独立完成、哪些必须靠人补上判断，这会直接影响人机分工的设计。

### AI agent 的能力边界：执行强、判断弱，以及语义跨度为什么要小

在介绍解决语义跨度和形式化验证这两件事的方案、方法论之前，作者先回顾了一下现有的 AI agent：它的能力强在哪里、哪些地方比较弱，以及如何做一些增强。

作者给出的直观感受是：AI agent 的执行能力一定非常强，尤其是在语义跨度比较小的任务上。他举了一个命题——让你写一个快速排序算法。这个时候几乎所有的 agent，哪怕用的是开源模型、不用思考模型，都会非常好地实现我们想要的预期结果。

另一点是，AI agent 在执行一些形式化验证时也很强，因为它可以去调用工具。比如让 agent 去调用一个方法，这个方法里面是有几百行代码来实现的，它只是去使用这个工具——在这一方面，它的能力也非常强了。作者因此说，它的执行能力几乎已经超过人类。

但另一点是判断能力，它相对会比较弱。作者说我们经常吐槽现在的模型"没有品位"：它不知道你的品位，不知道你的喜好，不知道你会怎么做选择。他给了几层原因。第一，我们在做一些复杂任务的时候，它未必把所有疑点都跟我们来确定，因为它觉得它已经知道了。第二层和第三层，是它不知道自己不知道，或者"它不知道我不知道"。作者把这件事归到一个所谓的"小哈利时创"（待确认）上：当两个人在协作的时候，必然有共同知道的、有共同都不知道的，也有 A 知道 B 不知道、B 知道 A 不知道的。像这样的一些问题，其实也没有办法很好地去解决。所以能力的短板，主要体现在判断这一层上面。

于是作者展开了一个所谓的信息框架，用来讲怎么把这个语义跨度降低一些。这个框架的第一层是数据，第二层是信息，第三层是知识，第四层是判断。他用一个例子来解释。

假设我说"今天 30 摄氏度"，这其实就是一个数据。作者说，我也不知道它是什么的温度：它是室温、气温还是水温，还是其他什么温度，我也不知道。但当我增加一些信息上来，比如把它放到一个上下文里——"今天是几月几号，杭州或者某个城市，气温是 30 摄氏度"——这个时候它就已经是一个信息了。

有了这样的信息，就一定会有一些相关的知识。比如：当气温是 30 摄氏度的时候，我们是不是就建议去开空调？或者说城市的道路是不是应该经常洒水，用来降低温度？但作者紧接着又问：这是通用的知识，通用的知识大家一定会去做吗？我一定要去开空调吗？我一定要让洒水车去马路上洒水吗？也未必。比如最近市政资金比较紧张，就不太适合去做这件事情；或者我身体弱、怕冷，我就不太喜欢开空调；但可能公共场所，比如商场之类，他们早就把空调开起来了。作者说，这其实就是到了所谓的判断这一层，或者叫选择这一层。

紧接着，作者讲了另一个要跟大家说明的概念，就是语义跨度。

他说，我们今天用 AI agent，agent 后面一定是用模型。那就变成一个问题：模型是怎么训练出来的，它是用什么样的语料训练出来的？是用语义跨度比较小的语料训练出来的，还是用语义跨度比较大的语料训练出来的？作者说，就我们目前了解，肯定是用跨度比较小的。

他的理由是：模型绝对不会选用"我说我要一个支付系统"，然后就是一个几十万行代码的仓库，用这样的语料来训练——感觉不是这样子的。所以它应该是用了一些均匀的语料。比如"我今天需要一个支付系统"，那么支付系统下一步的语料，可能就是它所在的语境：我这个支付系统有几个子系统，每个子系统有哪些功能清单，也就是 feature 是哪些；feature 分别是由哪些子系统去承担的；这些子系统之间的业务链路是什么样的，时序是什么样的，业务流程是什么样的。

再往下，包括接口协议，一定是这样一步一步去做语料的准备。

作者说，同样地，人也是这样。假设人没有一个很好的语义跨度，举例来说：我今天上一堂课刚学完四则运算，我已经学过了；接下来下一堂课就让我去学微积分，大概我也学不会。所以不管是模型的训练，还是人的认知，我们发现其实都是在均匀的、有一定跨度的语料上面去做的一些学习。

> **思考一下｜语料是均匀的，任务难度却常常是跳变的**
>
> 作者用"刚学完四则运算就上微积分"来说明学习需要跨度均匀。这个类比同时指向两个方向：一方面它解释了 agent 为什么在中小跨度的任务上表现很好；另一方面它也提示，当业务把一个跨度过大的命题直接丢给模型时，失败未必是模型不够强，而是输入没有被铺成台阶。
>
> **可以追问**：把一个大命题铺成台阶，这份成本由谁承担？如果拆解本身依赖资深判断，那么"降低语义跨度"会不会最终又绕回到人身上？
>
> **可延展方向**：可以统计团队里"agent 一次做对"与"必须拆成多轮"的任务比例，看看哪些维度的拆解最有效，这会沉淀出一套可复用的任务切分经验。

> **思考一下｜"判断力"是不是可以被工程化补偿**
>
> 作者把 agent 的短板明确定位在判断层，并顺着"数据—信息—知识—判断"四层往上走：越往上越依赖具体的人、具体的处境和具体的价值取向，也就越难用通用的方式给出答案。这一点和前面的语义跨度是同一个问题的两面——跨度越大，判断越是无人可代。
>
> **可以追问**：如果判断力难以直接训练出来，那么能不能通过"把判断所需要的信息提前结构化"来减少需要现场判断的次数？这种做法会不会把判断的成本转移到建模阶段，从而只是换了个地方付费？
>
> **可延展方向**：可以沿着这个四层框架，梳理一个组织内部"哪些判断可以沉淀成规则、哪些判断必须保留在人手里"，并把可沉淀的部分写成机器可执行的约束，这会直接决定 agent 的可托付边界。

### Working Backwards：面向制品，把语义跨度均匀拆开

作者接着提出，用 Working Backwards 这样的方法论来评估一下这件事情。

他说，我最终想要的其实就是发布到线上环境的一套系统。那么距离这套系统最近的，应该就是所谓的一些任务——这些任务包括前端的开发任务是什么、后端的开发任务是什么、测试任务是什么，还有一些运维等等。这些任务就是靠近我们最终想要的那个代码仓库、或者说上线现场那个产品最近的一层语料，或者说产物、制品。

那距离任务最近的，就变成了设计。同样，距离设计最近的变成了功能清单，而距离功能清单最近的，就变成了比如 User Story 之类的东西。作者说，这就是传统软件工程用来解决语义跨度问题的方式。

那是不是还有其他的方案？作者看了另外一个方案：靠角色。

靠角色的时候，你看我们有需求侧的——有业务方，然后有承接需求的产品经理或者说需求分析师，还有架构师，还有后端开发专家、前端开发专家，包括测试的专家，还有比如运维的专家。像这样的一些角色，其实也是在去做这些语义跨度的均匀消减。

但作者指出这里面有一个问题。我们比对一下：面向角色的时候，角色这件事就很难标准化，或者说同一个角色的不同的人，他体现出来的稳定性——也就是我们所说的，面对不同的需求、不同的产品、不同的任务时表现出来的效率或者质量等等——它的稳定性不太一样，所以这个事我们就很难去标准化。而今天我们面向制品的时候，比如我的这个需求应该怎么写，它必须用一些像什么样的格式；我的设计里面必须要有比如流程图、时序图等等这样的内容，其实它就容易标准化掉。

作者说，所以这是两种我们可以认为是降低语义跨度的方案，而他的倾向是面向制品。也就是说，把原来希望一步做掉的事情，现在拆成了中间有几个阶段，每个阶段也有若干步。

> **思考一下｜面向制品，还是面向角色**
>
> 作者在这里做了一个很具体的取舍：把"谁来做"换成"做出来的是什么"。角色的稳定性来自个人经验，制品的稳定性来自结构，这才让标准化成为可能；代价是组织必须先把制品的形态定义清楚，否则标准化只是一句口号。
>
> **可以追问**：在制品形态还没稳定下来的团队里，先定义角色职责与先定义制品格式，哪一种更容易推进，为什么？
>
> **可延展方向**：可以把团队现有的交付物盘一遍，看哪些已经有稳定格式、哪些还停留在个人习惯，这份盘点会直接决定引入本体建模应该从哪里起步。

### 拆成多步之后：成功率连乘，与单步成功率的三个限制

拆步骤一定会面临一个问题：我们的任务一定会增多。但还有另外一个问题——AI agent 在处理任务的时候，它一定是有一定的概率会失败的。

作者用概率连乘来说明这件事。假如处理一个任务的失败概率是 10%，也就是单步的成功率是 90%；或者单步成功率是 99.5%。那么当它是五步的时候，我们会发现低成功率大概在 59% 左右，高一点的那个是 98%。当它变成比如 100 步的时候，我们会发现 90% 的那个低成功率——做 100 步都能成功——大概已经趋近于零了；而那个高一点的，也已经到了 60%。作者说，虽然 60% 好像还行，但他觉得这也是非常低的：假如我拆了 100 个任务，结果只有三分之二的概率才可能成功，这事就不太现实。

所以就变成另外一个问题：我们怎么保证拆了不同阶段、而且每个阶段也有若干步、让它的语义跨度比较小的情况下，成功率也是非常非常高的？比如它的成功率已经变成了 99.9%，也就是失败率万分之一。作者说，这就变成这样一件事情。

那么解决单步成功率的问题，无非有这么几种手段。

第一种手段是：我同时有多个 agent，一起来处理同一个任务。那只要有一个成功了，就代表整个任务处理成功了。假如每个失败的概率是 0.05%，那三个都失败的概率其实就极低了。

另外一种方式是，用 loop 的方式去做。用 loop 的好处也是能看到的：它上一步可能执行失败了，但失败一定会有失败的原因，这个原因可以作为下一步执行的、也就是下一个 loop 的输入，它可以慢慢地去提升成功率。作者说，你比对前面的方式会发现：因为并行是三个不同的 agent 同时去做，它们之间失败的经验是没有办法共享的。所以目前选择的肯定是用 loop 这样的方式去做。

基于前面讲的这两种提高成功率的机制，作者提醒：我们其实要明白，真正限制每一步成功率的因素是什么。他觉得有这么三点。

第一点是判断标准不明确。基于一个判断标准不明确的前提，比如我生成了一个脚本，这个脚本执行完之后，我没有明确的判断标准，那我就不知道怎么去改进，也就变成了这样一个状况。

第二点是信息有一些缺失。比如他拿不到我们企业内部的编码规范，那他写出来的代码大概率是不符合我们要求的；因为他没有这些规范，我们又没有别的办法去让他纠正。所以就变成了前面那个问题——他没有一个判断标准，比如规范的判断标准他就没有；另外一点，错了、错在哪，他也不知道。作者举了同一个例子：他今天就是违反了企业的编码规范，但是因为他没有这个规范，他又怎么知道错在哪了呢？所以他又没有办法纠正回来。

作者说，这就是限制单步成功率的三个核心要素。

> **思考一下｜连乘模型真正提示的是"别拆"还是"每步都要确定"**
>
> 作者用 90% 与 99.5% 两种单步成功率，对比五步与一百步的结果，落点其实不在"少拆几步"，而在于：拆得越细，单步的确定性就越重要，否则链路的整体成功率会被指数级吃掉。这也解释了为什么他把后面的篇幅几乎都花在"怎么让单步变得可判定"上。
>
> **可以追问**：在不减少任务数量的前提下，还有哪些手段能提升单步成功率？把判断标准前移到建模阶段，是否一定比在 loop 里反复试错更划算？
>
> **可延展方向**：可以为一条真实的 agent 流水线记录每一步的成功率与失败原因分布，看看失败是集中在少数几步，还是均匀分布——这两种情况的改进策略完全不同。

### 可查、可校验、可强制：符号主义能补上的三件事

那怎么去保证单步的成功率比较高呢？作者说，就是把刚才这三个问题解决掉。

第一个，我们企业里面有各种规范，我一定是可以去查的。而且去查的时候，每次能查到的应该就是同一个——同一个任务换不同的 agent，它应该查到的这些规范也好、要求也好，都应该是一样的，而且是稳定的。不能说 agent A 查出来的跟 agent B 查出来的不一样，或者说同一个 agent 查两次也不一样，这事就不太现实。作者指出，比如我们传统的 RAG 就会存在一些这样的问题，因为它是靠语义去匹配的，不是很稳定；但如果我们今天是通过图谱的关系去查的话，其实它就非常稳定。

第二个，一定要可校验。作者举例说，我们今天大概率很多这样的制品，都是通过让大模型做语义上的检查。那我们今天是不是可以先让它做格式上的检查？举例来讲，我这个有一个接口，上面有 URL 的定义，那我们的要求是比如它必须是字段：第一段代表什么含义，第二段代表什么含义。像这样的一些标准格式上的校验，是不是可以让这个 agent 通过一些脚本、或者其他的方式，来把它校验掉？这就是变成一个"可校验"。

第三个，就是一些强制约束。他举例说，我们今天在走这样一个流程：前面的需求还没有做完，那时候它已经进入了设计阶段，这个事其实也不合理。那我们怎么保证说，一个 agent 在执行这个流程的时候，他会去检查一下流程的进展，而且去判断一下是不是应该进入到比如这个设计阶段？这是一个强制型的约束。

作者说，这个时候我们就会发现：其实通过符号主义这一套东西，可以很好地去解决。也就是说，我们能不能把它做成形式化的一些执行或者验证。

基于这个，作者引申出另外一个比较大的点，就是现在正在做的所谓"神经符号"这样一个概念。他解释说，符号主义或者说连接主义，其实是做人工智能的两个大的方向。符号主义它的实现成本是比较高的，比如前期需要大量的人去维护各种关系，或者你要写各种规则什么的；而且我们很难把所有逻辑都完美地闭合掉、不出纰漏，这件事的成本非常高。但是今天我们有了大模型之后，大模型比如感知、泛化等等这些能力非常强，它就可以很好地去弥补符号主义的这些缺陷。所以这两个结合起来，或许就是解决这个问题的一个比较好的途径。

> **思考一下｜"稳定地查到同一条规范"为什么比"查得更准"更重要**
>
> 作者在这里把可靠性拆成了两半：一半是正确性，一半是稳定性——同一个任务、不同的 agent、不同的时刻，应该命中同一份规范。这一点在工程上非常关键，因为只有输入稳定，失败经验才可复用、成功率才可累积；如果每次检索结果都在抖动，loop 里的"上一步失败原因"就失去了参照物。
>
> **可以追问**：在什么规模的规范体系下，用图谱关系做检索的收益会明显超过维护图谱的成本？如果规范本身还在快速变化，图谱需要付出多大的同步代价？
>
> **可延展方向**：可以把"检索稳定性"当作一个可测量的工程指标，比较向量检索与图谱检索在同一批任务上的命中一致性，进而讨论哪些类型的知识适合放进哪一种检索通道。

### 本体的四个要素，以及一套完整的语义层

接下来这部分，作者介绍什么是本体。他说，前面我们一直在讲，还是希望能够均匀地降低语义跨度，包括可以用一些形式化验证的手段或者方法来做相关的校验。那本体是不是具备这样的能力？可以展开来聊一下。

作者先把本体的四个要素简单介绍了一下：类、关系、实例，还有一些规则。他说，但凡做过编程，其实都会对类、还有关系、包括实例这些概念非常明确，所以简单快速说一下。

类是比如我们对某一个事物的定义，上面可以有属性，当然它也可以有一些相关的方法；而"这个方法其实就是后面的一些规则"。关系，比如我们老师和学生是一个教学关系，这就是一个一对一的关系；落到具体的实例上面，就可能说王老师跟张三是一个教学关系，张三是个学生。当然也有其他实例的关系，基本上是这样子。

作者说，这个本身它就可以形成一个拓扑的这样的关系，而且这也是我们对世界、或者说做一些抽象建模，就是对业务的抽象建模，或者说对物理世界的抽象建模等等，都是可以这么去做的。

接下来他给了一个实际例子：这是他们在 AI Coding 中，对整个 coding 流程里面的制品、还有这些规则等等做的一些建模。比如 Spec，这个地方主要是做一些需求相关的建模，它里面会有哪些字段？比如像 `Scoop`（待确认）、还有状态，然后比如是不是做过澄清等等。这里面还举了比如它的一些枚举值，因为这个是一些形式化的定义或者结构化的定义。还有比如具体的功能性需求——一个 Spec 上面可以有多个功能性需求，也可以有多个任务；然后还有 Task，Task 可能是跟 Plan 之间做的一些关系；另外还有比如像一些测试用例。这是一个简单的关系的拓扑图。

作者接着说明 class 之间的关系会是什么样。比如我们这边现在是有项目相关的管理，比如 ontology，这是一个项目。

它这里面会有若干的 feature。举个例子来讲，我要支持实例的增删改查，其实这个就是一个典型的 feature。另外比如这个 feature 上面，我可能会分多个 `p次`（待确认）去实现，举例来讲，新增或者是更新，或者就是增删改查；我作为一个 Spec，比如后续有增加的时候，我可以对 instance 做备注，备注也可以作为一个新的 Spec。还有相关的 plan，就是做一些相关的设计，主要是技术方案的一些相关设计。

然后包括这个 plan 上面会有比如技术决策，还有拆解出来的任务，还有一些相关的约束等等。作者说，这是一个简单的描述，而这个其实就是我们这次整个 AI Coding 基于 Spec 的、完整的一个语义层——它大概是一个什么样的关系图。

这张关系图里面会涵盖几块内容。一块是流程、命令相关的，我们可以理解成说，我要把这个 skill 也做一些本体化：skill 上面的命令之间，它也是有相应的前后依赖关系，或者使用的环节、语境。另外就是软件工程常规的，比如像需求、设计、实现、测试等等这些。另外还有两个：一个是代码的一些图谱化——我们也会把整个代码仓库，比如它里面的具体类文件，类文件里面有方法，方法有一些入参，包括方法的一些核心流程，我们也可以把它做图谱化的一些管理。另外还有一些外围的，比如我们是不是可以通过操作这个 instance 的方式，来去操作比如 Jenkins，或者是去查这个异常日志等等，像这样一部分外围的操作，我们也会把它做一些图谱化。

作者还给了一个实例的具体例子。比如我这边是有一个应用，这个应用其实就是我们这个 Ontology 的核心服务；这个服务上面，比如它有"关联关系完整性校验"这样一个特性，这个特性下面会有比如"存量关系体系的体检"这样一个需求；这个需求下面做了相关的设计，设计上面会有具体的任务拆解。当然这个需求也会有相关的比如功能性需求、非功能性需求等等，包括 User Story。

作者说，这个本质上是图谱化的数据，但是图谱的数据对人来说其实是很难阅读的，所以我们就可以把它比如转成报表式的，或者说其他方式、图形化的形式来呈现。在这边给大家展示了两个：一个是说我们这套系统建设的一些能力维度大概是什么样子，然后目前的建设进展是什么；另外一块就是一个产品效果图，比如我们正在开发的这样一些特性或者 feature 自己是在什么阶段，已经完成了哪些、哪些在规划中。

### 逻辑即强制力：Schema、关系基数、拓扑与函数动作

前面讲了有了基础的类，也有了基础的关系，接下来就是所谓的一些逻辑。作者强调，逻辑是强制力的来源，因为这些逻辑基本上我们是用机器去执行、或者用代码逻辑去执行，而不是让大模型去做推理。他把这些逻辑分了几层。

第一层是完备性的一些校验，也就是 Schema 的一些必填。比如我们正常填一个表单的时候，有些是字段值必填的，那你没填肯定提交不了，它会报错，而且提示你说你应该填什么内容。或者说有些选项哪怕它是非必填，但它有一些格式要求，例如说这个是电话号码，它可能 11 位、比如以几开头，它有一些正则表达，这就是典型的 Schema 校验。

作者由此对比说，我们以前可能就写一个 Markdown 文件，那没有那么多强制性的要求，所以有的时候哪怕它出现幻觉，或者写得不对了，我们也没有办法去发现。而像这种方式就不一样：比如你今天所生成的 User Story，User Story 上面有相应的成功标准，成功标准上面比如有 Given When Then 这样的语法结构——Given 是一个字段，When 也是一个字段，Then 也是一个字段——那至少能保证这种语法结构是不会被打破的。

另外一个是关系基数相关的校验。比如我这个 Spec 跟 Plan 可能是 1 对 1，一个 Spec 只有一个 Plan；那我这个 Plan 下面可以有多个，比如多个 ADR（原文作 `IDA`，待确认）、多个接口协议或者数据模型，这个都是可以的。像这样其实就是一个关系基数的校验，也是可以去做。

还有一些其他的，就是拓扑图的关系。毕竟是一个拓扑图，那我们可以把整个拓扑图拿过来，比如有一些数据可以做聚合，或者做堆栈等等。作者举了一个例子：当我的任务里面有很多已经变成了归档，其中一个还是实现中、就是在开发中，那我是不是要聚合出一个"当前"的、这样的一个任务状态出来？这个我们是可以去做的。这样的一些校验，也就是整个拓扑图的一些校验，或者说针对图谱做各种规则校验，其实都是行得通的。

当然还有一些比较偏弱一些的规则。作者说，这些弱的规则就是靠提示词，我们通过提示词来限制这个 agent 或者模型，这样的一些校验规则，这一层其实就变成最弱的。

那还有一些就是刚才讲到的：我竟然可以在图谱上执行逻辑，那它就会有一些强制力的延伸。例如今天我要检查这个制品的一致性：比如我现在有了 Spec，也就是所谓的需求，那我需求上面的比如 User Story 是不是大于两个？另外就是我的 Spec 是不是已经生成了相关的 Flow（原文作 `Flight`，待确认）？生成了之后，我才能去做这个任务拆解。作者说，这完全可以做一个函数、就是脚本，来去验证这样一个图谱关系的完备性。那就变成了我们前面讲的 Function，它可以做运算。

还有一类是说，当我们要修改图谱中的一些数据的时候，我们是希望对这个修改的过程要做权限的检查。比如你是不是有权限修改某一个 Command、比如说 Specify 的一些 Command，你是不是可以去修改？那如果所有人都去修改，这个肯定会乱了，所以就变成了一定要做一些权限的控制。另外修改完了之后，比如我们要不要做一些审计，或者一些高风险的操作是不是要发一些通知等等。作者说，其实这个就是 action——涉及到一些数据的改，包括一些审计，包括一些通知的一些能力，就变成这样。

在后面的话，作者说我们会去介绍基于这样的一个本体，怎么去做一些实战：比如从需求分析，然后再到相关的设计，再到相关的任务的拆解等等。

> **思考一下｜"强制力"的层次，决定了 agent 能被信任到什么程度**
>
> 这一段把约束按强度排了序：Schema 必填最强，关系基数与拓扑校验次之，函数与动作可以拦住流程，而提示词最弱。这个排序背后的意思是——越靠近"机器可判定"的规则，越不依赖模型的自觉；越依赖提示词，越容易在长链路里失效。
>
> **可以追问**：在一套真实系统里，哪些规则值得从提示词升级成 Schema 或函数，判断的依据应该是"这条规则违反后的代价"，还是"这条规则被违反的频率"？
>
> **可延展方向**：可以把团队现有的代码规范、评审清单、发布检查项做一次分层盘点，标出每一条当前处在哪一层强制力上，这会直接暴露哪些"写了但拦不住"的规则。

### 实战总览：一个需求如何从意图走到代码

基于这样的一个本体，作者接下来介绍怎么做一些实战，比如从需求分析、再到相关的设计、再到相关的任务的拆解等等。

他说，在这个过程里面，比如我们使用 agent，我们应该给它什么内容、怎么去读；这些指令读到之后，怎么让 agent 一步一步地比如沿着图的拓扑关系去加载相关的制品——比如先读制品的摘要信息，然后再读制品的详细信息；包括拿到这些制品的拓扑关系之后，它之间怎么去做推理、怎么做完备性的校验；包括它上面还有一些强制性的约束，比如刚才讲的 function、action 等等。

这些是怎么去执行的，作者说前面我们讲到怎么把一个流程中相关的制品、或者从需求到设计，然后到任务拆解，以及到编码实现的语义跨度给拆解掉；但是在介绍本体的时候，没有说怎么把这件事做成，所以在实战里面也会把这件事情介绍清楚。

他先讲了"对一个业务领域去做本体建模的时候，大概率会有的一些维度"。

第一个维度是流程。比如在软件工程这个主体里面，我们有拓扑，或者是"拧解"（待确认），这其实就是一个典型的项目管理流程。这个流程里面我们需要把比如每个流程里面需要的制品，包括每个流程、或者说每个环节里面要遵守的一些规范——不管是我们的业务规范、技术规范，还是产品、设计、测试等等这样的一些规范——其实都要把它能够本体化。另外还有相关的一些度量。

除了这些之外，流程里面还有最重要的一些东西，就是我们在流程里面的一些工作方法。举例来讲，我们在做需求分析的时候，会比如用 User Story，或者用什么"规划文字"（待确认）这样的一些语法结构，那这个其实就是它的一些工作方法。包括我们在做相关设计的时候，需要先做概要设计、再做详细设计，那详细设计里面比如要包含的一些制品之间的关联关系，其实就是流程的一些重要的组成部分。

像这些，我们在这个经典的模式里面就变成说，我要把它做成一些 skill。那这些 skill 怎么渐进地加载到这个 agent 的上下文里面去？而如果我要把这个东西变成一个本体的话，本体里面它应该是一些具体的 instance，就是实例，以及实例与实例之间的关联关系。那我怎么检索到、怎么用到？比如基于 spec id 做了这样一个本体，那我要用到 Specify 这个命令的时候，我怎么让它检索到 Specify 这个命令，并且能够加载到这个 agent 的上下文？作者说，其实这些都是我们要去解决的一些工程上的问题。

另外，我们按照整个软件生命周期来讲，就像刚才讲的，比如我们在做需求的这个阶段，我们如何去根据我们的意图找到相关的 skill 也好、或者是指令也好；那这些指令会驱动这个 agent，让我们来把相关的比如 User Story、功能需求（functional requirement），包括设计的 ADR，还有这个 contract，就是一些接口协议，然后还有比如这个测试用例，包括再把实现等等这样的一些制品驱动出来。作者说，这个其实也是我们刚才讲的，怎么把这个语义的跨度逐步降低，然后也应对了刚才提到的：如何把这些不管是指令还是制品，稳定地、且按照一定的顺序加载到这个 agent 的上下文里面去。

作者强调，这其实就挑战我们的一个本体建模——你做得好的话效果好，或者说效果不好，最重要的一个点就在这里。

接下来他介绍他们已经做过的一个本体建模大概是什么样子。整个语义建模是基于一个 Spec 的，我们可以看到它这里面已经非常庞大了，已经有大概 70 个这样的 class，还有若干的这个关系。

他说，我们大概看一下有了一些 class，图上其实已经能非常直观地展示出来，当然我们还可以用列表的模式来展示。这里面（原文提到了"七页"以及一个无法可靠识别的说法，待确认），大概有这七十多个 class，而且也是分了不同的子域。比如我们有代码相关的，就是一个 application；比如围绕某个（功能）建立起来的子图应该是什么样子的；还有比如 `CNCD`（待确认）的；包括还有一些执行日志，就是我们要采集它的整个执行过程。还有比如基于一个 feature 为中心，它的一个制品的拓扑图是什么样子等等。作者说，这边我们大概也有不少，一共有 23 个这样的拓扑子图。

回到 class 的整体，我们还会看到比如还有各种 relation，其实也是在这边。这就是我们已经做过的一个本体建模。

作者说，这个时候我们可以按照刚才说的：这里面整个软件生命周期里面会有需求、设计等等这样的一些本体的 class，还有关系。那接下来，我们可以先从制品和规范入手，让大家看一下怎么去操作这样一个本体。

### 演示（一）：接入 MCP，读本体、看 guide 与 command

进入到这个本体之后，它会去读相关的：比如它去罗列了所有的本体有哪些；然后找到 AI Coding 的这个本体之后，它会去拿这个本体的详情。当然这个工具它是把本体的详情马上直接保存在了一个文件里，这就不管了——不同的工具它的处理方式不太一样。然后这个地方，因为它是 opencode，它就委派了一个 subagent 去读。这个本体上有……因为我们有一个 guide 的字段，作者说给大家看一下我们这个本体上的。

那剩下的、其他的应该就散落在比如我们本体里面相关的这些所谓的 command 里。作者带大家看了一下相关的 command instance：比如我们有去生成代码图谱的这样的一个指令，然后有 plan 指令。打开看一下，这个 plan 指令就显示在这边。每一个 command 其实都可以认为是这个 skill 里面的一个技能。像这些，我们还是希望说，能不能把 guide 里面的引导区那种内容减少，其他的都分配到其他的 command 里面去——这是一种本体建模的方式，然而也还有其他的一些方式。

作者说，回到这个地方，这个肯定要花一些时间，你看它还是在跑。因为刚才给大家看到的就是 guide 里面的内容。再回到这个本体的 guide 里面，它有些内容是需要引导我们的，比如它里面的相关的 command 或者是什么之类的，这里面有一些约束；还有一些比如铁律——铁律是什么样子、有几条铁律，那些的比较多，这个肯定不是特别好。另外还有比如有一些门禁的检查，比如存在性检查等等。

这些门禁其实后面我们也是做了的，就是用比如 flow，也就是形式化的方式，来去检查，尤其是比如关键关系——前面也讲到了，我有很多关键关系其实没必要用语义推理去做，这个我们也会慢慢全都把它用 flow 化。在这里面其实就只要去介绍：假如这个地方我们用 flow 化了，里面这个其实就变成什么呢？好，我这边是有门禁检查的；那门禁检查的时候，请读取这个比如 workflow，看有哪些 workflow。

而 workflow 上面我们又会有相关的摘要信息。它类似地，那个 workflow 出来的时候只拿到了摘要信息，就跟我们去读一个 SDK（原文作 `sdl`，待确认）的时候，你肯定先看到的是它的元数据，就是这样子。然后你拿到那个 workflow 之后，workflow 还有一个详细的描述，另外它还有一个它自己的拓扑关系。那这个时候，那个 workflow 其实就不用我们在这儿去写这个长篇大论了。

好，我们再看一下它——刚才说的，已经之前（跑）完了。那这个时候我们可以去展示什么呢？第一，我们想知道这些流程有哪些，对吧？我们可以来问一下，比如说：我们现在本期中一共有多少个 command，各有什么用途，之间的依赖关系是怎样的，有哪些文件，如何执行这些文件。

作者特别说明：介绍给我，不需要实际（执行），我们只是让它来介绍一下、让它来分析一下。我们看一下它会怎么去处理这件事情。

那我们再回到这个 `PVT`（待确认）界面。这里面我们会看到，比如有这个门禁，然后有前置条件；还有比如我们 command 之间的依赖关系，它有 41 条什么之类的。像这些，然后至今比如说现在它说有这个 Spec 大概 197 个——当然因为我们这个是在不停地迭代，所以这个数据可能已经是比较老的、可能要过时；包括规范，规范可能会相对稳定一些，因为规范增加的不是特别多；度量，然后可以每次执行完，比如一个 Spec 从开始做 Spec（也就是做需求分析），然后到编码完成，然后做完这个归档之后，像这些度量的指标也都会发生一些变化。

我们回到"它现在一共有多少 command"这个问题。你看它这个地方直接就是 `list class`，它会去找这个（本体的类清单），把所有的（class）读到之后，它就能找到 command 的 class；然后它后面再会根据 command 的 class 去找相关的 instance；找到相关的 instance 之后，其实它就可以把这个 instance 之间的关系也读出来。你看这个地方就是（读到的）command。当然这个地方它还是执行一个脚本，去把这个数据读出来；而这个地方其实调了一个 MCP 工具，这个 MCP 工具其实它是把这个本体里面所有的 class、还有 class 之间的一个 relation 读出来。

回到这套本体的系统，选择刚才给大家看的那个地方，比如在 instance 里面是有这个 command 的：command 里面我们这个地方一共有 25 个。有的是想生成这个测试用例的，还有这个是做状态检查的，就是针对制品；另外这个比如说录入缺陷的时候，因为我们对缺陷的时候也是有一定的录入的规范。当然这个后面其实我们是可以把它弱化的。

### 演示（二）：instance 检索、拓扑子图，与从需求到任务的链路

接下来作者就沿着缺陷（defect）这个例子往下讲。他说，我们找一个 class 打开，比如打开这个 class 来看一下：这 class 上面有这样的一些字段，这些字段好像有点问题——比如它的内容是什么，然后是 required，然后它的严重性，比如还有一些其他的字段。

还有比如根因（原文作"根音区"）等等这些。这几个字段可能已经被删除了，还有其他的一些比如 `呼卡`（待确认）等等，我们现在还没有去把它充分利用一下。作者说，其实像缺陷，如果说这个字段管理得非常明确的时候，它本身就是说明书了——就不需要再写一个说"如何去录入这个缺陷"的这样的一个 command 或者 skill 来指导这件事情。也就是说，能不能把这个语义、或者制品本身就做成规范本身？作者觉得这件事也是本体的一个比较好的地方。

再来看这个地方，你看它已经读到了：首先它把所有的 class 拉过来，把语义层其实都找到了；另外它会根据这个 class ID——这个 class ID 406 其实就是 command 那个——就把所有相关的实体搜索出来；实体搜索出来之后，它又根据实体去找了这个 instance。

然后就是拓扑关系，也就是 `getInstantPology`（待确认）这样一个调用的关系，把这些关系找到之后，其实它又把整个 instance 的 detail 就已经能拿到了。拿到之后，你看它就说：比如我这边有 specify、plan 这样的一些，这个是流水线、就是流程相关的；然后还有一些辅助命令，比如做 reflect、做反思，做 `check and paste`（待确认），又注入缺陷的什么什么之类的。那关系之间的依赖基本上是这样。

作者说，好，那我们可以去问一下，比如哪些 command 是相关的。还有一个就是刚才我给大家介绍的时候说大概有哪些制品，那我们看一下有哪些 class 是跟制品（the artifact）相关的，帮我罗列并分析。

再比如，Spec 这个 class 目前有多少个 instance？我们可以看一下。刚才说这个 instance，我们可以按这个来做一下检索：比如我这边有一个 Spec，选用 Spec 这边的（原文此处作"技术"，语义不清，待确认），然后是 207 个。我们可以让它去看一下。另外我们也去让它查一下，比如我现在跟某一个特性相关的一个 Spec 会是什么样，看它能不能找到。

作者补充说，目前我们去做这些 instance 的检索，基本上就是使用这个关键字，还没有用特别好的、比如用语义来去做相关的检索。当然技术上已经支持了，那后面我们去调这个语义检索的时候会怎么做呢？举例来讲，我要去搜索一个 Spec 的时候，其实那个 instance 就是某一个 Spec 的 instance；最好是我让它根据我给它输入的这个语义，让它生成一个可能的这样的一个 Spec 的 instance，然后再对这个 instance 做一个（向量）化，然后再到这个（向量库，原文作"相量飞铺"，待确认）里面去做检索。那这个时候拿到的其实就会更好，因为它会更接近一些。

另外就是做检索，除了我们可以搜索 instance 之外，其实你看我们这边还有定义了各种拓扑子图。举个例子来讲，比如"发布图谱"这样一个拓扑子图：比如我有某一个 project，project 下面会有一些 release plan，然后它有一个某一次具体的 release，那这个 release plan 里面比如有一些里程碑；另外它肯定发布是跟一些 feature 相关的，那些 feature 肯定是某一个 Spec——就是我 release 的是某一个 Spec；然后那一个 release 里面可能会有多个部署，比如部署前端、部署后端。但其实像这样的一次发布，我完全可以：比如我找到了某一个 Spec，这个 Spec 然后说它有哪些 release，根据那些 release 其实又可以把这个图谱搜索出来。当然这个图谱它比较特殊，它里面就有制品，也有流程相关的一些记录。

有的时候其实我们就是完全搜比如 Spec 跟 Plan 这两个 class，我就只是想在这里面去做检索，看这两个 class 就够形成一个小小的拓扑子图；根据这样一个拓扑结构，我能不能去搜索？所以我们就决定了说，我要定义多少个拓扑子图、这些拓扑子图我要不要把这个向量化的数据铺进去、也就是放到向量库里——这也是我们的一些决策。作者说，这其实是一些业务上的决策，不是工具、也不是流程上的一些决策。基本使用就是这样子。

作者继续说，我们继续讲这个（本体视图）了，后续我们也会讲规范、度量，其实都是能去看得到的。另外也刚才讲了，我给你拿一个例子：比如我们找一个需求，然后去看它下面的 User Story，包括它的功能需求，其实我们都是可以去查的；然后另外包括它的设计等等这些东西，都是可以找到一条真实的链路。

大概是这样：比如这个地方我们有一个 feature，叫"海水引擎编排"（待确认），就是这个。在这里我们可以给大家看一下这个 feature 实现出来大概什么样子。其实就这边，然后有很多的 flow；这些 flow 里面，其实我们可以去把这个 function——我们 function 在这边是有的——我们可以给大家看一下。比如 function 里面它就会有相关的一些描述，另外比如它有接收的参数，还有它的执行脚本。

以及它可能可以在这个地方做一些执行，包括还有它的一些测试用例，也会维护在这边，比如它的执行结果是什么样子。这是 function，那 flow 大概是什么样？就变成这样：刚才我们给大家打开，大家能看到其实它的一个 DAG，就是图，然后它也可以去做这个 dry run，那我们可以执行一下，它的一些运行结果也会展示在这边。这就是一个 workflow。

作者说，刚才给大家说的其实就是这个了：那我能不能去做这个编排引擎？相当于这个 workflow 怎么去执行？它里面比如 User Story 有三个，function 里面功能性需求有 11 个，包括在设计、实现，还有验证等等；然后这里面一共比如做了 13 次执行，有 10 个门禁——这 10 个门禁部署两次，一次是在这个开发环境，另外一次是我们到了这个生产环境。大概是这样一个策略。

这个地方又是另外一个视角，就是我们把一个需求展开看一下。比如这个需求有 4 个 User Story，然后 7 个功能性需求，还有 4 个非功能性需求。但这里面，比如 User Story 这 4 个 User Story 里面有多少个验证点，还有 7 个什么之类的，就是举个例子给他看一下。另外就是我们打开 User Story 的时候，我们发现它这些字段其实都是结构化的，而且比如有些是必填、有些是非必填等等，甚至上面还有 Level、上面带这个枚举值，像这样；而且还有一些关联关系等等。

在后面，其实就面临一些双向追溯的问题。例如我们正常是把一个需求，从这个需求的分析、澄清，然后再到设计，然后再到实现，然后再到测试，基本上这是我们的一个主流程。但事实上我们在整个软件工程中，还有一些其他流程：比如我现在有一个线上的 bug 需要紧急修复，来不及去做什么需求设计等等，就是快速修复完之后，但是我这个时候代码产生了变化，那么能不能把这些变化反向地传播到其他的制品里？

> **思考一下｜"检索的入口"决定了图谱能回答哪些问题**

### 协作机制与扩展方向：把 instance 当黑板，把纪律本体化

最后这一块，作者跟大家讲了一些协作机制。他说，这个其实不属于本体，但他觉得：既然我们把 AI Coding 用本体来管理起来了，那我们的协作模式是不是也可以围绕本体来做？

他的设想是：我们的协作模式能不能把这个实例当成一个黑板？就是我们所有的比如这些交互，其实都是围绕 instance 来做的。比如我现在有一个 Spec，那我们基于这个 Spec 做一些备注；那我们做了这些备注之后，比如一个 agent 也好、人也好，都能够看到这个备注。人可能说打开系统看到，或者说通过即时通讯工具——比如 IM 工具，比如飞书也好、`婷婷`（待确认）也好——我能看到是谁对某一个需求做了一个备注。

那如果这个备注需要去触发一个 agent 去做一些处理，或者说触发一个小 agent 去做一些处理，比如有这个需求分析的 agent、有这个基础方案设计的 agent，而且它能够实时看到整个协作的过程，作者觉得这个也是衍生的一些功能性需求。

除了这个之外，还有一些衍生的。比如我们能不能把一些流程的东西也做成纪律？举例来说，我们在发布到预生产环境之前，必须要发布到开发环境；那开发环境发布完成之后，我们再发布到预生产，然后再到生产环境，而且生产环境的时候我们需要人的一个审批。那我们是不是在 agent 去执行这些的时候，都可以触发相关的一些动作？就变成了说，其实这些纪律我们可以把它本体化掉。

那未来可能要做的一些扩展是什么呢？作者说，我们是想办法做成比如叫"运筹运营运维一体化"（原文作"运筹运萎"，待确认）这样的东西。运筹大概什么概念？就是说我们上面会有一些所谓的业务指标。

这些业务指标可能就是有一些波动，然后这些波动是因为什么原因带来的？比如可能是一个业务问题，还是一个技术问题？如果是技术问题的时候，是代码的问题、还是配置的问题、还是基础设施的问题？其实就可以从这个大目标，拆到技术指标、或者说拆到一个小业务指标，然后拆到某一个业务链路，然后拆到业务链路下面的应用，应用下面的代码、或者配置、或是基础设施，我们都可以一步一步往下去做。

另外还有比如一些影响的分析。举例来说，我今天对我一个接口协议做了升级改造，他的影响范围是什么？以前可能就得说我们找相关的人，我知道这个影响到谁，所以我要跟他去沟通一下。但今天我们把所有的代码仓库、包括需求等等这些东西都做成了图谱，其实我改了那个图谱里面某一个 instance 的时候，那影响范围其实就可以通过图谱计算出来。那这个图谱上，他比如某一个应用，他肯定会有相关的负责人，那这时候他就应该能收到一条消息。

另外比如还有一些容量的规划。举例来说，我们经常会遇到的问题就是：假如说我现在这个 TPS 然后 10 倍了，那我这个相关的一些应用、或者是基础设施容量应该升级成什么样？容量升级完之后，哪些地方可能还是瓶颈，要怎么去做规划改造？像这样的一些场景。

另外就是可以把更多的东西做一些本体化。刚才我们也给大家介绍了比如某一样东西怎么本体化的。当然我们也可以把 `CPU`、`PRO`、`BMA`、`ADLC` 等等（以上缩写的识别存疑，待确认）这些比较优秀的工作流，都可以把它做一些本体化。当然我们刚才也看到一个，我们可以做一个就是用来建本体的、再一个本体。作者说，这些其实都是我们可以去做的一些事情。

"片子的内容基本上是这些"（原文如此），但是我们还是需要回过头来再给大家去演示一下具体的操作。好，回到这个地方，我们会看到：我们来到"有哪些 class 是制品相关的"，把它列出来然后并分析。这个地方比如它会说……另外我还让它去查了一下。

> **思考一下｜把协作搬进图谱，会不会反过来改变流程本身**
>
> 作者把"instance 当黑板"讲成一种协作机制：备注挂在制品上、人和 agent 共享同一个对象、消息按负责人自动触达。这个设想的价值在于让上下文不再散落在聊天记录里；但它的代价也很直接——协作一旦长在图谱上，流程的改动就不再只是改一张流程图，而是要同时改数据、规则和触达方式。

> **可延展方向**：可以把组织里现有的"口头纪律"逐条列出来，评估哪些适合固化成门禁、哪些必须保留人的临时裁量权，这份清单本身就能说明一个团队的工程成熟度分布在哪里。

## 综合解读

**作者的论点链。** 视频作者的论证是一条自上而下的链：软件生命周期管理里长期存在决策不落库、知识随人走、文档落后于代码、测试覆盖度说不清等问题，这些问题在整个生命周期里反复出现；把它们抽象之后剩下四个变量——意图模糊、系统复杂性、认知局限与现实不确定性。作者用数学领域做了一次反证：这四个变量在数学里几乎都被消解了，但 AI 在数学上也没有猛进，于是他判断真正的拦路虎是另外两个——语义跨度，以及能否形式化验证。往下，作者把 AI agent 的现状概括为"执行强、判断弱"，并给出"数据—信息—知识—判断"四层框架来解释判断力为什么难补；再往下，他用 Working Backwards 把"发布到线上的系统"逐层回退成任务、设计、功能清单、User Story，主张面向制品而不是面向角色，理由是制品可标准化、角色不稳定。拆细之后又出现新问题：任务变多、成功率连乘。于是有了最后一段主张——用符号主义补齐可查、可校验、可强制三件事，用本体（类、关系、实例、规则）把这套东西固化下来，让制品能沿着拓扑被稳定加载、让校验由机器执行、让流程被门禁拦住，从而把单步成功率抬到足够高。

**隐含前提。** 这段口播里有几个没有被明确论证、但整条链依赖它们的前提。第一，作者假设"语义跨度可以被均匀拆解"，也就是说从意图到代码之间存在一条可以被稳定切分的中间层；但现实中的需求并不总是可以均匀切分，有些需求的价值恰恰在于跨层重构，硬拆可能把问题变成更多的小问题。第二，作者假设"面向制品比面向角色更可标准化"，这在有成熟工程文化的团队里成立，但在制品本身还没定型的团队里，过早固化制品格式可能反而推高成本。第三，作者假设"成功率可以相乘"，这隐含了每一步相互独立；而在真实研发里，后一步的失败往往和上一步强相关（比如规范本身就有歧义），连乘模型可能高估或低估风险。这些前提在口播中是以"我认为""或许"的方式给出的，读者不宜直接当作结论。

**关于本体价值的定位（本文分析）。** 视频作者在这段口播里主张的，并不是"再多一个文档工具"，而是一个判断：把约束从提示词搬到机器可判定的层次上。他给出的层次排序（Schema 必填 → 关系基数与拓扑 → 函数与动作 → 提示词）本身比任何具体实现都更有迁移价值，因为它回答了一个很实际的问题——为什么很多团队写了满满一页规范，agent 还是照犯不误：因为规范停留在最弱的那一层。另一个值得注意的点是"制品即说明书"：当缺陷这类对象的字段被定义得足够完整时，指导录入的 skill 就变得多余。这个观察在很多知识管理场景里也成立：结构定义得越清楚，说明文档就越没有必要。

**待外部核验的事实。** 口播中出现的具体数字和产品事实，都属于作者单方面陈述，需要外部核验：包括但不限于"约 70 个 class""23 个拓扑子图""25 个 command""41 条 command 依赖""Spec 197 个 / 207 个""规范 154 条 / 151 条""任务 45 个、测试用例 34 个、AC 16 个、功能需求 16 个、非功能需求 6 个、澄清问题 29 个""13 次执行、10 个门禁""OpenRouter 账户余额 1000 美金"等等；以及演示中提到的具体工具与接口（opencode、`DeepSeq WastePro`（待确认）、`getInstantPology`（待确认）、`Cali Instance Detail`（待确认）、`YouTube` 关系（待确认）等）。作者本人也说明，本体在不停迭代，部分数据"可能已经比较老、可能要过时"。此外，关于"国产开源模型与闭源 SOTA 模型差距不大"的判断，属于作者基于自身使用经验的观察，不是可复现的评测结论。

**边界与反例。** 作者反复用"语义跨度小"作为 agent 可靠的依据，但演示中也有几处反例性质的细节：一是检索目前仍以关键字为主，作者承认还没用上语义检索；二是拓扑检索会遇到大量链接的"黑洞"节点，需要额外的检测能力，说明图一旦长大，遍历本身也会成为问题；三是渲染和生成过程"时间有点慢"，作者多次等待，说明这套流程的交互成本并不为零。这些都提示：本体带来的稳定性，是用额外的建模与维护成本换来的，它对小团队、小系统是否划算，口播里没有给出判断依据。

**可迁移的素材。** 抛开本体这个具体载体，视频里有几件可以直接搬走的东西：一是"四个抽象问题"作为需求评审时的检查清单（意图清不清楚、复杂度在哪、谁的经验在起作用、哪些只能在线上才知道）；二是"数据—信息—知识—判断"四层，用来判断一件事能不能交给机器；三是"面向制品而非角色"的拆解原则；四是"报错要能引导修复"这一条——把失败信息设计成下一步的输入，是 loop 能不能自愈的前提；五是把纪律（发布必须从开发环境开始、生产必须人工审批）显式化成可执行的约束，而不是停留在口头约定。

**一句话收束。** 视频作者在这段口播中给出的，是一个把"AI Coding 的可靠性"从模型能力问题重新定义为"语义跨度与约束强度问题"的框架；这个框架成立与否，取决于本体建模的投入能否被频繁复用的任务摊薄，而这恰恰是每一位读者需要在自己的业务领域里核验的第一件事。
