## 口播文章

### 上半场回顾：三种检索、Semantica 与一个最小 MVP

其实对于这个下半场来说，我们先快速地回顾一下，上半场我们做的是什么事情。我们给大家介绍了一下关于 Ontology 它不同的检索方式，然后如何基于我们构建的 Ontology 业务模型，针对特定的对象或者是关系，来检索出它相关的信息。然后也给大家介绍了一下 Semantica 这个项目：它作为本体和图知识检索的开源项目，其实提供了很多关于业务建模，以及与 Agent 或者 RAG 协同的快捷接口形式。

但是 Semantica 这个项目，如果大家了解过的话，你可以去看一下它的源码，各个阶段相当于把很多功能链路全都已经实现了，但是它实现得确实是比较粗糙。大家如果想直接使用这个项目，通过调一些接口，在你做项目的这个过程中直接去进行落地，肯定是不行的，你需要去做一些精细化的优化。

这里面就涉及到大家要有自己的技术理解和判断了。然后我们也是基于电商的客服场景，通过用户视角以及客服的视角，来真正让大家看一下：当 Agent 和你的本体业务模型，通过 function calling、或者是 Agent skills、或者是 sub agents 等等不同的形式来构建连接，连接到以后，它们的一个执行链路到底是什么样的。

> **思考一下｜框架把链路实现了，判断力留给谁**
>
> 作者给 Semantica 的评价很具体：功能链路是齐的，但实现是糙的，"调接口就能落地"这条捷径被他自己否掉了。这等于说，开源框架能替你省掉搭骨架的时间，但省不掉"哪一步要精细化、精细化到什么程度"的判断，而这部分恰恰是交付方要自己负责的。
>
> **可以追问**：一个开源框架"实现得比较粗糙"，你是选择在它的链路上做精细化优化，还是绕开它自己重写关键环节？判断依据是什么？
>
> **可延展方向**：把"哪些环节必须自己做精细化"整理成一张框架选型清单，用于评估任何开源 AI 框架的复用边界。

这个就是我们通过一个真实的业务体系，帮助大家快速地跑完了一个最小的 MVP。所以我们这里可以回顾一下：当一个客户发出了这样一个问题，在我们刚才构建的这样一个架构中，它完成的一个处理流程——从业务角度上来看，肯定又是用户提出的这个问题，然后我们去发给 Agent，让 Agent 通过 tool calling 的这个方式去连接到我们本体的这样一个业务模型，找到用户提出问题的这样一个核心的对象。

然后我们基于底层的 Semantica 它提供的这样一个本体业务模型的检索方法——其实也就是向量模型加图扩展的这样一个搜索的算法——来去查询到与输入的这个本体相关联的这样一些对象、属性或者是关联的信息，以及具体的这样一个事实的依据，然后返回对应的一个检索规范，最后生成最终的一个答案与回答，由客服发给最终的这个用户。

所以它就能够去省去客服在接收到用户的这个问题以后，然后他自己去查不同的系统、然后匹配对应的这个订单、然后自己再组织对话发给客户，在这样一个又慢又容易出错的这样一个链路的流程。所以我们也是快速地实现了这样的一个 MVP，那么这里面也是给大家去介绍了一下我们整个的这样一个链路。那么接下来我们再去给大家说明一下：如果我们在这样的一个基础上，为什么需要去结合 RAG 的这样一个信息来去进行构建呢？

### 从演示里的「核对结果明细」说起：为什么要接 RAG

就是大家其实可以在我们这里面的业务流程上应该是能够看到：它在构建的这个过程中有一个这个阶段，叫做——大家看，这里面有一个核对的结果明细。这次采用的这个规范原文是：只有确认包裹订单、所有的包裹均有可靠签收，才能够配送，才能够判定为整单的「送棋」（待确认）。物流确实不能直接判定。然后这里面会有一个订单「纽约」口径「PGF」（待确认）的这样一个页码。

所以它这里面相当于——哎，我好像是通过了一些外部的引入——这个肯定不是大家理解到的本体的这样一个业务模型，这是「夫婦」（待确认）的这样一个结构：通过对象、通过这个属性、通过这个 link 来去构建之间的关系；而是它更像是一个完整的这样一个文件。那么这个过程其实它是基于 RAG 来去进行的一个增强。

那么 RAG 和本体的业务模型，它们之间的关系以及在这个 agent 链路过程中它们到底有什么区别呢？这个就是我们在下半场要核心来给大家去进行探讨的这样一个点。

> **思考一下｜一个结论要带出处，系统里就得留一条证据路径**
>
> 演示界面上那段"只有确认包裹订单、所有包裹均有可靠签收才能判定整单"的规范原文，加上一个指向具体文件的页码，说明这条回答不是靠对象和关系推出来的，而是从一份完整文件里取回来的。作者由此把 RAG 的定位讲清楚了：它补的不是事实本身，而是事实的出处。
>
> **可以追问**：如果一条业务规则既有本体里的结构化约束、又有文档里的原文依据，两者版本不一致时，系统应该以哪一边为准？
>
> **可延展方向**：给每条自动结论设计一个"最小证据包"（结论、引用的规范原文、文件位置、生效版本），让可追溯性变成产品能力而不是排查手段。

### 本体给事实，RAG 给依据：两者到底怎么分工

我们首先来看一下：对于这个检索增强，它其实就是为了让你的 agent 在去获取到对应的这个上下文的时候，能够获得对应的事实和依据。举个例子，当用户提出的这个问题，首先它是可以去检索到你上面的这样一个实体、上面的这样一个本体的业务模型。这里面主要存储的就是你从不同的散落的文档里面，根据你定义的这样一个 Schema 然后抽取出来的对象，然后去定义对象和对象之间它们的一个 link、它们这样一个关系，然后你能够查询出这样一个事实。

但是其实每一个对象它可能是来源于某一个文件，它可能是来源于某一个链路，它也有额外的非结构化的这样一个信息是存在的。所以在本体和 agent 再去构建业务模型的这个过程中，如果我们想要去找到它对应的这样一个证据的路径——也就是它原本的这个片段、原本的这个出处——那么我们往往会结合 RAG 来去共同构成它再去进行回复的这样一个上下文。

所以这里面也就有大家看到的、我们在这里面构建的这条链路：你能够通过它的中间过程看到，它不仅仅是会查询我们的这种本体来拿到我们实体之间的关系，它还可以去检索到我们对应的 RAG 的链路的流程，来去确定一下基于本体查询到的这个事实依据、它返回回来这个结论，到底我们有没有一些文件来去制定它的这样一个业务规则是符合某样的一种情况。所以这个叫做 RAG 和本体它在 Agent 的协同过程中，它们之间的一个区别与联系。

所以这里面大家可能就会比较疑惑了：这个本体它也提供事实依据，那么 RAG 它也提供事实依据，它们之间到底是什么关系？我到底在什么情况下、在什么样的一个业务需求下，我需要去做 RAG？什么样的情况下我需要去做本体的建模？我又在什么样的情况下需要它们两个都去进行构建？

非常好理解，就是我们要去理解：对于 Agent 来说，它是一个组织执行的（编排者），所以它是通过 tool calling、它是通过 skills、它是通过 MCP 的这种不同的形式，来去接入像本体的这样一个接口、本体检索的这样一个接口，去接入 RAG 的这样一个接口，然后把本体和 RAG 检索出来的信息去把它组织成一个上下文来去进行一个回答。

所以这里面就意味着，我们去看一下本体它和 RAG 它们两个之间的作用的关系，你只要了解这个，你就知道在什么情况下是融合着使用、还是单独地去进行使用。这里面大家有个非常大的误区：可能就是我之前确实有很多散落的文档——

> **思考一下｜Agent 是编排者，本体和 RAG 是两种供给**
>
> 作者把三者摆成一个清晰的结构：Agent 不产生事实，它只负责把 tool calling、skills、MCP 这些接入方式拼起来，把本体检索和 RAG 检索的结果组织成上下文再回答。这样一来，"要不要做 RAG、要不要做本体"就不是二选一的技术题，而是"这个业务需要哪种证据"的需求题。
>
> **可以追问**：如果 Agent 同时接入了本体接口和 RAG 接口，谁来负责决定这一次该调哪一个、或者两个都调？这个决策写在哪里？
>
> **可延展方向**：把"证据类型"当作架构分层依据——确定型事实走本体、文档型依据走 RAG、混合型走编排——再据此设计接口的职责边界。

### 本体是业务约束，知识图谱只是它的一种展示形式

那么散落的文档是可以做 RAG 的，然后也可以做本体，但是它们两个之间的一个区别和联系就是在于：对于本体论来说，它其实不仅仅是大家看到的这样一个知识图谱，那么知识图谱只是本体论它展示的一种形式。它的一个核心定义就是：当我处在某一个业务领域范围内，我是可以通过本体它的这种定义，比如我明确地要去约束——在你的这个领域内，我需要有什么样的一个对象、我需要有什么样一个概念、我需要有什么属性、需要有什么样的关系，以及我需要有什么样的一个业务规则。

那么大家可以理解成这个它是底层的一个业务的约束，或者你可以把它简单理解成它一种规范。而知识图谱只不过是基于散落的这个文件，把它抽取成了类似于 GraphRAG 管理的这个形式，而底层它们遵循的这个约定，就是我们在本体定义好的这样一个业务的约定。

那么既然我们可以去做知识图谱，是不是可以也去做传统的 RAG？肯定是可以的。那比如对于传统的 RAG，那么我们无非就是在你去进行抽取或者是数据规范化的时候，去按你领域里面定义的概念、规则、业务逻辑来去进行抽取；在问答的时候，我要和你在本体里面定义的这些术语来去进行对齐，然后检测的这个过程中，和你的这个类型和约束去进行一个匹配，最后把它组织成上下文。

对于这个传统的 RAG 来说也是一样，对于这个知识图谱其实都是一样。你就可以理解成：那么 RAG 它是一个完整的实现方案，GraphRAG 它也是一个完整的实现方案，但是它们共同遵循的这个约定，就是你在本体论里面定义好的、关于你当前这个领域或者是你业务领域的这样一个知识体，或者大家简单地理解成业务的这样一个规范。

> **思考一下｜把本体当作"约束层"，图谱和 RAG 就都成了实现选择**
>
> 这一段是本集最有复用价值的判断：本体的核心定义不是那张图，而是"在这个领域里必须有哪些对象、概念、属性、关系和业务规则"；知识图谱、传统 RAG、GraphRAG 都是遵循这套约定的实现方式。约束层一旦独立出来，选型问题就从"用哪种技术"变成"用哪种技术来满足同一套约束"。
>
> **可以追问**：如果一个团队只做了知识图谱、从没写下过领域约束，它的"本体"到底存在于哪里？是在代码里、在文档里，还是只在人的脑子里？
>
> **可延展方向**：把领域约束单独维护成一份可评审、可版本化的规范文件，再让各种检索实现去对齐它，避免约束散落在每条抽取脚本里。

### 三种实现路径：传统 RAG、按本体约束抽取、向量与图融合

这里面我们假设对于这个传统 RAG：大家都知道它对于这个文档先去做解析——PDF 就通过 PDF 的解析器解析，CSV 就通过 CSV 的解析——然后我把它去进行一个切分，切分完转化成 embedding 的向量，存到向量数据库里面。在进行检索的时候，从向量数据库里面找到最相关的语义相似度——也就是计算它们之间的相似度（ASR 作「预先相度」）——找到最相关的语义，然后把它填充到上下文中，作为 AI 模型的上下文来去回答最后的这个问题。那么这个是传统 RAG。

那么当我们把它去做好了这样一个本体以后，那么是不是我们再去解析、进行切分的时候，我们让大模型按照我们构建本体的这样一个约定或者是规范，来去抽取它里面的这个实体和关系，去定位到它的一个原文的片段？然后对于这个原文的片段，我正常还是走我原始的 embedding 的这个路线，它是完全不影响的呀。只不过我们再去进行索引或者是关联数据的时候，那么我们去遵循本体论里面我们定义好的这样一个事实的约束。同理对于知识图谱也是一样的，它们之间的这个关系和联系其实就是这样。

那么还有一种方式，就是对于这个向量检索与图辅助检索的这样一个协同。那么这里面就包括了：本体里面有很多的这样专业的这个术语，比如你金融领域的这个术语、和你这个交通领域的、你教育领域的、你的医疗领域的，他们的这个术语肯定都是不一样的，而这些都是你在本体里面需要构建的这样一个业务的规范。

那么像比较通用的这些领域，其实有一些通用的这个定义的规范，大家是可以直接去在网上获取到的，然后把它放在你的……然后你对于你公司内部、或者是你独特领域里面，也是需要由人来去逐一地去进行一个确认。所以他在去进行检索的时候，无非还是：你既然是做向量检索，那我就走我向量检索的这样一个路径；那么图检索呢，我还是通过我图路径搜索的这样一个方式，只不过我最后去做一个融合、或者是去重的方式，然后把它做成一个增强的这样一个上下文。

这个呢，就和我们之前所介绍的你到底是做 GraphRAG、还是做 NaiveRAG，还是说做这个融合的这样一个融合的检索流程，其实本质上都是一样的，只不过在本体加入以后，它是可以去定义它们之间共同约束的这样一个规范。这个里面也是一样的，它的这个实现的路径也是完全一样的。

所以对于这种融合，我们就可以把它的单独的这个计算的相关性，针对于某一个问题它的一个相关性，来去判断一下我到底要采取哪一个检索路径返回回来的信息，作为更有效的上下文的推理。当然这个呢，是属于相对来说比较复杂的这样一个检索的链路的流程，它也是比较适用于那种大家实际情况检索过程数据比较乱、然后数据的形式比较多、然后检索的这个场景的定义也比较广泛的这样一个情况。它可以通过这样一个方式来去进行一个构建。

> **思考一下｜融合检索是解法，也是成本**
>
> 作者把"向量走向量、图走图、最后融合去重"讲成一条通用路径，同时给了一个很实在的适用条件：数据乱、形式多、检索场景定义广泛。换句话说，融合不是默认选项，而是数据复杂度逼出来的选项——单一形态的数据集用单一路径就够了。
>
> **可以追问**：在什么样的数据条件下，融合检索带来的收益会低于它增加的延迟与调试成本？这条线你怎么测？
>
> **可延展方向**：为检索链路设计一个"够用即止"的升级判据（数据形态数量、查询类型分布、错误归因），避免架构复杂度跑在业务需求前面。

### 回到项目：让 RAG 的原文与本体对象一一映射

所以这个就是我们在接入 RAG 它的一个实现的形式。那么对于我们的这个项目来说，无非就是我们可以去看一下刚才给大家所进行的一个介绍：我们把它接入到 RAG 的这样一个方式，就是我们再去构建 RAG 的这样一个链路流程，就是遵循整个我们在前面去构建本体它共同的这样一个约束，来去针对我们本体论里面定义 Schema 对象的这样一个信息，再去进行原文抽取的这个过程中，来去和它建立一一的映射。

也就是你对象来源于哪一个原始的文本、你的这个类型来源于哪一个文本、或者是你某些属性来源于哪一些文本，它就可以在你查询到相关的这样一个信息之后，去把它带出来。比如出现这样一个采用的这个规范原文，它就可以正常地去检测到。它就是这样的一套流程，OK。

所以讲到这里面，大家应该对它有个大致的这样一个了解了，对吧？好。

> **思考一下｜一一映射是"可解释"的工程代价**
>
> 作者给出的落地做法很朴素：抽取时顺手记下"对象、类型、属性分别来自哪一段原文"，查询时再把出处一起带出来。这一步没有任何模型技巧，却决定了系统能不能回答"你凭什么这么说"——也决定了后面做人工审核和验收时，有没有东西可审。
>
> **可以追问**：当一份原文更新、切分粒度改变之后，已经建立好的映射要怎么维护？谁来判断旧映射是否还有效？
>
> **可延展方向**：把"来源映射"当成一等数据资产来管理（记录来源文件、版本、片段、抽取时间），为增量更新与冲突检测留出接口。

## 综合解读

**作者的论点链。** 视频作者在这一集里承接上一集的 Agent 业务集成，把话题推进到"本体事实与文档证据怎么合到一起"。他的起点是一次自评：上半场已经把本体的检索方式和 Semantica 这个开源框架讲完了，框架把很多功能链路都实现了，但实现得比较粗糙，直接调它的接口去落地是不行的，需要做精细化的优化——这就意味着交付方必须有自己的技术理解和判断。接着他用电商客服场景跑通的最小 MVP 复盘了一遍执行链路：用户提出问题 → Agent 通过 tool calling 接到本体的业务模型 → 找到问题的核心对象 → 用"向量模型加图扩展"的检索算法取回相关联的对象、属性与事实依据 → 组织上下文生成回答、由客服发回用户。这条链路省掉的，是客服"收到问题后自己查不同系统、匹配对应订单、再组织话术"那种又慢又容易出错的流程。

本集的核心问题由此提出：既然本体已经能提供事实依据，为什么还要接 RAG？作者的回答可以概括为"本体给事实，RAG 给依据的出处"。他在演示界面的「核对结果明细」里指出，那段采用的规范原文（"只有确认包裹订单、所有包裹均有可靠签收，才能够配送，才能够判定为整单……"）连同指向具体文件的页码，明显不是由对象、属性、link 构成的本体结构，而更像一份完整文件，这一部分就是基于 RAG 做的增强。他进一步解释：本体里的对象来自散落文档，但每个对象可能来自某个文件、某个链路，还带有额外的非结构化信息，所以要追到"原本的片段、原本的出处"，就得让 RAG 和本体共同构成回复的上下文。

为了回答"什么时候单独用、什么时候融合用"，作者给出一条贯穿全集的判断：Agent 是组织执行的编排者，它通过 tool calling、skills、MCP 这些不同形式去接入本体检索接口和 RAG 接口，再把两边检索出来的信息组织成上下文来回答。由此他划出了本体与 RAG 的分工前提——本体论的核心不是那张知识图谱，知识图谱只是它的一种展示形式；本体的核心定义是在某个业务领域内明确约束"需要什么对象、什么概念、什么属性、什么关系、什么业务规则"，它是底层的业务约束或者一种规范。传统 RAG 与 GraphRAG 都是完整的实现方案，只是共同遵循本体里定义好的约定：抽取与数据规范化时按领域的概念、规则、业务逻辑来抽，问答时与本体里的术语、类型和约束对齐匹配，最后组装成上下文。

收尾部分，他把这些判断落成三条实现路径与一个项目做法。传统 RAG 是解析（PDF 用 PDF 解析器、CSV 用 CSV 解析）→ 切分 → 转成 embedding 向量入库 → 检索时找最相关的语义、算相似度 → 填充进上下文交给 AI 模型回答。加入本体之后，变化只发生在抽取环节：让大模型按本体的约定抽取实体和关系、定位原文片段，embedding 路线照旧，只是在索引或关联数据时遵循本体定义好的事实约束。再复杂一层是向量检索与图辅助检索的协同，两条路径各走各的，最后做融合或去重，形成增强的上下文，作者也明确说这属于相对复杂的链路，更适合数据乱、形式多、检索场景定义广泛的场景。最后他把结论落回自家项目：构建 RAG 链路时遵循前面本体的共同约束，对 Schema 对象做原文抽取并建立一一映射——对象、类型、属性分别来自哪一份文本——这样查到相关信息时就能把出处一起带出来。

**隐含前提与边界（我的分析）。** 这条论证要成立，依赖几个作者没有展开的前提。第一，"本体是底层约束、知识图谱只是展示形式"是作者在本集口播中给出的区分口径，他用的是"简单理解成"这种表述；它与学术或工程上对 Ontology / Knowledge Graph 的常见定义是否一致，属于待外部核验的范围。第二，把结论和出处绑起来的"一一映射"，说起来只有一句话，工程上却依赖抽取质量、切分粒度和增量更新机制三件事同时成立——原文改动、切分边界移动、对象合并之后旧映射谁来维护，本集没有涉及。第三，"融合检索"的决策被描述成"单独计算相关性来判断走哪条路径"，但作者没有给出阈值、评测方法或错误归因方式，只给了适用场景的定性描述，读者很难据此判断自己的项目该不该上。第四，作者说本体和 RAG 都提供"事实依据"，但这两类依据的强度其实不同：本体给出的是建模后的确定事实，RAG 给出的是文档片段，两者冲突时以谁为准，这恰恰是带出处的系统最先会遇到的问题。第五，"通用领域的规范可以直接在网上获取"这一句也偏乐观——公开的标准与本体资源确实存在，但覆盖度、许可与可直接复用的程度差异很大，落地时通常仍要人工逐条确认，作者自己在后半句也承认公司内部或独特领域需要人逐一确认。

**待外部核验的事实。** 本集出现的具体内容均来自视频作者的单方陈述，未经独立核验：他对 Semantica"各阶段功能链路都实现了、但实现比较粗糙、直接调接口落地肯定不行"的评价属于个人判断；他所说"通用领域的定义规范可以直接在网上获取"没有给出具体来源；演示中出现的规范原文、文件页码、检索链路与「核对结果明细」界面，都是项目演示内容，实际行为应以项目源码与运行结果为准；他把本体与知识图谱区分开的定义方式，同样属于视频观点，不应直接当作结论引用。

**低置信专名与本文的处理。** 本集 ASR 有多处读音近似导致的低置信内容。本文按系列统一口径处理了可以交叉验证的部分：`Semitic` → Semantica，`Reg / REG` → RAG，`graphreg / GraphRack` → GraphRAG，`原码` → 源码，`硬设` → 映射，`合对` → 核对，`驱虫` → 去重，`相量 / 限量 / 鲜粮 / 引白领 / 项链` → 向量 / 向量数据库 / embedding，`AZ 模型` → AI 模型，`刹下转 / 上下转` → 上下文，`减缩增强` → 检索增强，`Skema` → Schema；其中 `to calling` 与 `图考领` 依据同系列 P11 口播里"function calling 或者是 tool calling"的平行表述，按 tool calling 处理。仍在正文中就地标 `待确认` 的是这几处：`夫婦`（无法还原的表述）、`送棋`（疑为"送齐／妥投"一类说法）、`纽约` 与 `PGF`（合起来疑为"履约口径 PDF"，未能确认）、`Navrack`（疑为 NaiveRAG，未能确认）；另有 `预先相度` 一处，正文按"相似度"处理并标 `待确认`。

**可迁移素材。** 对做企业 AI 交付的人来说，这一集里有几样可以搬走的东西：一是"本体＝约束层、知识图谱与各类 RAG＝实现方案"这个分层讲法，可以直接用来向业务方解释"为什么我们既要写规范又要建图"；二是那张"本体给事实、RAG 给依据"的分工表——凡是最终结论要回答"凭什么这么说"，就该把原文片段的来源一并设计进链路；三是"证据包"的最小构成（结论、规范原文、文件位置、版本），可以当作可解释性验收的检查项；四是三种实现路径的升级次序——先传统 RAG，再按本体约束抽取，最后才考虑向量与图融合——以及作者给出的上融合的前提条件（数据乱、形式多、场景广）；五是"对象／类型／属性分别来自哪段原文"的一一映射，这是把可追溯性做进数据层，而不是做进提示词的最小工程手段。
