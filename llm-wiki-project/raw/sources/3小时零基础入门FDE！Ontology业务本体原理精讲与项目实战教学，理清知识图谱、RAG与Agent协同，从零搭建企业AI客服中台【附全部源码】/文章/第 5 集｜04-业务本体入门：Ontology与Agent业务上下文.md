## 一句话摘要

视频作者在这一集里把话题从 FDE 的岗位与流程推进到它的核心技术：企业 AI 落地的关键不在于模型有多强，而在于让 Agent 拿到稳定的业务上下文；Ontology 用对象、属性、关系三个概念，把散落在订单系统、仓储系统、PDF、CSV 里的数据连成一张共同的业务模型，作为 Agent 统一的上下文查询与推理入口。

### 上半场留下的问题：FDE 为什么离不开本体

大家可以回想一下这个问题，就像我们刚才所说的，我们刚才通过一个电商订单客服处理的这个过程，就是他去查询用户的这样一个需求，需要往返各个系统之间去查相关的这个关联关系，查得比较慢，而且又容易出错。那么我们当时提出的一个核心的概念就是：我们能不能通过一个所谓的这个建模的流程，就是把我现实世界、现实的这个生产环境里面所有的这些信息，去构建出这样的一个所谓的业务模型。那么这个业务模型，只要是与他相关联的这部分内容，都可以通过类似于这种建模的这种方式，或者通过某一种方式给他去进行一个关联。这样的话大家看，如果是这样的一个模型，那么你问这个奶泡壶，他是不是可以关联到这个买家是谁？你要问这个订单位号，他是不是可以关联到这个买家是谁？

### Agent 需要的是业务上下文

而对于 Agent 来说，大家要知道，我们再去进行企业 AI 项目落地的这个过程中，核心、最最核心的就是我们需要让 Agent 知道他要处理业务的这样一个上下文。他要知道处理这样一个上下文，其实这个非常好理解，就是背景信息。比如你的这个领导给你去发布一个新的任务，他明确地告诉你：我们为什么要做这个事情，我们要做到什么样一个程度，然后我们现在有什么样一个数据，你是不是就知道接下来要怎么做了？那如果什么都不跟你说，你肯定不知道嘛。那对于 Agent 来说，他在回答一些既定的这个事实的时候，肯定也是需要一些简直的（待确认）这个知识。

还是以我们刚才做的这样一个案例，就是当我们客服想要去问我们的这个系统说：啊，某个人他的这笔咖啡机的订单送到了吗？那如果我们想要 Agent 他快速地告诉他到底现在是处于什么样的一个状态，我们是不是要告诉他：你现在这个张三问的这个订单是哪一个呀？这个订单他关联了哪些包裹呀？这个包裹里面都有哪些商品呀？这些商品他们对应的这个状态是什么呀？以及我们要确定一下，那么当主要送的这个东西已经签收了，我们就确定这个包裹已经完成了；还是说只要是这个包裹里面所有的这个赠品有一个没送到，他都没有完成呢？

对吧，就是这些信息，你只要是能够在问答的这个过程中给当（待确认）你的 aim（待确认）模型——咱们也不用说你是使用这个 gbt（待确认）模型还是使用这个 sable（待确认）模型，你哪怕使用一个千问的 3B 模型、1.5B 模型——有了这些上下文，他都能给你回答出来。所以这里面大家就知道，AI 解决落地的一个核心关键就是：你不管是做任何的 AI 的业务流程，简单是做任务问答，那么负担（待确认）一点让他自主地去驱动做一些自动化的流程，核心都是你要让 Agent 他在做每一步的时候知道上下文到底是什么。

所以这里面，怎么让这个 Agent 知道你整个的这个领域、你整个的这个公司、你整个的这个项目组里面他们的这个数据以及他们之间关联到底是什么，所以才出现了这样一个 ontology，才出现了这样一样 ontology，共同的业务模型，共同的这个业务模型。

### 共同业务模型：把不同来源的数据连成一条链路

这个共同的业务模型，他的这个思路其实非常非常简单，他其实指的就是：我不管你在外部有多少不同的这样一个系统，你有这种订单系统，里面存储的是买家、卖家的这样一个订单；你有对应的这个仓储系统，里面存储的就是你每一个包裹，他们之间的订单的关系，以及包裹的一个实际的这个属性，以及对应的这个物流去判断这个当前这个包裹和什么更新，比如你是发这个京东呀、去发顺丰呀，还是发其他的这样一个快递。

我不管你是来源于哪一样的这样一个记录，甚至是你企业里面的一些 PDF 数据、PDF 的数据，然后 CSV 的数据等等，那么我就通过 ontology 来去构建一个所谓的这个业务模型。那么这个业务模型它核心解决的就是一个事：我需要让你所有散落的、或者是分散的不同类型的这样一个数据，通过同样的一种方式，构建出一个他们之间存在着相互关联的每一条链路——这个客户是什么，他执行了什么操作，他操作的订单是什么，然后他关联的这个包裹是什么等等等等。只要是涉及到其中每一个环节，就能给他前后构建起相关的这样一个关系。这个就是 ontology 他核心要做的事情。

### Ontology 的三个核心概念：对象、属性、关系

而为了要做到这个事情呢，其实 ontology 有三个核心的这样一个概念。一个叫做 objects、对象，他指的是我们要通过一种形式，我们要构建所谓的一种对象，来去描述我们现在正在做的一些具体的事物。然后以及 properties、属性，就是这个对象有哪些特征。就举个例子，那么这个对象呢，他可以就是客户，其实就是一个对象，那么客户他可以是张三，他可以是李四，他可以是王五；那么订单呢，他可以是 1042，他可以是 1045，可以是 1046 等等，都是可以的。

那么对于这个属性呢，他其实指的就是对于这个对象来说，他都有哪些特征和状态。举个例子，那么这个客户他可能是有一个姓名，他叫做张三，他年龄多少岁，然后他的这个住址、居住地等等，这些都是属于对象里面对应的这个属性。而这个 properties 呢，尤其是这个订单，他也是可以有下单的这个时间等等相关这样一个信息。以及对应的这样一个 links、他们之间相互的这样一个关系，比如客户和订单之间，他们是下单的关系；然后订单和这个主机和奶泡壶，包括他们之间是关联的这个关系；包括了你这个主机他与物流，他们的物流就是签收和运输相关的这样一个关系。我们去构建这样的一个体系。

所以对于 ontology 核心就是，他要用 optics（待确认）以及 properties 以及 links 这三个，去把分散的这种信息去组成一个共同的业务模型，来完成给 Agent 去提供对应的一个上下文这个信息。

> **思考一下｜对象、属性、关系这三个词够用吗**
>
> 作者用三个英文词把本体拆开，好处是立刻可操作；代价是这三个词本身很朴素，真正的难点会落到"谁来决定哪些对象该被建出来"。
>
> **可以追问**：三个要素里，哪一个最容易在客户现场出问题——是对象边界划不清，属性口径不统一，还是关系类型定义不完备？
>
> **可延展方向**：找一份真实的企业数据字典，尝试只用品类名（对象）、字段（属性）、外键语义（关系）三列，把它改写成一份最小本体草案。

这里面大家可以看一下一个本体他的关系吧，可能就长这样。当然我们是基于我们刚才构建的这样一个链路，就是我们的电商的这样一个情况来去构建。比如我们这里有很多的这个客户，那么有客户张三，有客户这个礼眉（待确认），然后我们的另外一个对象呢是订单，订单 2068、订单 1042，然后还有我们对应的订单的明细，然后对应的这个商品有咖啡机呀，有奶泡壶呀、其他的。

### 从散落资料到本体链路：下半场的实战内容

所以这里面给大家去看一下我们一会儿下半场会带大家去进行实践的这样一个内容。就是首先，你看我们正常在企业里面能够去接收到的，往往其实都是一些相关的这样一个散落的资料。这里面，我们是大家可以在我们的这个助教老师那边去领取到相关的这样一个原始的文件。比如我们如果要去构建的话，他会包括了仓储系统、有很多的订单、客服中心，以及签收的回单，以及商品对应的这个物流和相关的这个业务的规范等等，PDF 也有、CSV 也有。那么这些散落的这个文件，我们直接丢给模型让它去实践，肯定是不现实的。那我们肯定就需要通过构建 Ontology 的这样一个方式，来去把它做成这样的一个链路。

大家可以看一下，这个呢就是我们今天实战环节也会带大家去实现的。这里面比如我们要做的就是，我们会定义很多的这个实体，然后以及他们之间的这个关联的关系。当我们去点其中的某一个的时候，它会关联到对应的，比如说我们极强的这个明细，他有对应的这个包裹以及订单的这个明细，那你在点这个订单，订单里面就会对应相关的这样一个商品。那这个呢，其实对应商品、订单明细等等，这些就是属于他们之间的关联的关系。然后像商品呀、订单明细呀、包裹呀，其实他们都是属于对象。而当我们把它展开以后，那么对象呢可以是有很多个。比如我们去——稍等我们来清空一下——在这当我们去点这个商品的时候，它可以就有很多的保温杯、电子枪（待确认）、烘焙指甲（待确认），其实它都是对应的这个对象，包裹包在这个商品里面。然后你点进去以后，你还能够去看到它的一个实际的相关这样一个属性，包括它的位置在哪里，然后它的一个编号是什么，它的一个商品的这个参数是什么。我不知道大家这里能不能看到啊，其实这个就是它构建的这样一个链路。

所以有了这样的一个链路，我们再去把它提交给对应的这个 Agent 的时候，那么它再去进行构建问答的这个过程就会非常的清晰。所以这个就是本体它核心的这样一个构建的流程。

### 一次提问如何走通本体：主机到了，奶泡壶呢

OK，所以相信大家通过这个关系网也能够看到，如果我们想要去进行一个业务链路构建的话，其实它是可以去进行一个实现的。包括我们这里面可以去看到，当我们有了这样的一个本体的关系网络，然后我们去接住于 AI 把它去进行一个接入，那么其实当一个用户问题进入到我们所构建的这样一个 AI 系统以后呢，它在检索过程就会非常非常的清晰，而它最后的一个核心，其实本质上它要做的事情就是：我们不管要做什么，我们要通过所谓的这种检索的算法也好、Agent 推理也好，要把相关的这个信息提供给 Agent，让它去作为它去回答某些链路的这样一个上下文。

举个例子，这里面大家可以看到，其实这个呢就是我们构建本体的这样一个它的一个关系的网络。然后当用户发起一个提问的时候，那么它用户说：哎，我现在这个主机已经到了，我的这个奶泡壶呢？对吧，它问到这个客服，那么客服呢，首先它会核实对应的这个身份，然后进入到我们这个 AI 系统，它能够去根据客户张三然后看到它的这个订单，知道它现在是买了一个咖啡机的套装，然后订单是什么。然后根据这个咖啡机的套装呢，它可以下一步的路由能够知道，这个咖啡机的套装里面有一个主机的包裹、有一个奶泡壶的包裹。

而每一条链路呢，他们都有几点的这样一个关系。比如这个主机里面包括了它是哪一个快递给运行的，然后它现在是属于签收状态还是未签收状态，包括了对应的这个奶泡壶，它的运单是来源于呢、它的这个状态是呢（待确认）。然后有了这些以后，它就可以去组成接下来供给 Agent 来去回答客服的这样一个问题。包括了现在呢，我们找到了我们的这个知识库里面，这个主机呢它是有签收记录的，然后奶泡壶呢最新的这个记录为运输中。那 Agent 有了这样的一个上下文，它是不是可以非常清晰地就知道了，那我到底能不怎么去回答用户的这个问题？

其实这种这种情况下，就是我们已经不再需要那种性能非常厉害的模型，哪怕是一个非常轻量的这样一个小模型，也能够很快地去回答对应的这样一个问题。所以这个呢，就是我们要给大家去介绍的关于本体，它在去结合实际的这个业务的这个链路的流程所做的一个核心，就是它呢是希望通过以对象、以属性以及关系的这样一个形式，去把散落的这样一个数据先去做成统一的这样一个数据格式，然后呢把它做成这种共同的这个业务的模型。那么这个共同的业务模型，在业务模型里面任何一个单点的信息，他们之间前后的相互关联都是可以通过这种链的这个形式来去构建他们之间的信息。那么只要是构建出这样一个信息，触发其中的某一个核心的关键字，就能够把它左右的这样一个分支全部的信息都给带上来，那提供 Agent 它就可以完成对应这个问答也好呀，或者是自由链路（待确认）的这样一个核心的链路，而自由链路的这样一个构建。

> **思考一下｜"单点触发、全链路展开"改变了什么**
>
> 这段是一条完整的链路演示：身份核实 → 张三 → 订单 → 咖啡机套装 → 主机包裹 / 奶泡壶包裹 → 快递与签收状态 → 知识库记录 → 回答。作者想说明的是，答案不是"检索"出来的，而是沿关系"走"出来的。
>
> **可以追问**：当两条链路在某个对象上冲突（比如包裹显示已签收、知识库显示仍在运输），本体应该由谁来决定以哪个为准？
>
> **可延展方向**：为一条客服问答链路画出"关系跳数"，跳数越少的问题越适合先交给小模型或直接规则化处理。

## 综合解读

**作者的论点链。** 视频作者这一集的推进方式是"先痛点、后概念"：从电商订单客服要在多个系统之间往返查询、既慢又容易出错讲起，提出用建模把生产环境中的信息连成业务模型；接着把问题转到 Agent 一侧——Agent 在企业 AI 项目里最核心的需求是知道自己正在处理什么业务的上下文，并用"领导派活必须先讲清为什么做、做到什么程度、手头有什么数据"作类比；由此推出必须存在一个跨系统的共同业务模型，也就是 ontology；再落到三个核心概念 objects（对象）、properties（属性）、links（关系），并用一张电商关系网和一条"主机已经到了、奶泡壶呢"的提问链路来演示；最后收束为一句判断：FDE 在现场交付时的核心技术，就是为整个企业领域构建业务本体，并把它作为 Agent 统一的上下文查询与推理入口。

**隐含前提。** 这段论述成立依赖几个未被作者展开的前提：其一，业务实体和它们之间的关联是可以被事先枚举并稳定建模的，而不是高度流动、随业务随时变形的；其二，上下文一旦补齐，模型能力就不再是瓶颈——作者用"哪怕千问的 3B、1.5B 模型也能回答"来支持这一点；其三，企业现有系统里的数据虽然格式散落，但语义上仍存在一个可以对齐的公共口径，因此 PDF、CSV 与各类业务系统能够被同一套对象—属性—关系描述。这三点都是**作者观点**，本集并未给出实测数据或对照实验，属于 `unknown / 待外部核验`。

**待核验的事实主张。** 作者提到的具体平台与工具判断——例如某类编程工具"在国内用户数应该最好"、某个开源侧"目前没有太好的本体平台"、某工具官方将要进行较大版本迭代——都是他截至口播时的个人观察，会随时间变化，应作为 `unknown / 待外部核验` 看待，引用时需写成"视频作者在该段口播中主张……"。本集 ASR 中还有一批无法可靠识别的人名、产品名、术语（见文中就地标记的 `待确认`），例如 optics 等，这些字符串保留原样、未做猜测修正，正式引用前需要回看原视频确认。

**反例与边界。** 作者举的正面案例是电商订单客服——这类场景的关系结构相对稳定、对象类型有限、链路跳数可控，本体的收益因此容易体现。反过来的边界至少有三处：一是包裹签收状态与知识库记录不一致时，谁优先的问题，本集用"主机有签收记录、奶泡壶最新记录为运输中"一带而过，没有给出冲突消解规则；二是本体建设的成本主要在数据侧（作者自己也承认现场拿到的往往是散落资料），资料越多、口径越乱的领域，收益兑现越慢；三是"触发某个核心关键字就能把左右分支全部带上来"这种展开方式，在关系极其稠密的领域可能带来上下文膨胀，而不是上下文清晰。

**可迁移素材。** 本集可以直接拿走的有三样：一是"上下文需求清单"的做法——为一条业务流程逐步列出 Agent 在每一步最少需要知道什么，再对照现有数据是否具备；二是本体三要素的最小建模模板——用品类名、字段、外键语义三列，把一份数据字典改写成本体草案；三是本体的价值度量思路——把"跨系统查询的往返次数"和"问答的关系跳数"作为可测量指标，用来判断一个场景值不值得先建本体。至于下半场的实操部分（数据如何处理、如何与编程工具协同开发），本集只做了预告，具体内容需要看后续集数。
