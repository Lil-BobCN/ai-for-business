## 口播文章

### 本体的两层结构：模型定义与实例事实

接下来，我们再在这里考虑一个核心内容：本体其实分成两类内容，一类叫做模型的定义，这个模型的定义其实就是 Schema。这个 Schema 就是我们刚才一直说的 Objects、Properties 以及 Links，它们用来去确定背景属性以及它们之间的关系。比如我定义一些学生，这些学生有对应的属性；然后我们定义他们之间的关系，就是学生可以去选修定义的课程。

而这个课程其实它也是一个 Object，包括这个课程名称是什么、上课的时间是什么等等相关信息。而实例的事实，指的就是我们刚才说的这个实例的事实，它其实就是针对你定义出来的这些类型、属性以及他们之间的关系，描述他们到底是什么、发生了什么。比如我们的实体类型是一个学生，然后记录一条具体的关联：去选修了摄影入门等等，它是这样的一个链路。

> **思考一下｜本体的"定义层"与"事实层"**
>
> 这一段把本体分成了"我先声明世界上有哪些类型和关系"与"我记录世界上具体发生了什么"两层，后面所有的表达方式、校验和推理都挂在这两层上。
>
> **可以追问**：如果一个业务系统里类型定义和实际数据长期不一致（比如 Schema 里有课程对象，但数据里课程只是一段文本），应该先改哪一层？
>
> **可延展方向**：把这两层对应到数据库的表结构与表数据、或代码里的类型声明与运行时实例，看约束应该写在哪一层才最省维护成本。

### OWL：模型定义与实例事实的标准表达

而这个过程，其实我们可以通过一个所谓的 OWL 的这样一个概念来实现。这个 OWL 它的全称是 Web Ontology Language，它是一个 W3C 制定的、具有"形式化语义"的本体语言。大家可以怎么理解呢？这个 OWL 它其实就是提供对于本体它的模型定义加上实例事实的一个标准表达。

所以对 OWL 去构建实体来说，它不仅仅是说我可以去按照某一个"四段"（待确认）、某一个约束来去完成你当前领域"既定事实"的这样一个约定，而且它可以去提供一下你具体函数之间的这样一个描述、具体对象或者是关系之间的这样一个描述的关系，这个是 OWL。

那举个例子，对于 Schema 来说，我们刚才也知道，Schema 它其实是去定义我当前这个领域里面，如果去构建 Ontology 业务模型，我都要去定义哪些明确的关系。其实对于 Schema，大家就可以理解成它是一个模型的这样一个定义的规范，像我们一直说的类型 Objects、属性 Props 以及它的这个关系 LinkType，其实都是有相关的这样一个定义的。像对于 Palantir，像他们所说的就是 Objects、Property 以及 LinkType。那么这里面大家可以点击这个相关的链接，去看一下 Palantir 他们在这个 Meeting 上发布了这样一个关于本体的这样一个博客。

他们其实发表了很多 Palantir 内部对于 Ontology 它的一个定义的核心的概念。其实对于 OWL 来说，我们刚才也说了，它其实对照的具体的这个概念，其实就是对 Schema 它的一个标准化的定义的形式，你可以把它列成标准的这种表达式语言。当你去通过 OWL 这样一个约束规范，或者是在这种表达式语言去构建你的本体的时候，意味着它作为这种相对来说大家比较公认成熟的这样一个行业规范。

那比如你构建出了一个 OWL DL 的这样一个本体的知识图谱，那么你想要把它去应用于对应的 Agent 的推理，或者是签入到其他系统，那么可能大家都遵循对应的这样一个标准，那你构建出来的这个数据就可以无缝地去进行接入。当然你也可以去自己去构建一套属于你公司内部的这样一个标准，也完全没有任何问题，其实只要是能够让 Agent 去读取到对应的这个"商家文档"也是可以的。所以这个就看大家到底要不要去按照标准的这种表达式语言来去进行构建。

理论上还是非常推荐大家去采用这样一个，毕竟你自己去进行一个自定义规则的构建，它的一个适配度以及它的一个社区的生态肯定是不特别好的。所以这个是 OWL 以及对于 Schema 它们之间的一个可对照的这样一个关系。比如说对于 OWL，其实它对于类型来说就是通过 Class 的这样一个方式，然后对于数据属性是通过 DataProperty，以及通过对象关系是通过 ObjectProperty 来去进行的一个说明以及对应的约束。当然下面这一部分我们就不展开给大家去进行这样的一个说明了。

> **思考一下｜标准本体语言与公司内部规则**
>
> 作者给出的判断是：走 OWL 这类公认规范，跨系统接入和社区生态更顺；自己造一套内部标准也不是不行，只要 Agent 能读到对应的上下文。这里把"能不能用"和"好不好用"分开了。
>
> **可以追问**：在什么规模、什么阶段的项目里，自定义内部标准反而比采用 OWL 更划算？
>
> **可延展方向**：比较"标准优先"与"内部方言优先"两条路线在迁移成本、工具链支持和人员招聘上的差异。

### 跨领域对照：对象、对象身份、属性与链接

那么核心就是我们对于 Object，以及我们的对象身份、Property 以及 LinkType 它们之间具体的这样一个关联，给大家去做了一个跨领域的这样一个说明，帮助大家去进行一个理解。

首先对于这个 Object，它如果我们在不同的领域，像什么人力，它的对象类型可能是员工，然后具体的实例就是不同的人。然后对于制造业，它的对象类型可能是很多的这种生产设备，那么生产设备它具体的对象实例就是什么 1 号车床、2 号车床。所以这里面大家就能够看到，在不同的行业，当我们使用本体来去进行它的 Schema 定义的时候，那么你就需要结合你行业的特定的这样一个场景来去进行一个说明，这个肯定是没有任何问题的。

下面的对象身份，其实它解决的就是这样一个冲突的问题。比如我们对于人力的行业，那么人名经常会出现重名的这个问题，那如果你是通过实例的这个方式，就是通过名称的这个方式来去构建他们之间的这样一个"制度部"（待确认）的关联关系，那么很有可能两个重名了，他们的关系就会错乱。所以通过这个对象身份，我们可以通过不同的这样一个标识，比如它的工号是什么，可以通过不同的工号对应相同的两个人，然后用工号来去进行一个区别。所以这个是对象身份。

然后对应的这个 Property 就非常容易理解了，你每一个对象它可能有不一样的这样一个属性，像人呢有这个姓名呀、年龄呀，然后像设备呀它有什么生产日期呀、它的材质呀、保质期呀等等相关的这样一个说明，可以给它做一个辅助的这样一个联络。然后对于这个 Link 就更容易理解了，就是我们去定义不同对象之间他们到底是处于什么样的一个关系：什么员工任职于某一个部门，然后学生选修了什么课程，设备它在哪一个产线安装了，然后包括具体的这样一个链接其实都是一样的，这个 Link 其实应该非常容易理解，包括了对应的这个模型的约束。

> **思考一下｜对象身份是给机器看的"唯一性"**
>
> 作者用"人名会重名、工号不会"来讲对象身份，说明本体里主键式的设计不是为了好看，而是为了让关系不接错。
>
> **可以追问**：当一个行业里天然没有稳定唯一标识（比如设备被改装、人员跨主体流动）时，对象身份应该由谁、按什么规则来发放？
>
> **可延展方向**：把对象身份的治理思路迁移到数据中台的实体打通（ID-Mapping）问题上，比较两者对错的代价。

### 知识图谱与 Ontology 的分野：语义、校验与业务规则

这里面大家需要去进行一个说明的就是：我们之所以去区分知识图谱，或者是大家理解成这种静态的这种知识图谱和 Ontology，他们之间最大一个区别就是，知识图谱其实它更多构建的是基于你传入的这样一个数据来去抽取它内部的一些实体关系以及他们的属性，来去构建一个可查询的这样一个关系；而对于这个 Ontology 来说，它定义的更多的是你领域上面的一些业务的规范以及规则，比如包括了一些约束、校验和业务规则。

这里面怎么去秒（待确认）、怎么去理解呢？举个例子，比如说我们可以在我们构建出来的这个 Ontology 的语义里面明确地去跟他说什么是什么。比如说在教育行业，我们明确地就说这个研究生他就是属于学生的一种，那么这种就是属于我们可以通过 OWL 的表达式的语言来去表达他们之间相关的这样一个语义，去表达不同的对象类型他们之间的"互指关联"以及相关的限制等等。

那么对于这个数据校验来说，就是对于你每一个对象也好、你的这个属性也好，他们需要具备一定的入库存储的这样一个条件。比如你的这个设备编号必须不能为空，你的这个功率必须是数值。所以你是可以去针对于你确定好的这样一个规范、定义好的这样一个对象，那么这个对象它是什么数值的，你必须添入什么样的一个类型，只要是不是这个类型，那么说明有问题，你的这个数据是出错的。所以它是可以对这样去做一个限定，所以这个是数据校验。

以及对应的这个业务规则。所谓的这个业务规则，就是针对于 Ontology 来说，它不仅仅是把你抽取出来了这样一个内容去构建这样的一个关系网，而且它可以真实地去链接、和由人来去定义：当你在去使用这个关系网的时候，由 Agent 的去定的驱动要追寻什么样一个逻辑。那比如说如果是某一些阈值、某一些阈值变成了什么什么以下，它就会触发什么样的一个操作，那么这种就属于业务规则。

比如对于这个仓储来说，如果这个库存低于了这个阈值，就弹出一个相关的这个需求、建议补货，那 Agent 它就知道了我监测到你的这个库存低于 10 了，直接弹出来"我写下来需要你补货了"，交给人工来去进行确认。所以这种呢，它是属于对应的这样一个业务规则。

> **思考一下｜约束、校验、业务规则是三件不同的事**
>
> 作者把 Ontology 的"规则"拆成了三档：语义层说清什么是什么，入库时校验数据合不合规，运行时按阈值触发动作。三者写在同一份本体里，但生效时机完全不同。
>
> **可以追问**：把"库存低于 10 就建议补货"这类业务规则写进本体，和写在传统工作流引擎里相比，谁更适合作为唯一事实来源？
>
> **可延展方向**：梳理一条业务规则从"人工经验"到"写进本体、由 Agent 触发、再交人工确认"的迁移路径，看哪些环节最容易失控。

### 构建本体的全景图：两个方向与一份确认清单

所以通过最后的这张图，我们来去看一下，对于这个本体的构建，我们需要确定以及定义的都有什么。核心就是我们要去构建它的这样一个 Schema 来去约束它知识的含义与对应的这个结构。那么第二个，我们要去定义它的一个配套的约定，就是明确在我本体里面要录入的这个数据到底是以什么样的一个形式存储，我在使用的时候怎么去约束和检查它的一个规范性，以及在提供给 Agent 的上下文，或者是在进行"应用"的时候，采用什么样的一个业务逻辑。这个是两个大的方向。

而如果我们进入到它的里面的话，就是对于本体来说，我们要知道它的这个 Schema 里面，我们针对于某一个特征领域，我们都要定义出多少个类型的对象，然后这个多少个类型对象如果出现了一些冲突、互斥或者是兼容的情况，如何去构建他们的这样一个身份的约束；同时对于每一个对象，我们要明确的定义他们都需要包含和建立哪些属性，以及每一个对象之间他们的关系是什么样的。

而对应的这个语义的约束，就是我们可以进一步的去扩展不同对象、不同关系之间我们可以自定义的这样一个关系限制以及对应的这样一个约束规范。这个是本体的 Schema 我们要去构建了这样一个结构。而下面就是关于这个数据"映射"散落的这样一个信息系统也好、API 也好、数据库也好、PDIF 文档（待确认）、Markzang 文档（待确认），这些散落的数据到底按照什么样一个约束规范来接入到我们的这个本体的关系网络里面。

然后呢，针对于这样一个数据校验，我们已经明确的在 Schema 里面定义出来的这种对象的类型、属性的类型、关系的类型，他们的每一个我们在去存储数据的时候要遵循什么样的规范，我们要构建校验的这样一个机制，来去确保进入到我们的这个关系网络里面的这个数据全部都是纯净的、干净的，而且是不会出现任何问题的。以及对应的这个业务规则，而为了用于对应的这样一个 Workflow 也好，或者是 Agent 的上下文的信息的提供也好，我们要基于我们特定领域、或者是我们特定"虚构"下，在遇到某些场景特定的这种处理策略，我们是可以提前给他构建对应的一个业务规则。

那么 Agent 在去运行的时候，结合在你的这个本体论，他就知道了你数据的纯净性，他知道你数据的准确性，而且也知道了你在某些这个数据触发以后 Agent 接下来应该干什么。这个就是在构建本体前，其实有非常非常多这个信息是需要我们来去进行确认的。

## 综合解读

作者的论点链在本集里是清楚的：本体先分两层——模型定义（Schema）与实例事实；Schema 由 Objects、Properties、Links 构成，实例事实则记录具体发生了什么；这两层可以用 OWL（Web Ontology Language）做标准化表达，其中有类型对应 Class、数据属性对应 DataProperty、对象关系对应 ObjectProperty；接着作者用跨领域对照说明对象、对象身份、属性、链接分别在解决什么（行业差异、重名冲突、描述性信息、对象间关系）；最后用知识图谱与 Ontology 的分野收尾——前者侧重从已有数据中抽取实体关系、形成可查询的关系网，后者侧重定义领域规范与规则，包括语义表达、入库校验和业务规则，而业务规则决定了 Agent 在数据触发后应该做什么。

需要说明的是，以上是**视频作者在口播中提出的观点与框架**，属于教学性归纳，不是本集验证过的结论。按源文件头部记录，本集事实主张状态仍为 `unknown / 待外部核验`；作者提到的企业博客、行业规范成熟度、以及"标准本体语言能带来无缝接入"这类说法，都属于需要外部核验的主张，不宜直接当作既定事实引用。作者在取舍上的判断（推荐采用 OWL 这类公认规范，但自定义内部标准也可行）同样只是作者的观点，不是行业结论。

**我的分析**：这一集真正的骨架不是 OWL 本身，而是"约束分三档生效"这件事——语义层负责说清概念之间的从属与互斥（研究生属于学生），入库层负责挡住不合类型的数据（设备编号不能为空、功率必须是数值），运行层负责在阈值处触发动作（库存低于 10 触发补货建议并交人工确认）。三者共享同一套 Schema，但生效时机不同，这解释了作者为什么反复强调"知识图谱"与"Ontology"的差别不在技术栈，而在于谁定义规则、规则在哪里被执行。另一个值得留意的前提是：作者假设企业愿意并有能力先定义规范再录入数据；如果现实里数据先行、规范后补，那么"校验机制"和"身份约束"的落地顺序可能需要重排。

**边界与反例**：口播中"库存低于 10 就弹补货建议"这类例子隐含了阈值稳定、职责清晰的组织前提；在阈值频繁调整或补货决策依赖外部供应的场景里，把规则固化进本体可能反而增加改造成本。此外，作者对自定义标准的评价（适配度与社区生态"肯定不特别好"）是一个偏经验的判断，缺少对照数据。

**可迁移素材**：本集可直接复用的有——"模型定义 / 实例事实"两层拆分法；"对象身份解决重名"这一类唯一性设计思路；以及结尾那份构建前的确认清单（定义几类对象、身份如何约束、每个对象的属性、对象之间的关系、数据以什么形式接入、入库校验什么、触发后 Agent 做什么）。这几项可以作为企业知识工程立项时的检查项。

**ASR 不确定项**：本集转写中有若干专名与词组无法可靠识别，已就地标记（待确认），包括"四段"、"制度部"、"怎么去秒"、PDIF 与 Markzang 文档。这些均未做猜测性修正，引用时请以原视频为准；同时，OWL、Schema、Objects、Properties、Links、LinkType、Class、DataProperty、ObjectProperty、Agent、Workflow 等术语按视频语境与分P标题保留其通用写法。
