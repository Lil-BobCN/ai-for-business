视频作者在这一集里把话题从"怎么把零散业务数据建成本体"推进到"建好的本体怎么被用起来"，围绕一份 `.owl` 的电商订单客服本体，讲清三种主流的本体检索策略——结构化查询、图关系查找、语义检索加图扩展，并说明它们在什么条件下该被选用、又如何落到 Agent、RAG 与人机回环（Human in the loop）的组合链路上。

### 三种主流检索策略概览

其实这个我们在昨天的这门课程也给大家介绍了：对于本体来说，它和 AI 来去进行协同最最核心的，就是它要给 Agent 去提供必要的运行时的上下文。你做得越精准，你的这个上下文做得越好，那肯定你的这个执行准确度就越高。哪怕是你使用一个 1.5B 的这样一个模型，有了非常非常完善的这样一个上下文，它一样能够处理好相关的这样一个问答的任务。

所以这里面就是对于本体的业务模型，一些核心的、或者是他们之间可以互相组合的这样一个主流的实现策略，那么一共分享了三个。我们这里主要是给大家介绍三个，当然这个其他的变种还是非常非常多的；我们这里给大家介绍非常经典的、而且适用度最高的这三种。

> **思考一下｜"上下文够好，小模型也够用"这句话该怎么验**
>
> 作者在这里给出的是一个相当强的判断：本体的核心作用是供给上下文，上下文够精准，连 1.5B 级别的模型也能把问答任务处理好。这个判断如果成立，企业侧的投入重心就会从"换更大的模型"转向"把上下文做对"；但它同时也把风险转移到了检索环节——上下文一旦召回错了，小模型没有能力自我纠偏。
>
> **可以追问**：在同样的问答任务上，什么样的对照实验才能把"上下文质量"和"模型规模"这两个变量的贡献分开？
>
> **可延展方向**：把这条判断转成一个可测量的对照设计（固定模型换上下文 / 固定上下文换模型），用来给团队的模型选型提供依据。

### 第一种：结构化查询

首先第一个叫做结构化查询。这个结构化查询非常容易理解：我们和 AI 去进行协同的时候，我们给它提问的一般都是自然语言，比如说"你去给我查一下张三的这个订单到哪了""你去给我查一下我某某物件的这个物流信息到哪了"——我们传入的一般都是自然语言。

那么对于这个自然语言来说，如果按照我们之前 GraphRack（待确认）这样一个思路，它会把你自然语言去转化成这种 Sephora（待确认）的查询的语句，然后进入到图数据库里面去进行检索，然后返回最相关的、返回最终的这样一个统计结果，然后由模型基于你提供的这样一个上下文的数据信息，返回最终的一个答案。

那么对于这个本体来说也是一样的，我们就可以通过这个 FPA（待确认）的这样一个结构化的查询语言，来去把它精准地把问题转化成明确的类型、属性、关系——这个大家都应该清楚了吧：类型 Object、属性 Properties 以及关系 LinkType，那么第三个就是构成本体它的这个 schema 核心的这样一个定义的基础。我们去把问题转化成对应的这样一个（查询），以及匹配上对应的这个筛选条件。

大家就可以理解成：如果我通过模型去把用户问的这个自然语言问题转化成可以去查询本体的这样一个语言，然后呢去用我们的本体的这个业务模型里面去执行查询，它就能够得到最后的一个结果的范围，那我们就能回答对应的这个问题。比如我要去问"研发部有多少名员工""你现在有多少库存呢"，它其实就可以查询出满足条件的这些记录。这个是一种结构化的查询。

> **思考一下｜"自然语言转查询语句"这条路的可靠边界在哪**
>
> 结构化查询的链条是"自然语言 → 查询语句 → 图数据库 → 结果范围 → 模型作答"，作者把它讲成最容易理解的一种。但它对模型的信任点很集中：类型、属性、关系必须被翻译准确，筛选条件不能凭空生成。一旦问句里带着业务歧义（比如"到哪了"到底指包裹状态还是配送节点），错误会在第一步就被固化。
>
> **可以追问**：在结构化查询这条链路上，应该由谁负责在查询语句执行前做一次校验，本体本身能不能承担这个校验？
>
> **可延展方向**：把"哪些问题适合被翻译成结构化查询"整理成一份问句类型清单，作为路由策略的输入。

### 为什么很多人把本体和知识图谱混在一起

那么第二种就是图关系查找。大家可以去看到：其实为什么很多人会把本体的这个业务模型和知识图谱混在一起呢？其实就是因为很多业务模型往往都会采用知识图谱的这样一个方式把它展示出来，大家就以为这个本体它好像和知识图谱其实是一样的。其实并不是这样。

这个呢我昨天也给大家初步地去介绍了一下：其实本体它更多的是用来去定义你某一个领域里面的这样一个知识以及业务规则的，而和知识图谱这种纯净态（待确认）的知识编排以及知识结构的组织，是有一个本质性的这样一个区别。

> **思考一下｜显示形态相同，不等于定义职责相同**
>
> 作者的解释路径是：两者之所以被混为一谈，是因为业务模型常常"用知识图谱的样子画出来"。也就是说，混淆来自可视化形态，而区分要回到职责——一个负责定义领域里的知识与业务规则，一个负责知识的编排与结构组织。这条区分对做选型的人很实用，但它目前是作者的表述，并非标准定义。
>
> **可以追问**：如果本体和知识图谱在同一套系统里同时存在，两者的边界应该划在文件层、查询层还是治理职责层？
>
> **可延展方向**：用"谁定义约束、谁承载实例、谁负责可视化"这三问，去核对任何一个号称"本体 + 图谱"的方案。

### 第二种：图关系查找

所以基于这样的一个情况，我们确实在检索方法上也是可以通过图关系查找的这样一个方式来去进行一个构建。

那么比如我们之前构建出来这个知识图谱，它的每一个节点——或者我们在本体的业务模型里面把它叫每一个对象——它都是有对应的这样一个通过 Type 和其他的对象构建起相互的这样一个关联关系。那么他们既然有相互的这样一个关联关系，就类似于我的某一个员工参与某一个项目，然后这个项目归属于某一个部门，其实这是一个最小的两跳的这样一个链路。

那么基于图的这样一个算法，我的这个图的路径检索、遍历算法、路径搜索，其实就可以去解决这样的一个问题。这是第二个，我们基于知识图谱来去进行构建。

### 第三种：语义检索加图扩展

那么第三个就是语义检索了。语义检索加上图扩展，它其实指的就是：自然语言嘛，我去通过 Inviting（待确认）的这样一个方式，把你 Skemi（待确认）的这样一个定义、把你的这个对象类型、属性、它们之间的关系去把它编译成——通过 Inviting 模型去构建成相似度向量的、编译成这个向量 Vector——然后通过相似度的这个方式去找到候选集，然后再借助于图关系查找的这样一个思路去找到 Topkit（待确认）这样一个值。

所以这个就是：对于问题的这个向量，我们去搜索到它对应的这个相似的实体，然后找到这个实体它在你的这个本体的业务模型里面的这个位置，然后通过图检索的这样一个图的路径搜索的这样一个方式，去找到你相似实体对应的这样一个下游的这样一个信息，从而去构建它的一个信息的完整的链路。

所以这个呢就是语义检索加图扩展。其实这个用的会很多，其实确实是用的会很多，大家可以去关注一下。

> **思考一下｜"向量召回 + 图扩展"补的是哪一段能力**
>
> 这一种策略解决的是描述性模糊的问句：先靠向量相似度把候选实体捞出来，再回到图结构上补齐它下游的关联信息。它的成立依赖两个前提——向量空间里"相似"要真的对应业务上"相关"，以及图上的下游扩展不能把无关实体一起拖进来。作者没有展开的是召回失败和扩展过量的兜底路径。
>
> **可以追问**：当向量召回的实体本身就错了，图扩展只会放大错误，这条链路有没有可用的自检或回退机制？
>
> **可延展方向**：把"召回质量"与"扩展深度"当作两个可调旋钮，为不同类型的问句预先设定组合参数。

### 例子一：结构化查询的匹配、连接、过滤与投影

接下来我们重点通过一些核心的例子给大家介绍。这三个其实还是非常关键的，大家如果要是能够掌握的话，那么关于本体的业务建模它的一个执行搜索的过程，你会非常非常的清晰。这里面通过一个非常清晰的例子给大家介绍一下：关于结构化查询的这样一个方式，它到底是怎么在你的这个知识图谱里面去找到相关的这样一个结果。

这里面肯定就是你的自然语言它会借助于 LM 模型，也就是你的大模型，去生成一些候选的查询。那么假设——大家看这里面是我们构建的这个本体业务模型的一个 RDF 的这样一个三元组——那么对于这里面，像 A 和 B 他们是有关系的，那么 A 和 C 也是有关系的；那么 B 它的这个得分是多少、C 的得分是多少、D 的得分是多少，这个呢是属于我们再去构建本体它底层的一个数据的结构的模式。

那么当我们想要去查询这个 A 和某一个事情有关系的话，就是我们先去找到这个实体的这个 A，然后它和谁有关系呢？我们通过一个问号 X 这个方式把它去提取成一个待定、待填写的这样一个值。那么我们在这个三元组里面就能够知道，这个 A 它其实和 B 和 C 有关系，所以这个问号 X 就等于 B 和 C。

接下来我们再次地去向下找到：那么这个 B 和 C 他们的下游是什么呢？就是我们问号的这个 X 它的得分是什么。这里面就能够找到我的 B 的得分是 0.9、C 的得分是 0.4，以及 D 的得分是 0.95。所以这样就相当于渐进性地找到了这个 A 它和 B 和 C 是有关系的，然后 B 的得分是这个、C 的得分是这个，所以他们是不是建立起了初步的这样一个关系？

然后接下来它就会针对于他们找到的这样一个共享变量去做一个转换，也就是它只会去合并这个问号 X 相同的这样一个值：也就是我要去找到你 A，既然和 B 和 C 有关系，OK，那我就把你这两个关系给找出来。接下来我再去通过过滤和投影——所谓的这个过滤和投影就是：我既然 A 和 B 和 C 都有关系了，但是我这里面有一个过滤条件，就是你的这个得分的值必须是大于等于 0.8 的，那么是不是这个 C 它就淘汰了，然后这个 B 就出来了？

那么最后我们要匹配的类似于这样的一个查询的语句，就是 A 它找到了 B，以及 B 最后的一个得分是 0.9，就是构建起他们这样的一个关系。这个是它底层的这样一个算法的逻辑。

### 例子二：图遍历与路径搜索

OK，那么第二个就是图遍历与路径搜索。那么对于这个图遍历，其实大家和知识图谱——我们昨天看到的业务建模的本体模型——是非常像的，每一个节点之间它们都有相互的关联的关系。

那么对于图遍历这一块，大家就可以通过这种队列的这种形式。那么其实大家怎么去理解 BFS（待确认）的这种检索的查找的方式呢？其实它就是我从某一个节点开始，一个一个地去向外扩展，来去找到它的一个业务的链路的模型。包括了我最开始从 A 开始，那么 A 它的"一跳"，大家可以理解成和它直接相连的这样一个箭头叫做"一跳"。

从 A 首先初始化，我们就从 A 找到，然后 A 连接的是 B 和 C，OK，那我的 B 和 C 就是进入到我们的这个队列，然后把 A 弹出。接下来我们从 B 开始，B 它连接的一跳是这个 D，OK，我们把这个 D 入队，然后 C 保留，接下来剩下我们这个队列里面就是 C 和 D。然后找到了这个 B 以后呢，我们再去找 C，C 和 E 它们是相关联的，然后 C 弹出来，把 E 留下，最后弹出 D 和 E。因为我们只查询到对应的这个两条，所以我们就能够去找到最后的这样一个最短路径。

当然其实对于这种无权的这个图中，BFS（待确认）其实它是有多个最小的这样一个路径的，但是我们一般会把首次发现的这样一个路径去把它找成最优的这样一个结构路径。这个是一个。

接下来就是我们的这个语义检索和图扩展。那么对于这个语义检索，其实它就是属于我们要把我们的实体，然后通过 embedding（待确认）模型转化成向量的这样一种表示，然后呢再类似地放在我们的这个图结构里面，按照我们刚才的这样一个方式去找它的一个路径搜索的一个路径。所以这个呢是关于图检索它的一个方式、本体的这个业务模型。

> **思考一下｜"首次发现的路径"为什么可以被当成最优**
>
> 作者在讲 BFS 时给了一句很关键的限定：在无权图里可能存在多条最短路径，工程上一般把首次发现的那条当作最优结构路径。这句话把"算法保证的最优"和"实现选取的最优"分开了——后者依赖遍历顺序等实现细节，在等权假设不成立时会失效。作者也提示了"无权图"这个前提，但没有讨论带权或带业务优先级的图该怎么办。
>
> **可以追问**：当业务上存在"更可信的来源"或"更近的仓储"这类偏好时，如何把权重引入遍历顺序而不破坏最短路径的可解释性？
>
> **可延展方向**：把"路径长度 + 边的可信度/来源"组合成一个排序函数，用于替代单一的首达优先规则。

### 三种检索策略怎么选

我们这三种主要的这种检索模式，大家在实际使用的时候到底通过什么样的一个方式来去进行理解和选择呢？其实本质上就是非常清晰的：

一个呢，如果你的这个条件是比较明确的，那你不妨就让你的这个 Agent 去接入你的本体的业务模型，然后让它去生成这个 SP（待确认）的这样一个结构化的查询的语句。

或者是如果你想要去追查相关的这样一个关联关系，比如说你想要找到其中某一个对象它所关联的这样一个多链的、多跳的这样一个信息，那么你就可以通过这种图遍历的方式。

而更多的就是，如果是一些描述性比较模糊的，我们就可以借助 embedding（待确认）的这个方式来去搜索它相似的这样一个实体，也就是在本体模型里面这个对象，然后根据对象它关联的这样一个业务的模型，去通过图遍历的方式去检索到它全量的这样一份信息。

这个是它三个这样一个检索策略。

> **思考一下｜选择标准只有"问题明确度"这一维够不够**
>
> 作者给出的路由标准很干净：条件明确走结构化查询，要追多跳关联走图遍历，描述模糊走向量召回加图扩展。这条标准把"怎么问"作为唯一分岔口，但实际系统里还会有另外几个变量——本体的覆盖度、图数据的实时性、查询延迟和成本预算。它们同样会决定哪条路才走得通。
>
> **可以追问**：当三种策略给出的答案互相冲突时，应该以哪一条为准，需不需要在本体层记下优先级？
>
> **可延展方向**：把这条路由标准扩展成一个二维表（问题明确度 × 数据完备度），为每个格子预先指定策略与降级路径。

## 综合解读

**作者的论点链。** 视频作者在这一集里把主题从上一集的"怎么建模"推进到"建好的模型怎么被调用"。起点是昨天已经完成的那套电商订单客服本体：客户、订单、包裹、物流都已经作为知识图谱构建出来，可以理解成一份业务模型。作者随即提出今天的核心命题——这份 `.owl` 形式的业务模型，怎么和 Agent 协同去解决企业里真实的问题，无论是最基础的问答，还是让 Agent 自主决策、跑更高阶的自动化 workflow。

作者给出的核心判断是：本体与 AI 协同中最核心的作用，是给 Agent 提供必要的运行时上下文；上下文做得越精准，执行准确度就越高，他甚至认为配了非常完善的上下文之后，1.5B 级别的模型也能处理相关的问答任务。围绕这个判断，作者展开三种主流的检索策略：**结构化查询**（把自然语言经 LM 模型转成图数据库查询语句，落到明确的类型 Object、属性 Properties、关系 LinkType 上，再匹配筛选条件，得到结果范围后由模型作答，例如"研发部有多少名员工""现在有多少库存"）；**图关系查找**（依赖对象之间通过 Type 建立的关联关系，用图的路径检索、遍历算法和路径搜索解决多跳问题，例如员工参与项目、项目归属于部门这样最小的两跳链路）；**语义检索加图扩展**（把对象类型、属性及其关系经向量化模型编译成向量，用相似度找到候选集，再借助图关系查找取 top-k，定位实体在本体模型中的位置后沿图路径补齐下游信息）。

作者还专门澄清了一个常见混淆：很多人把本体和知识图谱混为一谈，是因为业务模型往往用知识图谱的形式展示，但本体更多是用来定义某个领域里的知识和业务规则，与知识图谱在知识编排和结构组织上有本质区别。最后，作者给出选择标准——条件明确就交给 Agent 生成结构化查询语句；要追查某个对象关联的多跳信息就走图遍历；描述性模糊的就用向量相似度找实体、再沿图遍历取全量信息——并说明本节课程配套提供了三个对应的 skills，以及一个可以直接领取源码的"FDE 本体应用工作台"项目，项目里集成了结构化的查询、关系遍历和语义检索加图扩展这三条链路，还结合电商本体文件做了客服场景下与 Agent 协同的演示。

**隐含前提与边界（我的分析）。** 作者这条论证要成立，依赖几个没有被完全展开的前提。第一，检索质量的上限由建模质量决定——如果昨天那套本体的对象、属性、关系本身有偏差，今天三种检索策略再好也只是在偏差上加速，而这一集没有再回到建模校验。第二，"上下文够好，小模型也够用"是一个经验性判断，作者没有给出对照实验，本集也没有落地评测环节；值得注意的是，作者自己把"人工参与之后效果评测到底是什么样"列为今天要谈的核心基本理论之一，说明评测这一环在本集里仍是被提出、而非被回答的问题。第三，三种策略被描述成可以互相组合，但组合的失败路径没有被讨论：结构化查询翻译失败后是否回退到向量召回，向量召回错了图扩展会不会放大错误，这些在演示链路里看不到。第四，作者给的选型标准只有"问题明确度"一个维度，而实际系统还要受本体覆盖度、图数据实时性、延迟与成本约束；第五，"首次发现路径即最优"这条工程惯例只在无权图假设下成立，作者也明确提到了"无权图"和"多个最小路径"，但没有延伸讨论带权或带业务优先级的图。

另外需要把作者的表述和标准定义分开看：**本体定义领域知识与业务规则、知识图谱负责知识编排与结构组织**，这是作者在本集口播中的区分方式，朗读稿里也承认是自己"初步介绍"的口径；它与学术或工程上对 Ontology 与 Knowledge Graph 的常见定义是否一致，属于待外部核验的范围，不应直接当作结论引用。

**待外部核验的事实。** 本集出现的具体内容均来自视频作者的单方陈述，未经独立核验：今天会提供项目源码（FDE 本体应用工作台，含"本体检索实验室"）、三个本体问答 skills、电商本体文件，实际交付物应以领取到的文件为准；作者所说的"1.5B 模型配完善上下文即可处理问答任务"属于经验判断，无对照数据支撑；讲解中出现的 B 得分 0.9、C 得分 0.4、D 得分 0.95、过滤阈值 0.8，以及 A→B/C→D/E 的遍历过程，都是为了讲清算法而构造的教学示例，不是生产数据；"很多高风险应用仍需人工批准、AI 才能执行下游任务"是作者对落地现状的观察，同样未经核验。

**可迁移素材。** 对做企业 AI 交付的人来说，这一集里有几样可以直接搬走的东西：一是那张三选一的路由标准——问题明确度决定走结构化查询、图遍历还是向量召回加图扩展，可以直接用作任何"结构化数据 + 图 + 向量"混合检索系统的设计起点；二是"本体检索实验室"这个产品化形态本身，它的结果面板把实体基本信息、直接关联对象、来源依据、处理过程四块固定下来，可以当作评估任何图检索演示是否合格的界面清单；三是 BFS 队列式扩展的讲法（入队、出队、首次发现即视为最优），是把图遍历讲给业务方听的最小例子；四是 Human in the loop 的落点——高风险动作由人工批准、AI 才继续执行下游任务，这是一条可以直接写进方案里的控制点。
