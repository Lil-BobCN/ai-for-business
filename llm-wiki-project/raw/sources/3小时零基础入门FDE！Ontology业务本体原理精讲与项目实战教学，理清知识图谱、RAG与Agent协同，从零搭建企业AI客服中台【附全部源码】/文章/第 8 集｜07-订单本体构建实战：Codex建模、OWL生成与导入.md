## 一句话摘要

视频作者在本集里把 Ontology 从概念推进到动手：把 79 份散落的电商业务资料（CSV、PDF、JSON、`TXT`、markdown）在一个 Codex 项目里跑完"业务对象梳理 → 模型逐轮确认 → 知识抽取 → 生成 `.owl` 本体文件 → 导入系统"的完整链路，并在过程中交付三个团队内部使用的本体构建 Agent Skills（Ontology Design、Ontology Extract、Ontology Build）。

## 阅读路线

1. 先看作者摆出的原始数据形态——电商领域下仓储、订单、客服、签收、商品中心、物流接口、业务规范到底散成什么样，这是他后面所有操作的输入。
2. 再看作者提出的建模难题和两条解法：有现成模型就基于它构建、反复调试；没有就梳理需求与痛点交给 AI 出方案，由人工逐轮判断。
3. 然后跟着 Codex 里的多轮提示词走一遍实战，看对象、属性、关系是怎么一轮轮被确认下来的。
4. 最后看 Ontology Extract 与 Ontology Build 两个 Skill 如何把对话结论变成标准 `.owl` 文件、导入系统，以及下一集要接的 Agent 问答与推理。

### 从散落文件到标准 `.owl`：79 份资料交给 Codex

那么这个的构建过程呢，我们采用的方案是这样的：首先，对于这 79 份——大家一共拿到的是 79 份的业务资料，包括了 CSV、PDF、JSON、`TXT`和 markdown 这些业务资料，我们把它统一地去交给 Codex 来去进行分析、读取和构建。

当然，严格意义上来说，这些数据我们肯定是不能直接给到 Codex 让他去做的，这个也不是行业的这个标准规范，因为我们如果想把它去构建成系统的话，那么我们要单独地去构建不同业务场景的这样一个解析的链路。就是今天呢，我们作为这个体验课，为了让大家快速地了解到，以及考虑到时间，我们就直接让它 Codex 来去进行一个读取和处理，直接做到最终的这个效果。然后我们让 Codex 把所有的这个文件读取、分析，然后构建；构建的这个过程中呢，我们去选择：当前在这个本体的知识图谱里面，我们如何去确定他的对象、他的这个关系以及他的这样一个属性，最后把它形成一个 OWL 的文件。

那么这个 OWL 的文件大家可以去看一下，这个就是一个非常标准的文件。大家可以在这里面找到，这有一个业务本体，大家找我们的助教老师也能够直接去领取到。这个是我们构建出来的这个业务本体，里面就是通过 OWL 的这个方式来去把我们构建出来的这些信息做相关的语义的关联。然后如果我们把它去导入到对应的这个系统里面，其实它就会就是这个样子——其实就是这个样子，把它收起。对，其实它就是这个样子，就是它们之间是有相互的这个关联的关系的。我们来实战一下这一部分的逻辑，我们来实战一下。

### 数据现状：各系统记录了什么，以及要先核对什么

首先啊，第一部分就是我们现在这个数据的情况。这个数据情况就是给大家提供的这个测试的文件，分别记录的就是：客户中心的是客户的"答案"（待确认）与业务编号，然后订单中心的是交易记录、商品明细，然后仓储系统记录的是出货的记录和装配、装箱的分配，"物流与回答"（待确认）事件轨迹和签收的评价，以及"客户与规范"（待确认）。然后关联之前，我们要核对的这个问题啊有很多，大家这里面给大家去调整几个：比如说这个编号的体系，包括订单号和运单号，它们不同的这个语义之间如何去进行"语义消息"（待确认），包括这种状态的描述——其实这种就属于我们对于业务的这种定义了。

那接下来我们要做的这个方式，大家可以想一下。这个呢其实我们刚才给大家在前面已经抛出了这样的一个问题。大家看啊，在这我记得我当时在这的时候，就是我们去把零散的这个资料去把它转化成清晰的关系网，最难解决的是什么？就是这个业务含义到底是怎么定义的。其实尤其是 FDE，你作为这个驻场的工程师去进入到客户的这个现场，你需要在短时间内去了解他的这个业务体系，然后去基于他们真实的这个业务的链路去构建出这样的一个 Schema，要去基于他的场景领域去构建。我们在做本体的时候都要去定义哪些类型，其实这个是很难的，这个真的是很难的。如果这个甲方或者是你们公司在做自己项目的时候，能够提供出之前已有的一些"参数对方"（待确认），那其实是非常好构建的；那如果没有，我们一般怎么做呢？

> **思考一下｜建模真正的难点是"业务含义从哪来"**
>
> 这一段把话题从工具拉回到定义本身：编号体系怎么对应、状态描述怎么理解，这些都属于业务定义，而不是技术选型。作者的判断是，FDE 驻场时最难的是在短时间内理解客户的业务体系，再把它翻译成 Schema 里的类型。
>
> **可以追问**：当甲方拿不出既有模型、又说不清业务规则时，FDE 应该先交付哪一份中间产物，才能让业务方开始有效纠错？
>
> **可延展方向**：把"驻场前 48 小时要问清哪些问题"整理成一份可复用的访谈清单，用来降低对客户既有文档的依赖。

### 没有现成模型时怎么办："人给口袋子"与人机分工

大家可以回复一下。我们刚才在前面其实跟大家说了，对于这个 FDE，他整个这个开发过程以及在各个链路阶段，虽然他包括了很多和用户去沟通、去理解业务需求、处理相关的这个方案、技术选型呀，其实都是一些相关的软性技能，它并不是属于那种强技术性的 AI 项目开发、工作流的构建——那这一部分其实也是可以和 AI 来去进行协同和构建的。

所以这里面我们给大家去分享的一个思路就是：首先，关于这个业务的"函数"（待确认）、业务的含义怎么去进行构建，也就是如何去确定某一个具体领域下面的类型、属性和关系到底怎么去定，有两种方案。

那么一种呢，是如果有的话当然是最好的：直接基于它来去进行初版的构建，然后反复地去进行调试，根据你构建出来这个业务，结合到你的 Agent 去接入到你的这个业务模型的这个 Ontology 本体的模型里面去进行推理，在不同的业务场景下去进行测试；如果出现问题的话，就即时再去调整你的这个业务模型的约束规范——这个是其中的一种。

那么第二种就是：如果一旦没有的话怎么办？……我们的小伙伴说了"人给口袋"（待确认），对呀，就是"人给口袋子"（待确认）呀。那这种方式就是：没有的话，你把需求梳理出来，你把痛点需求梳理出来，你把技术架构方案梳理出来，以及要解决的事情梳理出来——人给口袋子，对，人给口袋子——让他呢去帮你出方案、去出判断、去出结论，然后由人工来去进行判断，根据他一步一步地去进行体验，然后不断地去进行修订和确认，不合适就调整，直到业务含义清楚。就是你一定在这个阶段不要自己去梳理啦，也不要去自己定义了，交给 AI 帮你去进行一个解决。所以这个是非常核心关键的这样一个逻辑。

所以我们呢一会呢肯定也是通过这样一个方式。当然我们肯定不是上来就一股脑子给大家去瞎聊，那我们在今天会给大家去提供三个不同的这样一个 Agent Skills，关于本体构建的这样一个技能包。这三个呢是我们团队内部使用的，今天是免费给我们公开课的、参与我们公开课的小伙伴，可以直接找我们的助教老师去领取到。一共有三个高质量的这个 Agent Skills，我们可以把它给到任意的这样一个编程模型，比如说 Codex、Claude Code都可以，让他去读取。

> **思考一下｜"AI 出方案、人工做判断"把风险放在了哪里**
>
> 作者给的第二种路径很具体：人先把需求、痛点、技术架构和要解决的问题梳理出来，再让 AI 出方案、出判断、出结论，人负责逐轮体验、修订、确诊。他把"不要自己定义"说成核心逻辑，但判断权仍然留在人手里。
>
> **可以追问**：如果每一轮都由人来判断"合适不合适"，那 AI 产出的方案质量实际上取决于人的建模经验——这种情况下，什么信号说明该停下来重新梳理需求，而不是继续让 AI 改？
>
> **可延展方向**：把这条路径拆成"人负责什么、AI 负责什么、谁签字"的职责表，用于评估团队里是否有人能承担最终的业务定义责任。

### 三个本体构建 Agent Skills 与 Ontology Design 的流程

那么这三个它的作用是这样的：首先第一个叫做 Ontology Design，他指的就是你把文本的内容输入进去以后，接收到这个 Ontology Design 里面，他是会给你推荐：对于你当前的这个业务场景，你怎么去确定类型、属性和关系，以及如何去明确边界，包括了对应的这个身份和约束——就是我们刚才给大家讲解的这些核心的这个技术点，就是这一部分相关的这个逻辑，我们都把它封装到了这个 Agent Skills 里面。

大家可以在这里面去看到，大家拿到、找我们助教老师拿到的这个包里面会有一个 `.agents`，里面这三个就是我们的 Skills 文件。我们看一下这个 Design，它其实定义的这个流程是这样的：就是本体设计部分，他会将用户要表达的知识去整理成可实施、可验证的本体方案；领域输入的是规模和使用工具，然后输入的这个范围呢，就是读取用户的目标、已有的建模要求、可用的这个资料，然后没有目标时就会识别覆盖范围、提出少量能够影响建模的用途，包括了工作的这个过程。我们把它标准化了什么？稳定的中文名称、"海裔"（待确认）编辑约定的抽取格式，然后匹配这个 OWL 的语义，对应的产物是什么。然后这里面还有很多的这个 reference，建模与方案以及本体方案的这样一个模板。那么这个呢大家是可以直接拿过来去进行使用的。

> **思考一下｜把建模经验封装成 Skill 意味着什么**
>
> 作者团队交付的不是一份提示词，而是三个带流程、带输入约定、带产物模板的 Skill：Design 负责把知识整理成可验证的本体方案，还规定了命名与抽取格式这类"标准化"环节。这等于把资深建模者的判断步骤固化下来。
>
> **可以追问**：当业务方看到 Design 给出的类型与边界建议时，他凭什么判断这份方案是"对业务的正确抽象"，而不是一个看起来合理的通用模板？
>
> **可延展方向**：把本体设计拆成"命名规范、边界判定、身份与约束"三类可检查项，看哪些环节适合固化进 Skill、哪些必须留在人身上。

### Codex 实战：用自然语言提示词一轮轮驱动建模

OK，那这一部分这下我们可以尝试地去进行一下实操。因为这个 Codex 生成这个环节会比较多，我们这里面呢为了方便大家更清晰地看到，我们就不使用这个 CLI 环境了，我们直接使用这个 Codex 环境。这里面我们给大家去看一下，我们这是建了一个 ontology 企业订单项目的链路，这里面就是我们给大家去梳理的、它完整的这样一个实战环境。

其实我们是可以接收到我们的这个 Skills，然后通过自然语言去进行一个提问。大家可以去看一下，比如我们做的事情就是我们输的这个提示是：我们要把这个客户的订单、我们要把客户订单和物流这些分散的数据关联起来，然后呢解决客服查询订单时需要反复切换系统的问题。那么对应的这个资料里面放了从不同系统收集的 CSV、PDF 等文件，你要去梳理一下这些文件有哪些业务对象、各自记录了什么、哪些信息能够关联起来，读不出来、互相矛盾的就直接指出来，不要乱猜。

然后呢通过这样的一个自然语言提示，大家可以看一下，我们来看啊，它的这个用时过程呢其实比较清晰：就是首先你能够看到它加载的——看，它是加载了我们内置的这个 Ontology Design 的技能，就是它通过这个自然语言呢是可以直接去加载到我们给大家提供的这样一个 Ontology Design 的这样一个技能。然后它给输出的就是核对以后——就是它会把我们工作区里面所有这个资料直接去进行一个读取，然后给我们的这个回复就是我们把它先收起来，我们把它收起来，就是它会首先给我们一部分内容：业务对象和记录——客户、订单、商品明细、商品仓库，包括装箱明细、物流事件、签收回执、客户订单。然后其中它会给我们发很多的这样一个分析的这个过程，你就跟它去仔细地聊，去看它的这些——包括了啊里面其实这里面就是 object，这里面就是对应的这个属性 properties。然后他会给我们提示说这些信息可以按照什么样的方式去进行关联：客户跟订单去做这个 link，然后订单和商品明细等等，有一系列的这样一个说明，然后有很多的这样一个建议。大家就根据他的一个回馈来去确定一下是否符合你对业务的这样一个理解或者需求。

然后呢我们第二轮其实给他对应的这个问答就是：根据我刚才读取到的材料，分析一下这个业务适合怎么去构建本体，我们需要从客户找到订单、再关联到商品，包括物流信息。就是你在和他去进行构建的这个过程中呢，你需要去明确地描述一下你当前这个痛点，以及你在第二阶段你要基于你所构建的这个本体去解决什么样的一个核心的业务问题，以及相应的这样一个指标。然后让他去提出建议：哪些应该作为对象、把哪些类型需要包括哪些属性。最后是你把对象——你把建议直接列在对话里，分清哪些是资料依据、哪些是你的建模建议。

然后呢他就给我们吧啦吧啦说了一堆，包括了候选的类型客户，然后保留的这个数据属性，为什么要独立划分。其实这里面大家就可以根据你模型返回给你的这个信息来去确定一下是否符合你对当前业务的定义，甚至是你把这些你觉得没问题了导出来以后给你的这个甲方客户或者是给你的内部的这个领导去看一下，也没有问题，没问题你就继续往下推进。

然后接下来我们要提出的这个问题呢，就是把这个业务模型确定下来，然后让他逐条地去确认对象的类型、属性和关系，然后逐条去说明他要干什么。其实这种呢就是我们要去驱动他逐个地去分析整个的这个业务流程，由我们来人工地去确定。所以这里面大家就可以去看到，我们有很多的这个对话的过程，包括了第一个阶段他要确定的是两个对象类型，一个是客户和订单，然后保留的理由是什么，我们这里是——可以按照推荐执行；第二部分就是商品的明细、订单、装箱的分配，然后推荐的关系说了一堆。然后接下来我们审核完成以后告诉他：这个装箱分配要做成独立的这个对象。然后接下来又做的是推荐的类型。包括我们和他进行了多轮的这样一个对话，你能够看到他输出还是很多的。包括我们也会在中间的这个过程呢去给他提供一些我们个人对于这个业务的这样一个理解。以及在最后呢，我们在进行推荐的时候，你会明确地去看到，在最后结论的时候我们提供的这样一个提示词，就是我们要让他按照刚才的这个内容来生成业务本体的 OWL。

> **思考一下｜这条实战链路的节奏是"AI 提案、人裁决"**
>
> 三轮提示词各有分工：第一轮让模型梳理对象与可关联字段，并声明"读不出来、矛盾的就直说，不要乱猜"；第二轮要求它把候选类型、属性、建模依据与资料依据分开列；第三轮把模型固定下来，逐条确认对象、属性、关系。作者特别强调装箱分配要独立成对象，这类裁决是人做的。
>
> **可以追问**：当模型给出的对象划分与业务方直觉冲突时（比如"装箱分配"到底该是对象、属性还是关系），有没有比"逐条讨论"更省成本的判定标准？
>

### Extract 与 Build：从对话结论到标准 `.owl` 文件

## 综合解读

本集的论点链是：Ontology 的价值要落到一条可跑的链路上，所以作者直接用电商订单场景做演示——先把散落在仓储、订单、客服、签收、商品中心、物流接口与业务规范里的数据摆出来，声明这是"原始数据"；接着给出方案，把 79 份 CSV、PDF、JSON、`TXT`与 markdown 业务资料统一交给 Codex 读取、分析，在过程中确定对象、关系与属性，最后产出 `.owl` 文件并导入系统；为了不让这一步变成黑箱，他先抛出建模的真正难点——业务含义如何定义，并给出两条路径：有既有模型就基于它构建、反复调试，把本体接进 Agent 在不同场景下测试，出问题就即时调整约束规范；没有既有模型就把需求、痛点、技术架构与要解决的问题梳理出来，让 AI 出方案、出判断、出结论，由人工逐轮判断、修订、确认。随后他用三个团队内部的 Agent Skills 承接这个流程：Ontology Design 负责推荐类型、属性、关系并明确边界、身份与约束，Ontology Extract 负责按已确认的本体方案从原始材料提取知识，Ontology Build 负责把知识模型转成标准 `.owl` 文件；中间的实战通过三轮自然语言提示词完成——先梳理业务对象与可关联字段、再让模型给出候选类型与建模建议、最后逐条确认对象类型、属性和关系，其间由人裁决（例如把装箱分配独立成对象）。结尾他把本体定位为"给 Agent 提供上下文的关系网"，并预告下一集接入 Agent 做自然语言查单、异常处理审查与状态更新。

需要说明的是，以上是**视频作者在口播中提出的做法与判断**，属于教学演示与经验性归纳，不是本集验证过的结论。按源文件头部记录，本集事实主张状态仍为 `unknown / 待外部核验`；"把这些资料统一交给 Codex 解析不符合行业标准规范""文件格式只影响读取方式、不决定业务模型""本体是给 Agent 的上下文核心信息"这类说法，以及 79 份资料、8 个实战案例、60 个小时课程等数字，都属于作者的主张或课程介绍，不宜直接当作既定事实引用。作者还明确说，本集因时间原因没有带观众实际动手，演示的是 Codex 应用链路里已经跑完的过程，这一点在引用时应当保留。

**我的分析**：这一集真正值得迁移的不是某个提示词，而是三段式的建模节奏——先对账（让模型把文件里的业务对象、各自记录什么、哪些字段能关联说清楚，并要求"读不出来或互相矛盾就直接指出，不要乱猜"），再提案（要求把候选类型、属性、保留理由逐条列出，并分清哪些是资料依据、哪些是建模建议），最后裁决（把模型固定下来，由人逐条确认对象、属性与关系）。这个节奏解决的是"模型输出看着都对、但没人负责"的问题：把每次输出的性质标清楚，人只需要在关键分叉上做决定。另一个观察是作者对"AI 出方案"的用法——他并不要求 AI 一次给出正确答案，而是要求它给出可判断的候选与理由，判断权始终留在人手里，这一点和他在集末把本体定位成"上下文提供者"是一致的：本体的正确性最终由业务问题是否被回答来检验。

**边界与反例**：口播中的两处简化值得留意。其一，作者自己承认把全部业务资料直接交给 Codex 不是行业标准做法，真实系统要按业务场景单独构建解析链路，因此这套演示链路在数据敏感、来源异构或体量更大的场景下未必成立。其二，"打包成 Skill 就能完成建模"的说法隐含了模型能可靠遵守流程、且业务方有人能判断输出对错这两个前提；如果团队里没有能承担业务定义责任的人，三轮对话很容易退化成"看起来合理"的通用模板。此外，作者对"没有现成模型就让 AI 出方案"的推荐，缺少失败案例与验收标准的对照说明；"更快的实现思路""最快捷的技术方案"这类表述也只是预告，本集并未给出可比的数据。至于把装箱分配独立成对象这类具体裁决，属于该业务场景下的选择，换一个业务域未必成立。

**可迁移素材**：本集可直接复用的有几项——三轮提示词的模板结构（业务对象对账 / 建模建议与依据分离 / 逐条确认对象-属性-关系）；"读不出来、互相矛盾的直接指出，不要乱猜"这条对模型的显式约束；三个 Skill 的职责划分（Design 定边界与约束、Extract 从原始材料提知识、Build 生成标准 `.owl`）；以及"文件格式只影响读取方式、不决定业务模型"这条判断。对要做企业知识工程的团队来说，还可以把本集当成一份链路检查表：原始资料清单、业务对象清单、可关联字段、身份与约束、产物格式、导入目标系统，逐项对照是否齐备。

**ASR 不确定项**：源文件头部记录的术语纠正为把 `Ontology`/`ontology` 统一为 Ontology（共 7 处），本文沿用。此外，转写中同一常见词存在多种误识，本文按上下文取了唯一写法并在此说明：`语异` → 语义、`定来中心` → 订单中心、`仓复系统` → 仓储系统、`出户` → 出货、`链络` → 链路、`Skema` → Schema、`WL`/`WOL`/`点OWL` → OWL / `.owl`、`倒入` → 导入、`住场` → 驻场、`假方`/`假防客户` → 甲方、`作家老师`/`朱家老师`/`主要老师` → 助教老师、`政客` → 正课、`路波` → 录播、`答应群` → 答疑群、`实施的去提问` → 随时地提问、`供开课` → 公开课、`体验影` → 体验营、`合对` → 核对、`A正`/`A政`/`A政策` → Agent、`揭露` → 接入、`资料语言` → 自然语言、`牵手回纸` → 签收回执、`出版` → 初版、`文念格式` → 文件格式、`实仓` → 实操、`体问` → 提问、`体制词`/`体词词`/`体识词`/`体式` → 提示词、`名系` → 明细（商品明细、装箱明细），以及 `我们在下级啊` 一类口语重复按语义合并。仍无法可靠识别、保留原文并就地标记 `待确认` 的有："科词"、"TST"、"参数对方"、"人给口袋"/"人给口袋子"、`close code`、业务"函数"、"海裔"、"语义消息"、`Scuse`/`sluice`/`Skill`、从当前的"书"、"大约 7B"、`Design`（ASR 原文"比赛"）、"知识突破"、"新科"、`lambreg`/`graphreg`/`mvk`、"硬设"、"欧塞亚"、"增量能性"、"时间课"、"更刻"、"再个"，以及数据清单里的"答案"、"物流与回答"、"客户与规范"。这些均未做猜测性修正，引用时请以原视频为准；Ontology、Agent、RAG、Codex、OWL、Schema、Ontology Design、Ontology Extract、Ontology Build、Agent Skills、CSV、PDF、JSON、markdown、CLI 等术语按视频语境与分P标题保留其通用写法。
