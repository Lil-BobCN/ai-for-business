## 口播文章

### 本体与 Agent 协同要回答的问题

视频作者在这段口播中提出，接下来我们要重点讨论的，就是关于这个本体它和这个 Agent 到底如何去进行协同。首先，我们在上一个阶段能够拿到的是：如果我们输入一些信息，它是可以通过检索的这种算法，从业务模型里面、从我们的本体业务模型里面，去找到对应的这样一个对象以及他们之间的这个关系。而对于真实的这个业务流程来说，肯定不可能是把这个信息拿出来就够了，而是我们需要去提供 Agent，让他去问答，或者是执行其他的这样一个链路。

那么这里面就涉及了：我们到底应该如何去接入 Agent，让他去读取你的业务本体模型里面检索出来的这个信息，来用于下游的这样一个工作任务？这个就是本体与 Agent 的协同的一个核心的问题，就是我们现在 Agent 还需要接入什么，就是我们要明确地去确定一下：Agent 他在采用什么样一个方式，可以去连接到你的本体。

> **思考一下｜检索服务与 Agent 之间那条看不见的边界**
>
> 作者把这一集的起点放在一个很容易被跳过的接缝上：上游已经能"找到对象和关系"，下游却要"能问答、能执行"。这两件事之间缺的不是模型能力，而是一份明确的接入契约——谁提供什么、以什么形式提供、下游怎么用。把它讲清楚，本体才从一份数据文件变成一项服务。
>
> **可以追问**：如果接入契约只约定"能查到数据"，却没有约定返回哪些字段、失败时怎么表达，Agent 会在什么环节开始编答案？
>
> **可延展方向**：把"本体 → Agent"的接入点写成一份接口说明（输入、输出、错误语义、可追溯字段），作为本体交付物的固定附件。

### GraphDB 的做法：抽取 schema，再用查询工具去查

那么这里面其实我们在这个 PPT 里面是有这样的一个说明。就是其实对于 GraphDB，它的一个公开的做法就是：对于本体，它不是有这个 schema 吗？这个本体我们都是定义它非常详细的这样一个 schema，然后它去进行一个提取，然后通过对象标识的这样一个方式来去进行查找，然后内置 SPARQL 的这样一个查询工具。其实就非常类似于将自然语言转化成 NL2SQL 去查数据库，将自然语言转化成 SPARQL 去查知识图谱。

然后只不过本体对于我们来说，就是提取它的这个 schema，来去通过这个 SPARQL 做它的一个查询的工具。关于这个怎么去进行检索，我们在刚才已经给大家去做了一个详细的介绍。所以这里面就有几个问题：就是当我们在实际地去进行实践的时候，那么我们如何让 Agent 去接入我们的业务模型本体，去写相关的这个 SPARQL？

### 最轻的接入：把高频任务写成 function calling

那么最简单的这个方式，就是通过 function calling 的这样一个能力，就是函数调用的这个能力。那么我们可以去把一些高频的这样一个任务去把它定义成所谓的一个函数，这个函数大家就可以理解成外部调用的这样一个工具，把所有的这个逻辑都给它写进去。那么对于这个 Agent 来说，他去通过意图识别的这样一个方式，去检索不同的这样一个 function calling 来去做。

其实这种做法，对于 Palantir，他们其实是在官博上、他们的官方博客上，应该是官方文档上，是有这样的一个 logic function 的这样一个概念，也就是他们会倾向于把他们在这个领域内构建的这样一个本体的业务模型，去把它做成可供 Agent 调用的这个 function，而核心的这个逻辑就是通过 function calling，也就是 tool calling 来去进行的一个构建。这个是这一部分的逻辑。

所以这里面接入了这个 function calling，那我们就对于这些高频的问题，或者是如果我们涉及到业务更新、业务的这个模型的更新，或者是我们本体模型内部数据的一些更新，其实都可以通过这样的一个形式来去进行一个构建。那我们在本体里面不是有很多的这种业务的规则吗？有很多这种数据的校验吗？那我们都可以把它去做成 function calling 的、或者是 tool calling 的这样一个约束和规范，只要一触发，我们就可以去操作我们的 OWL 的、或者是这个业务模型的本体的数据，来去完成对应链路的这样一个操作，这个是完全没有任何问题的。其实它很像我们之前去操作这个知识图谱，也是一样的这个逻辑。

> **思考一下｜当业务规则变成可以触发的接口**
>
> 作者这句话里藏着一个不小的动作：本体里的业务规则与数据校验，不再只是写在模型里的约束，而是被封装成"一触发就能操作本体数据"的函数。规则的载体从文档变成了接口，好处是可执行、可复用；代价是它从此有了版本、有了责任人、有了"改错一处影响一片"的风险。
>
> **可以追问**：当一条业务规则发生变更时，应该由谁来决定是改本体里的约束，还是改那个已经上线的 function？
>
> **可延展方向**：为每条被封装的业务规则补一张卡片（规则原文、触发条件、影响的数据、责任人、变更记录），让"规则即接口"这件事可审计。

### 四种接入形态：function calling、MCP、sub agents 与 skills

那么重点我们要给大家去进行的一个说明就是：对于这个本体，我们把本体它的一个检索的服务确实可以去封装，或者是做成一个其中可用的这个工具。那么对于工具来说，模型去调用工具它是可以有多种的形式，那这里主要是这几种：

首先第一个叫做 function calling，其实也就是 tool calling，现在统一都改名叫 tool calling；那么第二个叫做 MCP；那么第三个叫做 sub agents；第四个叫做 skills。

那这几种怎么去和我们的 Agent 来去进行协同？也就是大家可以简单理解成：我到底是把这个本体它的这个业务模型的搜索的渠道、搜索这个接口，去做成 tool calling，还是去做成 MCP，还是去做成 Agent，还是去做成 skills？

其实从结果上来看都可以，具体就要看你的一个架构的设计。如果是你要是设计到一些全链路的，包括了查询、更新、定期巡解（待确认），然后校验等等，那么推荐大家可以去尝试 MCP。因为对于 MCP，我在一个 MCP 里面可以封装成多个不同的这样一个子函数来去完成一个校验，当然它要承担的这个问题就是它要消耗更多的这样上下文，以及它的一个服务延时的这个问题。

而对于一些轻量的，我们是可以通过 skills 来去进行一个构建。那么对于 sub agents，sub agents 它能够承担的这个工作其实是更多的，它不仅仅是调用工具的这样一个其中的链路，而是 sub agents 可以承担多种不同渠道的，而我又可以去调用工具，我又可以执行相关的这个任务，我甚至可以把一些 workflow 放进去。那么同理，sub agents 和 Agent 的 skills，他们两个就可以去承担——如果你设计到在你的本体、在某一些场景下构建的过程中，设计到一些自定义的，或者是需要由 Agent 来自主驱动的这种工作流，那么不妨你就把它封装成这样的一个 skills。这个就是 Agent 和它去构建的这样一个链路。

> **思考一下｜同一种能力，四种封装，选的是成本结构**
>
> 作者说"从结果上来看都可以"，这句话是真的，但它也把真正的差异推到了后面：封装成 skills、tool calling、MCP 还是 sub agents，决定的是上下文消耗、调用延时、可观测性和权限边界。他明确点出了 MCP 的两项代价（上下文与服务延时），但没有展开它在鉴权、审计与版本兼容上的要求——而这恰恰是"哪一种更适合上生产"的关键。
>
> **可以追问**：如果同一个检索能力同时存在 skills 与 MCP 两个版本，团队应该按什么标准决定保留哪一个、废弃哪一个？
>
> **可延展方向**：为四种封装形态各写一行成本项（上下文、延时、可观测性、权限与审计、维护成本），做成一张选型对照表，用在接入方案评审上。

### 三类任务的组织方式：workflow、工具调用与 sub agents

所以针对于这种任务的组织方式，像大家比较关注的 Agent skills 这个 workflow，或者是工具调用，它们到底如何去应用于本体在业务建模的这个过程中和 Agent 这样一个落地的方案，大家可以通过这三个方面去简单地理解一下：

那么首先第一个，固定的这个流程与分支，那你不妨就直接做成这种 workflow，或者是 Agent skills 编排的这样一个形式。那么如果你要是想要去通过外部的这种工具，由 Agent 根据用户的这个意图，或者是你任务的意图，自主地去决定怎么去操作本体业务模型里面的数据，那么你不妨就把它去封装成 tool calling 或者是 MCP 的这种形式。那么第三个，如果是涉及到一些比较复杂的，你就通过这种 sub agents，或者是 workflow 加 Agent 这样一个形式，比如我们经典的人机交互的这样一个流程，那肯定我们要把它做成 workflow 的，你要在这个 workflow 里面明确地定义：在什么样的一个场景下，我的人工需要去进行一个介入。这个是我们要去处理以及考虑的这样一个问题。

所以它就涉及到大家在面对着一些你真实遇到的这个问题，或者是你想解决的这样一个需求痛点，它在技术选型上，包括你在最终实现效果验证上的这样一个方案的设计，这个就非常考验大家的这样一个能力了。因为它并没有通用的这样一个解决方案，而是需要大家根据实际的情况来灵活地进行选择，甚至是没有一种最佳的这样一个实践，你只有实测下来，它只要是能够达到最终的这样一个效果，那它就是一个好的方案。所以大家千万不要盲目地去追求到底在某些场景下什么是最佳实践，你不妨就按照你自己的思路和你自己的这样一个技术的理解，来去进行一下尝试。

> **思考一下｜"没有最佳实践"这句话的松与紧**
>
> 作者这条建议的前半句是松的：别追最佳实践，按自己的理解先试。后半句其实很紧：判断标准是"实测下来能不能达到最终效果"。松紧之间的缺口是——"最终效果"由谁定义、用什么样本测、测到什么程度算过。如果没有这三样，实测很容易退化成"演示时跑通了一次"。
>
> **可以追问**：一个本体接入方案在什么条件下可以判定"通过了实测"？是问题集全对，还是关键场景不出现事实性错误？
>
> **可延展方向**：把三类任务分流规则（固定流程／自主决策／人工介入）与一份最小验收题库绑定，让每次选型都有对应的验证动作，而不只是架构偏好。

### 一次任务的完整生命周期

所以对于这个 Agent 的协同，我们可以去通过它的一个任务的构建过程来去看一下。像这种任务入口，我们再去提交一个相关的一个问题，然后对于 Agent，它肯定是可以通过外部的这种事实工具或者是文档工具，来去定位和拿到相关对应的这样一个参数的接口，然后如果是涉及到文档查询的话，那么它就可以通过 RAG 的这样一个形式来去额外地去提取补充的这样一个外部的知识。

这个是希望大家能够看到，对于这个 Agent 和本体再去进行构建、或者是构建业务流程的这个过程中，它的一个完整的生命周期。如果我们简化来看，大致就是这样的一个情况。

OK，然后接下来呢，其实我们就来做一个实战。我们说了很多这个 Agent 和本体来去进行构建，它们之间可以通过什么 function calling，可以通过 MCP，可以通过 Agent skills，那对于我们来说，它的一个实际的效果到底是什么呢？

### 实战演示：从"奶泡壶为什么还没到"到订单客服回复

我们来看一下我们现在构建的这样一个系统。首先大家拿到的这个项目的系统源码它是在这里——我把我的头像先隐藏一下。这个大家找到我们的这个 AI 的服务台，首先我们所构建的这个本体模型它是属于一个客户的订单业务本体，那么这个客户的订单业务本体，它本来里面就有很多的这个物流的信息，或者是商品信息，以及订单的这个信息。

那么当用户来去进行提问的时候，比方说我们在这个平台上，大家看左侧呢，企业的 AI 服务台这个是属于给我们的这个客户用的，那么右侧呢，这里面有一个用户视角，就是用户可以在这里面提出相关的这个问题，比如"我的这个订单咖啡机收到了，奶泡壶为什么还没有到"，这个是用户进行了一个提问、发送。

OK，用户发送完成以后，你作为这个 AI——或者是你要借助 AI 去解决你查单又慢又容易出错这个问题——你通过这样一个系统想要去进行解决，那么是不是用户的这个问题，我们就考虑我们现在构建的这个 Agent 系统是不是可以完成这一部分的查单呢？所以大家看右侧，当用户输入这个问题以后，他这个服务请求都放在这里面了，说用户现在有这个问题过来了，然后我们呢，让我们构建出来的这个 Agent 来去进行处理，他去帮我们检查一下这个订单到底是什么样的一个情况。

然后我们点击让 Agent 去进行一个处理，大家看 Agent 就开始去选择下一步。他整个的这个过程就是：首先第一个他要去定位一下客户的订单，那么这个订单呢，就是这个订单——他的这个，稍等一下，看第一个查询订单，他的这个订单呢是客户的张三，关联的商品是咖啡机主机，然后他执行的这个参数，就是看这里面是不是 tool calling 的标准的这样一个调用的流程，就是相当于我们在 Agent 里面呀，去和本体的这个业务模型去通过 function calling、或者这个 tool calling 来去构建相关的这个关联的联系。

然后我们再往下看，他呢接下来又会去查询本体的关联的这个事实，这里面查询的就是这个明细编号、销售渠道是哪里、客户是什么，然后这次清单的这个完成性包括了一个咖啡机主机、一个奶泡壶，然后咖啡机主机是已经签收了，这个奶泡壶是运输中的这样一个状态，然后呢装箱的明细啊，包括了本阶段的这个结果。他一步一步地全部都查完了以后呢，他会发现，啊，这里面给我们最终的这样一个回复，就是："你好，感谢你的咨询，根据我们的这个查询呢，你的这个订单主机已签收了，然后奶泡壶正在运输中，尚未签收。"那你作为这个客服，是不是可以直接在这里面去回复用户？哎，你看，在右侧是不是就回复了。

所以这个视角呢，就是我们通过这样的一个页面，把它让大家直观地去感受到：当我们这个系统如果是给用户、去在给这个客服去解决查单慢的这个问题下，如果我们通过构建出来的这个本体模型，然后加上 Agent，当用户的这个问题进来以后，他的一个完整的执行链路，也就是去检索我们本体中的业务模型，然后生成对应的这个回复。其实这个就是我们刚才说的，Agent 和本体啊他们之间协同的这样一个规范。

所以通过这个场景呢，大家也可以实际地去拿到我们的这个项目啊，来去进行一下测试。然后这里面啊，唯一需要说明的就是，我们这个集成的是 OpenRouter，然后大家需要填写一下自己的这个 OpenRouter 的 Key，然后就可以快速地去进行一个试用了。

OK，然后我们在这个 PPT 里面啊，也把相关的这个执行的这个链路啊也给大家去做了一个相关的说明，包括了每一个场景，这里面也能够看到：其实当我们去、用户提出一些问题的时候，我们如果借助 AI 客服去进行查单，他就会先去针对我们查询这个订单去对象进行一个定位，然后去查询他的关联，然后去查询他的状态，最后通过我们的规则去进行校验。整个的这个过程呢，大家都是非常透明的，是可以直接地去看到的，这个是没有任何的问题。

然后我们第二个啊，就是还有一个——我们刚才说了，我们可以在整个的这个交互链路中去给他接入一些这个人机交互的这样一个流程。当然这个人机交互的流程呢，我们在下半场，就是我们今天直播的这个下半场，给大家去进行一个讲解。

> **思考一下｜"每一步都看得见"本身是不是交付物**
>
> 这段演示里最值得记的不是那句客服回复，而是回复之前的每一步都摆在界面上：定位了哪个对象、用了什么工具、传了哪些参数、查回哪些事实、按哪条规则校验。这种可见性让业务方能复核"答案是怎么来的"，也让问题定位从"模型答错了"变成"哪一步取数错了"。
>
> **可以追问**：如果真实订单出现拆单、缺货、部分退货或跨渠道下单，这套"定位 → 关联 → 状态 → 校验"的顺序会在哪一步先失效？
>

**作者的论点链（视频观点）。** 这一集承接上一集的检索工作台，回答的是"本体检索出来的信息，怎么真正交到 Agent 手里"。作者的推进顺序是：先定义问题——能检索出对象与关系不等于业务闭环，还要让 Agent 能问答、能执行，所以要明确"Agent 用什么方式连到本体"；再给出行业公开做法——GraphDB 抽取本体 schema、通过对象标识查找、内置 SPARQL 查询工具，本质上是"把自然语言转成 SPARQL 去查知识图谱"，与 NL2SQL 同构；然后把接入手段分成四种形态：function calling／tool calling、MCP、sub agents、skills，并给出各自的适配面——全链路（查询、更新、定期巡解（待确认）、校验）建议用 MCP，因为一个 MCP 里能封装多个子函数，代价是上下文消耗与服务延时；轻量任务用 skills；复杂任务用 sub agents 或 workflow 加 Agent。他还特别提到 Palantir 官方文档里的 logic function，即把领域内构建的本体业务模型做成可供 Agent 调用的 function。接着是三类任务的组织建议：固定流程与分支做成 workflow 或 Agent skills 编排；需要 Agent 按意图自主决定怎么操作本体数据的，封装成 tool calling 或 MCP；涉及人工介入的复杂流程做成 workflow 加 Agent，并在 workflow 里显式定义人工介入的场景——他同时强调这里没有通用方案、也没有最佳实践，"实测下来能达到效果就是好方案"。最后用一个可运行的订单客服演示收束：用户问"咖啡机收到了、奶泡壶为什么还没到"，Agent 依次做订单定位（客户张三、关联商品咖啡机主机）、以 tool calling 的标准流程调用本体、查询关联事实（明细编号、销售渠道、客户、清单完整性、装箱明细）、拿到状态（咖啡机主机已签收、奶泡壶运输中）、按规则校验，再生成一段客服可直接发出的回复；底层是 LangGraph 做编排、Semantica 提供检索算法、直接读取原始 OWL 本体文件。直播后半段转入中场答疑与新课介绍：零基础学 FDE 的五个阶段（懂业务与方案设计、必须有一个能干活的 Agent 并学会驾驭它、Agent 与 RAG 的技术选型、企业知识治理与 Ontology、业务建模与项目实战），以及课程的六个阶段、八大项目、交付物与直播间提问。

**隐含前提与边界（我的分析）。** 这条论述有几处值得单独拎出来看。第一，作者把四种接入形态的差异归结为"从结果上来看都可以，具体看架构设计"，这句话降低了选型焦虑，但也把真正的成本项推到了后面：他在 MCP 上只点了上下文消耗与服务延时，没有展开鉴权、审计、版本兼容与可观测性——而这几点在生产环境里往往比延时更早暴露问题。第二，"没有最佳实践，只有实测效果"这半句是对的，但它默认了"效果"是可判定的；如果没有问题集、没有样本量、没有失败定义，实测很容易缩水成"演示时跑通一次"，这也是他自己在订单演示环节反复强调"整个过程非常透明"的原因——透明是复核的前提。第三，把业务规则与数据校验一并封装成"一触发就能操作本体数据"的函数，等于把业务规则从文档推进到了接口；接口一旦发布就有版本、有责任人、有回归测试的问题，这一层作者没有展开，而它恰恰是交付后最容易腐烂的地方。第四，演示本身是有说服力的，但演示场景是干净的：订单、商品、物流状态都清晰，没有拆单、缺货、部分退货、跨渠道下单这类真实例外；顺序化的"定位 → 关联 → 状态 → 校验"在遇到例外时是否需要回退与重规划，视频里没有给出答案。第五，直播后半段属于商业介绍，其中的薪资区间、岗位年限、证书含金量、接单收入等都属于作者的单方陈述，与前面技术内容的证据强度完全不同，阅读时应当分开对待。

**待外部核验的事实。** 本集出现的具体数字、产品判断与承诺均来自视频作者的单方陈述，未经独立核验：GraphDB"公开做法"的定位、Palantir 的 logic function 概念、四种接入形态的划分与各自适用面、订单客服演示中的执行细节（客户张三、商品咖啡机主机与奶泡壶、明细编号与销售渠道、清单完整性与装箱明细、已签收与运输中状态、生成的客服回复），"集成 OpenRouter 并需自备 Key 即可试用"的说法，底层"LangGraph 编排 + Semantica 检索 + 直接读取 OWL 文件"的架构说法，两个项目案例与课件、源码、数据集、白皮书、零基础可落地作品集模板的领取方式与直播口令，课程时长（60 小时／60+ 小时、直播课约两个月）、六大阶段划分、八大项目构成（三个热门项目、两个 1:1 工业级复刻、两个企业落地百万级项目、一个综合结课大作业）与交付物（12 个可复用 Agent、6 项项目结果、七个可写进简历的项目），薪资与岗位口径（零基础一般 20–40K，蚂蚁 1–3 年、高阶岗 3–5 年），工信部发文与"8 月份发布"的时间点及相关链接，以及"课程从 23 年开课""录播长期可看""答疑群不关闭""提供工信部人工智能应用工程师报考渠道"等服务承诺。这些都需要按项目主页、官方文档与政策原文另行核验。

**可迁移素材。** 对做企业 AI 交付的人，这一集里有五样能直接搬走的东西：一是"同一能力、四种封装"的对照视角（function calling／MCP／sub agents／skills × 上下文、延时、可观测性、权限审计、维护成本），可以直接当接入方案的评审表；二是三类任务的分流规则——固定流程走 workflow 或 Agent skills，需要自主决策的走 tool calling 或 MCP，涉及人工介入的走 workflow 加 Agent 并在流程里写明介入条件——这是一条低成本的选型起点；三是演示里"每一步工具调用与参数都可见"的做法，可以作为本体类项目验收时的展示要求；四是把业务规则与数据校验封装成可触发接口的路径，它确实能把规则从文档变成可执行能力，但必须自带版本与责任人；五是直播后半段的五阶段学习路径与"业务调研 → 需求与方案拆解 → 数据治理 → 开发 → 评测上线 → 迭代"的项目链路，可以直接拿来当个人能力自评表或项目复盘模板，对照岗位 JD 做差距分析。
