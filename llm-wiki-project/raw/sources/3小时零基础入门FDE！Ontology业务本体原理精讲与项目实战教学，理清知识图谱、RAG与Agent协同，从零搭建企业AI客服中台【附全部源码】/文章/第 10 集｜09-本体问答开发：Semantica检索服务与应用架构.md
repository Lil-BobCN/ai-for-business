### 为什么不能把检索能力直接丢给 Codex

视频作者在这段口播中提出，接下来就要去考虑一下：通过这样的一个方式，我们快速地知道了，当我们构建出来的这个业务本体模型，其实是可以通过一些方式来完成它的快速检索的——也就是我们基于某一个实体，也或者是某一个关系，能够通过我们介绍的这个结构化的查询，或者是图的这种遍历，或者是我们加上语义的 embedding 加上图扩展这三种方式，来完成对应的这样一个数据的搜索。那如果我们去把它封装成“四个优势”（待确认），在企业里面部署，是不是可行呢？

其实肯定是不行的。为什么不行呢？就是因为你企业里面这个数据它是日常运行的，而且它这个数据量很大，它也需要一个稳定的环境。你直接通过“四个优势”（待确认）把它丢给 Codex，肯定是不行的。我们要把它做成这种系统，因为我们要考虑：当你企业里面的这个数据是持续变化的，一直要进行一些业务或者是功能量度上的这些更新，或者是有很多的用户持续地去进行访问；也包括了你在构建的这个过程中，你需要知道你的每一个过程，它的一个追溯的来源到底是不是符合你的这样一个事实的依据。

那么这一些呢，我们通过 scales（待确认）加一个 Agent 肯定是不行的，我们肯定需要一些更加复杂的这样一个处理的流程。所以这里面我们不得不去考虑一下：现在是不是有一些好用的这些开源框架，能够把我们刚才所介绍的这种检索的策略、构建实体、构建本体的这样一个业务模型，包括 Agent 的推理的全部的功能量度全部可以集成进来，我们可以调一些接口就实现了呢？

### 检索链路怎么走：配置组合、种子实体与 BFS 扩展

大家如果刚才要是理解了我们给大家去介绍的这个本体，他在进行搜索这个过程中，他是怎么去搜索我们本体业务模型里面的这些数据的，那么你再去理解这个 Semantica 他的一个底层的实现原理，基本上不会有太大一个出入。那么首先第一个，他就是会按照这个配置组合来去进行一个候选，那你可以去通过图的这种结构的模式，也可以通过向量的一个形式，来去构建你的整个的这个检索的路径，这个就取决于你在存储原始数据的时候，你以什么样一个方式来去进行存储。

然后呢，他会有一个取得种子实体的这样一个链路：就是把你输入的这个自然语言，通过 embedding 的这个方式来去找到最相关的这样一个实体，然后呢做一些基本的什么去重、清洗、校验的这样一些基础的操作，然后他把它称之为这种种子实体。接下来就把这个种子实体放到我们的这个图的路径搜索里面，通过 BFS 这种方式来去向外扩展，你可以去设定——我要检索到几条的这样一个参数，最后就会返回最后的一个结果。他是 Semantica 他的一个实现的思路，就是我们刚才给大家讲解的这样一个链路。好啊，这个是他搜索的这样一个链路。

> **思考一下｜种子实体与扩展深度：检索质量的两个旋钮**
>
> 这条链路里有两个可调的量：输入被 embedding 命中成哪个“种子实体”，以及从种子出发用 BFS 向外扩展几跳、取几条。前者决定起点对不对，后者决定召回多少、噪声多少。作者把它讲成实现原理，但这两个旋钮对最终答案的影响，其实比模型选型更直接。

### 检索之后怎么回答：上下文直答与规则引擎推导

那么对于 Semantica，当我们通过这个本体模型找到了对应的这样一个关系以后，或者是我们获取到了最终有效的这样一个实体内容，我们到底怎么去引导模型来去回答问题？或者是能不能够基于他检索出来的这个实体之间的链路关系，来去推导一些在我们原本本体模型建模里面没有构建的这样一些关系，是不是可以呢？其实他是提供了两种的这样一个链路。

那么第一个呢，就是我们可以直接让大模型根据他经过本体业务模型搜索的检索算法搜索出来的这个信息以后，直接把它做成上下文来回答最终的这样一个结果，这个是其中一种，就非常类似于 RAG 的这样一个流程。

那么第二个呢，就是我们可以借助于 Semantica 里面的这个规则引擎来去进行一些推导。那么举个例子，比如你的这个实体里面、这个本体的业务模型里面介绍了这个小李是经理，然后你制定了相关的这个规则——这个规则我们在昨天已经跟大家说了，你的这个业务规则是可以在本体的这样一个、在构建本体的时候去构建这样的一个规则的。所以如果你有对应的规则，就是“经理也是员工”，那么哪怕你的本体里面根本就没有去定义说小李是员工，那么经过本体的这样一个检索路径的算法，他一定也可以去推出小李他就也是一个员工。

所以这个就是本体：当你去定义好了他这个业务规则，以及他的这个校验的格式，以及对应的这个 SKMR（待确认）的规范以后，他相较于我们从知识图谱里面去进行查询的话，他是可以去进行有效的推导的，这个是大家需要知道的。

> **思考一下｜检索与推理的分界线**
>
> 这一段给出了本体区别于知识图谱的一个具体证据：本体里没写“小李是员工”，但因为有“经理也是员工”的规则，系统仍然能推导出来。也就是说，答案可以来自规则而不是来自数据本身——这既是能力，也意味着规则写错了会稳定地错。
>
> **可以追问**：业务规则由谁维护、什么时候更新？如果规则和事实数据发生冲突，系统应该相信哪一边？
>
> **可延展方向**：为规则推理设计一套最小治理流程（规则来源、审核人、变更记录、冲突处理），避免“能推导”退化成“推导出没人能解释的结论”。

## 综合解读

**作者的论点链（视频观点）。** 这一集承接上一集的“把资料跑成 OWL 本体”，回答的是“建好之后怎么用”。作者的推进顺序是：先把上一集讲过的三种检索方式（结构化查询、图遍历、语义 embedding 加图扩展）复述一遍，然后直接判定“把它封装起来丢给 Codex 在企业里部署”不可行，理由是企业数据日常运行、数据量大、需要稳定环境、持续变化、并发访问，并且构建过程必须能追溯到事实依据；接着他给出替代方案——找一个开源框架，把检索策略、实体与本体构建、Agent 推理的能力都集成进来，用接口调用；再逐层展开 Semantica 的四层能力（数据处理、本体构建与校验、三种检索、应用接入与溯源）、它的底层检索链路（配置组合生成候选 → embedding 命中种子实体并做去重清洗校验 → BFS 向外扩展并可设定条数 → 返回结果），以及检索之后引导模型回答的两条链路（把检索结果做成上下文直答，接近 RAG 流程；或借规则引擎推导出本体里没写的关系，例如由“小李是经理”和“经理也是员工”推出“小李是员工”）；最后落到他自己的两个交付物：一个基于 `ask` 接口的问答小项目，和一个前后端分离、提供三个服务、可导入 `.owl` 的本体应用工作台。

**隐含前提与边界（我的分析）。** 这条论述成立依赖几个作者没有展开的前提。第一，他默认“检索结果里的引用依据与来源文件”足以支撑业务侧复核，但没有讨论当多个来源文件互相矛盾时该怎么办。第二，规则引擎推导这条路径的价值，完全建立在业务规则本身被正确建模与持续维护之上——作者举的“经理也是员工”是稳定规则，而真实业务里的规则往往是带时间、带例外、带审批口径的，规则一旦写错，系统会稳定地推出错误结论。第三，作者反复把“用接口调用”当作复杂度已经解决的标志，但对交付方来说，复杂度只是从“实现检索”转移到了“选择与配置”：用图结构还是向量存储、BFS 扩几跳、取几条、选哪个模型，这些决定仍然要人来做。第四，作者用“封装成四个优势 / `scales` 加一个 Agent 不行”来否定轻量方案，这个判断在演示场景下成立，但他自己也承认那套轻量做法本来就是体验课的权宜手段——所以这里更像是“生产 vs 演示”的对比，而不是“框架 vs 工具”的对比。

**待外部核验的事实。** 本集出现的具体数字与产品判断均来自视频作者的单方陈述，未经独立核验：Semantica“本体与图数据的开源框架”“14k Star”“想直接用本体开源方案时的首选之一”，四层能力划分与接口命名（含 `retriever query with reasoning`、`context.context_retriever`、`ask` 等），部署与使用形态清单（源码部署、CLI、REST API、`MTP`、`Explore`、SDK），项目文件构成（`adapt`、`ontology`、`openrouter`、`demo.py`、`data/业务本体.owl`），工作台“三个服务”“前后端分离”“React + 发词 EPI（疑为 FastAPI）”的分层说法，以及资料领取与 PPT 说明等。值得记一笔的是：按本系列第 1 集的转写，作者当时说的 Star 数是 13000 多，本集说 14k——两个数字都属作者口播，应以项目主页为准。此外，本集 ASR 在后半段（尤其 12 分钟之后）读音近似导致的低置信专名较多，本文的处理方式是：属于系列已确认口径的（Semantica、Agent、RAG、GitHub、Codex、React、CLI、REST API、MCP、OWL 等）直接采用正确写法；属于明显的技术通用词误识别（语义、向量、检索、策略、路径、清洗、去重、校验、源码、接入、推导、复用、自然语言、出库、装箱明细等）按上下文还原；其余无法可靠识别的一律保留 ASR 形态并就地标注`待确认`，不做猜测修正。

**可迁移素材。** 对做企业 AI 交付的人，这一集里有四样能直接搬走的东西：一是“演示链路 → 企业级要求”的对照问法（数据变更、并发、稳定、可追溯），可以当作任何原型上线前的自检；二是“检索结果作为上下文直答 / 规则引擎推导”这条二分法，用来决定某个业务问题到底该靠召回还是靠推理；三是“种子实体 + BFS 扩展跳数与条数”这两个旋钮，提示检索质量可以脱离模型选型被单独调优；四是把结论、引用依据、来源文件固定成返回契约的做法，让问答服务的输出可被人复核、也可被系统审计。
