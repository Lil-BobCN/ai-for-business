## 口播文章

### 人机交互为什么是 AI 落地的核心

接下来我们再进入到我们最后一部分：我们要把它进行一个闭环，加入人机交互的这样一个流程。所谓的人机交互，对于 Agent 的落地来说，其实本质上是非常非常核心的，因为我们现在很多的这个业务流程，肯定是不可能把它全盘地去交给 Agent 让它进行接管的，尤其是像一些操作数据、库存操作，这个数据、金额等等这些高危的操作，一般来说都是需要人工来去进行确认。所以这里面就要求，对于 Agent 来说，它能够知道在什么样的一个情况下可以停下来、等待着人来去进行审核。

> **思考一下｜Agent 该在什么时候停下来**
>
> 作者把“人机交互”放在整条链路的最后一段来讲，但它其实是一个前置设计问题：不是等 AI 做错了再补人工，而是先约定清楚哪些动作不能由 AI 单独完成。高危操作清单一旦确定，系统的中断点也就跟着确定了。
>
> **可以追问**：如果一个业务动作很难事先判断危险程度（例如金额不大但涉及承诺时效），中断条件应该由系统规则决定，还是由模型自己判断？
>
> **可延展方向**：把业务流程里的动作按“可逆性”和“影响面”两个维度排队，先给不可逆且影响面大的动作设置强制人工确认。

### 实战演示：先问一句“奶泡壶怎么还没到”

那么举个例子，我们来看当前的这个流程。OK，我们看一下，对于这个 AI 服务台：首先我们还是问这个问题——这个订单，“咖啡机到了，奶泡壶怎么还没到”，对吧？我们来去进行一个发送，我先把我的这个信息先发送。发送完成以后，这里面是不是出现了一个我们可以让 Agent 来去进行处理的地方？然后你看啊，它还是先定位客户的订单，然后 Agent 正在选择下一步、查询关联的事实，然后还是一样走了当前的那个路径，然后给了我们一个回复，然后我们点击它“回复用户”。对吧，这个就是客户，我们作为客户已经进行了一个回复。

然后接下来用户又开始问了：“我的……我看看我的，但是我的主机没有收到，怎么办？”你看我们在知识查询里面，明明这个咖啡机的主机它已经点击了送达，对吧，已经签收了。然后这个用户他就说“我的这个主机没有收到”，我们去发送，OK。

### 一旦事实对不上，人工就要接手

然后我们让 Agent 来去进行一个处理，点击处理，看他马上就进入到了人工审核这个阶段。就是因为用户问的这个问题，它其实和我们查询到的这个事实是有出入的：我们明明订单里面提到了已经签收了，但是用户他就说没有签收。这种阶段你可能交给 Agent 去进行处理吗？那 Agent 直接来的话——“OK，那你没收到，我再给你发一个”，那不行吧？对吧，他这个肯定是不行。

所以一旦涉及到这种你与查询到的这个既定事实不符的话，人工就需要开始介入，而 Agent 他需要知道在什么情况下来去提出和暂停当前的这样一个链路。比如我们现在做的这个链路，就是明明我们这里面显示已签收了，然后用户说没收到，Agent 现在决定“这一步我不知道怎么办了，我不能给他退款，我也不能给他再新发一个，接下来我们让人工来去确定”。所以这个人工就在这里面了，说我们可以去按照建议继续，或者是按照补充意见——我们这里面就写，比如“可以和物业前台确认一下”。OK，这个就是我们人工介入了，然后我们去提交意见。

接下来你会发现，OK，Agent 接收到需求以后继续去提供下一步、继续去选择下一步，最后它生成的这个草稿，这里面我们把它回复给用户。我们去看一下它回复给用户的就是：“你好，关于咖啡机主机的包裹，根据我们系统的查询，确实已经在这个时间点签收了，然后建议你和前台先确定一下是否代为保管了你的包裹，同时这个奶泡壶正在查询中。”

那么这些是不是我们既定的这个事实？那么他说他没收到，然后我们让他去和前台（确认），是不是 Agent 让我们人工去确定了以后，他才去进行这个回复？所以这个才是我们和 Agent 交互，以及我们在构建业务链路的一个核心，就是因为 Agent 他并不能够帮助我们解决所有的这个事情，涉及到这种情况，你说 Agent 给他退款肯定是不行的吧。所以这个就是为什么我们在 Agent 的开发链路里面，要去设计人机交互的这样一个链路的流程。

> **思考一下｜人工介入不是兜底，而是链路里的一个节点**
>
> 这段演示里最值得注意的是回复的构成：既保留了“系统查询确实已签收”这个既定事实，也带上了人工补充的“是否代为保管”这条意见，最后还交代了另一件事（奶泡壶）仍在查询中。人工没有推翻系统结论，而是在结论上追加了一条可执行的下一步。
>
> **可以追问**：当人工补充意见与系统事实冲突时（人工说“再发一个”，系统说已签收），系统应该以谁为准，又该在哪里留下痕迹？
>
> **可延展方向**：把人工节点当成一个有输入、有输出、可审计的组件来设计——记录谁在什么时候以什么依据做了什么判断，这比“支持转人工”这句话本身更有交付价值。

### 哪些场景应该设成 Agent 的检查点

所以这里面就是我们要去根据业务规则来去判断：在我们作为 FDE 去交付一个项目的时候，当我们在什么样的一个场景下，我们要把它设置成 Agent 停下来的这样一个检查点。比如在我们的客服里面，查询到多个订单不知道是哪一个了；关键的信息不够，让我们去和用户再去进行沟通、让他提供更多的信息；或者是去查询一些用户和我们既定事实返回数据不符的这样一个情况，需要由人工来进行隐移性（待确认）的决策。所以它是这样的一个流程。

> **思考一下｜把业务规则翻译成中断条件**
>
> 作者给出的三类场景其实对应三种不确定性：指代不明（多个订单）、信息不足（需要追问用户）、证据冲突（数据与用户陈述不符）。前两类是“还缺东西”，第三类是“东西互相打架”——第三类才是真正需要人来承担判断后果的地方。
>
> **可以追问**：这三类条件里，哪一类适合用规则硬编码，哪一类更适合交给模型判断后再由规则校验？
>
> **可延展方向**：把每个业务场景的中断条件写成一行可测试的判定（触发条件、需要的输入、恢复条件），就能把“人机协同”从口号变成可以回归测试的用例。

### 用 LangGraph 的 checkpoint 把流程停下来

针对于这样的一个流程，我们肯定也是可以去借助一些框架来去进行构建。那么最最简单的或者是最最容易实现的，肯定是 LangGraph 的这样一个技术体系。那么对于 LangGraph 的这个技术体系，其实就是它可以根据我们的这样一个业务需求的预定义——大家这个本体它这个 schema 里面其实就是有业务规则，我们就可以把这些业务规则去加入到这个本体的业务模型里面。当 AI 触发到这样的一个业务模型的规则，它就知道接下来我该停下来了，等人工来去进行审核；然后人工把相关的这个信息给它传进来以后，那 AI 接收到以后继续再执行下面的流程，要么就是继续执行，要么就中断相关的这样一个运行。

那么对于这个 LangGraph 来说，我们肯定是可以通过 checkpoint 的这样一个方式、它的这个机制来去进行一个构建。当然，时间关系，如果大家不太了解 LangGraph 的话，我们今天也确实没有办法给大家去展开地进行介绍，因为 LangGraph 还是一个非常庞大的这样一个学习体系。大家可以简单理解成，这个 checkpoint 指的就是我把某一份快照停在这里面了，等待着别人输入进来以后，我再次地去进行下一轮的这个一个开发，就是它会保留它当前的这样一个运行的进度。

> **思考一下｜把“暂停与恢复”做成一等公民**
>
> 作者用“把某一份快照停在这里”来解释 checkpoint，这句话把工作流从“一次调用跑到底”变成了“可中断、可续跑”的对象。代价是运行状态必须被完整保存下来：谁在等、等到什么、等多久、恢复时用哪份状态，都要有明确答案。
>
> **可以追问**：如果人工隔了两天才处理，这份快照应该继续有效，还是应该过期重跑一遍检索？
>
> **可延展方向**：为人工节点补一份状态生命周期约定（等待上限、超时策略、恢复时的数据新鲜度校验），这是把演示链路推向生产时最先被问到的问题。

### 这条链路底层用了什么：Semantica、RAG 与审核界面

好，回到对应的这个实战。我们可以看一下，我们刚才在这个项目源码里面实现的这样一个案例，本质上就是我们会通过 LangGraph 它构建的这样一个 Agent，然后对于本体的这个查询工具呢，我们肯定还是使用的是 Semantica 来去完成它的一个图检索，去查询我们业务本体的这个 OWL 文件；那么对于这个文档检索的这个工具呢，我们就是集成了这个 RAG 的这样一个构建的流程，然后共用我们构建本体的这样一个业务模型的定义。同时对于这个审核界面，我们可以通过业务规则的定义，在什么情况下来去停下来由人工去进行审核，然后我们借助于 LangGraph 在 Agent 里面构建的 checkpoint 以及它的 `thread_id`，也就是它的这个线程 ID 的这样一个机制，让它停下来等待人工去进行一个交互。所以这个就是我们刚才那条链路它底层实现的完整的这样一个逻辑，包括了每一步它都是干什么的，大家可以拿到我们的这个课件来去进行一个详细的学习和了解。

当然对于这个项目呢，大家现在我们一直给大家去演示的这个项目，它接入了这个本体的检索，以及对应的这个 AI 服务台它接入的对应的我们的这个本体，以及它人机交互闭环的这个整个的检索链路。那么整套的这样一个项目的源码其实都是在这里面的，大家可以随时找到我们的助教老师来去进行一个领取；领取好以后呢，你就让你自己的这个 Agent 来给它快速地去部署一下，然后在这里面应该是直接去填写一下你自己的 `API Key`，或者是你直接在这个启动的这个平台上可以去填写一下你自己的 `API Key`，你就可以完整地去进行一个实现了。包括对应的这个本体的这个模型，也是支持大家可以自己去进行导入的，大家可以直接导入这种 `.owl` 的文件，这个是完全没有任何问题的。所以我们今天的这个直播课呢，会给大家把这个源码完整地去进行一个提供，大家可以找我们的老师来去领取一下。

> **思考一下｜三条链路共用一个本体定义**
>
> 这段把整套系统的分工讲清了：Agent 负责编排，Semantica 负责本体侧的图检索，RAG 负责文档侧的证据，审核界面则由业务规则决定何时插进来。作者强调的关键点是“共用同一套业务模型定义”——如果本体、检索和审核各写一套规则，人工审核的判断口径就会和 Agent 不一致。
>
> **可以追问**：共用一份本体定义时，审核界面需要展示哪些字段，人工才能在几秒内判断“这条事实可不可信”？
>
> **可延展方向**：把“同一份业务定义被几个模块共同消费”作为架构自检项，凡是需要重复定义规则的地方，都是将来口径漂移的高风险点。

### 业务验收：用什么证明这个 AI 真的有效

好，那最后一步我们就给大家去介绍：当我们去完成整个项目这样一个构建，那么我们的审核的这个状态肯定是需要你作为 FDE 一定要能够去具备——你针对于你提出的这样一个解决方案，去解决用户具体场景下的某些痛点，它在什么样一个情况下、通过什么的一个方式、以及通过什么样的指标来去确定你构建这个 AI 对他们来说是真实有效的。那这里面我们就简单地去找了几个，比如说对应的这种正常的查单、没有可用的条件依据，或者是快照后的状态，或者是人工修改等等，以及应该看到的是什么情况，然后关键的这个检查点是什么——这个其实就属于 FDE 它在去完成客户现场的这样一个项目交付以后，它要有这样的一个评估、迭代和优化的这样一个指标。然后只有这些有你的甲方或者是你公司的这个领导认可了，也确实是认定是有效的，才能够证明你当前的这个项目已经交付完成了。

> **思考一下｜用什么证明它有效**
>
> 作者把验收拆成了“情形—应该看到什么—关键检查点”三列：正常查单、无可用条件依据、快照后状态、人工修改，每种情形都要有一个可被旁人复述的预期。这比“准确率提升了多少”更贴近交付现场，因为甲方真正关心的是异常情形下系统会怎么表现。
>
> **可以追问**：如果甲方只认可“老板觉得好用”，验收清单应该怎样才能把这种主观判断转成可复查的证据？
>
> **可延展方向**：把每种情形对应的检查点整理成一份验收用例表（含人工介入率、误判处理时长等可计数的指标），让验收在项目开工时就谈定，而不是上线后再补。

## 综合解读

**作者的论点链（视频观点）。** 这一集是整期公开课的收口：前面几集分别讲了本体建模、检索机制、Agent 工具调用与 RAG 增强，这一集补的是“最后一公里”——人在链路里的位置。作者的推进顺序是：先给出判断——业务流程不可能全盘交给 Agent，像操作数据、库存操作、金额这类高危操作必须由人工确认，所以 Agent 要知道自己在什么情况下可以停下来等审核；接着用客服台的现场演示把这个判断坐实——用户问“咖啡机到了、奶泡壶怎么还没到”，Agent 走“定位订单 → 选择下一步 → 查询关联事实 → 生成回复”的既有路径；随后用户改口说“主机没收到”，而系统里明明显示已签收，Agent 立刻转入人工审核；人工按补充意见写下“可以和物业前台确认一下”并提交，Agent 恢复执行、生成草稿，回复里同时保留“系统查询确实已签收”这个既定事实与“建议和前台确认是否代为保管”这条人工意见，并交代奶泡壶仍在查询中。作者由此给出应当停下来等人工的三类场景（查到多个订单无法确定是哪一个、关键信息不足需要再与用户沟通、检索到的事实与用户陈述不符需要人工做决策），并说明落地方式：把业务规则写进本体的 schema 里，AI 命中规则就知道要暂停；用 LangGraph 的 checkpoint 保存快照与运行进度，配合线程 ID 实现“停下 — 等人输入 — 恢复”。之后他交代这条链路的底层构成——Agent 由 LangGraph 编排，本体查询用 Semantica 做图检索并查询 OWL 文件，文档检索集成 RAG 流程并与本体共用同一套业务模型定义，审核界面由业务规则决定何时请人工；再落到业务验收：正常查单、无可用条件依据、快照后状态、人工修改等情形分别“应该看到什么”“关键检查点是什么”，只有甲方或公司领导认可有效，项目才算交付完成。结尾他把整期内容串成一条链（FDE 是什么 → 本体建模 → 检索 → Agent 接入与联调 → 人机协同与 RAG 接入），随后转入课程与体验营介绍：零基础到中高阶的定位、60+ 小时体系、8 个真实项目、六个阶段的能力路径、八大项目与结课大作业、学习平台与 AI 助教、工信部认证渠道，以及直播间的优惠与常见提问。

**隐含前提与边界（我的分析）。** 这条论述要成立，依赖几个作者没有展开的前提。第一，中断条件完全建立在业务规则被正确建模、并被持续维护之上：规则写进本体之后由谁更新、规则之间冲突怎么办、规则过期了系统会不会继续停在一个早已不该停的地方，这些都没有答案。第二，演示里的人工只做了一件事——提交一条补充意见，然后就交回 Agent；如果人工给出的判断本身是错的（比如坚持“再发一个”），系统是否有留痕、复核与回滚机制，口播里没有涉及，而这恰恰是“人机协同”从演示走向交付时最容易被追责的部分。第三，“把某一份快照停在这里”隐含了状态可完整序列化、可长期保存、可在恢复时仍然有效；人工如果隔几天才处理，检索到的事实是否还成立、快照要不要过期重跑，是必须补的约定。第四，验收部分列出的“情形—应该看到什么—关键检查点”方向是对的，但最终判据落在“甲方或领导认可”，这仍然偏主观；人工介入率、误判处理时长、首次响应时间这类可计数的指标，作者没有展开，而它们才是能跨项目复用的部分。第五，本集后半段有明显的销售语境（薪资数字、红利期、首发优惠、名额稀缺），前半段的技术判断与后半段的课程主张应当分开看。作为全系列的收口，这一集把“本体 — 检索 — Agent — RAG — 人机协同”串成了闭环，但它也暴露出一个尚未展开的环节：上线之后的持续评测与迭代，作者只给出了指标的存在，没有给出指标怎么采集、怎么看趋势。

**待外部核验的事实。** 本集的演示过程与演示结论均来自视频作者的单方展示，未经独立核验：Agent 是否真的能在“事实冲突”时自动进入人工审核、草稿文本的实际生成方式、审核界面与业务规则的对应关系，都需要看源码与运行环境。技术主张同样待核验：LangGraph 的 checkpoint 机制能否在生产负载下稳定支撑“暂停—恢复”、Semantica 与 RAG 是否真的共用同一份业务模型定义、把业务规则写进本体即可触发中断的可行性与代价。课程与市场相关的一切数字与判断都属于课程方主张：60+ 小时、8 个真实项目、六大阶段、八大项目构成（三个热门项目、两个 1:1 工业级复刻、两个百万级企业项目）、FDE“应届生起薪年包超过 30 万、年薪中位数超过 50 万”、“没有任何一个行业比 FDE 更火”、“现在是岗位多、人才少的红利期”、以及“工信部颁发的高级认证”与报名渠道，都应以招聘平台的原始数据、发证机构的公开公告和课程页面为准。此外，作者引用的 Palantir 与 OpenAI 对 FDE 的“官方定义”在两处出现，但均未给出处，需要回到原文核对。

**可迁移素材。** 对做企业 AI 交付的人，这一集有四样能直接搬走的东西：一是“高危操作清单 → 中断条件”的推导方式，先列不可全自动的动作，再倒推 Agent 该在哪里停；二是三类中断场景的分类（指代不明、信息不足、证据冲突），可以直接当作客服、工单、审批类场景的检查表；三是“情形 — 应该看到什么 — 关键检查点”这张验收表，把主观的“好不好用”拆成可复查的预期；四是把人工节点当成可审计组件来设计的思路——记录谁、何时、依据什么做了什么判断，既满足交付方的验收要求，也为日后的责任界定留下依据。
