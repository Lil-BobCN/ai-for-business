## 一句话摘要

视频作者认为，本体建好之后，Agent 与 Ontology 的交互可以拆成五层——Context、Query、Logic、Action、Governance：系统确定性地准备背景知识，模型自己决定要查什么，专业计算交给函数，受控变更交给动作，而权限、审计与安全约束贯穿前面四层；Agent 全程不直接访问底层数据库表，只通过受治理的语义接口与业务世界打交道。

## 阅读路线

先看作者抛出的结论——Agent 既不碰底层表、也不自由扫描完整 schema；接着看他为什么坚持把 Ontology 叫"操作层"而不是知识图谱（语义元素与动态元素的两分法）；中段是全集主体，五层交互架构一层一层拆开，每层的问题、机制与典型模式都保留了作者的举例；之后是一条端到端链路把五层串起来，再加上内部 Agent 与外部 Agent 的两套 MCP 接入；最后是作者的 demo 演示与"最小可工作版本"的思路。如果只记一句：**Agent 只通过受治理的接口访问业务世界**。

## 口播文章

### 结论先行：Agent 不直接碰底层数据

视频作者开场回顾，前面已经聊过了 Ontology 是什么、怎么建本体，接着很多朋友问：建好本体以后有什么用呢？Agent 又怎么跟本体进行交互呢？所以这一期视频，作者说会跟大家详细剖析 Agent 跟 Ontology 是怎么进行交互的，解读完之后还会有一个小的 demo，帮大家更直观地理解。话不多说，直接开始。

作者先简单说结论：在 Palantir 的体系里面，Agent 是不直接访问底层数据库表的，也不自由扫描完整的 Ontology schema。它是在一个配置与授权的权限范围之内，通过 Ontology 包含的像对象、关系、上下文、函数、动作等等来完成跟业务的交互。

所以你可以简单理解：Ontology 就是企业业务世界受治理的语义接口，而 Agent 就是通过自然语言去使用这些接口的操作员。作者说，你也可以把 Ontology 理解为 Agent 的操作系统——Agent OS。

### Ontology 不是知识图谱，而是操作层

作者说，我们先看这张图。很多人一听到 Ontology，或者看过之前那期 Ontology 介绍的视频之后，第一反应就是说：Ontology 不就是一个知识图谱，或者说数据结构的一种形式嘛。但作者认为，它其实是一个 Operational layer，是一个操作层——做在数据库、数据表、模型之上，把底层技术资产翻译成业务语言的一个操作层。

Palantir 官方把它分为了两种能力。

第一种叫 Semantic elements，是描述世界的能力。比如说像 Order、Warehouse、Customer 这些 Object Type，也就是实体的类型；还有像 Status、ETA、Priority 等等这些属性；还有像 Shipment 归属于 Order、Order 又归属于 Customer 这些 Links，也就是关系层面。作者说，这部分其实解决的是 Agent 怎么知道企业里面有什么东西、谁跟谁关联这个问题。

第二种叫 Kinetic elements，改变世界的这种动态元素。它分为两个大的类型：第一个叫 Actions，比如说像 Update Shipment ETA 这种动作，它其实是以函数形式存在的，去动态地更新我们运输的预估到达时间；第二种叫 Functions，直接来说就是函数，它可以帮助我们去计算一些实际的东西，比如说计算一些延迟的风险，或者直接有一些优化的函数去优化我们的调度。作者说，这部分其实解决的是 Agent 如何从一个回答问题的工具，变成真正能够帮助我们去执行业务、产生业务价值的工具，比如说帮助我们去做一些仿真的决策。

所以作者强调，Palantir Ontology 的核心不是简单把一个表换了一个名字叫做本体而已，而是把企业的名词、关系、规则、动作、权限都放到了一个受治理的语义层里面。他说这点非常重要，后面也会反复用到。

> **思考一下｜把动词也建模进语义层**
>
> 语义元素让 Agent 知道"有什么、谁连着谁"，动态元素让它能"改什么、算得出什么"。作者把这两类并列，等于承认一件事：能被执行的动词和能被描述的名词一样，都需要事先被定义、被授权。没被建模成 Action 的业务动作，Agent 不会凭空发明出来。
>
> **可以追问**：如果一个业务动作没有被预先建模，Agent 应该报错停下，还是应该退回给人来接手？
>
> **可延展方向**：梳理本体时把"对象清单"和"动作清单"放进同一张评审表，先确认哪些动作值得被建模、由谁批。

### 五层交互架构总览

作者说，Agent 与 Ontology 的交互，我们可以分成五层来理解。他先用一段话把五层过了一遍。

第一层叫 Context Layer。每次当你发消息，系统自动会把相关的背景知识都准备好。注意这里是自动准备好，而不是说等 LLM 自己来决定要不要查。

第二层叫 Query Layer。LLM 自己判断需要查什么，主动去查，支持像过滤、聚合、沿着关系链逐步探索。

第三层叫 Logic Layer。调用封装好的一些业务函数，关键的设计是不要让 LLM 自己判断、自己去代劳计算，而是把专业计算交给专业的函数。

第四层叫 Action Layer。执行一些受控的业务变更。到这里，Agent 就从问答的助手变成了业务的操作员。当然，像高风险的一些操作你还是要确认，而低风险的操作你就可以让 Agent 自动执行。

第五层叫 Governance Layer，作者说这也是非常重要的一层。像权限、审计、安全约束都要贯穿到前面的四层，这也是 Palantir 跟普通的 Agent 框架最核心的一些差异。

作者接着说，之后我们都会把这五层一层一层地剖析给大家看。

### 第一层 Context Layer：系统替你准备好背景

第一层 Context Layer，官方叫 Retrieval Context。作者说逻辑很简单：你每次提问的时候，系统都帮你把一些背景知识准备好；但它是确定性触发的，每条消息都会执行这件事，不需要 LLM 判断"我需不需要进行检索"。

它其实有三种准备的方式，分别是 Ontology Context、Document Context，还有 Function-backed Context。

第一种，Ontology Context：从对象类型里面进行检索，可以绑定一些固定的对象。比如说你在页面上选中了某个仓，比如华南仓，Agent 就会自动拿到华南仓相关的信息，比如说它的库存、它整体的面积，还有它对应的负责人等等。当然在这个过程中，你也可以用一些语义搜索，比如说问"华南仓有没有冷链断链的一些投诉"，系统也可以自动去做相关性搜索，去捞一些历史的投诉，然后在上下文里面返回最相关的五条。作者打了个比方：前面这种就像秘书，在老板走进会议室之前，把所有相关的、关于客户的档案都放到桌上了；第二种就像图书管理员听到你的问题之后，可以自动从书架上抽出最相关的五本书翻到你面前，不需要你自己去找书，直接翻阅就可以了，这种就非常方便。

第二种，Document Context：直观地看这个名词你就知道，它是跟文档相关的，它是从文档里面去捞。全文模式是把整份合同比如说给到 LLM；片段模式只返回最相关的几个文档块。比如说你问"承运商 A 关于延误赔偿条款是什么"，系统自动会从三份合同里面去筛选相关的片段，而不是把整个合同都丢给你。作者说，打个比方，就是图书管理员听到你的问题之后，把最相关的五本书翻到你面前。这看起来跟语义检索类似，只是它变成了一种文档形式，用的方法也是类似的，也是用了 Vector embedding 的方式去找最相关的一个向量——有可能是文档片段和相关段落，也有可能是整份文档加进来。

第三种，Function-backed Context：前面两种不够用的时候，就写一个 TypeScript 或者 Python 的函数去做自定义的检索。比如说"客户 360"的视图，它会同时拉取 CRM 的记录、活跃的订单、投诉的工单，拼成一个综合情报给到 LLM。作者打了个比方：就是秘书在老板开会之前，同时打电话给销售部、客服部、法务部，把各方的信息汇总成一份信息给到你。针对 Function-backed Context，你可以理解为：针对企业高频检索的场景，预先会设置一些函数，把相关的信息一次性拉起来，再交给 LLM 总结回答。比如说关于客户的问题，你不管它会问什么，所有关于客户的信息你都会写成一个函数；只要问了客户的问题，你就会把所有客户的信息都产生出来，喂给 LLM，做成它的上下文。

### 第二层 Query Layer：让 LLM 自己决定查什么

第二层叫 Query Layer。作者说，刚才的 Context 是系统自动帮你准备的，而这一层就是让 LLM 自己决定要去查一点东西。

它能干什么呢？像过滤、聚合、检索，或者顺着关系链进行搜索、往下追，它都可以做。作者提醒注意一个关键的区别：它查的是 Ontology 里的对象和关系，而不是去写一个 SQL；Agent 面对的是订单、承运商、仓库，而不是直接的表和字段。作者说，这里是一个核心的区别。

它有三种典型的查询模式。

第一种叫多条件过滤加聚合。比如说我问了一个问题："今天的华南仓有多少个延误的高优先级的订单？"那么它就会做几个操作：首先第一个，做一个 Filter，再加一个 Count，返回来说有 7 个；接下来可能追问"哪些是 VIP 客户的"，那接着就会沿着整个 Ontology 的 Link，可能从 Shipment 到 Order 再到 Customer，Service Level 等于 VIP，然后接着返回了 3 个。作者打了个比方：这就像老板在开会自己翻资料的时候，他会先按地区筛选订单，然后再追问哪些是 `Stark`〔ASR 作 `Stark户`，所指待确认〕客户的资料——反正这些资料都是在桌上，具体要筛选哪些类型，是老板自己来决定的。

第二种叫 Link 遍历与逐层追溯，作者说这个更硬核。比如说你有一个订单 8832，这个订单你去问它"延误是在哪一个环节出问题的"，它就会沿着这个 Ontology 网络状的结构，沿着 Link 去逐层追溯。当然你这里有一个超参数，就是你会去设置它到底最深追溯多少层。比如说像这里，从 Shipment 追溯到 Carrier，承运商的履约率是 72%，综合判断是因为车辆故障加枢纽拥堵导致的延误，所以这就给出了一些实际上的原因。作者简单类比了一下：就像侦探，它会沿着这个线索链逐步追查——从案件到嫌疑人，从嫌疑人到同伙，从同伙到据点，每一步都是顺着这个关系渐渐往下查的。

第三种就是聚合，聚合出运营的概念。比如说"各区域仓库绩效的情况"，它是怎么去得到这个结果的呢？它会按区域去 group by 聚合起来。比如说管理层要一张各区域的红绿灯看板，它不是看区域每单的数字、只看一个汇总数字的话，通过这种方式就可以一眼判断出来。

接下来作者专门提了一下 Retrieval Context 和 Query Layer 之间的一个关键区别，因为特别容易搞混。比如你必须让 Agent 知道的一些信息，就放到 Retrieval Context 里面，比如当前的仓库信息、今天的 KPI 信息、你的权限等级等等——因为每一轮对话都需要有这些信息输入，所以在 Agent 给出回答之前，它就会作为一个 context 给到 Agent。而如果有一些东西你可以让 Agent 自己去探索、自己去判断，就可以放到 object query 里面，比如说"帮我对比一下两个仓的情况""这个承运商过去三十年的表现"等等——这些是临时提出的、没办法完全提前预测的，就把它放到 Query 里面。

放错了有什么后果呢？后果就是：Context 里面会塞很多的信息，token 会浪费，噪声也会干扰你，你就需要那种上下文处理能力非常强的模型来支撑，成本也会上升。而如果你的 Query 配得太窄，LLM 有可能就查不到你想要的信息，有可能就会开始编了。

所以简单来说，你可以记住一条原则：确定性的，你走 Context；允许 Agent 进行一些探索的，就走 Query Layer。

> **思考一下｜"确定性走 Context、探索走 Query"是一条可执行的分界**
>
> 作者给出这条原则的时候，把两侧放错的代价也一起给了：放进 Context 的太多，token 和噪声一起上升；放进 Query 的太少，模型查不到就开始编。也就是说，这条分界线画在哪里，同时决定了成本与幻觉率。
>
> **可以追问**：当同一条信息既"每轮都可能需要"又"不一定用得上"时，你会把它放在哪一侧？
>
> **可延展方向**：把"每轮必须注入"和"按需检索"做成两张清单，在需求评审阶段就分开维护，而不是等上线后再调。

### 第三层 Logic Layer：把专业计算交给函数

第三层叫 Logic Layer。作者说，Agent 查到了对象、有了相关的信息之后，很多场景还要调用封装好的业务逻辑。

为什么不让 LLM 自己算呢？作者举了个例子：用户如果问了一个问题，比如说"这批延误的订单的风险等级怎么样"，如果没有对应的 function，LLM 只能说"看起来有风险"——但这不是我们企业用户能够接受的答案。

那有了 function 之后呢？Agent 就能够调用，比如说像 calculate delay risk 这种函数。它会去计算出来这个风险的影响范围：会去查过去 90 天同路线延误的数据，读承运商当前的履约评分，调天气的 API，然后看目的地未来 24 小时有没有暴雨等等一些恶劣天气，甚至跑一些已经训练好的预测模型，最后输出一个结果，比如说"这个订单有高风险，原因是什么呢？原因是仓库积压加目的地暴雨预警"——这样一个具体的答案。

作者强调，LLM 拿到的是一个结构化的结果，而不是原始数据。它的工作是理解意图、选择合适的函数、用自然语言解释结果；业务规则和模型交给 function，不要让 LLM 直接做一些专业的判断。

除了像风险评分以外，比如说像跨对象的业务逻辑，它也会给你做一些推荐；还有像做一些优化类的计算，你让它去做一些算法，比如说像资源的分配方案等等。作者说，你不需要会运筹学，但是看懂结果、能够做决策就行了；LLM 知道调用函数来解决你的问题就行了。

> **思考一下｜把"算"和"解释"分开之后，责任也分开了**
>
> LLM 拿到的不是原始数据，而是函数算完的结构化结果；它的职责退回到理解意图、选函数、解释结果。作者用"看起来有风险"和"高风险，原因是仓库积压加目的地暴雨预警"这两句话的差距，说明专业判断一旦交给 LLM 自由发挥，结论就失去了可核对的依据。
>
> **可以追问**：当一个函数的结论和业务方的直觉相冲突时，系统应该让谁来做最后判断？
>
> **可延展方向**：把"必须有唯一正确答案"的计算交给函数，把"需要权衡与措辞"的部分留给 LLM，这条分工线可以直接写进 Agent 的设计说明里。

### 第四层 Action Layer：从问答助手到业务操作员

第四层叫 Action Layer。到这里，Agent 会从问答助手变成一个业务操作员。作者说，Action Tool 就是让 Agent 能够做 Ontology 的一些变更。

它有两种场景。

第一种叫高风险的操作：首先 LLM 会生成一个 action，它需要用户进行确认。比如说换承运商、涉及合同还有成本的一些动作，这些高风险的操作会弹出提示，比如说"承运商 B 单价比 A 高 12%，预计增加运费 340 元，但是时效可以提升 10%，需要你点击确认才执行"。

那像低风险的操作呢，就会自动触发。比如说天气原因延误了两小时，系统会自动更新 ETA，自动给客户发通知。

此外还有三个辅助的工具。第一个叫 update application variable，就是让 Agent 能够改应用的一些状态——你说"只看华东"，页面就会联动进行刷新。第二个叫 command tool，它可以触发一些其他应用的操作，比如说它在地图上标出五个延误的订单。第三个叫 request clarification，执行前向用户去确认一些模糊的指令，比如说"你指的是哪个订单"等等。作者打了个比方：这个就像护士在给药之前，先会给你确认一遍"你是左手还是右手"——宁可多问一句，也不在不可逆的操作上去犯错。

### 第五层 Governance Layer：权限与防幻觉贯穿始终

第五层叫 Governance Layer。作者说，这是重头戏——它不是单独的一层，而是贯穿前面全部四层的约束机制。

他讲了一个场景就懂了。比如说有一个运营助手的 Agent，调度员登录和区域经理登录，看到的世界完全不同。

调度员呢，Context 里只注入三条线路的 Shipment，他只能查这三条线路相关的东西；不能调利润查询函数；可以计算一些延误风险，但是不能计算利润；然后可以自动更新 ETA，但是不能指派承运商。这就是一线调度员的一个权限。

区域经理呢，它的 Context 里注入了整个华南区的概览，可以查所有的线路加承运商的绩效，也可以查利润，可以用优化分配的函数去分配承运商、换承运商等等。作者说，这就是权限的分层统一。他打了个比方：这就好像实习生只有自己楼层的门禁卡，而总经理有全楼的门禁。

更关键的是防幻觉的机制，作者说这也是企业里面用 Agent 最看重的一个问题。那怎么去防幻觉呢？比如说用户问了一个问题："公司今年总营收是多少？"普通 Agent 可能直接编了一个数字告诉你，因为它没有数据的基础、没有来源。但 Palantir 的做法不是说写一条 prompt 说"你不要编造数据"就 OK 了，而是它有好几层。

第一层，它会去看一下：没有配置财务的 Context，Agent 看不到，没办法给出这个结果。第二层，它没有这个 Financial Report 的 Object Type，它检索不到。第三层，它没有授权这个财务的权限，所以算不了。第四层，它没有授权这个财务的函数，所以同样算不了。这几层叠加之后，Agent 对营收这件事情是彻底不知情的——不是被告知不能说，而是根本接触不到，这是从架构层面解决的问题。所以它最后给出的答案就是："我没有权限访问公司的财务数据。"

作者接着说，所有的这些操作都会进我们的审计日志：谁、什么时候、通过这个 Agent 干了什么事情、结果如何，全链路你都要实现可追溯。所以他强调，这不是一个简单的基础问题，还是一个很大的工程问题。

作者随后简单说了一下，这些工具是怎么让 Agent 可以调用的、或者说怎么暴露给 Agent 的。其实有两种模式：第一种叫 prompt tool calling，就是把工具的说明写进了 prompt 里面，所有模型都能够支持；第二种叫 native tool calling，用模型原生的 tool calling 能力，可以并行调用多个工具。

作者提醒一个容易误解的点：prompt 里其实不是把 Ontology schema 全量塞进了 system prompt，只是当前这个 chat 被打开、被授权的那一部分。

> **思考一下｜让 Agent"接触不到"，而不是"被告知不能说"**
>
> 作者把防幻觉从一个提示词问题改写成一个架构问题：缺 Context、缺 Object Type、缺权限、缺函数，几层叠加之后，模型连编造的原料都没有。这比在 prompt 里写一句"不要编造"要可靠得多，但也意味着权限与配置本身成了系统的单点。
>
> **可以追问**：如果权限配置出了疏漏，由谁、通过什么方式发现 Agent 其实"看到了不该看的"？
>
> **可延展方向**：把"Agent 本应答不上来的问题"整理成一组回归测试用例，每次权限或本体发生变更之后跑一遍。

### 端到端走一遍：五层怎么串起来

作者说，接下来我们用一个端到端的交互链路，给大家把整个五层串起来看一下，也就是这张端到端的流程图。

第一个比如说有个问题："帮我看一下今年华南仓有哪些订单有延误风险？"

第一步，Context Layer 就会自动触发了。它会做一个系统级的、确定性触发的语义搜索，会返回 Top 10 最相关的 Shipment 注入 LLM——LLM 没有参与决策。

第二步就是 Query Layer。它会过滤华南仓，再加上延误的条件，再选出 32 个结果；沿着 Link 会搜索到 Order 和 Customer，读相关的优先级和客户等级。

第三步，调用函数了。计算延误的风险，23 个里面它会告诉你有 5 个有风险；再调用 document resolution（函数名 ASR 如此，所指待确认），就会给出一个建议的方案。

第四步就是让 LLM 去生成回答，它会问你说是否要执行。

第五步就是点击确认。你确认之后，就会分派给承运商，去创建一个异常的 case；然后执行，Ontology 就会更新它的一个结果，同时会有审计日志来保存下来。作者说，这就是一个交互链路的总结。

### 内部 Agent 与外部 Agent：两套 MCP

作者提到这里要提一个概念，就是 local Agent 跟外部 Agent。前面我们提到的五层架构，主要都在描述 local Agent 跟 Ontology 之间的交互；而外部 Agent 的接入有两个机制。

第一个叫 Palantir MCP，它是面向开发者的，能够去修改 Ontology 的类型定义，但不能直接去写数据。第二个叫 Ontology MCP，它是面向外部业务的 Agent，能够读数据、执行 action、写数据，但不能改 Object Type 的类型定义。

作者说，不管是哪一条路，核心原则它都是不变的：就是 Agent 通过受治理的 Ontology 的接口来访问一切，但绝不绕过 Ontology 去直接碰底层数据。

当然，如果你要自己去设计一个类似的系统，作者说他这边也提供了一个最小可工作版本的设计，包含这几个模块、9 个核心的主线，还有最小用例，你可以基于这个思路去构建一个最小版本的 `Ontology Oval Agent`〔ASR 原文如此，写法待确认〕。

### Demo：角色仿真与推理过程

作者说，接下来就由他给大家演示一下。他做了一个简单的 demo，让大家有更加直观的认识：Agent 跟 Ontology 怎么进行交互、能够帮助我们做什么。

进入首页之后，会有一个简单的介绍，我们可以去开启对话、去导入 Ontology，或者做模型配置。最简单的三部分就是：你先要去做 Ontology 的导入，然后再选择 LLM，接下来你就可以进行对话和交互。

在本体的配置、也就是导入 Ontology 这边，作者说他这边已经上传了一些示例的 Ontology，比如说像物流的 Ontology，还有采购的 Ontology，你也可以直接导入。这个 Ontology 导入之后，作者说他也会尝试把他之前创建本体的那部分跟这部分结合到一起，做一个交互。本体创建完成之后，可以直接连结果来完成本体的搭建。之后我们可以去做模型的配置，你可以自己去添加模型。接下来你可以做用户的管理，不同的角色我们可以设置不同的权限——作者说，这也是 Governance 的某一层。

好，完成这些配置之后，我们可以进入对话的功能。作者说他这边有一个完整的对话，可以让大家直观地看到我们可以做什么。

首先第一个，就是你可以问它相关的问题、"你是什么样一个角色"，它可以去做数据查询、业务函数调用、业务操作等等。其中很重要一个呢，对于角色来说，我们可以去做角色的仿真，去对比不同的方案，去看不同方案的 performance、它的 metrics 到底怎么样。

比如说像这样，作者说他可以查询现在所有订单的一个情况，让它告诉我哪些有风险，它就把 12 个订单的总览都告诉我了。然后其中标注了有高风险的订单，其中这两个呢，它是已经延误了、风险的评分达到 100%。针对这两个警戒订单，作者说他问它有什么建议、能够进行一些角色仿真对比、给到我一些建议的方案吗。

然后它接着呢，就会去做一些建议方案的输出。比如说它建议两个都要进行承运商的更换，更换完成之后的延误时长可能会缩短多少，但是它可能会额外成本增加多少，然后它会给你一个综合的建议；后续你也会考虑说，针对这种情况你要对客户主动进行沟通。作者说，它会给你这种实操性的建议，帮你去做角色（仿真）。

其中作者说他这边也做了一个功能叫"推理过程"，其实是帮助大家看到：它在这个过程当中调用了哪些工具去跟本体做交互。首先第一个就是上下文创建，看它去加入哪些上下文给到 LLM；接着呢，它会去调用这个 Query Tool，去查询哪些本体，比如说像查询 Customer、Order、Shipment、Carrier（此处 ASR 另有一个词作 `google`，所指待确认）；以及查询完之后，我们要去调用哪些函数；还可以去做角色的仿真模拟。

作者说，那这就是一个比较具象化的、实际对我们业务决策能够产生价值的例子，它会去反问。

> **思考一下｜角色仿真的价值在于"可重算的差值"**
>
> demo 里最有意思的不是那两条建议本身，而是"换承运商之后延误缩短多少、额外成本增加多少"这类对比可以被反复重算——决策者拿到的不是一条结论，而是几套方案之间的差值。这也解释了作者为什么要把"推理过程"单独做出来给人看。
>
> **可以追问**：当仿真给出的最优方案需要额外成本时，成本与时效的权重该由谁来设定，系统又该怎么把这个权重记录下来？
>
> **可延展方向**：把"角色仿真 + 推理过程可见"当成决策前的标准动作，而不只是 Agent 的一个附加功能。

## 综合解读

**论点链。** 作者的推论从上一集的"本体怎么建"往下一步走：本体建好之后，真正要回答的是"Agent 怎么用它"。他先钉死一条边界——Agent 不碰底层表、不自由扫描 schema，只能在配置与授权的范围内活动，于是 Ontology 被重新定义成"操作层"而非"知识图谱"；为了让这层操作层可被调用，他把企业世界切成语义元素（对象、属性、关系）与动态元素（动作、函数）两类，前者回答"有什么、谁连着谁"，后者回答"能改什么、能算什么"。接下来是全集主体：交互被拆成五层，Context 负责确定性注入、Query 负责按需探索、Logic 负责把专业计算从模型手里拿走、Action 负责受控变更、Governance 负责权限与审计并贯穿前四层。五层讲完，他用一条端到端链路把"Top 10 注入 → 过滤与追溯 → 函数算风险 → 模型生成回答 → 人确认后落库并留痕"串成一个闭环，再用两套 MCP 说明这套治理边界如何延伸到外部 Agent，最后用 demo 里的角色仿真与推理过程把抽象架构落成看得见的交互。

**隐含前提。** 这条链条依赖几个没说出口的条件。第一，企业的业务对象、动作与权限边界本身是清晰的、可以被写下来的——否则"把名词、关系、规则、动作、权限放进一个受治理的语义层"就无从落地，防幻觉的几层机制也会因为配置本身含糊而失效。第二，函数化的业务逻辑是可信的：作者说"业务规则和模型交给 function"，这一步实际上把判断权从模型转移到了函数与其维护者身上，函数写错时，Agent 会输出一个错得很自信的答案。第三，权限即产品：Governance 之所以能"从架构层面解决"，前提是权限模型足够细，细到能区分"能不能查利润"与"能不能算利润"；权限模型一粗，这层就退化成开关。第四，审计日志的价值依赖于有人真的去看它，作者把"全链路可追溯"列为工程问题，但没有说清谁来消费这些记录。

**待核验主张。** 以下均为作者在视频中的陈述，未经独立核实，逐条列出：

1. 五层架构的划分与官方命名（Context / Query / Logic / Action / Governance），以及"Governance 贯穿前四层、是 Palantir 与普通 Agent 框架最核心差异"这一判断。
2. Ontology 元素的两分法（Semantic elements / Kinetic elements）与示例对象 Order、Warehouse、Customer，以及 Shipment 归属于 Order、Order 归属于 Customer 的 Link 关系。
3. 端到端示例中的筛选链条：Top 10 → 过滤后 32 个 → "23 个里面有 5 个有风险"。前一个数字 32 与后一个数字 23 在叙述中并不自洽，需核对原音。
4. 高风险操作的示例数字：承运商 B 单价比 A 高 12%、预计增加运费 340 元、时效提升 10%。
5. 逐层追溯示例：订单 8832、承运商履约率 72%、"车辆故障加枢纽拥堵"的归因结论。
6. 风险函数的数据来源：过去 90 天同路线延误数据、承运商履约评分、天气 API、目的地未来 24 小时天气，以及"已经训练好的预测模型"。
7. 防幻觉机制的层数：文中列举了 Context、Object Type、权限、函数四项，而叙述中另有"三层叠加"的说法，列举项与层数不一致，需核对原音。
8. Demo 数字：12 个订单、其中 2 个高风险且风险评分达到 100%。
9. "这个承运商过去三十年的表现"这一表述（从上下文看疑为"三年"，需核对原音）。
10. 两套 MCP 的能力边界：Palantir MCP 面向开发者、可修改 Ontology 类型定义但不能写数据；Ontology MCP 面向外部业务 Agent、可读数据与执行 action、写数据但不能改 Object Type 定义。
11. "最小可工作版本"设计所包含的模块数量与"9 个核心的主线"这一说法。
12. Function-backed Context 中函数的实现语言（TypeScript / Python），以及"客户 360"视图的数据来源（CRM 记录、活跃订单、投诉工单）。

**边界与反例。** 作者自己给出的边界是：这套交互只在一个已建好的、受治理的 Ontology 之上才成立，视频开头的结论句本身就是适用范围；五层里的 Query 与 Logic 各自都有"太宽"和"太窄"的失败模式，作者明确说放错了要么浪费 token 与注意力、要么逼模型开始编。反例方面，至少有三处可以提出质疑：其一，防幻觉依赖"配置文件里没有"，这意味着失效模式从"模型乱说"变成了"权限配错"，而且后者更不容易被用户察觉；其二，demo 里的角色仿真给出的是"延误缩短多少、成本增加多少"这类数字，但没有说明这些数字来自历史数据回归、规则推算还是模型估计，缺少对照就无法判断可信度；其三，端到端链路里"3—4 步"之间的数量对不上（32 与 23），如果连演示流程的数字都不闭合，实际系统的可复现性就更需要验证。

**可迁移素材。** 抛开 Palantir 本身，这一集能搬走的东西不少：把"Context 放确定性信息、Query 放探索性需求"当作一条可执行的检索设计原则，并用两侧放错的代价来校准分界线；把"必须有唯一正确答案的计算"从 LLM 手里拿走，交给可测试的函数，让模型只负责理解意图与解释结果；把防幻觉从提示词工程升级为架构约束——让 Agent"接触不到"比让它"被告知不能说"更可靠；用"高风险要确认、低风险可自动执行"把动作分级，并给不可逆操作配一个 request clarification 式的确认环节；把"角色仿真 + 推理过程可视化"当成决策工具，让使用者看到 Agent 调用了哪些工具、查了哪些对象、算了哪些函数，而不只是看一个结论；以及最后一点——无论是内部 Agent 还是外部 Agent，都只经过受治理的接口访问数据，不绕过中间层直接碰底层表。
