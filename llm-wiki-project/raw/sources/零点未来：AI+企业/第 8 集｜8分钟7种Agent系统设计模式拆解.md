## 一句话摘要

视频作者认为，真正把 Agent 用进生产的团队几乎都不是从造一个全自主的智能体开始的——从写死的代码流程到全自主的多智能体，中间每一档都有成熟的设计模式：五个工作流模式加两个 Agent 模式，再叠上记忆与检索、护栏、人在回路、评估监控和可观测性这五件生产级的事。

## 阅读路线

作者先划清"工作流"和"Agent"的界线，再逐个拆五个工作流模式，然后进入单个 Agent 的循环与多 Agent 的两种架构，最后收束在生产级五件事和一套选型原则上。需要提前说明的是，本集模式名多为英文术语，ASR 转写存在误差：能按上下文唯一还原的已在正文中还原（如 Prompt Chaining、Routing、Parallelization、Evaluator-Optimizer、while loop），无法唯一确定的保留 ASR 原文并加〔待确认〕。如果只记一句，作者想留下的是：**从简单开始，只在值得的时候才让模型自己决策**。

## 口播文章

### 别急着造一个"全自主"的 Agent

视频作者开篇说，现在到处都在说 AI Agent，好像不搞个 Agent 就落伍了。但真正把 Agent 用上生产的团队，几乎都不是从重造一个全自主的 Agent 开始的。作者认为，从完全写死的代码流程到全自主的多智能体，中间每一档都有成熟的设计模式，这就是本集要聊的 Agent 系统设计模式。

他先做了一个区分：workflow（工作流）和 agent（智能体）这是两回事。

### 工作流是编排，Agent 是现场决策

作者给出的第一个例子是工作流：LLM 被编排在预先写死的代码路径里，流程固定，模型只在每一步里面去干活，不能决定下一步。他举的例子是 RAG——先检索、再拼提示词、再生成，顺序写死，模型说的不算。

而 Agent 是 LLM 动态决定自己的执行过程。作者用客服 Agent 举例：用户说"我想退货"，这里没有固定的脚本，Agent 自己来决定先调用工具查订单，再核对退货政策，判断在不在窗口期内，最后才执行退款。每一步用什么工具、要不要继续，都是模型现场决策的。

作者提到一个反直觉的事实：Anthropic 和几十个团队合作之后发现，所谓大道至简，最成功的实现几乎都没用复杂的框架，而是用简单和组合的一些模式。他说，Agent 的系统往往都是用更高的延迟和成本换更好的任务表现，所以要记住：只在值得的时候才做这笔交易。

> **思考一下｜自主性的定价**
>
> 作者把工作流与 Agent 的分界放在"谁决定下一步"，同时又把 Agent 的能力标价为延迟和成本。两条线合起来其实是一个采购问题：这一步的自主决策，能换来多少任务表现。
>
> **可以追问**：如果一个环节的失败代价很低、结果又容易验证，"让模型自己决定"到底买到了什么？
>
> **可延展方向**：按"步骤能否被验证"给流程分段，可验证的段落写死成流程，不可验证的段落才交给模型循环。

### LLM 是模型，Agent 是系统

作者接着分清一对最容易混淆的概念：LLM 和 Agent。本质上 LLM 是模型，Agent 是系统，区别不在于聪明的程度，而在于有没有行动的闭环。LLM 大语言模型会说话但不会干活：不调用工具、不查数据、没有记忆，也不能行动。你问它"我的订单到哪了"，它只能基于训练数据给你猜一个答案——它既不知道你的真实订单，也查不了物流系统。而 Agent 会干活、完成任务闭环：同一个问题，Agent 会调用查询订单的工具拿到真实的订单，再调物流的工具查实际的状态。它不是在那里猜，而是在做事情。

那么 Agent 到底由什么构成？作者说，OpenAI 的温历〔人名 ASR 原文如此，待确认〕给出的经典框架就是四件套。第一，LLM 是核心的大脑，负责规划——把任务拆解成可执行的子任务，走不通就反思调整。第二，记忆——短期记忆就是对话的上下文，长期记忆存在外部的存储系统里面，跨会话保留你的偏好还有决策。第三，工具——工具就是它能碰的系统，分三类：拿数据的、干动作的，以及把别的 Agent 也包成工具。

作者补充说，如果实际在生产里面使用，我们还要补全两样东西：一个是 instruction（指令），也就是 Agent 的标准操作手册 SOP，好的指令来源于真实的运营文档；第二个是护栏（guardrail），它是边界——如果没有这些护栏，Agent 是不能够用在生产环境里面的，企业用起来也有风险。

### 工作流的五个基本模式

基本概念有了基础之后，作者接着讲工作流的五个基本模式。

第一个模式叫提示链（Prompt Chaining）：把任务拆解成一串固定的步骤，每一步处理上一步的输出，就像工厂的流水线一样。作者说它的好处是每一步的错误不会滚雪球，因为每一步都要被检查一遍。简单总结就是：提示链把每个 LLM 调用变成一件更小的任务，用延迟来换准确率。

第二个模式叫路由（Routing）：它有点像一个智能交换机，LLM 给输入做分类，然后送进最合适的通道——简单的小问题给小模型，这样省钱；难题就给推理模型。作者打了个比方，它有点像医院的分诊台护士，不治病，只判断你该挂哪个科。

第三个模式叫并行化（Parallelization）：多个 LLM 同时干活，然后再汇总结果。作者说它有两种形态：第一种是切分，把独立的子任务拆开并行跑；第二种是投票，同一个任务可以跑多次，然后取多数。他补充说，复杂任务交给单一的 LLM 一次性处理，效果通常不如拆开、让多个 LLM 各自负责一块。

第四个模式叫评估与优化（Evaluator-Optimizer）：首先有一个生成器（Generator）产出一个输出，再加上一个评估器（Evaluator），构成一个简单的小循环，直到评估通过、或者最大的迭代次数到了就停下来。作者强调，给到评估器的评估标准必须清晰可见——如果标准含糊的话，这个循环就会原地打转，甚至越改越糟。

> **思考一下｜循环能不能收敛，取决于评估器被交代得多清楚**
>
> 在评估与优化这个模式里，真正被优化的往往不是生成器，而是那套标准。标准含糊的时候，多跑几轮不是逼近正确答案，而是放大抖动。
>
> **可以追问**：这套评估标准该由谁写——写提示词的工程师，还是每天看这些输出的业务人员？
>
> **可延展方向**：把评估标准当成一份可评审的交付物，先确定它写清楚了，再决定这个自循环值不值得开。

第五个模式是编排〔英文模式名 ASR 未捕获，待确认〕：一个编排者进行任务的动态拆解，然后派给具体的"功能"〔ASR 原文如此，所指待确认〕，再把这些结果合成在一起。作者说，它跟并行化的区别就在于：任务不是预先定义好的，是编排者根据具体的输入现场决定的。

### 单个 Agent：一个 while loop 和它的两个敌人

作者说，前面聊的更多是五个 workflow，它们是固定的流程、预先定义好的内容，缺乏足够的自主性。接下来聊两个主要的 Agent 设计模式。

首先是单个 Agent 的模式，本质非常简单，就是一个 while loop（循环）：把 LLM 输出的内容反馈回去，让 LLM 基于真实环境的反馈和结果来校准自己，而不是凭空猜。作者说它也有几个退出的条件：第一是调用了最终的输出工具；第二是模型直接返回答案；第三是达到了最大的迭代次数。

作者认为这个模式有两个潜在的敌人。第一个是重复无效的调用：模型反复调用同一个工具，拿到同样一个"死"的结果，这种情况下就没有效果了。他的对策是设一个迭代上限和超时的限制；工具报错的时候，先反思是不是参数错了，还是问用户有没有问题。第二个敌人是工具非常多：如果你的工具超过 10 个，而且这些工具可能还非常相似，那模型就会开始选错工具。这个时候我们可以用清晰的命名去描述它、说明什么情况下可以用什么工具，给它一个范围。

> **思考一下｜工具数量的天花板其实是个接口设计问题**
>
> 作者给出的量级是：超过 10 个工具、而且彼此相似，模型就开始选错。这说明瓶颈未必在模型能力上，而在"什么时候该用哪个工具"没有被写清楚。
>
> **可以追问**：把 20 个工具合并成 5 个带参数的接口，和把 20 个工具的描述重写一遍，哪一种更接近作者说的"给它一个范围"？
>
> **可延展方向**：把工具的命名和调用条件当作提示词的一部分来验收，而不是留给调用者临场判断。

### 多 Agent：经理模式与交接制

既然有单个 Agent，那就有使用多个 Agent 的 Multi-Agent 协作模式：多个各有专长的 Agent 进行分工。作者说有两种主流的架构，一种是经理模式，第二种叫交接制。

经理模式就是有一个中央的 Agent，我们叫做经理 Agent 或者 CEO Agent，它通过工具的调用协调一群专家来完成任务。CEO Agent 是唯一直接面向用户的 Agent，像老板一样，把活分给各个组，自己对外汇报。至于交接制，Agent 有可能是同级别的，没有一个中央的分配者，不同 Agent 之间的执行权可以转给另外一个 Agent，连同对话状态都一起交接过去。

那什么时候适合上多个 Agent 的这种模式呢？作者说，当领域差异大到单个 Agent 装不下、工具又多到单个 Agent 放不下的时候。但他建议，先考虑能不能在单个 Agent 上最大化它的能力，因为多个 Agent 的成本还是比较高的，而且比较难调试：如果遇到问题，有可能是协作的问题、编排的问题，也有可能是单个 Agent 的问题，还有一些踢皮球式循环的风险。

> **思考一下｜多 Agent 的门槛是"装不下"还是"说不清"**
>
> 作者主张先榨干单个 Agent，理由是成本更高、故障面更大：协作、编排、单个 Agent 三层都可能出错。这句话的潜台词是，拆得越多，定位问题的成本涨得越快。
>
> **可以追问**：如果一个团队的领域边界本身还在争论，把它拆成多个 Agent 会让问题更清楚，还是更难查？
>
> **可延展方向**：给多 Agent 系统先配一份出错归因表，写明每类失败该去查协作层、编排层还是单个 Agent。

### 生产级 Agent 绕不开的五件事

作者说，不管你是提示链还是多个 Agent，在生产级别里面的 Agent 设计模式，我们都需要考虑五个事情。

第一是记忆和检索：RAG 解决知识够不够的问题——够不够新、够不够专；长期记忆则解决记不记得你是谁、之前聊了什么、之前我做过什么样的一个决策。

第二是护栏：在企业里面落地 AI Agent，一定要考虑安全权限的问题，我们要设置规则的护栏，还有安全的权限审核。

第三个是人在回路的触发机制。作者给出两种触发机制：第一种是超过失败的阈值，比如重试了多次还没有搞清楚，就要升级为人工；第二种是高风险的操作，比如取消订单、大额退款、付款这种，就需要人工参与。

第四个是评估和监控的机制。

最后是可观测性设计：我们需要保留日志，多个 Agent 的调试〔ASR 作"调色"，所指待确认〕都要靠日志来进行留痕，才可以进行审计。

作者最后补充，现实中的 AI Agent 系统设计其实都是混合在一起的，都是一个混合模式设计，有可能是一个简单的模式加一个复杂的模式混合在一起。

> **思考一下｜"高风险"由谁定义，什么时候定义**
>
> 作者给出的两种触发机制很实用：失败阈值，以及取消订单、大额退款、付款这类高风险动作。但阈值和名单本身都需要有人持续维护，否则它们会过期。
>
> **可以追问**：如果高风险名单写得过宽，人工通道会不会变成瓶颈，反而把团队推回"全自动"那一侧？
>
> **可延展方向**：把触发条件写进配置而不是代码，让业务方能自己调整失败阈值和高风险清单。

### 怎么选：三条原则和三条铁律

作者说，前面讲了五个 workflow 和两种 Agent 的设计模式，这些模式我们应该怎么选呢？整体的原则简单来说就三条。

第一，我们从简单开始：能确定的部分就用 Prompt Chaining。第二，逐步增加复杂度：先从一个简单的把流程跑通，然后需要动态决策、或者说领域要分离开来，不同领域用不同的 Agent，这样逐步去增加复杂度。第三就是组合：我可以用不同的组合去完成整个一个任务，比如一个确定的 Prompt Chaining 里面，某一个步骤就是让 Agent 去动态调 API，常常比整体进行升级更划算。

另外，作者说 Anthropic 还有三条铁律：第一是保持简单——最成功的系统没有用复杂的框架；第二是透明可解释——能解释、能展示 Agent 的规划步骤；第三是精心打磨 Agent 和工具的接口，这个值得我们更多的投入。

在结尾，作者提到他在自己的 GitHub 上也放了这 7 个不同模式的 Agent 示例，感兴趣的话可以上他的 GitHub 去看这些模式的一些示例代码。他说，这就是本期视频的全部内容了，如果觉得还不错的话，欢迎点赞、收藏、关注，我们下期再见。

> **思考一下｜把"要不要上 Agent"降级成"哪一步先上"**
>
> 作者最实用的一句是：在一个确定的提示链里，只把某一步换成 Agent 动态调 API，常常比整体升级更划算。这让架构决策变成了一个可以逐步推进的步骤题。
>
> **可以追问**：一个流程里哪一步最值得先换成自主决策——出错代价最小的那一步，还是人工最耗时的那一步？
>
> **可延展方向**：把现有流程图直接当作升级地图，逐步替换，每一步都留一个可以回退的开关。

## 综合解读

**论点链。** 作者的主张从一次纠偏开始：Agent 的价值不在于"全自主"，而在于把自主性放在该放的位置上。他先用 workflow 与 agent 的分界立起判据——谁决定下一步；再把 LLM 与 Agent 的分界确定为"有没有行动的闭环"；然后按自主性从低到高铺开七种模式：五个固定流程的工作流模式，一个带退出条件的单 Agent 循环，以及两种多 Agent 架构。生产级五件事（记忆与检索、护栏、人在回路、评估监控、可观测性）是这些模式进入生产的准入条件，收尾的选型原则和三条铁律则回到同一个立场：先简单，再按需增加复杂度，用组合而不是整体替换来演进。

**隐含前提。** 这套框架成立至少依赖三个没说出口的条件。一是任务可以被分解成可验证的步骤——提示链、并行化、评估与优化都要求每一步有明确的验收信号，否则"每一步都要被检查一遍"就无从谈起。二是评估标准、护栏规则、高风险清单这些元数据有人持续维护，作者把它们统一交给了"设置"，却没有交代设置者是谁、多久复核一次。三是工程基础设施（日志、留痕、审计、权限）已经就位，否则可观测性和人在回路都只是纸面条款。此外，作者引用的两处权威——Anthropic 的团队合作结论与三条铁律、OpenAI 相关人物的四件套框架——在视频里都是转述，没有给出来源。

**待核验主张。** 以下均为作者在视频中的陈述，未经独立核实：Anthropic 与"几十个团队"合作后得出"最成功的实现几乎不用复杂框架"的结论；Anthropic 三条铁律（保持简单、透明可解释、精心打磨 Agent 与工具的接口）的原文归属与措辞；OpenAI 相关人物（ASR 作"温历"，人名待确认）提出的 Agent 四件套框架，以及作者补上的 instruction 与护栏两项；七个模式的命名与归类，尤其是第一个模式的英文名——ASR 前后转写为 `plombed training`、`PoM Training`、`Prompt Training` 三种形态，本文按上下文还原为 Prompt Chaining，建议与作者 GitHub 上的示例代码交叉核对；并行化两种形态（切分、投票）与 Anthropic 原文里 Sectioning / Voting 的对应关系；编排模式是否即 Anthropic 体系中的 Orchestrator-Workers；"工具超过 10 个且彼此相似，模型就开始选错工具"这一量级；多 Agent "成本更高、更难调试"以及"踢皮球式循环"的风险；以及作者称已在自己的 GitHub 上放出这 7 个模式的示例代码。

**边界与反例。** 作者自己给出的边界很明确：多 Agent 只在领域差异大到单个 Agent 装不下、工具多到放不下时才上，而且要先最大化单个 Agent 的能力；他也承认现实中的系统几乎都是混合模式，不存在纯粹的理论形态。可以补上的反例有两条：其一，"评估标准清晰可见"在工作流模式里被当作前提，但在开放域任务（写作、策略判断）中，标准本身往往就是要产出的东西，此时评估与优化循环容易空转；其二，人在回路的两条触发机制都依赖事先定义，事前无法枚举的高风险动作仍会漏网。另外，"工具超过 10 个"这类经验阈值通常与模型版本、工具描述质量强相关，换一个模型或重写一遍描述就可能失效，不宜当作硬指标。

**可迁移素材。** 抛开具体产品或框架，能搬走的东西有几件：用"谁决定下一步"给流程分段，而不是笼统地问"要不要上 Agent"；把评估标准、护栏规则、高风险清单当成配置项交给业务方维护，而不是写进代码；给每个 Agent 循环设迭代上限与超时，并把工具报错后的第一反应定为"检查参数、必要时问用户"；用协作层 / 编排层 / 单 Agent 层的出错归因表来定位多 Agent 系统的故障；以及把升级路径设计成可回退的步骤替换，而不是一次性重构。
