## 一句话摘要

视频作者用一集把五个最容易混在一起的词拆成两类：本体、知识图谱、上下文图谱、代码图谱回答的是"系统知道什么"——它们分别是规则书、世界网、业务上下文地图和代码的管网图；图谱工程（Graph Engineering）回答的是另一件事，"系统怎么干活"——它是给 Agent 铺好的那条轨道。

## 阅读路线

作者这一集是"先上结论、再逐个拆词"的走法：开篇用一句话把五个词分成两类，然后按本体 → 知识图谱 → 上下文图谱 → 代码图谱 → 图谱工程的顺序，逐个交代定义、边界和适用场景；中段他特意停下来讲上下文图谱在数据平台厂商与学术界之间的定义差异，因为那是他眼中"今天最容易讲错的一张图"；后半段是一张场景对照表、一张四层全景架构，以及一个采购寻源 Agent 的串场例子。如果只记一句，作者想留下的是：**五张图各司其职、缺一不可，它们不是互相替代，而是分工协作**。

## 口播文章

### 五个词，两类东西

作者以"Hello 朋友们"开场，说这期视频要聊几个带 graph 的词：ontology、knowledge graph、context graph、code graph 和 graph engineering，翻译过来就是本体、知识图谱、上下文图谱、代码图谱，还有图谱工程。他说这五个词单独拎出来好像都听说过，放在一起直接就蒙了——它们到底是不是同一个东西？做 AI Agent 到底应该用哪一个？

作者的结论先上：这五个词其实是两类东西。前四个——本体、知识图谱、上下文图谱和代码图谱——回答的是同一个问题，叫做"系统知道什么"；它们是地图，是原料，越攒越值钱，就跟数据一样。而最后一个图谱工程回答的是另外一个问题，就是"系统怎么干活"，它跟业务是要天天打交道的。所以作者让大家记住一句话：**"知道什么"决定答得对不对**，这是前四个词干的事情；**"怎么干活、稳不稳"**，才是 graph engineering 做的事情。

### 本体 Ontology：公司的标准术语加家规

作者说本体这个概念他之前的视频也分享过，这里再打个比方：本体就是公司的标准术语，加上家规。

它不记录张三、李四这些具体的实例，它指定的是规矩——比如说"客户"怎么定义、实体之间允许什么样的关系、哪些规矩永远成立。所以作者说，本体简单理解就是**字典和语法书的合体**，它严格到机器和 AI Agent 都能读懂。

他提到行业里有一个比较著名的公司，就是 Palantir，它的 ontology 由这几个部分组成：第一个是实体 objects，还有 links，也就是实体之间的关系；properties 是实体的属性；logic 是逻辑、规则；还有像 actions 动作；以及 security，权限操作，也就是 AI Agents 能做什么。所以作者强调，本体不只规定有什么、什么关系，还规定谁能做什么、什么条件下能做。

作者认为，本体最开始做的事情其实是统一语义关系、统一口径。他举医药领域的例子：多个团队的系统要统一口径，而医疗里面的诊断是绝不允许有两种意思的。在这样的情况下，有了本体，我就可以让机器、让 AI 自己推理出新的知识——比如说某种药可以治什么病，患者有这个病，这个药就可以试用在这个患者身上；它可以保证领域知识是相对稳定的。作者说，像金融领域、医药领域都有一些开源的本体可以使用，比如金融领域的 `FIBO`〔ASR 作 `fibre`，拼写待确认〕，还有医疗的 FHIR。

作者接着说，本体其实就是一本规则书：它定义了实体的关系，比如说怎么定义 person 这个人，还有 company 公司、还有城市，它们之间的一些关系，以及这个规则链路。他也提到本体还有一些〔`倾启`，待确认〕的地方，说待会再跟大家展开讲。简单理解，本体就是一个建筑规范——它规定了墙要多厚、房屋怎么连、城镇怎么计算，但规范本身不盖房子；而知识图谱，就是照着规范盖出来的房子。

> **思考一下｜"规则书"和"实例数据"的分工线**
>
> 作者把本体定义成不含张三、李四的规矩，把知识图谱定义成挂着实例的那张网。这条分工线其实决定了改动成本：动规则要牵动所有实例，动实例只影响一个节点。
>
> **可以追问**：当某条实例长期违反规则时，团队应该先改本体，还是先改数据？
>
> **可延展方向**：把"这条判断属于规则还是属于实例"当成建模讨论的第一个问题，可以省掉后面大量的返工。

### 知识图谱 Knowledge Graph：照着规范盖出来的房子

作者说，前面提到本体是一个建筑规范或者家规；有了本体这道家规，就往里面填一些真的东西，那**织出来的一张网**就是知识图谱。

知识图谱是一种实例的数据和关系的网络状结构，它回答的是"什么普遍为真"——比如说巴黎在哪个国家，然后谁在哪家公司。作者说，你可以把它想象成一个长得像神经的百科全书：不单查得到条目，还能顺着关系一路问下去。它的公式也很简单：首先它有本体的规则，加上一些具体的实例，再加关系。

作者继续解释：本体定义的是客户和订单有什么关系，知识图谱就是把"张三"〔ASR 作 `瞻山`，人名待确认〕、"还有一个订单号叫 882"这些真实的人和事填充进去。也可以认为，知识图谱就是本体的实例数据，实际的数据是挂在具体的实体下面的。他举了个例子：我的 Person 就是一个实体，本体定义的实体 Person 下面可能有不同的人名——张三是工程师，李四是架构师，张三和李四都在零点未来里面工作，零点未来的总部在北京。

什么时候用知识图谱？作者说，比如一些常识的问答、推荐——看过这部电影的人还喜欢什么。但它有一个天生的短板：**它只知道全世界普遍为真的事情，不知道你们公司此时此刻在发生什么**。所以这就引出了下一张图，也是今天最容易讲错的一张图。

### 上下文图谱 Context Graph：今天最容易讲错的一张图

作者说，上下文图谱是比较新的一个概念。知识图谱描述的是实体关系和事实，而上下文图谱是在它的基础上加了一些**任务状态、事件和一些历史的决策**，形成了面向 Agent 的、用来做决策的业务上下文地图。

它告诉你的是：这张表〔ASR 作 `来战表`，待确认〕现在质量怎么样、谁负责改了哪一列、谁会被影响、谁批准过什么样的一个例外；它跟业务会做一个实时的更新，然后 Agent 就有一个正常的上下文，能够去干实际的活。

什么时候用它？作者说，首先 AI Agent 要进公司干活之前，需要一个可信的业务上下文地图：它要理解这个事情到底是怎么样的、它关联的数据、关联的一些信息、还有 KG 这样的信息，去做影响分析——比如说改了某张表〔ASR 作 `自然表`，待确认〕，哪些仪表盘可能会坏掉。还有审计和归因，它要追溯：谁在核实、因为什么批准了什么东西。所以作者总结说：图谱告诉企业有什么，上下文图谱告诉 Agent 现在为什么重要、该怎么做决策。

作者说它分三层：第一个是底层的**语义基础**，也就是实体是什么意思；中间是它运行的**元数据**，比如说数据的血缘关系、数据是哪来的、质量分多少、谁负责、谁能看；顶层是**决策轨迹**，比如说谁在核实、为何批准了什么。

作者特别说明，针对 context graph，不同的公司还有学术界的人还是有一些差异化的定义。比如说一些数据平台厂商，像 DataHub 还有 `Atlant`〔拼写待确认〕的用法，它是站在一家公司的角度来说这个事情的，更加注重的是决策轨迹和治理。而学术界还有一篇论文，讲的这个 context graph 是另外一件事情：知识图谱描述的是一些事实，在知识图谱的基础上，为了去反映现在的一个状态以及上下文信息，要在知识图谱上增加时间、地点、出处、还有置信度的一些信息。他举例：同样是 A 先生，A 先生住在上海和 A 先生住在北京，这两个在知识图谱里面就是两个事实，而且是冲突的事实；但如果你加上时间关系，比如说上个月 A 先生住在上海、这个月 A 先生住在北京，它就是成立的。所以我们需要这样一个上下文（context graph）来帮助我们。

作者最后用一句话把前两张图串起来：knowledge graph 知识图谱告诉 Agent 企业有什么，context graph 告诉 Agent 当前为什么重要、以及如何基于这些信息来帮助我们做决策。

> **思考一下｜一个词，三种定义**
>
> 作者在这里没有把差异抹平，而是把三种用法并排放着：厂商口径偏决策轨迹与治理，论文口径偏给事实补上时间、地点、出处与置信度，作者自己的口径则是"企业此刻的业务上下文"。
>
> **可以追问**：如果同一份方案里三方各用一套定义，"到底上没上 context graph"这个验收问题还能不能回答？
>
> **可延展方向**：在方案文档开头显式写出"本文中的 context graph 指什么"，比争论谁的定义更正确省时间得多。

### 代码图谱 Code Graph：代码的内部管网图

作者说，接下来是代码图谱，这个是最好懂的，因为它本质上就是一个**代码的内部管网**——画起来就是代码内部管网的网络图。

它包括一些函数、类、模块，这些就是节点；谁调用谁、数据怎么流、谁继承谁、文档在哪里等等。作者说，改一行代码之前，先顺着图看一下谁会被受影响。简单说，代码图谱就是有比如说源代码，加上抽象语法树，再加上依赖关系，再加上一些执行关系等等；要先解析成这个语法树，再推导出谁调用谁、数据往哪里流，整个软件系统就会变成一张可以查的图，也就是整个代码的网络。

那什么时候用到它？作者说，当你一个软件代码量大到人脑记不住这个关系的时候，我们就可以去建立一张 code graph，比如说就像这样的一张网络图、各个部分之间互相调用的一个关系〔此处 ASR 作 `拍什么一件`，所指待确认〕。所以他打比方：代码世界就像一张水电的管网图——管线怎么走、阀门在哪，关掉这边那边会停水；改代码之前，都去做一些风险预演。

> **思考一下｜管网图的价值在"改之前"**
>
> 作者给的使用时机很具体：不是等人来查文档，而是在动手改一行代码之前。这等于把代码图谱的验收标准，从"图画得全不全"换成了"能不能在下刀前回答影响面"。
>
> **可以追问**：如果代码图谱本身已经过期，它算出来的影响面还剩多少可信度？
>
> **可延展方向**：把"图谱与主干代码的同步延迟"当成一项运维指标来管，而不是当成一次性建模工程。

### 图谱工程 Graph Engineering：给 Agent 划流程图

作者说，前面四张图解决的是"想知道什么"，最后一张图 graph engineering 解决的是"怎么干活"，跟前面是两种完全不同的东西。一句话总结：**graph engineering 是给 Agent 划流程图**。

具体来说，一个节点干一件事情，一条边决定干完去哪；哪些步骤必须要按规矩来走、哪些放手让模型自己去推断——给 Agent 的自主规划划分得一清二楚，而不是让它自由发挥、错了再补救。

作者说 graph engineering 有很多元素和构件，比如说 data engineering、graph modeling、retrieval、reasoning 推理，还有 Agent 的编排。什么时候去用它？比如说你的业务流程有一些固定的套路，而且要稳定、可预期的回答；还有多个 Agent 之间进行协同工作，那也要编一张网络，然后去让 Agent 之间能够互相共享一些上下文，以及 Agent 之间能够互相影响、协同工作。

作者提到，之前的视频里他也跟大家详细讲过 graph engineering 到底是什么：它本质上是一个 multi-agent 的系统，然后通过一个网络的结构把 Agent 串起来。比如说这样一个 loop，它就是一个最简单的 graph engineering——Agent 去调用工具，调用工具之后有另外一个 evaluate Agent 进行检查，如果不够好的话再回去这个 Agent 进行循环的操作。这样一个就是一个非常简单的 graph engineering。

所以作者的总结是：graph engineering 本质上是**给 LLM 装上了一个轨道**，然后在入口处让 Agent 自己去判断，其余的路段就按既定的轨道去走——既给了自由，又保证了一个 `cope`〔ASR 原文如此，所指待确认〕。

> **思考一下｜"轨道"的自由度到底留在哪一段**
>
> 作者把自由集中在入口的判断上，其余路段交给既定轨道。这样换来的是可预期，代价是入口一旦判错，后面整条轨道会顺着错误方向一路跑完。
>
> **可以追问**：出现什么信号时，应该让 Agent 跳出轨道、回到人这里？
>
> **可延展方向**：在设计稿里为每个节点标注"这一步是固定边还是模型自选"，比上线后靠调试去发现要早得多。

### 五张图放在一起比一比

作者把五张图都讲完之后，放在一起做了个对比。他给的一句话记忆是：**规则书 ontology、世界网 knowledge graph、业务上下文地图 context graph、代码的管网图 code graph，以及最后一张 Agent 的轨道 graph engineering**。

他还做了一下类比：ontology 有点像游戏的规则、城市的规划图；knowledge graph 有点像游戏里面的角色还有建筑；context graph 就是当前游戏的一个关卡、任务目标还有资源的状态；code graph 有点像游戏引擎里面的代码结构；graph engineering 就是游戏引擎和运行的整个系统。

什么场景用什么图？作者用一张简单的表帮大家做了总结：你要进行机器的推理、推出一个新的结论、统一语义和术语，就用 ontology；你做一些通用的常识问答、还要做推荐、还有多跳的一些问答，就是 knowledge graph；Agent 要进公司干活、帮你做一些影响推理的分析、审计的追踪等等，这些就是用 context graph；code graph 是最好理解的，它就做一些代码的导航，要去看改这个代码对于之后的影响评估；最后一个就是有套路的一些业务流程的编排，还有要稳定可控的 Agent 流水线，就用 graph engineering。

作者说，你可能还会想问：这些到底怎么样一起干活？他给了一张图做全景的架构参考，分为四层：

第一层叫**定义层**，其实就是 ontology，定义这些概念和语义的关系，它是一个基础；第二层叫**表示层**，或者叫表征层，它表征的是一个整体的、实际的数据情况，比如像知识图谱，还有上下文图谱以及代码的数据；第三层是**工程层**，工程层其实就是 graph engineering 这一层，就是我们有各种工程上面的运作，给 Agent 的一个工程；最后一层叫**应用层**，应用层其实就是给 Agent 提供的各种运行环境和运行工具。这样去构建一个完整的、我们 Agent 和企业的运行系统。

接下来作者拿一个真实的场景再帮大家理解一下：比如我们有一个采购寻源的 Agent 要做，这个 Agent 去自动寻找、评估，还要推荐供应商。首先我们要用本体去定义采购业务域——什么是供应商、品类、还有零件这些实体，先定义清楚，做一个基座；它能支撑语义关系，还有我可以用的规则和动作是什么，把基座给搭好。接下来知识图谱就去存这些数据，查询企业里面已经有的一些供应商、供应关系，还有历史的采购记录等等。那上下文图谱其实就是根据当前的一个任务去理解你的任务背景，然后去分析本次采购的品类、需求、数量是什么，目标成本是什么，然后给你去做一些辅助决策〔此处 ASR 作 `反正决策`，待确认〕，还有历史推荐决策的一些原因，去分析一些历史数据。那 code graph 就比较好理解了，就是你自己本身去实现这一套相应系统的代码，这些代码的结构。最后就是我用 Agent 去做这个事情的话，我要去做一系列的工程，去建立 Agent 执行的一个轨道。

作者用这个例子收束这一段：五张图各司其职，其实缺一不可；它们不是互相替代，而是分工协作。

> **思考一下｜四层架构是分工，还是一条施工顺序**
>
> 定义层被放在最底下、并且被称作"基础"，但另外三层并不会等它做完才存在——企业里通常已经有数据、有代码、也有在跑的流程。这四层更像是各管一段，而不是一道严格的先后工序。
>
> **可以追问**：如果定义层只覆盖了采购域、没覆盖财务域，上面三层会怎么表现？
>
> **可延展方向**：把四层当成四张验收清单，分别回答"概念对不对、数据准不准、流程稳不稳、Agent 好不好用"。

### 收尾：企业里其实有两类图

作者最后做了一下小总结：今天我们讲了 ontology、knowledge graph、context graph、code graph、graph engineering；当然我们可以用很多的定义和概念去描述它，但简单理解就是——AI Agent 为了在企业里面落地，其实出现了两个类型的图：一种类型的图能去描述企业的业务情况、还有知识、还有定义企业里面的语义关系、实体对象等等；最后一个 graph engineering 其实是去做 Agent 的执行。Agent 怎么去帮你执行呢？我需要有一个编排的轨道，这个就让 Agent 既系统、又靠谱。

## 综合解读

**论点链。** 这一集的推论是一条"先分类、再定位"的链：五个词之所以让人混乱，是因为它们被当成同一层的东西在比较；作者先用"系统知道什么 / 系统怎么干活"把前四个与最后一个切开，再把前四个按"规则—实例—当下状态—代码结构"依次排开——本体是规则书（能被机器读懂的字典加语法书），知识图谱是照规则填出来的实例网络，上下文图谱在实例之上补进任务状态、事件与历史决策，代码图谱把软件自身变成一张可查的管网图；最后用 graph engineering 把 Agent 的执行路径固定成轨道。收尾处他把两类图重新合起来：一类描述企业，一类驱动执行，两者缺一不可。

**隐含前提。** 这套分类要成立，依赖几个没说出口的条件：一是这些词在企业里确实可以被分层、互不重叠——而作者自己也承认 context graph 在厂商与学术界之间定义并不统一，同一层的边界本来就是可争的；二是"知道什么"与"怎么干活"可以分别建设、分别验收，但现实里上下文图谱往往是从运行中的系统里长出来的，而不是先建好再接入；三是本体里的规则真的能写全、写稳，作者讲本体时留了一句"本体还有一些〔`倾启`，待确认〕"，说明他对这一点也没有把话说满；四是用图来表达企业的成本低于它带来的可解释性收益，而这一点作者在本集里没有展开算账。

**待核验主张。** 以下均为作者在视频中的陈述，未经独立核实：

1. 五个词分成"知道什么"和"怎么干活"两类，以及"知道什么决定答得对不对"的对应关系——这是作者提出的概念框架，不是行业公认的划分方式。
2. Palantir 的 ontology 由 objects、links、properties、logic、actions、security 六部分构成。
3. 金融领域开源本体 `FIBO`（ASR 作 `fibre`）与医疗领域 `FHIR` 的定位；`FHIR` 通常被描述为医疗数据交换标准，它是否属于作者所说的"开源本体"，需要单独核实。
4. 上下文图谱的三层结构（语义基础 / 元数据 / 决策轨迹）属于作者或厂商的整理，不是通行定义。
5. DataHub 与 `Atlant`（疑为数据目录厂商 Atlan，ASR 拼写待确认）对 context graph 的用法被描述为"更注重决策轨迹和治理"。
6. 学术界有一篇把 context graph 定义为"在知识图谱上补时间、地点、出处与置信度"的论文——作者未给出处，需自行检索确认。
7. 代码图谱由源代码、抽象语法树、依赖关系与执行关系构成，以及"代码量大到人脑记不住时才需要建图"这一使用时机判断。
8. 四层全景架构（定义层 / 表示层 / 工程层 / 应用层）是作者给出的参考架构；采购寻源 Agent 是演示性示例，不是客户案例。

此外，本集若干表述在 ASR 中并不清晰（如开篇"是地图、是原料，越攒越值钱"一句、"它跟业务是要天天打交道的"一句，以及 `倾启`、`来战表`、`自然表`、`Atlant`、`拍什么一件`、`cope`、`反正决策`），引用时宜回到原视频复核。

**边界与反例。** 作者自己给出的边界有两处：一是适用时机——代码图谱只在"代码量大到人脑记不住"时才值得建，图谱工程只在"流程有固定套路、要稳定可预期"时才用，它们的反面（探索性、一次性、不需要稳定结果）并不需要这些图；二是定义上的不统一——context graph 一词在数据平台厂商、学术界和他自己的用法之间并不一致。可以提出的反例有三个：其一，代码图谱是静态产物，而代码每天都在变，图谱的新鲜度可能比覆盖度更决定它有没有用；其二，"给 LLM 装轨道"提高的是可预期性，但如果入口判断错了，整条轨道会稳定地跑向错误结论，稳定性在这里是放大器而不是保险；其三，作者把"知道什么"与"怎么干活"分开讲，但在真实系统里，Agent 每次执行都会产生新的状态和决策记录，这些记录本身又会回流成上下文图谱的输入，两者的边界是流动的。

**可迁移素材。** 抛开具体产品，这一集能带走四件东西：其一，一张概念对照表——本体=规则书、知识图谱=世界网、上下文图谱=业务上下文地图、代码图谱=代码管网图、图谱工程=Agent 的轨道，用来快速判断一场讨论里大家说的"图"是不是同一个东西；其二，用"系统知道什么 / 系统怎么干活"这两个问题给任何 AI 方案做一次定位，先问清它补的是知识侧还是执行侧；其三，建图之前先问"我什么时候会用到它"——作者给代码图谱的答案是"改代码之前做风险预演"，这个使用时机比"图里有多少个节点"更好当验收标准；其四，作者处理 context graph 的方式本身可以搬走：遇到一个被多方使用的热词，先把各方定义并排写出来，再决定用哪一套。
