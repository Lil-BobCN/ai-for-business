## 一句话摘要

视频作者认为，这次 OpenAI 真正卖的不只是模型，而是把 Codex 背后那套 `Honest`〔ASR 原文，所指待确认〕开放成了 Agent API：上下文压缩、工具检索、程序化调用工具与多 Agent 编排被一起收进平台层——模型只是发动机，企业真正该沉淀的是自己的业务上下文、可调用的动作与治理规则。

## 阅读路线

先看作者如何区分"模型 API"和"Agent API"（一个给大脑，一个给数字员工的运行时），以及他为什么说模型能力不等于 Agent 能力；中段逐条拆解这次开放的四项能力：上下文压缩、tool search、programmatic tool calling、multi-agent；后半段是运行时（harness）与执行环境（sandbox）解耦之后越来越清楚的三层架构，以及作者对"Agent framework 会不会被模型厂商吃掉"的判断；最后是他给开发者的转向建议和一句话总结。如果只记一句，作者想留下的是：**模型只是发动机，harness 决定这辆车能开多远**。

## 口播文章

### 这一次，OpenAI 卖的不只是模型

视频作者开篇提到，OpenAI 刚刚发布了 Agent API〔产品名依 ASR 原文，待确认〕。乍一看，它好像只是 OpenAI 又发布了一个新的 API 而已——但作者认为，这一次 OpenAI 真正卖的不只是模型，而是 `Honest`〔ASR 原文，所指待确认；同一个词在本集草稿中另有多处被转写作 `hunnies`〕，而且就是 Codex 背后那套 `Honest`。

作者先解释 Agent API 到底是什么。过去我们开发一个 Agent，通常要拼很多的东西：最下面是大模型，然后是接 Tools，再往上还要自己处理 Memory、Context、Workflow、Tools Calling、Multi-agents、Sandbox、Checkpoint 等等。

而这次 OpenAI 做的事情，就是把 Codex 已经在使用的那套 `Honest` 直接通过 API 开放出来。就像这样：你只要告诉它，我要完成什么任务、用什么模型、以及使用什么工具、在哪个环境里去执行，剩下的 Agent Loop、Context Management、Tool Management 以及 Sub-Agent 的协调，OpenAI 都会帮你处理掉。所以作者说，过去的模型 API 更像是我给你一个大脑，而 Agent API 更像是我直接给你一个可以持续工作的数字员工的运行时软件。

### 模型能力不等于 Agent 能力

作者接着讲为什么这件事情很重要：真正做过 Agent 的人很快就会发现，模型能力并不等于 Agent 能力。模型可以负责推理、判断、生成，但一个 Agent 如果想在连续工作几十步、几百步，在企业生产里面去应用，还需要很多模型之外的基础设施——比如说上下文怎么管理，工具怎么使用，复杂任务怎么拆给 Sub-Agent，失败了怎么去恢复，代码和文件到底在哪个环境里面去执行。这些东西过去往往都需要开发者自己来搭。

作者的概括是：Demo 很容易，真正做生产系统却非常难。他随即给出一个比喻：像 GPT 这样的模型就是汽车的发动机，而 `Honest` 更像是变速箱、方向盘、底盘、导航和控制系统；发动机再强，没有后面这些东西，这辆车也很难稳定地跑几百公里。所以这就是为什么 Agent 需要 `Honest`。

> **思考一下｜Demo 与生产之间，差的到底是哪一层**
>
> 作者把差距归给模型之外的基础设施，而不是"模型还不够强"。这个归因很实用：它把"我们的 Agent 还不好用"翻译成了一串可以被检查的工程项。
>
> **可以追问**：这五项——上下文、工具、任务拆解、失败恢复、执行环境——里，哪一项最容易被自研团队低估工作量？
>
> **可延展方向**：用"这套运行时交给平台还是自己维护"做一次 buy-or-build 盘点，按任务长度与合规要求分档，而不是一刀切。

### 变化一：上下文管理成了基础设施

作者说，让 Agent 去跑长任务，其实就是 long running agent：Agent 跑得越久，上下文就越长。前面查了资料、写了文件、调用了工具，后面上下文快达到上限的时候就会出现一个麻烦——哪些内容要保留、哪些可以丢，之前做到了哪一步，关键状态怎么去恢复。这些都是打造 long running agent 过程中会遇到的问题。

以前程序员经常需要自己去做 summary memory 或者 checkpoint；有了 Agent API 之后，是把上下文压缩（context compression）做进了 `Honest` 里面。作者提到，大家如果用过 Claude Code 以及 `collects`〔ASR 原文，所指待确认〕，都会遇到上下文压缩的这种情况。

按作者的描述，当一次 session 接近 context limit（上下文上限）的时候，Agent API 里面的功能会自动压缩前面的上下文，同时尽可能保留后面继续工作需要的信息——也就是在 context window 上做了一些工作。这就意味着，一个任务往往可以跨多个 context window 继续执行。作者由此判断：Agent 也真正从短对话走向了连续工作几个小时〔此处一句 ASR 转写不完整，措辞待确认〕，而上下文管理也越来越像一个标准的基础设施，而不是每个团队都要自己重新打造一遍。

> **思考一下｜自动压缩，是把取舍权交了出去**
>
> "压缩"本身不是难点，难点是"哪些信息不能丢"。作者讲清了机制，但没有说这个取舍由谁来定规则。
>
> **可以追问**：如果被压掉的是某次审批的依据、某个口径或某条例外条件，事后还能不能还原？
>
> **可延展方向**：把"压缩之后还能否复现关键决策"写成长任务 Agent 的回归测试用例。

### 变化二：tool search，让 Agent 自己去找工具

第二个变化是 tool search，也就是工具的使用。作者说，现在很多 Agent 一启动，就把所有的 tool definition（工具定义）一次性塞给模型。如果企业里面只有 5 个工具，当然是没有问题的；但企业里面可能是 ERP 100 个接口、采购系统 200 个 action，再加上 CRM、财务知识库、MCP server 等等，最后可能有上千个、三万个的工具〔数字依 ASR 原文"上千个三万个"，待确认〕全部塞进大模型的 prompt 里面，不仅浪费 token，还会让模型更难选对工具。

所以 tool search 的思路非常简单：不是把整个工具一次性一股脑塞给 Agent，而是 Agent 真正需要什么，再去把相关的工具找出来。作者举例：你现在要调查一次现场事故，它可能只搜索日志查询、deployment 还有 metrics 这几个相关的工具，然后把这些 tool schema 加到上下文里面。

所以作者判断，未来企业 Agent 的问题可能不再是"Agent 能不能调用工具"，而是"企业里面有这么多工具、甚至上万个工具的时候，它怎么找到正确的那一个"。

> **思考一下｜工具目录本身变成了要治理的资产**
>
> 检索要选得准，前提是每个工具的命名、描述与权限标注都写得足够清楚——这份工作不会因为有了 tool search 就消失，只是从"写调用代码"挪到了"维护目录"。
>
> **可以追问**：工具数量过千之后，谁负责这份目录的质量与准入？
>
> **可延展方向**：把工具当成对外接口来治理（命名规范、schema、权限、废弃流程），检索准确率才有可维护的下限。

### 变化三：programmatic tool calling

第三个变化叫 programmatic tool calling，也就是 PTC 模式。作者说，之前讲 DeepSeek Harness 的时候也提到过。过去很多 Agent 是这样工作的：LLM 思考一次、调用 tool，结果回来再拿 LLM 思考一次、再调用 tool，一个任务下来几十次模型调用，不仅慢而且非常贵。但很多工作其实根本没有必要让 LLM 每一步都参与。

作者举了一个例子：拿到 10 万条日志，合理的做法不是把 10 万条日志全部都扔给模型，而是先用代码过滤、聚合、统计，最后只剩下 20 条异常再交给模型分析。所以 Agent API 允许 Agent 用程序并行调用工具、串联工具，以及过滤和组合结果，最后把真正重要的信息交给上下文。这里有一个很重要的原则：该模型判断的时候模型判断，该代码计算的代码计算，该业务系统执行的交给确定性的工具和函数。

> **思考一下｜判断、计算、执行的三分法**
>
> 这条原则的价值在于它可执行：任何一步都能被追问"它到底属于哪一类"，从而判断这一步该不该经过模型。
>
> **可以追问**：分类的边界由谁拍板——按"是否需要自然语言理解"，还是按"出错的代价"？
>
> **可延展方向**：把三分法写进 Agent 设计评审模板，作为第一个必答问题。

### 变化四：multi-agent 进入底层

第四个变化是 multi-agent：多 Agent 的协同工作开始直接进入底层，由 `Honest`〔草稿此处作 `hunnies`〕提供给你。作者举例：一个 Agent 要调查线上系统为什么突然出现大量的 500 错误，主 Agent 可以把任务拆开——一个 Sub-Agent 查部署（deployment）的情况，一个 Sub-Agent 查错误日志，另一个 Sub-Agent 查依赖项和关系级的分析；几个 Agent 可以这样并行工作，而且每一个 Sub-Agent 都维护自己的上下文，最后再由这个主 Agent 进行汇总。

作者补充说，以前这种 Agent 的编排，你可能自己会用 LangGraph、`out of jam`〔ASR 原文，所指待确认〕或者自己写一套 workflow；现在 OpenAI 是把这套能力直接植入到 Agent API 里面，作为一个原生能力。这也释放了一个很明显的信号：模型公司已经不只是在提供模型，它开始把 Agent runtime 里面越来越多的通用能力一起提供——之前的 `dbc hunnies`〔ASR 原文，所指待确认〕也是类似的事。

### 关键设计：没有把运行时跟执行环境绑死

作者特别点出一个很关键、但非常容易被忽略的设计：OpenAI 没有把 `Honest` 跟执行环境绑死。`Honest` 可以由 OpenAI 托管，但 Agent 真正运行代码、操作文件的那个 sandbox，你有很多种选择：你可以使用 OpenAI 托管的 sandbox，也可以放到自己的基础设施里面，或者第三方的 sandbox 环境。这样架构就变得非常清楚——`Honest` 负责的是怎么去思考、怎么去协调、上下文管理以及什么时候去调用工具；sandbox 负责的是代码在哪里执行、文件在哪里操作、依赖在哪里安装、计算资源从哪里买。作者觉得这种结构非常重要，因为企业可以把敏感数据的执行环境放在自己的基础设施，同时使用托管的 Agent `Honest`。

接下来作者梳理了整个架构：这次 Agent API 的发布，让 Agent runtime 的分层越来越清晰。最下面是 model，也就是我们的模型，负责推理；中间是 `Honest`，负责上下文管理、工具的管理、Sub-Agent、Agent 的编排以及长期的运行；旁边是 sandbox，负责代码、文件、计算环境。OpenAI 这次跟 `cloud failed`〔公司名 ASR 未可靠识别，待确认〕等几家公司一起来提供托管的沙箱服务。

再往上，是企业真正应该关注的应用层：业务数据、工具 actions、权限、规则和用户体验等等。也就是说，底层通用能力越来越可以标准化了，企业没有必要把大量工程资源花在重复造 Agent `inflow`〔ASR 原文，所指待确认〕上面；真正产生差异化的，越来越集中在企业自己的 business context。所以作者建议：如果大家想在未来做产品，应该往 Agent `inflow` 上面的产品去迭代，跟这些大模型公司合作；或者模型公司自己也会花时间去沉淀 Agent `inflow` 的产品，企业里面其实就用这套通用的 `inflow`，结合自己的业务上下文，把真正的 business application 打造出来。

### Agent framework 会消失吗

最后一个问题：Agent 的 framework 会消失吗？会不会被模型厂商直接吃掉呢？作者觉得答案不是——LangGraph、CrewAI 这些 framework 不会突然消失，而是大量通用的 Agent `inflow` 会慢慢往下沉。他说，tool calling 已经进入模型的 API，web search、file search、computer use 也进入了一些平台；现在连上下文管理、工具的搜索、多 Agent 的编排、长任务的管理，都由模型厂商开始提供了。

所以未来开发者真正应该投入精力的，可能不再是我用了哪些 Agent framework，而是：你的业务 context 是什么？Agent 应该理解哪些业务对象、哪些数据是可信的？有哪些 actions 和 function 它可以调用？权限怎么控制？什么事情能够自动运行、什么事情必须人工审批？

> **思考一下｜通用能力下沉之后，企业剩下什么**
>
> 作者把"用了哪个框架"降级成实现细节，把业务上下文与治理提到台前——这其实是一次资产位置的搬家。
>
> **可以追问**：如果框架每两年换一次，团队的沉淀放在哪一层才不会跟着一起被换掉？
>
> **可延展方向**：把"业务对象、可信数据、可调用的动作、权限与审批线"整理成一份可交接的清单，作为选型与自研共用的底稿。

### 作者的一句话总结

作者用一句话来总结这次 Agent API：OpenAI 其实是把 Codex 背后的 agent harness〔草稿此处直接转写作 `harness`，与上文的 `Honest`／`hunnies` 是否同指未经确认〕做成了一个基础设施、做成了 `inflow`〔ASR 原文，所指待确认〕。他说，以前我们讨论 Agent，经常把注意力都放在模型的能力上面，但到真正生产落地的时候会发现，模型只是发动机，harness 才决定这辆车能不能连续开几百公里；而当底层的 harness 越来越标准化的时候，企业自己的 context、Ontology、Tools、Business Logic（业务逻辑）以及 Governance（治理）反而会越来越重要。

最后作者照例收尾：OK，这个就是本期视频全部内容了，如果你觉得还不错呢，欢迎点赞、收藏和关注，我们下期再见（结尾另有一串 ASR 未能识别的字符 `by bwd6`，待确认）。

## 综合解读

**论点链。** 作者的推论是一条从下往上的线：做 Agent 的痛点不在模型，而在模型之外的那一整套运行时 → OpenAI 把 Codex 里已经跑过的这套运行时（他口中的 `Honest`）通过 Agent API 开放出来 → 于是上下文压缩、工具检索、程序化调用工具、多 Agent 编排这些"原本每个团队各造一遍"的能力被收进平台 → 平台同时把运行时与执行环境（sandbox）解耦，企业可以把执行留在自己的基础设施 → 通用能力标准化之后，framework 不会消失但会下沉，差异化的位置从"用了哪个框架"搬到"业务上下文、可调用的动作、权限与审批" → 结论落在企业侧：模型只是发动机，harness 决定车能开多远，真正属于企业的资产是 context、Ontology、Tools、Business Logic 与 Governance。这条线和本系列前几集的落点是一致的：越往底层，能力越通用、越会被厂商吃掉；越贴近业务语义与治理，越留在企业手里。

**隐含前提。** 这套说法依赖几个没说出口的条件。一是"Codex 里被验证过的运行时"能平移到企业的长任务场景——视频里的例子集中在工程排障（日志、部署、依赖、500 错误），这类任务的边界比跨部门业务流程清楚得多。二是"哪些信息可以丢"可以由平台侧的通用压缩策略决定，不需要业务规则参与；如果被压掉的是审批依据或例外条件，这一点就会从效率问题变成合规问题。三是工具目录的质量已经足够好，检索才能选对——命名混乱、描述缺失、权限不清的工具集会让 tool search 失效。四是"把 sandbox 放在自己的基础设施"就等于解决了数据主权，但模型调用与上下文仍会离开企业边界；作者给出了执行环境这一侧的答案，没有给上下文这一侧的边界规则。

**待核验主张。** 以下均为作者在视频中的陈述，未经独立核实：

1. 这次 OpenAI 发布的是"Agent API"（草稿另作 `agents API`、`agent 的 API`），且是把 Codex 正在使用的那套运行时通过 API 开放；产品名称、发布形式与发布时间均需外部核对，视频只说"刚刚发布"，未给时间点；
2. "模型 API 给大脑、Agent API 给数字员工运行时"这一对比，以及过去开发者要自己处理的清单（Memory、Context、Workflow、Tools Calling、Multi-agents、Sandbox、Checkpoint）；
3. 上下文压缩（context compression）已内建在 `Honest` 中：接近上下文上限时自动压缩前文、尽量保留后续所需信息，任务可跨多个 context window 继续执行；
4. 企业工具数量的量级：ERP 100 个接口、采购系统 200 个 action、CRM、财务知识库、MCP server，最终"上千个、三万个"（草稿原文即写作"上千个三万个"，数字待确认）；
5. tool search 的机制与"现场事故"示例（只检索日志查询、deployment、metrics，再把 tool schema 加进上下文）；
6. PTC 允许程序并行调用工具、串联工具、过滤和组合结果；"10 万条日志筛成 20 条异常"是作者的说明性举例；
7. multi-agent 由底层原生提供、每个 Sub-Agent 维护自己的上下文、由主 Agent 汇总；"500 错误"调查同样是举例；
8. `Honest` 与 sandbox 解耦，sandbox 可选 OpenAI 托管、自建或第三方；企业可"敏感数据执行环境自持 + 托管运行时"；
9. OpenAI 这次与 `cloud failed` 等几家公司一起提供托管沙箱服务（合作方名称 ASR 未可靠识别，需核对）；
10. tool calling 已进入模型 API，web search、file search、computer use 已进入一些平台，"现在连上下文管理、工具搜索、多 Agent 编排、长任务管理都由模型厂商开始提供"；
11. **`Honest` 这个词的身份**：它是本系列中反复出现却始终没有被可靠识别的一个词——第 1 集出现 1 次，本集草稿出现 13 处（写作 `Honest` 6 处、`hunnies` 7 处），且本集结尾又有一处直接转写作 `harness`。它到底对应哪个产品、组件或概念，本集没有给出任何可核对的写法，需要外部核验后才能使用；
12. 结尾"OpenAI 把 Codex 背后的 agent harness 做成了基础设施"以及"framework 会下沉、企业资产在业务侧"属于作者的判断与预测，不是已发生的事实。

**边界与反例。** 作者自己划的边界是"生产落地"这个语境——他谈的是能连续跑几十步、几百步的长任务，以及上千个工具的企业规模；他也明确说 framework 不会突然消失，只是通用部分往下沉。可以补充的张力有三处。第一，这套叙述来自平台侧的发布信息，作者的示例（日志、部署、500 错误、事故调查）几乎都是工程排障场景，换成需要跨系统写操作、审批链长的业务场景，"自动压缩 + 自动拆解"是否同样成立，视频没有检验。第二，"企业不必重复造 Agent 运行时"与"企业要沉淀自己的 context 与治理"之间存在成本转移：省下的工程资源要投到建模、权限与审批上，而这部分通常更贵，也更依赖业务方而不是工程师。第三，运行时托管给模型厂商与作者强调的数据主权之间需要一条明确规则（哪些上下文可以出企业、哪些绝对不行），视频只在 sandbox 一侧给了答案。

**可迁移素材。** 抛开 OpenAI 本身，这一集能搬走的东西不少：一是长任务 Agent 的五项基础设施清单——上下文管理、工具使用、复杂任务拆解、失败恢复、执行环境，可以直接当作自研或选型的验收表；二是"接近上限时自动压缩、并保住后续继续工作需要的信息"这个设计意图，它比"要不要做记忆"更接近工程现实；三是工具规模上千之后的判断句：问题从"能不能调用工具"变成"怎么找到正确的那一个"，以及随之而来的工具目录治理；四是那条三分法——该模型判断的交给模型，该代码计算的交给代码，该业务系统执行的交给确定性的工具和函数；五是 harness 与 sandbox 分离，把"谁负责思考与协调"和"代码在哪跑、数据在哪落"拆成两个可以独立选择的决定；六是当通用层下沉时，企业侧的资产清单：业务 context、Ontology、Tools、Business Logic、Governance，以及那条审批线——什么能自动运行，什么必须人工审批。
