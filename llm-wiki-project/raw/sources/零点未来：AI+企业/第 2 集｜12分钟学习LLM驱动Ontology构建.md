## 一句话摘要

视频作者认为，用 LLM 建 Ontology 已经不再是"能不能"的问题，而是"怎么建得更好"的问题：他先摆出四道坎——类型数量未知、模型幻觉、粒度难控、评估没有标准答案——再把过去两年学术界与工业界的应对归纳成五种流派（拆解派、聚类派、两步走派、框架派、直给派），并给出一条按工程复杂度与幻觉风险选型的判断框架，分界线就是"玩具"和"生产系统"。

## 阅读路线

先看作者用一个"供应商评分忽高忽低"的场景说明没有 Ontology 的世界长什么样，以及一张知识地图能带来什么样的链式推理；中段是四道坎与五种流派的逐一拆解——拆解派的验证闭环、聚类派的让数据说话、两步走派与框架派的不同起点、直给派的快与险；随后是选型判断框架、三条实战教训，以及作者用 vibe coding 做的那个 Ontology 构建小工具演示。如果只记一句，作者想留下的是：**关键不是数据，是数据治理和约束的合理性**。

## 口播文章

### 开场：这一集聊"怎么建"

视频作者开场说，上一期视频介绍了 Palantir 和 Ontology，这一期我们来聊一聊如何用 LLM 构建 Ontology。他说话不多说，直接开始，但先要回顾一下：搞清楚 Ontology 是什么，以及它为什么重要。

### 没有 Ontology 的世界：同一个问题，三个答案

作者先描绘了一个场景。你的老板让你做一个企业的 AI 知识库，你很兴奋，直接就把公司所有的文档丢给 LLM——比如说 GPT 或者 Claude，让 GPT 来回答问题。当天同事或领导就来用了，比如说我问"供应商 A 的评分是多少"，AI 回答说 85 分；第二天你再问的话，它可能变成 92 了；后天再问，它又变成 78 了。每次它好像都是在"猜"一样，领导脸色就变了。

为什么会这样？作者说，本质上 AI 其实没有在说谎，它只是根本不知道"供应商""评分"还有"日期"这三件事情之间有什么关系，它每次其实是在做一些数据的模仿。作者说，这就是没有 Ontology 的世界。

> **思考一下｜不一致的答案，暴露的是缺失的模型**
>
> 值得注意的地方在于：作者把 85、92、78 这三个数字归因于"缺少关系与规则"，而不是"模型不够强"。也就是说，同一个症状既可以走"换个更大的模型"这条路，也可以走"补一层语义"这条路，作者选择的是后者。
>
> **可以追问**：如果要求 AI 每次回答都带上依据和日期，这个不一致会自行消失，还是只是被隐藏起来？
>
> **可延展方向**：把"同一问题在不同时点的答案是否稳定"当成一个可测量的验收指标，比只看单次回答质量更能暴露语义层缺失。

### Ontology 是知识地图：从查事实到链式推理

作者说，Ontology 翻译成中文，前面有讲过，叫做"本体"；说白了它本身就是一个知识地图。它不只是告诉 AI 有哪些数据，还告诉它这些数据之间有什么关系、遵守什么样的规则。有了这张地图之后，AI 才能够从随机猜测变成有据可查，能够跟随你的业务流程来走。

他举了一个更直观的例子：你定义好供应商有名称、评分、所在地区、材料、库存，还有安全阈值；供应商和材料之间是供应的关系。这一套定义在知识图谱里面构建好 Ontology 之后，AI 就会查到结构化的事实，不用再猜了。更厉害的是，它能够顺着这张地图去推理：这个材料缺货了，会影响哪条产线，进而影响哪个客户的订单。作者说，这种链式的推理，也只有构建好 Ontology 本体之后才可以给。所以顺序是先建好知识地图，然后再让 AI 进来用。

### 传统建法为什么走不通

那么问题来了：这张地图、这个 Ontology 怎么建呢？作者说，传统的方式就是由一堆知识工程师或者说业务专家坐在一起，花上几个月的时间在白板上画来画去，写了各种标准格式的定义；等建完了之后，业务也可能发生了变化，又慢又贵，还没有人愿意持续地维护。这就是为什么大部分公司的知识管理系统最终都变成了所谓"死档案"。

### 四道坎：LLM 建 Ontology 没那么简单

LLM 来了之后，这件事情有没有解法呢？作者说有，但不是你想象的那么简单，因为用 LLM 构建 Ontology 有四道坎。

第一道坎，你根本不知道有多少种类型。在一个领域的知识地图之前，你不知道这里面有什么东西——是十种还是一千种；即便是对于人来说，他也不一定了解有多少个实体类型。

第二道坎，LLM 本身会输出幻觉。它有可能创造出你输入给它的数据里根本没有的概念，然后把这些想象当成事实。

第三道坎，粒度难以控制。关系太宽泛没有用，太细又没有人能够维护，有一些实体之间的联系又太密；什么样的粒度更合适，这本身就是一个难题。

第四道坎，建什么样的 Ontology 其实没有一个标准的答案，它也没有对错之分；怎么去评估这个好坏，或者说这个 Ontology 建完能不能用，也是一个问题。

作者说，这四道坎在过去两年当中，学术界和工业界都发展出了应对方式，总结起来就是五种完全不同的应对方式，可以把它称作五种流派。

> **思考一下｜四道坎里，哪一道不是工程问题**
>
> 前两道坎是工程问题——类型枚举可以靠数据探索补齐，幻觉可以靠校验压制；后两道坎不是。粒度合适不合适、本体好不好，取决于业务上要拿它回答什么问题，而这恰恰没有客观答案。
>
> **可以追问**：如果第四道坎没有标准答案，那么"双重验证通过"到底验证的是正确性，还是仅仅验证了自洽性？
>
> **可延展方向**：在建模之前先写下一句"这个本体要回答的业务问题"，把它当作判断粒度是否合适的唯一依据。

### 流派一：拆解派——每一步都设验证闭环

第一个流派叫拆解派。核心思路就是把一个很大的 Ontology 拆解成小的任务，每一步都用最合适的工具：提取实体、提取关系、去重归一、验证、存图，一步一步来。这里最关键的设计就是验证的闭环——每一个新的事实，都要先通过结构化的检查和逻辑的检查，才能够进入可信的图谱；通不过的，只能保留为日志，不让它污染整个知识库、污染整个本体。

作者举例说，法国的电力公司 EDF 就用这套方法管理核电站的技术文档。缺点就是工程量非常大，前一步出错就有可能污染后一步；但如果你真的要上生产系统，这是目前最可靠的选择。他打了个比方：就好比做一道复杂的菜，先洗菜、再切菜、再炒菜、最后装盘，其中的 LLM 只是作为一些辅助工具去帮你提取这个关系，核心还是需要有业务专家去梳理整个业务的规则。

作者说这里面有两个案例：第一个是刚刚提到的法国电力，第二个就是〔`Wingtonic`，专名待确认〕去构建一个完整的知识图谱。这里面提到的双重验证分为两层：首先第一个叫结构的验证，第二个叫逻辑验证；只有两层都通过了，才可以上可信的 Ontology。

> **思考一下｜验证闭环才是可以搬走的那一件**
>
> 拆解派列了五个步骤，但真正让它区别于其他流派的只有一步：验证。而且验证分了两层——结构（格式、类型是否自律）和逻辑（关系是否成立），两条都过才入库，不过的进日志。
>
> **可以追问**：这些校验规则由谁写？如果规则本身也来自 LLM 的推断，闭环是不是变成了自证？
>
> **可延展方向**：把"错误进日志而不进图谱"当成一条工程约定——它让错误可见、可回放，又不至于污染下游。

### 流派二：聚类派——先别急着定义

第二派叫聚类派。它的思路就是先别急着去定义有什么东西，让数据自己去说话：把文档中的名词提取出来，可以用一些聚类的方式，比如说用 AP 聚类。作者解释了这里为什么不用 K-means 聚类——因为 K-means 首先你要告诉它我们有几类，而在我们的数据当中，我是不知道它有几类的，所以要用一些密度聚类的方式，比如说像 AP 聚类。

聚完了之后，再用 LLM 给每一组、每一个 group 起名字。这里最代表性的论文是 2025 年的〔`LLM for Ontology`，论文名待确认〕，它构建了一个方法论，核心的流程就是先输入文档、提取其中的名词，然后这些名词用 BERT 模型做向量化，基于向量去做 AP 聚类，再用 LLM 进行命名，最终构建好 Ontology。作者打了个比方：这就好比去搭乐高积木一样，先把颜色相近的放在一起，再给每组贴标签，然后再看这个组之间怎么去连接到一起，以及有哪些动作。

在刚刚提到的这篇论文里面，核心就是三步关系提取法：第一步从实例中提取关系，接着把实例关系上升成为一个本体关系；这里面构建的其实是一个三元组——实体，以及实体之间的 relation，还有另外一个实体，这样一个三元组。它的优点就是可以通过数据来驱动、拆解成一个个小任务，幻觉风险会比较低一些。但缺点也是聚类的质量直接影响最终的结果，而且在开放域上面，比如说用 Wikipedia 的一些 data 去做本体的构建，会发现整个开放域的场景输出来的粒度就有可能过细了。这种方式适合探索一些全新的领域——比如说你不知道有什么样的 Ontology 类型的时候，这种场景就可以用。

### 流派三、四：先列提纲，或先有框架

第三派叫做两步走派：先让 LLM 从文档里面去提取一些概念的清单，再让它把这个清单整理成有上下级关系的一个层次结构，最后序列化生成一个标准的格式。作者说好比写论文一样，先列一些提纲，再组织成章节；中间的产物是可以看的，可以人工审查、调整。这种方法更适合快速输出一版草稿，来验证我们整个 Ontology 的想法。也有一篇代表性的论文〔`Onto1kg`，论文名待确认〕，它就是通过这种方式去快速地提取文档模块化的一些类型，然后序列化生成整个标准的 Ontology 格式。

第四种叫做框架派，思路就是先有一个已经存在的框架，比如说 Wikidata——全球最大的开放的知识库，里面有几亿个实体。先定义好可以有什么类型、什么样的关系，然后让 LLM 基于这个框架去提取实体，不能乱发明；这样就可以去减少 LLM 的幻觉问题，输出天然符合大家共识、合规的一些实体类型。作者说，如果你所在的行业有标准的规范，比如说像医疗、法律、电力，这种方式是最合适的，因为本身你有标准的一些 schema，可以基于这个框架、在这个框架里面去提取你的 Ontology。

### 流派五：直给派——最快，也最危险

第五种叫直给派，是端到端的 prompt 方式，其实也是最简单、最危险的：就是设计一个 prompt，让 LLM 直接从文本中去输出 Ontology，一个人包圆了所有的工作。实现起来也是最快的，半个小时可能就能出结果；但幻觉的风险是最高的，输出的质量也是不稳定的，只要 prompt 一变，它的结果有可能就完全不同。

作者说，这种就适合快速地验证想法，不要马上拿去生产；比如说你要去学习如何理解一个 Ontology 的话，就可以用这种方式。去年也有一个挑战赛，就是通过 LLM 去提取 Ontology 的一个挑战赛，就会发现其实 prompt 稍微改一下，整个 Ontology 就会变掉，所以它是 prompt 极度敏感的一种方式。它适合一些 PoC 的原型验证，但不适合整个生产系统的应用。

### 五种流派怎么选：玩具与生产系统的分界线

作者把五种流派汇总到一起，整理好了一个表格，每个流派都有它自己的优缺点。比如说幻觉风险，在直给派里面就是最高的；但如果你去用拆解派或者聚类派，相对整个幻觉风险就更低。如果你要一眼看清哪个流派最适合你的需求，你会结合工程复杂度以及幻觉风险去综合选择——要选择哪个流派的方式去做，根据你的场景来。

那么五种方法具体应该怎么选呢？作者给了一个简单的判断框架：如果你就想快速试试，看看 PoC 的验证效果、看方向对不对，你直接用直给派，用 LLM 加 prompt 的方式去提取 Ontology；如果你想探索一个全新的领域，不知道里面有什么，就可以参考这个聚类派的方式，让数据告诉你答案；如果你已经有行业标准和现成的一个知识体系，你就可以用框架派，比如说用 Wikidata 里面的，或者行业标准的约束，让 LLM 去输出满足这行业标准、合规的 Ontology，少走弯路；如果你要上生产系统、不能出错，就可以用拆解派加双重的验证机制，虽然工程量比较大，但是它给你的结果也是最好的——这就是玩具和生产系统之间的分界线。

> **思考一下｜选型轴线上，幻觉不是唯一成本**
>
> 作者把选型压成两个维度：工程复杂度与幻觉风险。这两个维度其实对应两种不同的代价——人力代价与错误代价。直给派省下的是人力，付出的是错误；拆解派相反。
>
> **可以追问**：如果错误可以被人拦住（比如人工审核），"玩具派"能不能也进生产？
>
> **可延展方向**：给每个流派补一列"错误在什么时候被发现"，往往比补一列"幻觉概率"更能决定它能不能上生产。

### 三条实战教训

作者说还有实战教训要大家记住。

第一，大部分错误其实都会发生在第一步，就是实体的提取这一步：比如说像类型标错了，或者说它的关系是错误了，别名混在一起了，这些错误都会一路传导到后面，越展越多。所以宁可在构建的这一步多花功夫，也不要在后期持续返工。作者说这个有点像我们以前做数据治理一样——你是要把数据治理好之后，后面模型输出的结果才是对的，我们叫 garbage in 和 garbage out：就是你输入的数据是垃圾，那你输出的结果也有可能是垃圾。

第二，prompt 的措辞非常敏感。同一个 LLM，prompt 换几个词，有可能生成出来的知识结构完全不同；用结构化的模板，而不是随便写几句自然语言，就能够大幅减少这种波动。

第三点可能有点反直觉、反而是共识：在构建 Ontology 的过程中，并不是数据越多越好。比如说像这边的〔`Wingtonic`，ASR 又作 `week ontic`，专名待确认〕，就是用了不到 1000 个 token，就建立了一个有效的知识图谱。所以作者说，关键不是数据，而是数据治理和约束的合理性。

他用一句话总结：LLM 建 Ontology 不再是能不能的问题，而是怎么建得更好的问题；这五种方式各有它上场的地方和它适用的场景，你要根据自己的场景选择对的方法、选择更适合的方法，来应对你自己场景的需求。

> **思考一下｜"不到 1000 token"推翻了什么，又没推翻什么**
>
> 这个反例真正推翻的是"数据量等于知识质量"的直觉，但它依赖一个前提：那批数据已经被治理过、并且约束是合理的。换句话说，省下的是数据规模，付出的可能是前期挑选与定义的成本。
>
> **可以追问**：如果换一个约束写得更松的领域，1000 个 token 还能撑起一个可用本体吗？
>
> **可延展方向**：把"约束的密度"当成与数据量并列的投入项来核算——小数据 + 强约束，可能是一种可复制的起步姿势。

### 作者自己的工具：OntoPrompt

作者说，为了更好帮助大家理解 Ontology 是什么以及怎么构建，他基于直给派——也就是 prompt 加上一些约束规则的方式，vibe coding 了一个 Ontology 的构建小工具，他把它叫做〔`OntoPrompt`，工具名按 ASR 还原，待确认〕，就是基于 prompt 来构建 Ontology；当然他还加了一些抽取和验证的规则。

他简单演示了这个工具。首先左侧有几个功能：第一个是概览，还有本体管理、提示词管理，以及模型管理，还有设置。比如说在设置里面，我们就可以去设置 LLM 读取文档过程中识别实体逻辑的置信度——比如说 Action 最低的置信度要达到多少，我才可以去提取这个 Action；还有就是我们的 LLM 读取和验证的规则，可以去选择性地开启，比如说要多文档实体验证，还有就是比如像本体质量验证等等这些规则。

第二个就是提示词管理。在这个提示词管理里面，可以去创建和编辑不同业务域的本体，比如说像供应链、财务和营销的这些应该是怎么去构建。作者点开一个给大家看：这个就是供应链领域的本体提取，它会假设你是什么样的领域的专家，以及它要提取的一些内容，这是一个详细的 prompt。

接着我们就到本体的管理，你可以点击这个"创建本体"来创建新的本体。比如说我们输入一个 test，然后我们选择供应链领域的本体，这样就建好了。接着我们就需要去上传我们需要解析的文件，它支持不同种文件类型：作者说他上传了 10 个文档，有文本类型、有 Markdown 的文件类型，还有 CSV 等等不同的文件类型。接着我们可以去配置 LLM，比如说选择"供应链本体提取"的 prompt 模板，然后选择配置 DeepSeek V4 的模型进行提取，我们就可以点击"开始提取"，它就会显示提取的进度。当然中间这个过程当中，可能要消耗几分钟来提取本体。

## 综合解读

**论点链。** 这一集是上一集的自然续接：上一集说"语义先行、AI 才能跑起来"，这一集回答"那层语义到底怎么造"。作者的推进一步扣一步：没有本体的 AI 只能模仿数据，所以同一个问题会给三个答案 → 本体就是一张知识地图，让 AI 从查事实升级到沿关系做链式推理 → 但人工建模又慢又贵，产出还会过时，于是知识管理系统变成"死档案" → LLM 看起来是解法，可它有四道坎（类型数量未知、幻觉、粒度、评估无标准）→ 过去两年学术界与工业界给出了五种应对方式 → 因为这五种在工程复杂度与幻觉风险上分布不同，所以选型的落点不是"哪个最好"，而是"你在玩具阶段还是生产阶段" → 而无论选哪一种，成败都压在第一步的实体提取与约束设计上。收尾处，作者用自己那个基于直给派加约束的小工具，把这套判断落成了一个能点的界面。

**隐含前提。** 这条链条依赖几个没说出口的条件。其一，它假设领域里存在一个相对稳定、可以被写下来的实体与关系体系——如果业务对象本身还在争议中，"四种实体类型"这类定义就只是临时共识。其二，验证闭环要成立，前提是有人能先写出结构校验与逻辑校验的规则；作者描述了"两层通过才可信"，但没有说明这些规则由谁定义、是否也由 LLM 生成，这决定了闭环是校验还是自证。其三，"五种流派"是作者对过去两年工作的归纳，它更像一份选型地图而非学术分类，边界是模糊的：直给派加约束之后就带上了拆解派的成分，作者的 OntoPrompt 本身就是这种混合体。其四，"不到 1000 个 token 就能建出有效知识图谱"这类结论成立的前提，是那批数据已经被挑过、被治理过——省掉的是数据规模，不是前期定义的成本。

**待核验主张。** 以下均为作者在视频中的陈述，未经独立核实：EDF（法国电力）用拆解派方法管理核电站的技术文档；拆解派是"目前最可靠"、可以上生产系统的选择；`LLM for Ontology` 是 2025 年的代表性论文，其流程为"名词提取 → BERT 向量化 → AP 聚类 → LLM 命名"，并采用三步关系提取法的三元组结构；`Onto1kg` 这篇论文用两步走方式快速提取模块化类型并序列化生成标准 Ontology 格式；Wikidata 是全球最大的开放知识库、有几亿个实体；去年存在一个"用 LLM 提取 Ontology"的挑战赛，且结论是 prompt 稍改就会让整个 Ontology 变掉；`Wingtonic` 用不到 1000 个 token 建立了有效的知识图谱；作者自己的工具 OntoPrompt 具备置信度阈值、多文档实体验证、本体质量验证等设置，并以 DeepSeek V4 完成一次供应链本体的提取演示。此外，"五种流派"这一分类本身也出自作者的总结，如需引用宜先找到对应的论文清单再逐一比对。

**边界与反例。** 作者自己给出的边界相当明确：直给派半小时出结果，但 prompt 一变结果全变，只能停在 PoC；聚类派在开放域上会输出过细的粒度，适合探索而不是交付；框架派要求行业已有标准 schema，医疗、法律、电力之外的领域未必有这套现成框架；拆解派工程量最大，前一步的错误会污染后一步。把这些边界摆在一起看，会发现五种流派其实没有一种同时满足"快、准、可维护"，作者的选型框架本质上是在让人承认这个取舍。另外值得注意的是效果证据的形态：EDF、`Wingtonic`、挑战赛都是单点案例式的叙述，没有对照组，也没有给出"本体质量"的度量口径——如果同一批文档交给两个流派各建一版，谁更好仍无从比较。

**可迁移素材。** 抛开 LLM 与工具本身，这套讲法里有几件可以搬走的东西：把"验证"设计成结构校验加逻辑校验的两层闭环，且失败事实进日志而不进图谱；用"要不要预先指定类别数量"来挑选聚类方式，这个问题本身就能帮你想清楚自己是否已知领域的边界；把"工程复杂度 vs 幻觉风险"当成任何 AI 方案的双轴选型表；记住错误集中在第一步，先治理数据再谈输出，garbage in, garbage out；以及最后一个反直觉的提醒——投入项不是数据量，而是约束的密度与治理的合理性。
