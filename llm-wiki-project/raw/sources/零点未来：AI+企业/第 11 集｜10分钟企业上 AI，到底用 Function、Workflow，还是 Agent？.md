# 第 11 集｜10分钟企业上 AI，到底用 Function、Workflow，还是 Agent？

> 系列：AI+企业（Bilibili 合集，共 12 集）
> 作者：零点未来（Bilibili）
> 来源：https://www.bilibili.com/video/BV1sVbg6LEbS
> 口播状态：本地 ASR，`partial`（非官方字幕，专名、缩写与数字可能有误）
> 主张状态：视频观点未经独立核验，属 `unknown / 待外部核验`

## 一句话摘要

视频作者认为，企业上 AI 的真正命题不是"要不要上 Agent"，而是"哪一部分需要用模型判断、哪一部分必须由代码、权限系统还有人来控制"；他用一张报销单把 Function、Workflow、Agent 三条路线拆开，并给出两个轴（语义的不确定性、路径的不确定性）加一条红线（后果是否严重、是否容易发现、是否必须有责任主体）作为选型判据，结论是多数企业把 L2 级的 LLM Workflow 做深就已经够用。

## 阅读路线

先看作者如何用一张报销单把问题问对；接着是各家大厂的共识、三种选择的组合方式，以及"两个轴加一条红线"的判据；中段把 Function、单次 LLM、Workflow、Agent 四个概念和五级架构成熟度模型讲清楚；后半段是国内的现实约束、最小闭环与渐进式路径，再把三条路线放回报销单各管一段，最后收在权限边界、可解释性与验收指标上。如果只记一句，作者想留下的是：**把控制权交给最不需要的那一层**。

## 口播文章

### 一张报销单，先把问题问对

视频作者开篇说，这期要聊的是：企业上 AI 到底应该用 Function（函数），还是 Workflow（工作流），还是 Agent（智能体）。他说这个问题很多人谈到企业 AI 转型时，上来就是"我要上 Agent"，但实际上企业落地的时候，大家都在纠结这个选型到底应该怎么选。这期视频就来聊一聊这个问题。

他先给了一个场景：一张报销单。比如你有一个同事，上周去北京见客户，机票花了 2300，酒店三晚花了 2700，还有两张打车票，酒店发票还没有开出来，问能不能先报。作者说，就这么一句平平无奇的话，几乎每家公司都遇到过——最常见的场景就是财务收到一条微信，里面就是上面那句报销说明。

作者接着问：如果你想象一下，这种情况下该怎么让一个系统来处理这个问题？要回答这个问题，就得先搞清楚，我们要把选择权到底交给谁，谁来负责任。他强调，真正的命题从来不是"我们要不要上 Agent"，而是"哪一部分需要用模型来判断，哪一部分必须要由代码、权限系统还有人来控制"。

### 大厂的共识与三种选择

作者说，OpenAI、Anthropic、Google 和 Microsoft 等，几乎都在讲同一句话：优先用最简单、最可测量的架构来实现，只有当简单方案真的达不到我们的业务目标的时候，才逐步引入模型判断、动态编排和自主执行。

他提到，很多人上来就问"我这种业务情况能不能上 Agent"，其实这个问题问早了；应该先真正想的是，哪一部分需要模型判断，哪一部分必须要由代码、权限系统还有人来控制。我们其实面临的是三种选择：第一种是 Function，第二种是 Workflow，第三种是 Agent。

作者用一句话概括三者的分工：规则清楚就固定算，也就是用 Function；如果流程能定下来，就照着走，就是 Workflow；只有真正能让 AI 自己定的，才叫 Agent。而且后果越严重，自主权就越小——越重要的事情，越不能让 AI 自己做主。

他强调，这三样不是三选一，而是能够组合到一起：底层 Function 兜底，上面挂 Workflow，真要随机应变的时候，才让 Agent 接管。

### 两个轴、一条红线：不确定性怎么判断

那么这里面的不确定性到底怎么判断？作者说其实有两个轴。

第一个轴，是输入里面是不是藏着我们要理解的东西，比如像自然语言、图片、例外说明等等，这些我们可以用 LLM，这就叫语义的不确定性。第二个轴叫路径的不确定性，就是执行的时候，你提前是不是知道下一步具体要干嘛，你是不是有明确的任务执行步骤。

作者说可以画一个坐标来看语义和路径是否都确定了：如果语义和路径都定下来了，就直接用 Function；语义不定、路径定，就用单次 LLM 或者说 Workflow；如果两个都不定，我们才考虑上 Agent。

这两个轴之外还有一条红线：这个事情如果影响很大、错了又难以发现、而且一定要有责任主体来确认的话，就一定要给人；影响小、容易发现，我们才可以放心交给 Agent。

作者说这里有一句"一句话的架构原则"，大家可以直接抄走：**语义不确定但路径确定，就用单次 LLM 和 Workflow；语义和路径都不确定，才考虑 Agent**。之后可以用这句话去套用你遇到的那些企业需求。

> **思考一下｜不确定性是设计出来的，不是测量出来的**
>
> 两个轴听起来像在做体检，实际上更像在做设计：输入里有没有自然语言、路径能不能提前写死，很多时候取决于表单、接口和例外流程怎么定，而不是业务本身天生如此。
>
> **可以追问**：如果一个流程的语义不确定性主要来自"例外说明"这类自由文本，把它改成结构化字段，算不算把这条路线从 Agent 拉回 Workflow？
>
> **可延展方向**：把"这条路线的不确定性由谁引入"写进选型评审，比只给一个不确定性等级更有用。

### 把四个概念彻底搞清楚

作者说，前面提到了四种东西、四种概念，在具体判断之前，先把这几个概念彻底搞清楚。

第一个是 Function，就像计算器，输入输出永远一样，算钱、查权限、判超标都行，这是系统可靠性的一个基座。

单次 LLM 就是只能一次次抽一次信息，比如说识别发票、抽出日期金额，常常一次调用就够了，不要为这点小事去搭建整套流程。

Workflow 其实就是把这个流程步骤先定好，AI 只干中间看得懂的部分。

Agent 其实就是模型自己决定下一步，自己用工具，自己判断什么时候算完。

作者指出很多人有一个误区，就是以为"Agent 能够做任务拆解"。他说，任务拆解能力不一定等于 Agent，关键看模型到底拿了多大的自主权。他举的例子是 Anthropic 的 orchestrator-workers 模式：这个模式同样会动态拆解任务，但它的外围被工程师严格约束。所以，有多大的自主权，才决定了是否要上 Agent。

> **思考一下｜任务拆解不是那条分界线**
>
> 作者把 Agent 的判据从"会不会拆任务"换成"拿了多大自主权"，这条线是可以写进架构文档的：拆解能力可以外包给一个受约束的循环，自主权才是需要签字确认的那一项。
>
> **可以追问**：如果外围约束足够紧——工具固定、预算固定、步数固定——这种"会拆任务的循环"还剩下多少自主权？
>
> **可延展方向**：与其争论某个实现"算不算 Agent"，不如先列出它能自行决定哪些事，这份清单可以直接当评审材料。

### 五个步骤、五级架构与一张决策矩阵

作者说，前面把概念捋顺了，选起来就有抓手了。他整理了五个步骤：能写成具体的规则了，那我们就用 Function；只要能做一次分类或者抽取生成，就用单次 LLM；步骤能够详细列出来的，就用 Workflow；连下一步都无法确定、定不了的，才上 Agent；影响大、不可逆的，就要能够人工把关。

作者概括成一句话：从简到繁、不够再加，所以是 Code First（代码优先），然后一次 LLM 调用，再到 Workflow，再到受约束的 Agent，再到自主的 Agent。他还给了大家一个决策矩阵的表格：Function 最便宜、最稳；Agent 最灵活、最贵，风险也最大。

如果这五步记不住，作者说还有一个更直观的说法，叫"五级架构成熟度模型"：

- L0 是纯计算，就是 Function；
- L1 是单次 LLM；
- L2 是 LLM Workflow，大多数企业的默认选择；
- L3 是有边界的、自己定，也就是 bounded agent（受约束的 Agent），它能够调用固定范围内的一些工具、做预算内的动态规划；
- L4 是 autonomous agent，自主规划的 Agent。

作者特别提醒，注意这不是一个"越往上越牛"的竞赛。L0 到 L3 还能够共存：Function 兜底，Workflow 走主线，Agent 只处理少量、搞不开的一些局部流程。他给出的判断是，多数企业其实把 L2 做深就可以了。

> **思考一下｜L2 做深是克制，不是落后**
>
> 把成熟度模型读成"升级路线图"，很容易得出"迟早要上 L4"的结论；作者的原意恰好相反——每一级都有自己的适用范围，停在 L2 是一个结论，不是一个过渡状态。
>
> **可以追问**：如果 L2 就是终点，什么样的信号才算"该往上走一档"，而不是"再优化一下 Workflow"？
>
> **可延展方向**：给每一级配一个明确的退出条件（比如例外率、接管率、人工介入时长），让升级变成一次有依据的判断而不是一次冲动。

### 国内企业的现实：三件实在事与一个最小闭环

作者说，前面讲了很多方法论和一些概念，这套东西看起来其实挺理想的，但现实非常骨感，国内的企业现在是另一番景象。

他提出，最先拦路的问题不是"AI 能不能用"，而是三件很实在的事情：系统各管各的、流程没有打通、数据的口径也对不上。所以最划算的走法是：先用 Function 把一些〔ASR 作"进而全新的状态"，待确认〕还有合规规则给固化下来，然后再用 Workflow 把模型能力切入这些系统，但同时要保留人工审批的一个口子。

具体怎么做？作者说，我们可以先挑一个高频、边界清楚、能够算清结果的流程，打通一个最小的闭环，跑顺了再扩大。

他提醒，动手之前有四件事情要理顺。其中他明确展开的是第一件和最后一件：第一，数据要准、系统要稳定、接口能够审计，还要把责任人、执行者和安全、财务、法务拉到一起，这就是组织基础；最后一件，把权限和责任边界，包括数据范围等等定清楚，这就是第四个，治理基础。

> **思考一下｜"最小闭环"的验收标准要在闭环之前写**
>
> 高频、边界清楚、结果可验证——三个条件里，"结果可验证"最容易被事后补：流程跑通了往往就没人在意当初打算拿什么判定它成功。
>
> **可以追问**：如果数据口径对不上是常态，那"数据要准"到底是开工前提，还是最小闭环本身要交付的东西之一？
>
> **可延展方向**：把组织基础和治理基础各自产出一份可签字的清单（谁负责、能用哪些数据、谁批），让"理顺"有交付物。

### 渐进式路径：从 Function 到 bounded agent

作者接下来总结了一条渐进式的路径。

第一步，选一个高频、边界清楚、结果可验证的业务流程。第二步，把确定的系统规则、权限和数据沉淀为 Function 这种方式，再用 Workflow 把这些模型节点和业务系统连接到一起。第三步，用真实的流量去看一下它跑的情况，比如有哪些失败的样例、接管的原因是什么。

作者说，把这些原因和接管的情况总结下来之后，当异常处理的时候，下一步就知道可以用 bounded agents——可以在受控的范围之内用一些 Agent 去处理这些异常的问题。

### 回到那张报销单：三种干法各管一段

作者说，光讲理论还是太虚了，我们把这个场景放回前面说的那张报销单。这里面有三种干法——Function、Workflow 和 Agent，各管一段。

像金额规则、封顶，就交给代码（Function）；正常步骤我们就走流程。作者举的例子是〔ASR 作"北京 p7 啊三网"，所指待确认〕：代码一算封顶 2400，实际是 2700，那算出来就可以只报 2400，超标的那 300 要再查；缺发票就不付款——全是这些 Function 干的活。

Workflow 负责的，就是把整个流程给串起来，并且处理一些比如像 PDF 文档、图片、各种发票的文本抽取。

作者把这个流程串起来大概是这样：第一步材料识别；第二步字段抽取，从这些材料、PDF、票据里面把关键的字段抽出来；第三步做一些规则校验，这里要用到 Function；第四步异常路由，通过代码来判断，用这些异常的代码来判断，也要走一个审批流程。如果都是正常的话，我们就可以直接用模型生成这个结论，必要的时候进行人工审批；可如果遇到这种异常的情况、流程走不通的情况，我们就可能要上 Agent。

他举了异常的例子：比如说这个员工万一临时改到去天津呢？公司会卡重复扣款、又退款、行程变更，而行程变更还只有口头标准，流程就卡到这里了。这个时候才轮到有边界的这个调查员 Agent，他负责去查证、收集证据。当然他也不能自己拍板，最后还得是人点头，然后再执行一个 action，这个 action 是通过代码来写的，通过代码来付钱。

作者强调，同一张单子，三种干法配合起来才是一个完整的答案。他说这个案例说明〔ASR 作"AI 在讲"，待确认〕：其实数字、规则、审批记录这些才是关键，可信度来源于全部的证据点和数据，而不是它随口推理就给你一个结论。

> **思考一下｜例外路径的边界，就是 Agent 的边界**
>
> 报销单里真正需要 Agent 的那一段，触发条件是"规则覆盖不到、又必须有人担责"，而不是"这一步比较难"。也就是说，Agent 的位置由例外定义，而例外由规则定义。
>
> **可以追问**：当"行程变更只有口头标准"这类例外反复出现，正确的动作是升级成 Agent，还是把它补进规则、退回 Workflow？
>
> **可延展方向**：为异常处理显式定义升级与降级规则（什么情况下交人、什么情况下交 Agent、什么情况下补规则），比逐个案例拍板更可复用。

### 管住几件事：权限边界、可解释性与验收

作者说，AI 自己干不等于撒手不管，要管住几件事情。

第一，权限与自主的边界：什么能碰、什么不能碰，只给最小的权限。尤其针对高影响的动作，必须要人工审批；Agent 不能直接进行规则的修改，不能让 Agent 自己批自己、直接付钱。

第二，不要信 Agent 的可解释性。不要信它讲一堆大道理——看起来解释得头头是道，但不代表它真的是这么想的，也不代表它真的是这样的执行路径。我们具体还是要看证据、看规则、看审批记录。作者说，有研究就点破过：模型的解释越漂亮，可能根本没有说实话，只是提高了一种〔ASR 作"性能度"，所指待确认〕。

第三，要用考试的方式进行验收，做好 Agent 的 evaluation。要看什么呢？看业务结果对不对，而不是看它嘴上说做完了就认为它做完了；而且要看它的越权率、人工介入是不是按预期的步骤执行、延迟、成本，以及换了模型还稳不稳、我们的 token 消耗率等等。作者说，这些指标我们都要来具体看，这些都是我们做 AI 项目的验收指标，尤其是 Agent 的验收指标。

他还说，这里也给大家整理了一个项目评审清单：如果你遇到企业 AI 转型的一些项目，可以按不同的领域去看一下这些评审问题——到底是要用上 Agent，还是用 Function 或 Workflow 就可以解决了。

> **思考一下｜可解释性不能当验收证据**
>
> 作者把"看解释"和"看证据"分开，等于把审计对象从模型的措辞换成了系统留下的记录：规则怎么写的、谁批的、数据从哪来。解释可以生成，记录必须被留下。
>
> **可以追问**：如果只认结果和记录，那模型给出的理由在现场还有什么用——是给人提供线索，还是给人制造安慰？
>
> **可延展方向**：把"证据点、规则、审批记录"当成一个可审计三元组，要求每一次 Agent 动作都能同时回溯到这三样。

### 收束：把控制权交给最不需要的那一层

作者最后把前面讲的东西收成一句话：把控制权交给最不需要的那一层。能用规则就不用模型判断，能预先编排就不要让模型临时决定，能把后果留给人的地方就别交给机器。

他还说有三条要记住：执行一次分类或抽取，不一定要上整套流程；能对话也不等于可靠；Agent 不应该是一个高风险决策的默认执行者。

结合现在国内企业的实践，作者认为多数项目应该把 L2 级 LLM Workflow 做深，用真实运行的数据去检验一些标准，看具体在企业落地里面的那些验收标准能不能真正影响到我们的业务目标，只把少数确实搞不开的一些异常环节，升级成 bounded agent、受约束的一些 Agent。

最后他说，这就是本期视频全部的内容，如果觉得还不错，欢迎点赞、收藏、关注，我们下期再见。

## 综合解读

**论点链。** 作者的推论从"把问题问对"开始：企业 AI 的起点不是要不要上 Agent，而是把控制权归属问清楚——谁负责、哪一部分交给模型、哪一部分交给代码与权限系统和人。判据被压缩成两个轴（语义的不确定性、路径的不确定性）加一条红线（影响大小、是否容易发现、是否需要责任主体），由此得到 Function、单次 LLM、Workflow、Agent 四个概念，以及一条从简到繁的梯子：Code First → 一次 LLM 调用 → Workflow → 受约束的 Agent → 自主的 Agent，并对应成 L0–L4 的五级成熟度模型。接着他把镜头转向国内现实：系统各管各的、流程没打通、数据口径对不上，所以先固化规则、再用 Workflow 切入、保留人工审批，从高频且结果可验证的最小闭环起步，用真实流量里的失败样例和接管原因决定何时升级到 bounded agent。报销单这一段是全篇的落点：Function 管计算与规则，Workflow 管串联与抽取，Agent 只管规则覆盖不到的例外，且必须由人点头、由代码付钱。最后用权限最小化、不可轻信的解释和一组验收指标收口。

**隐含前提。** 这条链条依赖几个没说出口的条件。一是业务流程里存在足够大、足够稳定、可以被写成规则的部分，否则"先用 Function 固化规则"就无从下手；二是两个轴可以在动手之前被判断出来，而现实中很多项目的不确定性（尤其"错了难以发现"这一条）只有跑起来才暴露；三是组织有能力把业务、财务、法务、安全拉到一起，并真的划出权限与责任边界——作者把这步归为"组织基础"和"治理基础"，但没给出对齐的方法；四是人的审批是真实判断而不是橡皮图章，否则"保留人工审批的口子"只是把风险挪了个位置；五是"用真实流量检验"要求已有可用的流量，冷启动阶段的项目拿不到这份证据。

**待核验主张。** 以下均为作者在视频中的陈述，未经独立核实：OpenAI、Anthropic、Google、Microsoft"几乎都在讲同一句话"（优先用最简单、最可测量的架构）这一概括；Anthropic 的 orchestrator-workers 模式"同样动态拆解任务、但外围被工程师严格约束"；L0–L4 五级架构模型，以及"L2 是大多数企业的默认选择"；决策矩阵的结论（Function 最便宜最稳，Agent 最灵活、最贵、风险最大）；报销单案例里的全部数字（机票 2300、酒店三晚 2700、封顶 2400、实际 2700、超标 300），这些更像举例而不是某家公司的真实制度；"国内企业最先拦路的是系统各管各的、流程没打通、数据口径对不上"这一现状判断；"有研究点破过：模型解释越漂亮，可能根本没有说实话"——作者没有给出处；Agent 的验收指标清单（业务结果、越权率、人工介入是否按预期步骤执行、延迟、成本、换模型是否稳定、token 消耗率）；以及作者提到"整理了一个项目评审清单"，但口播中没有读出清单内容，无法核对。

**边界与反例。** 作者自己划了几条边界：不是越往上越牛、L2 做深对多数企业就够、Agent 不该是高风险决策的默认执行者、后果越严重自主权越小。有两处值得进一步追问。第一处是张力：判据说"错了难以发现"就不该交给 Agent，而报销单里的例外（行程变更只有口头标准）恰恰是既难发现又难规则化的那部分，作者仍把它交给了 Agent，只是加了一道人工审批——这说明红线并不是禁行线，而是"必须有人接手"的标记。第二处是证据链："接管率、失败样例"被当作升级的依据，但高接管率既可能是 Agent 能力不足，也可能是上游数据口径问题的症状；如果是后者，升级架构正好绕过了真正该修的地方。另外，"能用规则就不用模型判断"在规则本身会频繁变动的业务里反而更贵——把变化写成代码需要发版，而模型对表述的容忍度更高，这条成本在作者的账里没有出现。

**可迁移素材。** 抛开具体厂商和模型，这一集可以搬走的东西不少：两个轴的判据和那句可以直接抄的原则（语义不定、路径定 → 单次 LLM/Workflow；两者都不定 → 才考虑 Agent）；以"自主权大小"而不是"会不会拆任务"判定 Agent；Code First 的升级阶梯与 L0–L4 分级，以及给每一级配退出条件的做法；最小闭环的挑法（高频、边界清楚、结果可验证）连同动手前的组织基础与治理基础；一份可执行的 Agent 验收指标清单；以及报销单式的分层分工表——把一张单据拆成"规则段 / 流程段 / 例外段"，先写清楚每段由谁负责，再决定用哪种技术实现。
