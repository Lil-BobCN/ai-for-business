## 一句话摘要

视频作者认为，企业 AI 落地里最容易被跳过、也最耗人的一段，是"一堆文件怎么变成 Ontology"这件脏活累活（Dirty Work）；他以 Palantir 官方文档里的航空公司场景为例，把"数据连接 → 存储 → 清洗解析 → 标准表 → 映射成本体"这条五阶段链路逐段拆开，再补上增量更新、宽表拆分与 FDE 成本这几处现实约束。

## 阅读路线

先记住三类数据（结构化航班运营数据、半结构化预订 JSON、非结构化维修 PDF）和五个阶段的总链路，再沿着三条完全不同的清洗路径走一遍；中段是干净表如何映射成 Object、Property、Link、Action，以及让本体真正能跑起来的 Logic 与 Action；后半段是增量更新的图书馆比喻与两个坑、现实里的宽表拆分、FDE 为什么贵、行业模板为什么沉淀不下来，最后落在 Ontology 与普通数据库 Schema 的三点真正差异。如果只记一句，作者想留下的是：**真正值钱的不是定义实体，而是把一张宽表拆成实体的那套映射规则**。

## 口播文章

### 开场：被跳过的"Dirty Work"

视频作者开场先做了两件事。一是回顾：之前的视频里他介绍了 Palantir 和它的 Ontology，以及如何用 LLM 帮助构建 Ontology；他放在 GitHub 上的 `Ontoplome`〔项目名待确认，ASR 另有 `Ontoplamt`、`Onto Plompt` 等写法〕也收到了很多朋友的反馈，包括有朋友帮他修复 Bug、希望他持续更新。他说今天的内容也会更新到这个项目里面，欢迎大家使用，也欢迎提交 PR 一起把 `Ontoplome` 构建好。

二是点题：今天这期他想聊一个很多人都会跳过的话题——Palantir 的数据是怎么跑起来的。如果企业里面有一堆各种 PPT、PDF 文档、表格，一堆来自不同系统的文件，还有线下的这些表格文件，它们是怎么一步一步变成 Ontology 的。作者说，这一步其实是一个脏活累活的过程，很少有人完整地讲过，而它也正是涉及 Ontology 企业落地很大一部分的工作，俗称 Dirty Work。所以他今天打算用 Palantir 官方文档里的一个航空公司的场景，把这个链路完整地走一遍。

### 三类数据，五个阶段

作者先设定场景：假设你是某个航空公司数字化的负责人，手上会有三类数据。

第一类是航班运营数据，它是结构化的 CSV 或者 Database，来自比如说 `欧罗克`〔数据库名待确认〕的数据库还有 MySQL 数据库；每一个航班有出发时间、状态、飞机尾号这些字段，这些都是最标准的结构化数据。第二类是乘客预订数据，它可能是 JSON 这种格式，来自 OTA 订票系统，每一份预定单里面嵌套了乘客信息、多段行程，结构会有点复杂。第三类比如维修工程师的维修报告，这种是 PDF 的扫描件，工程师手写了一些维修记录，完全没有数据化的结构。

这三类数据要去构建一个 Palantir Ontology，怎么做、有什么链路呢？作者说，简单来说整体的链路有五个阶段：首先是数据连接，我们把数据接进来；连接进来之后是存储，我们可以分类，比如刚刚的结构化数据、预订的 JSON 格式数据，还有一些非结构化的数据比如 PDF；接下来我们进行清洗解析，得到标准表格；最后构建成 Ontology 的对象。简单来说就是这五个阶段。但作者提醒，同样是五个阶段，三类数据走的路径都是完全不同的，所以接下来他把每一个阶段都拆开来跟大家剖析。

### 阶段一：数据连接，原封不动地拉进来

第一个阶段叫数据连接，其实就是把数据原封不动地拉进来。作者说，Palantir 要求数据从原系统拉进来的时候不要做任何的预处理，只要所有的变换都在 Foundry 内部完成——也就是 Palantir 这个数据平台 Foundry。这样你才能够从 Ontology 里面任意一个数据点追溯到最原始的那个文件。作者强调，在金融和医疗这些合规严格的行业，这是一些硬性的要求，所以 Palantir 的第一个原则就是不做任何的预处理。

直接拉原始文件，Foundry 里面会有 200 种连接器对接不同的数据源，可能直接是文件的一种格式，也可能是像 PDF、PPT 甚至视频、图片等等格式。拉取的方式主要有两种：第一种叫 snapshot，就是每次都要全量替换；第二种就是只追加新数据 `upam`〔待确认〕。作者说，后面讲增量更新的时候，这一点区别是非常重要的。

> **思考一下｜"不做预处理"是一条治理原则，不只是工程洁癖**
>
> 把变换全部关进平台内部，换来的是任何一层都能回溯到原件；代价是原始数据的冗余、存储成本和平台侧的合规责任都变重了。作者把它称为"硬性要求"，说明这条原则的驱动力来自审计而不是效率。
>
> **可以追问**：当上游系统本身不允许原始数据出域时，这条"原封不动"的原则还成立吗？
>
> **可延展方向**：在自建数据链路时，把"能否追溯到原件"当成一条独立验收项，和清洗效率分开评估。

### 阶段二：存储层，DataSet 与 MediaSet

数据拉进来之后，就存在 Palantir Foundry 的存储层，作者说这里有两个关键的概念。

第一个格式叫 dataset，它是一个通用的存储容器，可以存 CSV 表格、JSON 文件，甚至每次更新都会有版本记录，作者把它叫作 git for data——任何一个历史版本都能找回来。第二种叫 media set，是专为图片、视频、音频和 PDF 这类媒体文件设计的一个存储的单元，它在 dataset 的基础上额外提供了一层和 AI 提取工作流对接的基础，因为像这些 PDF、视频还有音频，我们要单独通过 LLM 或者说通过 OCR 这些模型进行解析。

作者说这里面关键的设计叫 media reference，就是在 dataset 的某一列里面可以直接引用 media set 里面的文件。比如说维修记录的表，每一行会有一个报告的编号、维修日期这些结构化的字段，同时会有一列指向原始 PDF 扫描件——这样就把结构化和非结构化的数据关联起来了。

### 阶段三：清洗解析的三条路

把数据存储好之后，就进入了最核心的部分——Pipeline Transforms，也就是把我们的数据进行清洗解析。作者说，三类数据走了三条完全不同的路。

第一条路是结构化的 CSV 或者结构化的这种数据，是最简单的一条路。拿航班的 CSV 举例，比如说我们有 200 万行的原始数据，Foundry 里面会有一个叫 Apply Schema 的按钮，点击一下，它就会扫描整个 CSV 数据样本，自动识别哪类是时间、哪类是数字、哪类是文字等不同的数据类型；之后你可以用拖拽式的 Pipeline Builder 去做过滤和去重，就得到了干净的 `Clean Flight` 表，也就是一个清洗过的航班表，不用每一行去核对。作者说，所以它有一个自动推断 Schema 的逻辑。

第二条路是为半结构化的数据比如说 JSON、XML 这些数据格式做准备的，它需要做的一个工作就是把整个嵌套结构摊平。比如说我们有一个预订的 JSON 文件，就是乘客预订的 JSON 文件，我们有乘客信息和多段的行程，它是嵌套在一起的一份订单，可能包含两段行程，所以这里有个核心操作叫 Explode，就是把嵌套的数据给炸开、摊平，变成独立的一行。就像这样，一个 JSON 文件就变成两张关联的表：有乘客表和预订表，然后用订单 ID 把这两个表给关联在一起。

第三条路是针对非结构化的数据，比如说刚才说的维修报告 PDF 扫描件，它没有任何数字化的结构，所以必须让 AI 来读。Palantir 有一个产品叫 AIP Document Intelligence，就是专门处理这个的。作者说这套流程分五个步骤：第一步就是把 PDF 存进 MediaSet；第二步就是用 OCR 加多模态的视觉理解大模型，直接看页面输出 Markdown 格式的文字。作者在这里做了一个简单处理，他说你可以用 Microsoft 的 `Mockdown`〔库名待确认〕这个开源的库，把任何其他的非 Markdown 格式转成 Markdown。第三步就是从 Markdown 里面去解析业务字段，比如说像飞机尾号、维修日期等等，更换了哪些零件。第四步也是最容易被跳过的，就是校验还要复核，这里面其实有人工的参与：校验看看是否格式是正确的、AI 提取的置信度够不够，还需要随机抽几个样本，对照原始的 PDF 进行核查。作者建议这部分不要省略，因为这部分也是特别容易出错的地方。

第五步，也就是最终的输出：经过这个置信度的过滤、格式的校验以及人工的抽样核查之后，我们就会输出一个干净的 `Clean Maintenance` 表，也就是根据我们的维修报告输出的一个结构化的表，每一行还保留了一列指向原始的 PDF，方便后面去进行数据的追溯。

> **思考一下｜AI 抽取的可信度，最后落在谁身上**
>
> 三条路里只有第三条是"让 AI 读"，而作者把人工抽样放在了它后面，等于承认准确率不能靠模型自证。这条链条上真正决定能不能上线的，是那几次随机抽查。
>
> **可以追问**：如果抽样只覆盖几个样本，剩下几十万行 PDF 的错误率靠什么保证？
>
> **可延展方向**：把"抽样核查的样本量与判定标准"写成交付物的一部分，和置信度阈值放在一起评审。

### 从干净表到本体：Object、Property、Link、Action

前面我们花了大量的工作把数据做解析、清洗成结构化的干净表格，现在要去把它变成 Ontology 本体，怎么去做 Mapping 和映射呢？作者给了一张对比表。

首先一张干净的表，你可以直接把这个表对应成一个 Object Type，像我们刚刚说的航班 CSV 的结构化表，那就对应一个 Object；表里的每一行数据对应一个 Object，比如说具体的航班号 CA1234，一个具体的航班号就对应一个 Object Entity；接下来表里的每一列就是一个 Property，也就是一个针对这个航班的属性，比如说它的出发时间、状态等等；两张表之间有关联关系，那就是用一个 Link Type 把它连接到一起，比如像 Flight 这个航班都是通过尾号关联 Aircraft，Aircraft 就是另外一个实体表。

对于数据的一些读写操作，作者说我们可以认为是一个 Action Type，航班可以进行改签、更新状态等等。Action Type 是 Ontology 的一个核心。传统的数据目录只能查不能改，而 Palantir 的 Ontology 让业务用户也可以直接修改数据，而且改动写入独立的一个 writeback dataset，不污染原始的数据，原始的数据始终保持干净。

### Logic 与 Action：让本体真正"活"起来

作者说，Ontology 已经构建了 Object 还有刚刚说的一些基本的 Action、Link Type 之后，我们其实还需要两样具体的东西才能真正活用起来。

第一个就是 Logic。Logic 就是逻辑的推断、逻辑的计算，自动推导出新的信息。比如说这个航班延误了多少分钟，不需要人工去录入，系统可以直接从出发时间和实际的起飞时间里面自动算出来；再比如说每家公司的平均延误，可以跨所有的航班聚合得到。第二个就是 Action，前面我们也说了 Action Type 是 Ontology 的一个创新点，那怎么去抽取这个 Action 呢？作者说每个 Action 都有四个部分：第一个是参数，需要一些输入；第二个就是规则，执行的时候做什么；第三个就是前置条件，什么情况下才能执行；第四个就是副作用，执行后会触发什么东西。所有的这些修改都会写入独立的记录，不覆盖原始数据，所以谁改的、改了什么、什么时候改的，全程都可以进行追溯。

> **思考一下｜"能写回"划出了本体和数据目录的分界线**
>
> 只读的语义层和可写的语义层在治理上是两回事：前者出错大不了看错，后者出错会改坏业务数据。作者强调改动要写进独立的 writeback dataset，本质是给"可写"这件事加了一层隔离。
>
> **可以追问**：writeback 记录与原始数据长期分叉之后，哪一份才是业务上认可的"真相"？
>
> **可延展方向**：评审本体时，把"哪些对象允许写回、写回后如何回灌原系统"和对象定义分开讨论。

### 增量更新：图书馆的比喻，以及三层配合

Ontology 建好之后，原系统的数据每天都会变化，比如说新航班加进来了、乘客改签了、维修记录更新了，那这些数据我们怎么去同步呢？是不是要全量更新、去重新构建 Ontology 了？作者拿一个图书馆的比喻来理解这个更新的逻辑：图书馆比如说已经有 2000 万本书了，可以当作一个历史的航班记录；那每一周我们可以更新 100 万本，这个就相当于有新的航班。这样我们有两种操作：第一种就是全量重算，把每一周重新整理 2100 万本书，这样我们要花很多的时间；第二种方式就是做真正的增量更新，每周只处理新到的 100 万本书，这样可以节省很多的时间。

作者说，真正的增量更新需要三层的配合：首先是从数据同步，我们只拉取新的数据；接着我们要去做 Pipeline 的处理，只处理新增的行；最后我们要做 Ontology 的索引，只更新有变化的那些对象。这三层缺一不可。

### 增量更新的两个坑

作者提醒，这里会有两个容易踩的坑。首先第一个，如果航班状态被修改了，从准点变成了延误，其实用追加的模式同步就会出现新版本和旧版本同时存在的问题，这就需要 Pipeline 里面去做去重，只保留最新的一个状态。第二个踩坑点是，用户在 Ontology 的界面去点击改签的时候，修改是立刻生效的；而 Pipeline 的批量更新是定时跑的，两个数据来源会有一个时间差。两个来源的数据 Ontology 会自动合并，但是中间有一个时间差的窗口，所以我们需要注意这个时机。

> **思考一下｜定时批处理和实时写入之间的那道缝**
>
> 一个数据源按秒生效、另一个按批生效，系统能合并数据却合并不了时间。这类"双写不同步"的问题不只在 Palantir 出现，凡是既有交互式修改又有批量回灌的系统都会遇到。
>
> **可以追问**：如果业务上必须在这段窗口内做决策，应该以哪一个来源为准，谁来定义？
>
> **可延展方向**：把"写入时效"作为实体属性显式建模，让用户和 Agent 都能看到这条数据有多新。

### 现实里的宽表：一个 Object Type 只能对一张表

作者说，前面我们取的例子假设数据已经是几张整洁的小表了，但现实往往不是这样的。企业里面比如从 `鸦皮`〔待确认〕里面导出的数据，通常都是一张几百列的大宽表，订单、客户、商品（ASR 作 `三屏`，待确认）、物流全部放在一起了。这里 Palantir 有一条硬性的规则：一个 Object Type，也就是一个实体的类型，只能对应一张表。所以宽表不能直接去做映射，我们必须把它拆开——在 Pipeline 里面它就会拆成几张聚焦的小表，比如说像订单表、商品表、物流表，各自映射到对应的 Object Type，再用 link 把它连接到一起。

作者说，Palantir 的 Pipeline Builder 里面有 AI 功能，可以去帮你写一些拆分的代码，但是决定怎么拆、哪一列属于哪个实体，还是需要人为来判断的。这是纯粹的业务场景的建模，也是 Palantir FDE 工程师最贵的那部分时间。为什么 Palantir 有 FDE？其实很大程度上就在这里：决定企业里面哪些要构建实体、哪些不构建，这些宽表怎么拆，FDE 要花大量的时间、要懂业务逻辑，去帮助企业做这个判断。

### FDE 为什么贵，模板为什么沉淀不下来

这里可能有人会问了：这些不同业务域、不同行业的模板能不能沉淀下来，下次我们就可以快速低代码部署、一键安装？作者认为，Palantir 技术上其实可以把这个做出来，但是他们没有动力做，因为 FDE 常驻咨询是他们的商业模式，也是绑定客户的一个核心资源。

所以作者判断，真正的机会不在于定义实体的本身——比如说像供应链的 Shipment、SKU，医疗的 Patient，这些行业的共识度都很高；那真正值钱的是当客户给你一张 SAP 的非常大的宽表时，哪些列映射到哪些实体，把这套 Mapping 规则产品化。作者认为，垂直行业的玩家就比 Palantir 更有动力来做这件事。

> **思考一下｜把"拆表规则"当成产品，卖的到底是什么**
>
> 作者把这条链上最难被替代的一环指认为"宽表到实体的映射规则"，而不是实体清单本身。这个判断的商业含义是：护城河来自行业里反复出现的表结构，而不是来自某个行业的对象命名约定。
>
> **可以追问**：如果每个客户的 SAP 宽表都千企千面，沉淀下来的到底是模板，还是一套拆表的决策流程？
>
> **可延展方向**：把"字段到实体的映射规则"当作可复用资产管理，可能比沉淀整套行业本体更接近能交付的形态。

### 与普通数据库 Schema 的三点真正差异

最后回到最开始的问题：Palantir 的 Ontology 和普通的数据库的 Schema，真正的差别在哪里？有人可能会觉得 Ontology 不就是做一些数据处理吗？作者说我们可以去看三点真正的差异。

第一点就是全链路可追溯，Ontology 里任意一个字段值都可以追溯到原始文件的某一行，这一点尤其在刚刚提到的金融、医疗，还有像 Palantir 很多的客户是政府机构、军情局等等——这些合规要求严格的一些行业，他们是硬性要求。第二点就是可以进行写回，前面我们说了 Palantir 的 Action Types，如果我们修改 action，其实是写到 writeback dataset 里面的，不污染原始的数据。第三层就是应用层会直接消费，不需要再写 API，AI 和应用直接操作 Ontology 的对象，一次操作可以全部完成，基于 Ontology 就可以进行各种决策、业务决策的仿真等等。作者说，这三点合在一起，就使它成为一个 Agent 的操作层，而不只是一个数据结构目录。

### 收尾：项目进展与推荐阅读

作者最后做了收束：刚刚我们已经把整个 Palantir Foundry 从原始的一堆文件到 Ontology 的整个 Pipeline 跟大家讲了一遍，而且针对增量更新、针对企业里面的实际情况我们怎么去做增量更新、面对这种宽表的时候怎么处理，也都介绍了一下。如果感兴趣，他也罗列了推荐阅读的一些文章，其实都是来源于 Palantir 的官方文档，大家可以自己进行查阅。他说今天分享的 Pipeline 整个过程都会更新到他的 `Ontoplome` 这个项目当中，目前已经在开发当中。

他顺带演示了目前的进展：比如说已经增加了数据管道这个类型，你可以新建这个 Pipeline，比如点输入 Test，然后业务语义我们选择供应链，点击创建，我们就可以进入这个 Pipeline 的画布当中。我们可以把连接器、存储器还有转换器、输出等等拖出来：比如连接器的话，你可以选择去编辑你数据源的类型，比如你通过文件上传或者说通过 MySQL 进行连接；存储器的话就会去自动检测，或者直接区分 DataSet 和 MediaSet 这两种类型；转换器的话就会去分析你是结构化的数据、半结构化的数据还是非结构化的数据，以及宽表，或者你直接让它自动检测，让它自己去判断数据类型，然后选择对应的路径；数据节点的话就是结构化的数据节点。

他还举了一个已经创建完的例子：这是我有上传的数据源的文件，自动检测存储类型，然后它做多路径的转换，输出这种结构化的数据表。有了这些之后，我们在创建本体的时候就可以选择创建新的本体，支持之前的简易的 LLM Prompt 的提取方式，也支持 Pipeline Mapping 的一个方式；选择这个本体名称，然后一起选择对应的结构化数据，创建 Mapping，它就会按照整个 Ontology Mapping 的方法论把它生成出来。这就是他后面要持续再更新的 `Ontoplome` 项目，也欢迎大家提意见，帮他一起进行改善和优化。最后是常规收尾：这就是本期视频的全部内容，如果觉得还不错，欢迎点赞、收藏、关注，我们下期再见。

## 综合解读

**论点链。** 作者的推论从"Ontology 是什么"下沉到了"Ontology 是怎么来的"：企业里的数据先按原样接入，再分层存储，然后沿着结构化、半结构化、非结构化三条路各自清洗成标准表，最后逐列映射成 Object、Property、Link、Action——链路的前半段是数据工程，后半段才是建模。链条再往前走一步：光有对象不够，还要 Logic 与 Action 才能用起来；系统跑起来之后，靠三层增量更新维持同步；而真实企业数据往往是一张几百列的宽表，于是"怎么拆成实体"成了最贵的一环。收尾处，作者用三点差异（可追溯、可写回、应用层直接消费）把 Ontology 定性为 Agent 的操作层，而不是数据目录，从而把第 1 集"语义层"的说法落到了工程细节上。

**隐含前提。** 这条链路依赖若干没说出口的条件：一是原系统允许原始文件出域、并且平台愿意承担随之而来的合规与存储责任，"不做预处理"在技术上简单、在组织上昂贵；二是增量更新的三层成立，前提是上游能提供可靠的增量信号，否则"只拉新数据"这一步就无法保证；三是业务实体与字段归属存在一个稳定且可判定的答案，因此可以由 FDE 判断出来——如果企业内部对"什么算一个订单"本身就有分歧，最贵的那部分时间只会更贵；四是人对批处理与实时写入之间的时间差有容忍度。作者本人对成本是有意识的，他反复把 FDE 的时间称为"最贵的部分"，也把模板沉淀称作被商业模式挡住的可能。

**待核验主张。** 以下均为作者在视频中的陈述，未经独立核实：Foundry 有 200 种连接器；拉取方式分为 snapshot 全量替换与只追加新数据的 `upam`〔待确认〕两类；dataset 每次更新都有版本记录、被称作 git for data；media set 与 media reference 的机制与用途；AIP Document Intelligence 的处理流程（OCR 加多模态视觉理解大模型直接输出 Markdown，以及可用 Microsoft 的 `Mockdown`〔待确认〕把非 Markdown 格式转成 Markdown）；"一个 Object Type 只能对应一张表"这条硬性规则；Pipeline Builder 内置 AI 拆分代码的能力；FDE 常驻咨询是 Palantir 的商业模式、并且因此没有动力把行业模板产品化的动机判断；航班 CSV 200 万行、图书馆比喻中 2000 万本与每周 100 万本的数量级；增量更新需要数据同步、Pipeline 处理、Ontology 索引三层配合，以及状态覆盖与实时改签两处时间差；Ontology 与普通数据库 Schema 的三点差异；作者自己项目 `Ontoplome` 的功能清单与开发进度（属作者自述）。视频中提到的推荐阅读均来自 Palantir 官方文档，可作为交叉核对的入口。

**边界与反例。** 作者自己给出的边界有几条：这套做法服务于合规严格、体量大、且有专职 FDE 参与的场景；行业模板短期不会因为技术原因而普及，卡点在厂商的商业模式；增量更新在"状态被覆盖"和"用户即时改签"两种情形下会暴露不一致。需要额外留意的是，官方文档里的航空公司场景是一份理想化的三类数据样本，真实企业里还有大量数据停留在人的手上或纸质流程里；PDF 路径的准确性被交给人工抽样，但样本量与判定标准作者没有给出，这会直接影响这条路径能否规模化；所谓"追溯到原始文件的某一行"，在扫描件场景里对应的其实是某一页，两者不是同一件事。

**可迁移素材。** 抛开 Palantir 本身，这一集至少有六件东西可以搬走：把"连接 → 存储 → 清洗 → 标准表 → 映射"当作任何本体项目的检查清单，用来定位自己卡在哪一阶段；把"不预处理、保留原件"当成可追溯性的前置条件，而不是可选的工程偏好；按结构化、半结构化、非结构化分三条清洗路径，各自配一套固定动作（自动推断 Schema、Explode 摊平嵌套、OCR 加多模态转 Markdown 后抽字段）；沿用 media reference 那种"一行结构化字段加一列指向原件"的关联模式；在建模时坚持一个实体一张表、宽表先拆再映射；以及在增量更新上按"同步、处理、索引"三层分别做增量，并把状态覆盖与写入时效这两个坑提前写进设计。
