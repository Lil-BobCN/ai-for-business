## 一句话摘要

作者用"业务变大、单机不够、多机组集群"这条最短的路径引入负载均衡，先按实现方式把负载均衡器分成 DNS、硬件、软件三类并比较各自代价，再聚焦到软件方案里性能最高的四层负载均衡 LVS，逐个讲清 NAT、DR、TUN 三种工作模式的报文流转过程与适用边界。

## 阅读路线

1. 先读开场一段：单机 → 集群 → 负载均衡器，这是全篇的引入逻辑，也是理解后面"为什么要在四层做"的前提。
2. 再读负载均衡器的三分类（DNS、硬件、软件）。DNS 一段值得细读，作者在这里解释了"为什么 DNS 方案在生产环境里不常用"，理由是缓存与 TTL。
3. 接着读软件负载均衡一段，注意作者给出的四层与七层分工：Nginx 与 HAProxy 是七层，LVS 是纯四层、工作在内核态。
4. 然后读 NAT、DR、TUN 三种模式。这三段技术密度最高，建议对着报文里的 IP 变化来读：NAT 改目标 IP 且回包也经过调度器，DR 只改二层 MAC 且回包直达客户端，TUN 在原有报文外再封装一层 IP。
5. 最后对照三种模式的特点总结，看作者如何用一句话概括每种模式的核心代价。

## 口播文章

### 开场：从单机到集群，再到负载均衡器

视频作者开场说，无论你是开发还是运维，应该经常听说负载均衡，但你真的了解它吗？今天五分钟让你系统认识它。

作者说，在业务初期，通常采用单台服务器即可满足需求；随着用户流量增长，单台服务器逐渐难以应对压力，这时我们会将多台服务器组成集群来提升处理能力。为了统一管理流量入口，需要通过负载均衡器将海量请求按照预设算法智能分发到集群中的不同服务器，这就是负载均衡。作者提示，本集讲的是广义的负载均衡器。

### 负载均衡器的三分类：DNS、硬件、软件

作者把负载均衡器分为三类：**DNS 实现负载均衡**、**硬件负载均衡**、**软件负载均衡**。

**DNS 实现负载均衡。** 作者说，DNS 是最基础、最简单的方式：用户访问域名（比如 `www.aq.com`），通过 DNS 解析到多个 IP，然后访问每个 IP 对应的服务器实例，就完成了流量调度。它没有使用常规的负载均衡器，但也的确完成了简单负载均衡的功能。优点是实现简单、成本低，但缺点明显：

第一，服务器故障切换延迟大。DNS 与用户之间是层层缓存，即便故障发生时及时修改 DNS 或摘除故障服务器，由于中间经过运营商的 DNS 缓存，且缓存很有可能不遵循 TTL 规则，导致 DNS 生效时间缓慢，用户仍会访问到故障服务器——这时你老板都要叫起来了。

第二，它的流量调度策略简单，支持的算法较少，DNS 一般只支持轮询方式〔待确认：ASR 记为"只支持 R2 的轮巡方式"，按上下文应为"轮询"〕。所以实际上生产环境中很少用这种方式来实现负载均衡。

作者补充，上面描述 DNS 负载均衡方式，只是为了让你能够更清楚地了解负载均衡的概念。一些大公司一般也会利用 DNS 来实现地理级别的负载均衡，实现就近访问、提高访问速度；这种方式一般是入口流量的基础负载均衡，下层会有更专业的负载均衡设备实现负载架构。

**硬件负载均衡。** 作者说，硬件负载均衡是通过专门的硬件设备来实现负载均衡，类似于交换机、路由器，是一个负载均衡专用的网络设备。目前业界典型的硬件负载均衡设备主要有两款：F5 和 A10。这类设备性能好、功能强大，但价格非常昂贵，一般只有"土豪"公司才会使用，普通业务量级的公司一般负担不起。

**软件负载均衡。** 作者说，它是指可以在普通服务器上运行的负载均衡软件，实现负载均衡功能。目前常见的有 Nginx、HAProxy、LVS：

- **Nginx** 是七层负载均衡，支持 HTTP 协议；
- **HAProxy** 也是七层负载均衡软件，性能也很不错；
- 而 **LVS** 是纯四层的负载均衡，运行在内核态，性能是软件负载均衡中最高的；因为是在四层，所以也更通用一些。

软件负载均衡的优点：简单、部署维护简单、便宜，买个 Linux 服务器装上软件即可；灵活，四层和七层负载均衡可以根据业务进行选择；方便进行扩展和定制功能。

> **思考一下｜为什么"DNS 也算负载均衡"值得单独讲一段**
>
> 作者用两段讲了一个不在常规负载均衡器范畴里的方案，并把它的缺陷落在两件具体的事上：缓存的 TTL 不一定被遵守，以及算法选择少。这两条缺陷都不是"功能不够"，而是"控制权不在你手里"——DNS 记录的生效时间由运营商缓存决定，调度策略由 DNS 协议能力决定。对照后文，LVS 的卖点恰恰是把这两件事拿回来：立即切换、算法可选。
>
> **可以追问**：如果 DNS 的生效时间不可控，那么在类似 CDN 这种依赖 DNS 调度的系统里，故障切换的兜底应该放在哪一层？
>
> **可延展方向**：把"控制权边界"作为选型维度之一——问清楚一项能力是平台承诺的、协议保证的，还是别人缓存决定的，再决定是否把它放进关键路径。

### 聚焦 LVS：四层、内核态、成本低

作者说，开源软件负载均衡器 LVS 全称 **Linux Virtual Server**，它工作在网络四层，性能出色，关键还能节省很大的成本。很多大厂的负载均衡产品底层都有基于 LVS 做开发，比如某云以前的四层负载均衡 CLB 就是通过 LVS 加 Keepalived 的方式实现〔待确认：ASR 记为"Keep Alive"，按上下文应为 Keepalived〕。中小型公司使用开源的 LVS 足够满足业务需求。

接下来讲 LVS 的三种主要工作模式：**NAT、DR、TUN**。

### NAT 模式：改目标 IP，往返都经过调度器

**NAT 模式。** NAT 全称 Network Address Translation，即网络地址翻译。作者先说明角色：**客户端 Client**、**负载调度器 Director Server**（它实际是安装了 LVS 模块的服务器）、最后是**真实服务器 Real Server**。

报文流转过程是：客户端 Client 首先访问负载调度器 Director，此时报文的源 IP 为 Client IP（简称 CIP），目标 IP 为 LVS 主机的 VIP。这时基于 Linux 内核的四层负载均衡技术 IPVS，在 LVS 上会把数据包的目标 IP 地址修改为后端服务器 Real Server IP（简称 RIP），目标 IP 为 RIP——在这个过程完成了目标 IP 的转换。此时去访问 Real Server，报文的源 IP 仍为 CIP。

数据包发送给 Real Server 后，Real Server 会构建响应报文发回给 Director Server，此时报文的源 IP 为 RIP、目标 IP 为 CIP。Director Server 在响应客户端前，会将源 IP 地址修改为自己的 VIP 地址，然后响应给客户端，此时报文的源 IP 为 VIP、目标 IP 为 CIP。

NAT 模式的特点是：后端服务器无需暴露真实 IP，但负载均衡器需处理双向流量，所以容易成为性能瓶颈。

### DR 模式：只改二层 MAC，回包直达客户端

**DR 模式。** DR 全称 Direct Routing，即直接路由技术。作者说明，实现 LVS 的 DR 模式，首先 Director Server 和 Real Server 都要配置同一个 IP，都为 VIP：Director Server 将该 IP 配置到对外的网卡上，Real Server 将该 IP 配置到本地回环网卡上〔待确认：ASR 记为"老网卡"，按上下文应为"lo 网卡"〕。因为同一个 VIP，这里通过配置 ARP 的 `ignore` 参数〔待确认：ASR 记为"ARP 的 ignal 参数"，按上下文应为 `arp_ignore`／`arp_announce` 一类参数〕来实现：数据包发出 ARP 请求时，只有 Director Server 会响应该请求。

接着是流转过程：客户端访问 Director Server，源 IP 为 CIP、目标 IP 为 VIP。Director Server 在收到客户端的数据包后，根据调度算法找出对应的 Real Server，并发给这台 Real Server：把目的 MAC 地址改为 Real Server 的 MAC（即 RIP 的 MAC），源 MAC 为 Director Server 的 MAC（即 DIP 的 MAC）。这是 Real Server 通过网卡 ETH0 收到这个数据包，由于 Real Server 上的 lo 网卡配置的也有 VIP，所以 Real Server 接收数据包并处理后直接返回给客户端。

作者强调，DR 模式要对二层包头进行改写，所以 Director Server 和 Real Server 必须在一个广播域；它需要 Real Server 配置 VIP 并禁用 ARP 响应，也可以简单地理解为在同一台交换机上。

作者在这里有一处口误：他先记为"NAT 模式的特点是仅请求流量经过负载均衡器，响应流量直达客户端，性能极高"，但按上下文与前一节的结论，这应当是 DR 模式的特点〔待确认：ASR 记为"NAT模式的特点是仅请求流量经过附载均衡器响应流量实达客户端性能极高"，与 NAT 一节"双向流量"的结论矛盾，按上下文应为 DR 模式〕。

### TUN 模式：在报文外再封装一层 IP

**TUN 模式。** TUN 全称 IP Tunneling，即 IP 隧道技术。

作者说明流转过程：客户端首先将请求发往前端的负载均衡器，请求报文源地址是 CIP、目标地址为 VIP。负载均衡器收到报文后，发现请求的目标地址在规则里面存在，那么它将在客户端请求报文的头部再封装一层 IP 报文，将源地址改为 DIP、目标地址改为 RIP，并将此包发送给 Real Server。

Real Server 收到请求报文后，会首先拆开第一层封装，然后发现里面还有一层 IP 头部、目标地址是自己 lo 接口上的 VIP，所以会处理此请求报文，并将响应报文通过 lo 接口送给 ETH0 网卡直接发送给客户端。ETH0 网卡一般是和 Director Server 在一个网段的网卡，注意需要设置 lo 接口的 VIP 不能在公网上出现。

TUN 模式的特点是：支持跨机房部署，但隧道封装、解封装带来额外开销，Real Server 需支持隧道协议且需配置 VIP。

作者收尾说，负载均衡原理你懂了吗？我是架构师阿Q，如果有用记得点赞收藏。

> **思考一下｜三种模式的差别其实只在三件事上**
>
> 把 NAT、DR、TUN 的流转过程并排看，差别可以压缩成三个问题：请求报文改了哪一层（NAT 改三层目标 IP、DR 改二层 MAC、TUN 加一层 IP 封装）；响应报文走不走过调度器（NAT 走，所以调度器承压；DR 与 TUN 不走，所以性能高）；以及由此带来的拓扑约束（NAT 要求后端网关指向调度器，DR 要求同一广播域并禁用 ARP 响应，TUN 要求后端支持隧道协议）。记住这三问，比记住三段流程更耐用。
>
> **可以追问**：如果响应流量不经过调度器（DR、TUN），那么调度器还能看到完整会话吗？这对限流、审计、连接数统计这类功能意味着什么？
>
> **可延展方向**：把"控制面与数据面是否分离"作为分析任何网关类组件的通用视角——只走请求的架构性能好但可观测性弱，双向都走的架构可控但容易成为瓶颈。
>
> **思考一下｜"性能最高"这个评价需要配上场景**
>
> 作者给 LVS 的定位是"软件负载均衡里性能最高"，理由是纯四层、工作在内核态。四层的代价是不解析应用层内容，因此无法按 URL、Header、Cookie 做路由，也做不了七层的健康检查与内容改写。作者在文中已经点出四层"更通用"，但没有展开它的能力边界——例如需要按域名分流、按路径灰度时，四层方案通常要配合七层组件一起用。
>
> **可以追问**：在真实的入口链路里，"四层 + 七层"两级负载均衡各自承担什么职责？如果只保留一层，会失去什么能力？
>
> **可延展方向**：为负载均衡层建立一张职责表，把"连接分发""协议解析""灰度路由""证书卸载""限流"等能力逐项标到四层或七层，用来判断某一层是否被用超了范围。

## 综合解读

**作者的论点链（视频观点）**：这一集的结构是"先分类、再深入"。引入部分用最朴素的推理建立了必要性：单机不够 → 多机组集群 → 需要统一入口与分发 → 负载均衡器。分类部分按实现方式给出三种方案，并各配一条主要代价：DNS 简单便宜但切换受缓存与 TTL 牵制、算法少；硬件（F5/A10）性能强功能全但价格昂贵；软件（Nginx、HAProxy、LVS）便宜灵活，其中 LVS 因工作在内核态、是纯四层，性能最高。深入部分只针对 LVS，逐个讲清 NAT（改目标 IP、双向流量、调度器易成瓶颈）、DR（同 VIP、改二层 MAC、响应直达客户端、需同一广播域并禁用 ARP 响应）、TUN（外层再封装 IP、支持跨机房、有封装开销）三种模式。

**隐含前提（我的分析）**：作者的讲解预设读者的关注点是"哪种方案更快更省钱"，因此评价维度集中在性能、成本、部署复杂度三条；对于可观测性、会话保持、灰度发布、安全防护（如 LVS 本身不做应用层防护）这些运维中同样关键的能力，本集只在"四层更通用"一句里带过。另外，文中把"某云四层 CLB 用 LVS 加 Keepalived 实现"作为例证，这一说法会随厂商架构调整而变化，属于需要外部核验的现状描述。

**待外部核验的事实**：本集出现的具体产品与断言——"硬件负载均衡典型设备主要是 F5 和 A10""Nginx 与 HAProxy 是七层、LVS 是纯四层且性能是软件方案中最高的""很多大厂负载均衡产品底层基于 LVS 开发，某云 CLB 通过 LVS 加 Keepalived 实现""DNS 一般只支持轮询"——都是作者的概括性描述，未经独立核验，`unknown / 待外部核验`。其中产品能力与实现方式随版本与厂商策略变化，不能直接当作选型依据。

**边界与反例（我的分析）**：本集是一条约 7 分 11 秒的原理讲解，没有给出任何配置示例、压测数据或真实故障案例，三种模式的性能对比也只给了定性结论（"性能极高""容易成为性能瓶颈"），没有量级数据。DR 模式一段存在一处明显的口误与一处 ASR 疑误：作者把 DR 的特点误记为"NAT 模式的特点"，并把 ARP 相关参数记为难以识别的"ignal"。此外，本集没有讨论负载均衡器自身的高可用（例如调度器挂掉怎么办）——而这正是文中所举的 Keepalived 存在的原因，属于本集未展开但与主题直接相关的一环。

**可迁移素材（我的分析）**：可复用的有三样。第一是"三种模式压缩成三问"的记法——改了哪一层、回包走不走过调度器、由此带来什么拓扑约束，这套问法可以直接用来分析其他网关类组件。第二是 DNS 方案的缺陷给出的通用教训：把控制权交给别人缓存的机制，不适合放在需要快速切换的关键路径上。第三是四层与七层的分工视角，可以用来检查自家入口链路里"哪一层被用超了范围"，例如是否在用四层组件承担需要解析应用层内容的路由职责。
