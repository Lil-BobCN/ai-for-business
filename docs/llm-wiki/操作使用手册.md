# LLM Wiki 操作使用手册

本手册说明如何在本机使用 `nashsu/llm_wiki`，以及它如何接入当前工作区的 `raw/` 素材。

当前安装版本：`v0.6.12`

当前应用：`/Applications/LLM Wiki.app`

项目目录：`/Users/Admin/orca/ai-for-business/llm-wiki-project`

原始资料真源：`/Users/Admin/orca/ai-for-business/raw`

## 一、先理解数据边界

LLM Wiki 项目包含三层：

```text
raw/sources/       输入资料副本，供应用读取
wiki/              LLM 生成的页面、索引、图谱和研究结果
.llm-wiki/         应用设置、聊天历史、审核队列和缓存
```

本工作区另有一个更高优先级的原始真源：

```text
/Users/Admin/orca/ai-for-business/raw/
```

同步关系是单向的：

```text
工作区 raw/  ──同步──>  llm-wiki-project/raw/sources/
                                  │
                                  └──> LLM Wiki 生成 wiki/
```

LLM Wiki 不应直接修改工作区 `raw/`。如果原始资料发生变化，先修改或替换工作区 `raw/`，再重新运行同步脚本。

## 二、启动应用

### 图形界面

```bash
open "/Applications/LLM Wiki.app"
```

首次启动时，在应用中选择 **打开项目**，打开：

```text
/Users/Admin/orca/ai-for-business/llm-wiki-project
```

项目已经包含 `purpose.md`、`schema.md`、`raw/sources/` 和 Wiki 目录。如果应用提示创建新项目，不要在当前工作区根目录重新创建项目；选择已有项目或打开上面的独立目录。

### 从源码启动（可选）

只有需要修改 LLM Wiki 源码时才使用这条路径。仓库当前要求 Node.js 20+、Rust 1.88+ 和 `protoc`：

```bash
brew install protobuf
git clone https://github.com/nashsu/llm_wiki.git
cd llm_wiki
npm install
npm --prefix mcp-server ci
npm run mcp:build
npm run tauri dev
```

生产构建：

```bash
npm run tauri build
```

## 三、每次导入前同步素材

先预览变更：

```bash
cd /Users/Admin/orca/ai-for-business
scripts/sync-llm-wiki-sources.sh --dry-run
```

确认预览内容后执行：

```bash
scripts/sync-llm-wiki-sources.sh --apply
```

同步脚本会：

- 读取工作区根目录的 `raw/`；
- 保留三个一级目录和原文件名；
- 把文件复制到 `llm-wiki-project/raw/sources/`；
- 删除目标副本中已经从原始 `raw/` 删除的文件；
- 不写入、不重命名、不修改工作区 `raw/`。

同步完成后，在 LLM Wiki 的 **资料源** 页面点击重新扫描；如果已经开启 source folder 自动监听，也可以关闭并重新打开项目以触发扫描。

## 四、配置模型

进入 **设置 → LLM Provider**。当前版本支持：

- OpenAI；
- Anthropic；
- Google；
- Ollama；
- Codex CLI；
- Claude Code CLI；
- 自定义 OpenAI 兼容端点。

建议先只配置一个稳定的聊天模型，先关闭向量搜索。当前资料规模不足以要求向量数据库，关键词检索和图谱扩展可以先用于验证链路。

模型配置建议：

1. `Chat`：用于问答、比较、综合和研究讨论；
2. `Ingest`：用于资料分析和 Wiki 页面生成；
3. 如果服务支持，Chat 和 Ingest 可以使用不同模型；
4. 语言设为中文；
5. 上下文窗口先使用默认值，处理长文档时再增加。

如果使用本地 Ollama，需要确认 Ollama 已运行并且模型已经下载。若使用 Codex CLI 或 Claude Code CLI，应用会启动对应 CLI 子进程，相关登录状态和网络权限由 CLI 管理。

## 五、配置联网研究

进入 **设置 → 外部信息源 / Deep Research**，选择一个网络搜索 Provider：

- Tavily；
- SerpApi；
- SearXNG；
- Ollama Web Search（如果你的账号和服务支持）。

联网研究必须和本地资料区分：

- 本地资料回答：只引用 Wiki 和 `raw/sources`；
- Deep Research：使用外部网页搜索并把结果保存为研究输出；
- 最终结论：只有人工确认后才写入长期综合或决策页面。

第一次使用建议只配置一个搜索 Provider，先验证搜索结果、引用和写回是否符合预期。

## 六、第一次导入

导入顺序建议从小到大：

1. 先导入 `raw/sources/Ontology：AI Coding 在本体中的建模和实战/`；
2. 检查资料摘要、引用和待核验项；
3. 再导入 `raw/sources/零点未来：AI+企业/`；
4. 最后导入 3 小时 FDE 课程目录。

在 **资料源** 页面选择文件或文件夹，加入摄入队列。应用会执行：

```text
读取原始文件
  → 解析 Markdown / JSON / 其他支持格式
  → LLM 分析实体、概念、观点和潜在关系
  → 对照 purpose.md 和 schema.md
  → 生成 source / entity / concept / query 等 Wiki 页面
  → 更新 wiki/index.md、overview.md、log.md
  → 写入 sources[] 和 wikilinks
  → 更新图谱、搜索索引和审核队列
```

不要一开始把三组资料一次性批量生成并直接接受所有结果。先检查第一组的质量，再决定是否批量。

## 七、导入后的检查顺序

每批导入完成后按以下顺序检查：

1. **资料源**：文件数量、目录结构和文件名是否完整；
2. **Wiki**：每份资料是否有 source 页面；
3. **Overview**：总览是否把不同来源混成了一个确定事实；
4. **审核**：哪些项目被标为需要人工判断；
5. **Lint**：死链接、孤立页面、缺失 frontmatter 和未解决冲突；
6. **知识图谱**：实体、概念和来源关系是否合理；
7. **搜索**：用原文中的精确术语和同义问题各测试一次。

当前素材的特殊检查：

- ASR 文字不能自动升级成 `verified`；
- 视频作者的数字、案例和产品能力必须保留“作者主张”归属；
- `_提取汇总.json` 和索引中的 SHA-256 不要被 LLM 摘要覆盖；
- `_改造规范.md`、`_术语统一口径.md` 等规范文件要作为方法资料读取，但不应被当成业务事实。

## 八、如何提问

推荐从三类问题开始。

### 本地事实问题

```text
只根据我的 LLM Wiki，解释 Ontology、知识图谱和 RAG 的分工，并列出引用页面。
```

### 比较和分析问题

```text
比较三组资料对“本体是业务约束还是知识图谱”的说法，区分作者观点、已核验事实和我的当前分析。
```

### 需要联网的问题

```text
先查我的 LLM Wiki，再指出哪些地方需要外部核验。只对缺口做联网研究，并把本地来源和外部来源分开列出。
```

提问时明确说“我的 LLM Wiki”或“我的知识库”，这样安装的 Agent Skill 才会路由到本地 LLM Wiki。

## 九、审核和写回

LLM Wiki 会把一部分内容放入审核队列。审核时使用以下判断：

- 原始资料页：一般可以保留，但要确认路径和来源数组；
- 概念页：检查是否把多个作者的观点写成统一事实；
- 实体页：检查产品名、人名和工具名是否存在 ASR 误识别；
- 综合页：检查每个关键断言是否有来源；
- Deep Research 结果：检查 URL、访问日期和来源类型；
- 决策页：只有确认后才保存为项目长期判断。

有价值的聊天回答可以使用 **Save to Wiki** 保存到 `wiki/queries/`，但保存前要检查它是否混合了推测和事实。

## 十、图谱和知识空白

**知识图谱**用于查看 `[[wikilinks]]`、来源重叠和概念关系。图谱上的边表示页面之间的关系，不等于事实已经被独立证明。

**图谱洞察**可以发现：

- 孤立页面；
- 稀疏主题簇；
- 连接多个主题的桥接页面；
- 可能的惊奇连接；
- 资料覆盖不足的知识空白。

对知识空白启动 Deep Research 前，先确认研究主题、搜索式和外部信息源，再开始联网搜索。

## 十一、让 Codex 使用 LLM Wiki

### 构建 MCP Server

如果使用源码仓库：

```bash
cd /path/to/llm_wiki
npm --prefix mcp-server ci
npm run mcp:build
```

然后在应用的 **设置 → API + MCP** 中开启本地 API、生成 Token，并复制应用显示的 MCP 配置。应用的本地 API 默认是：

```text
http://127.0.0.1:19828
```

API 支持项目列表、文件读取、混合检索、Agent Chat、图谱查询、资料重新扫描和单页 embedding。

### 安装 Agent Skill

```bash
npx skills add https://github.com/nashsu/llm_wiki_skill.git --skill llm-wiki
```

Skill 默认只读，会让 Codex 能够：

- 搜索 LLM Wiki；
- 读取 Wiki 页面；
- 查看图谱邻居；
- 触发资料重新扫描；
- 返回可在应用中核对的页面路径。

Codex 的实际工作链路应当是：

```text
用户问题
  → Codex 调用 LLM Wiki 本地搜索 / Chat
  → 读取 Wiki 页面和原始来源
  → 判断是否需要联网
  → 用浏览器或搜索工具查外部一手资料
  → 把外部结果整理成待审核研究记录
  → 输出带来源的讨论结果
```

### 当前队列状态

队列已暂停，状态文件为：

```text
7 failed       旧 Codex 配置下的任务，主要错误是 401 或 MCP 鉴权失败

```

### 恢复操作

1. 先确认应用中的项目仍是 `llm-wiki-project`，并保持 **设置 → 网络** 的代理为当前可用的 `http://127.0.0.1:7897`；如果本机 Clash 端口变化，先更新这里。
2. 对单个失败来源点击 **Retry**，观察它是否完成两步：`Analyzing source` → `Generating wiki pages`。不要同时点整批 Retry。
3. 单个文件成功后，再按目录顺序处理剩余 `pending` 和 `failed` 文件。成功文件会由 SHA-256 缓存跳过，不会重复生成。
4. 每批结束后核对 `wiki/sources/` 数量、`.llm-wiki/ingest-cache.json` 和 Review 项。只有 30 个来源全部有成功缓存，才可以把全量试点标成完成。

### 已确认的模型问题

- Claude Code CLI 独立调用可以正常返回，但应用子进程在本次长队列中出现无外部连接、长时间停留在分析阶段；隔离模式会失去本机 Claude 登录，因此当前保持关闭。
- Codex CLI 的 `gpt-5.4-mini` 在自定义网关上返回“没有可用通道”；切换到本机配置中的 `gpt-6.1-sol` 后，独立功能测试成功，但长队列仍有超时和旧进程残留。
- 应用内 Custom OpenAI-compatible provider 的兼容性探测返回网关 `403`，因此没有把本机 Codex 令牌复制到 LLM Wiki 设置中。

这意味着当前 Wiki 是**可检索的部分试点结果**，不是 30 个来源全部完成的最终版。继续处理前，优先完成一个失败文件的单文件 Retry 验证，再扩展到整组资料。

不要把 LLM Wiki 的读取权限等同于允许 Codex 自动改写所有页面。写入仍然应通过明确的保存或审核动作完成。

## 十二、更新资料和重复运行

工作区原始资料发生变化时：

```bash
cd /Users/Admin/orca/ai-for-business
scripts/sync-llm-wiki-sources.sh --dry-run
scripts/sync-llm-wiki-sources.sh --apply
```

然后在应用里重新扫描资料源。LLM Wiki 使用 SHA-256 增量缓存，未变化的文件应被跳过；变化文件会重新进入摄入队列，并更新受影响的 source、entity、concept 和索引页面。

删除原始资料前先确认它不是误删。同步脚本在 `--apply` 模式会删除目标项目中的对应资料副本，应用随后会执行相关 Wiki 页面和链接的清理流程。

## 十三、备份和恢复

至少备份以下内容：

```text
llm-wiki-project/purpose.md
llm-wiki-project/schema.md
llm-wiki-project/raw/sources/
llm-wiki-project/wiki/
llm-wiki-project/.llm-wiki/
```

其中：

- `raw/sources/` 可以从工作区 `raw/` 重新生成；
- `wiki/` 是最重要的派生知识资产；
- `.llm-wiki/` 包含聊天、审核和应用状态，不能假定全部可由 Wiki 页面重建；
- 当前工作区的 `raw/` 仍然是原始资料最终真源。

推荐把 `llm-wiki-project/` 单独放入 Git，并在每批导入和审核后提交一次。提交前检查是否有 API Key、Token 或隐私内容进入文件。

## 十五、常见问题

### 应用无法连接模型

检查 Provider、模型名称、API Key、Base URL、代理和本地服务状态。先用聊天功能测试，再开始批量摄入。

### 导入任务失败

查看活动面板中的具体文件。长文档、复杂 PDF 和图片可能需要更长超时或专用解析器。不要因为一份文件失败就重复整批任务。

### 搜索没有命中

先运行重新扫描；确认页面已经生成；再检查关键词是否出现在 source 或 Wiki 页面中。向量搜索是可选能力，不应作为第一阶段的唯一检索路径。

### 外部研究结果不可信

检查是否保存了 URL、访问日期和原文摘录。没有这些信息的内容只能作为当前对话中的候选分析，不能进入长期结论。

### 需要把项目迁移到另一台机器

复制 `llm-wiki-project/` 和同步脚本，在新机器上重新安装应用。不要只复制聊天缓存而遗漏 `wiki/`、`purpose.md` 和 `schema.md`。
