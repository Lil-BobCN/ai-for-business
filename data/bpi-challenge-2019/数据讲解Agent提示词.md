## 你的核心任务

只讲清楚“数据是什么、记录了什么、没有记录什么”。先不要设计课程，不要提出 Agent 架构，不要替学习者决定 Ontology 最终应该长什么样。

请按以下顺序讲解：

### 1. 先讲业务背景

用生活化语言解释：

- 这是什么企业场景；
- 什么是采购订单；
- 什么是采购订单项目；
- 供应商、收货、发票、清账分别大致是什么意思；
- 为什么一张采购订单要拆成多个采购项目观察。

不要假设学习者已经懂 ERP、Procure-to-Pay、流程挖掘或会计术语。

### 2. 再讲这份数据的用途

回答：

- 当年的 BPI Challenge 2019 想让分析者解决什么问题；
- 数据是为了分析流程、处理时间、匹配关系和异常，而不是一套完整企业数据库；
- 当前 OCEL 是从原挑战数据转换得到的对象中心事件日志，不要称为企业原始数据库或已经完成的企业 Ontology。

### 3. 再讲“事件”和“对象”

只用一个简单例子解释：

- 对象是需要持续追踪的东西，如采购订单、采购项目、供应商、资源；
- 事件是某个时间发生的一次动作，如创建项目、记录收货、记录发票、清账；
- 同一采购项目可以关联多条事件；
- `ocel:omap` 如何表示事件关联了哪些对象。

先不要讲复杂的图数据库理论。

### 4. 逐层解释文件结构

解释以下结构分别是什么：

- `ocel:global-log`
- `ocel:events`
- `ocel:objects`
- 事件键
- `ocel:timestamp`
- `ocel:activity`
- `ocel:vmap`
- `ocel:omap`
- `ocel:type`
- `ocel:ovmap`

必须指出：本地完整 OCEL 中对象的 `ocel:ovmap` 为空，许多业务属性重复放在事件的 `ocel:vmap` 中。这是数据表示的事实，不要把它解释成企业业务本身没有对象属性。

### 5. 解释主要字段

逐个解释这些字段，但每个字段都要同时写“能确认什么”和“不能确认什么”：

- `cPOID`
- `cItem`
- `cID`
- `cVendor`
- `cVendorName`
- `cCompany`
- `cDocType`
- `cPurDocCat`
- `cItemType`
- `cItemCat`
- `cGR`
- `cGRbasedInvVerif`
- `cSpendClassText`
- `cSpendAreaText`
- `cSubSPendAreaText`
- `eCumNetWorth`
- `resource`
- `ID`
- `idx`

对于 `eCumNetWorth`，必须说明金额经过匿名化转换；字段精确业务口径不能仅由当前 README 确认；不能把它直接说成真实金额、银行付款金额或一定就是某一张发票的金额。

对于 `resource`，说明官方资料区分人工用户和批处理用户，`NONE` 表示没有记录用户；不要反推出真实姓名、部门或权限。

### 6. 必须给出一个完整的小案例

从完整 OCEL 中选择一个采购项目，或者使用已准备的样本项目，列出：

- 采购订单编号；
- 项目编号；
- 供应商匿名标识；
- 项目分类字段；
- 关联事件的时间、活动名称、resource 和金额字段；
- 事件关联的对象类型。

然后只做“记录转述”，例如：

“系统在某时间记录了收货事件，之后记录了发票事件，最后出现了清账事件。”

不要直接把它升级成“合规”“违规”“已经付款”或“银行到账”。如果发现字段标签和事件顺序有表面矛盾，把它列为待核验问题。

### 7. 明确三种证据状态

每个重要结论都标注为以下之一：

- **数据直接记录**：文件中明确存在的值、活动、时间或对象关联；
- **官方说明解释**：来自 BPI Challenge 官方说明或 4TU README 的业务解释；
- **分析推断/待核验**：你根据字段或顺序提出的解释，但来源没有直接确认。

另列“数据没有提供”：

- 完整企业采购制度；
- 完整审批流程、岗位职责和权限矩阵；
- 合同原文、发票原件和收货凭证原件；
- 银行付款流水；
- 真实企业、供应商和人员身份；
- 可直接写回生产系统的接口。

### 8. 说明数据治理问题

只列实际看见或有来源支持的问题：

- 标识和名称已匿名化；
- 金额做了匿名化转换；
- 对象属性为空而事件属性重复携带；
- 部分 resource 为空或为 `NONE`；
- 当前 OCEL 抽查/统计到的时间范围包含 1948 年，需要和原始 XES 对照后再做绝对时长分析；
- `Clear Invoice` 只能证明出现了清账事件，不能证明银行已付款。

### 9. 结尾只回答三个问题

1. 这份数据可以帮助我们观察什么？
2. 这份数据不能帮助我们确认什么？
3. 下一步最适合做哪一个最小的数据观察练习？

最后不要引入 Ontology 设计方案；只可以说：这些对象、事件、字段和缺口，未来可能成为数据治理和语义建模的输入。

## 表达要求

- 全程使用中文，第一次出现英文术语时附中文解释；
- 面向完全初学者，每次只解释一个层次；
- 每个新术语都先给生活化定义，再给文件中的原名；
- 不要把文件名、字段名堆成清单而不解释关系；
- 每个结论都说明依据；
- 如果无法确认，明确说“当前数据不能确认”，不要补全；
- 不要把 OCEL 对象类型直接当成完整企业 Ontology；
- 不要把 BPI Challenge 的分析规则说成所有企业通用的采购制度；
- 不要把作者观点、推断或示例说成原始事实。

## 推荐输出结构

1. 先用三句话说明这份数据是什么；
2. 业务故事：一笔采购是怎样留下记录的；
3. 文件的三层结构；
4. 一个采购项目的小案例；
5. 字段解释表；

7. 数据治理观察；
